## Round 1 — Independent architecture and evidence audit

### 1. Executive decision

**Choose D: a modular combination of existing platforms, with a small ROS-free analytical entry.** Use separate parameterized planar arm and differential-drive reference problems, then a low-DOF tabletop arm and a small base. Introduce ROS 2 integration only after a learner can test the underlying math/algorithm. Use MUR5e as an advanced architecture/comparison case, not the default installation, primary assessment oracle or cheap-hardware blueprint. Adapt its useful mission decomposition, not its commercial robot's assumptions wholesale.

The first executable milestone proposed for approval is **two local, CPU-only, narrowly assessed frame/FK labs**, with a schema/design review before coding; the first-five specification is below. No robot, GPU, ROS, Docker, account or cloud service is required for those outcomes. A kinematic numerical model is honestly labeled kinematic, not high-fidelity physics. MuJoCo is a later optional dynamics/contact backend; Gazebo Harmonic/ROS 2 Jazzy is the selected advanced integration profile. Neither backend is mandatory for basic algebra/FK. Do not maintain equivalent complete graded scenes in two simulators from day one.

Use TurtleBot3 plus official simulator packages for a provisional advanced navigation reference; inspect OpenMANIPULATOR-X separately for manipulation. **Their existence does not establish a working combined mobile manipulator.** Composition, arm/base transforms, collision geometry, time sources and actions need a tested integration milestone. Andino is the stronger customizable hardware/BOM alternative; Linorobot2 is a flexible base-stack alternative. LeRobot is useful later for data and imitation, not a replacement for geometry, ROS navigation or independent assessment. Revisit these choices after a clean pinned integration build; confidence in the educational decomposition is higher than confidence in the final robot combination.

### 2. Baseline: what CoreLab really supports

The production map remains 169 topic identities and 310 prerequisite edges. The prior v2 synthesis proposes seven extra identities (M17, R16–R20, E16); those are proposals, not installed curriculum. Preserve all old scopes even if a lab touches several topics.

CoreLab is Next.js/React/TypeScript, Node 24+, local SQLite and browser UI. `scripts/verify-lab.mjs` is an explicit local CLI, imports the learner file via `lab-tests.py`, runs a child process with a 30-second timeout, and signs a report with the workspace Ed25519 key. `lib/labs.ts` accepts only `corelab-lab/1`, `corelab-fixed-tests/1`, topic M02/PY01, exact group counts 8/6 and a matching local key on trusted import. M02 is dot only; PY01 is mean only. Existing signatures must never be reinterpreted as robotics competence. These strict contracts cannot already import an arbitrary practical-lab report.

The verifier executes local Python; the timeout is not a filesystem/network sandbox. A user intentionally runs their own trusted exercise from a terminal; never move execution into a web request or run downloaded learner code as if isolated. Signatures bind artifacts/provenance, not authorship or resistance to the local owner's modifications. A0 independence is self-attested; A1 conceptual hint, A2 specific example/hint and A3 supplied solution are practice, not independent evidence. C/M/I/T dimensions and L0–L4 remain. Current quizzes support narrow C/M, repeat passes ≥7 days contribute T1 retention, signed labs support narrow I; open L3/L4 review is not implemented.

Practical gaps: 31 authored lessons/diagnostics, 138 overviews, two fixed verifiers, no generalized robot lab manifest/report, no trusted simulation transcript format, no reviewed novel-transfer workflow, no scoped current-readiness interface, no integrated robotics runner. The current one-C/three-number diagnostic shape cannot validate a robotics experiment. Existing demos are intuition tools; running a launch file or watching a successful pick is not implementation evidence. Localhost checks must stay; no public database, remote execution API or always-on ROS bridge.

The seven requested repositories and two justified official companion repositories are enumerated below with commits. Branch names alone are insufficient lockfiles. A CI YAML is evidence of intended checks, not passing CI or physical functionality.

Host inspection finds ROS 2 **Humble** at `/opt/ros/humble`, `gz` and `colcon`; default `python3` has no importable MuJoCo/NumPy/pytest. I did not replace the host ROS environment, install Jazzy/Harmonic, or pretend a Humble path validates Jazzy. Absence from this interpreter does not prove absence from every virtualenv. MuJoCo XML parsing by the standard library is not simulator validation.

Official Gazebo documentation currently lists Ubuntu 24.04/Jazzy/Harmonic as a supported previous-LTS combination and 26.04/Lyrical/Jetty as newer. Choose Jazzy/Harmonic here because candidate code targets it, **not because Jazzy is the newest**. Official MuJoCo bindings bundle the engine in the Python package; its passive viewer on macOS requires `mjpython`. This supports a potentially light separate backend, not a cross-OS CoreLab lab result. Windows/macOS headless/viewer/driver behavior must be tested for a pinned release before advertising support. [MuJoCo Python installation/viewer](https://mujoco.readthedocs.io/en/stable/python.html).

### 5. MUR5e: what the twelve steps actually establish

The BT defines: (1) acquire pick pose, (2) optimize pick base, (3) navigate, (4) open/preposition/approach/servo/advance/close, (5) attach collision payload, (6) stow; (7) acquire place, (8) optimize place base, (9) navigate, (10) descend/open, (11) detach, (12) stow. Step 4 and 10 labels recur across sub-actions; it is twelve reported mission stages, not twelve primitive algorithms. Place phase can be skipped if place pose is empty. Failure fallback detaches scene payload and tries to stow, then returns failure. Detaching a physical carried object during recovery would need a different safety policy. [pick_place_mission.xml](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/pick_place_orchestrator/behavior_trees/pick_place_mission.xml)

**Target acquisition is not global camera search.** `TargetAcquisition::tick()` reads a pose input and checks nonempty frame, then succeeds. `mission_trigger_node.cpp` supplies parameterized default pick/place map coordinates; the action caller can supply other poses. Thus “all targets hardcoded forever” would be too strong, but “camera automatically finds an arbitrary initial target” is unsupported. A nonempty frame alone does not check finite coordinates, covariance, transform freshness or task identity. [target_acquisition.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/pick_place_orchestrator/src/behavior_tree_nodes/target_acquisition.cpp) [mission_trigger_node.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/pick_place_orchestrator/src/mission_trigger_node.cpp)

**There is real camera-based local correction, with narrow assumptions.** VisualServo subscribes to RGB, depth and camera info; masks yellow in HSV, selects the largest contour, samples centroid/neighborhood depth, deprojects with intrinsics, adds a fixed cylinder-radius offset and transforms to the planning frame. It commands intermittent MoveIt Cartesian corrections with current Z held for alignment; this is not demonstrated general 6-DOF IBVS or semantic object acquisition. Source assumptions include known color/size/approach, camera naming, fallback intrinsics, separate unsynchronized latest image pointers and latest-time transforms. A bypass flag can skip servo. Critically, max-iteration exhaustion returns SUCCESS with a best-effort corrected pose even outside the threshold. Missing images/no yellow can remain RUNNING; inspected BT execution loop has cancellation but no overall elapsed-time deadline. These are reasons to add explicit time/freshness/error contracts before assessment or hardware, not claims of observed crashes. [visual_servo_action.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/pick_place_orchestrator/src/behavior_tree_nodes/visual_servo_action.cpp) [behavior_tree_engine.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/pick_place_orchestrator/src/behavior_tree_engine.cpp)

**Placement is sampled feasibility/heuristic ranking, not proven globally optimal navigation.** It samples angles/radii, points the base inward, tests a hardcoded rectangular footprint against a costmap snapshot, computes an effective grasp target with fixed offsets, runs collision-aware IK and scores manipulability plus inverse **base-to-object Euclidean distance**. Returned `path_distance` is that radial distance, not a Nav2 computed path length. A current-base Euclidean-distance guard prunes distant candidates but does not prove route feasibility. Manipulability and inverse metres need a defined normalization if the score is to transfer across robot scales. The hardcoded footprint, grasp geometry and arm link assumptions must change for another robot. [optimizer_node.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/base_placement_optimizer/src/optimizer_node.cpp)

The footprint function returns true if no costmap exists. With a costmap, it checks centre and five samples on each of four boundaries: 21 points, not every interior occupied cell or a continuous polygon sweep. A source-derived 1-cm-cell example places a lethal cell at local `(0.25,0.10)` inside the 0.99-by-0.68 rectangle but outside all 21 sampled cells, so these checks miss it. I reproduced this geometry in a small independent arithmetic script; I did not execute the C++/ROS method. Unknown/out-of-map checked points are rejected, which is a positive safeguard, but does not fix missing interior coverage or stale/no-map data. No full swept-volume certificate follows from this check. [optimizer_node.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/base_placement_optimizer/src/optimizer_node.cpp)

**Payload attachment does not confirm grasp.** `payload_actions.cpp` creates a fixed cylinder `AttachedCollisionObject` in MoveIt's planning scene, allows finger/wrist touch links, and applies/removes it. This is useful collision bookkeeping. It neither creates a demonstrated Gazebo weld nor checks finger contacts, object motion, slip, force or sustained retention. Gripper action sets/plans/executes a named target; no contact/retention success oracle was found there. High-friction simulation settings do not replace an independent grasp check. The scene object and world object can disagree. [payload_actions.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/pick_place_orchestrator/src/behavior_tree_nodes/payload_actions.cpp) [gripper_control_action.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/pick_place_orchestrator/src/behavior_tree_nodes/gripper_control_action.cpp)

**Tests are substantive but narrower than the demo claim.** End-to-end action test mocks optimization, navigation, MoveGroup, ExecuteTrajectory and planning-scene services; it asserts mission SUCCEEDED. Payload test inspects scene-service requests, not physical retention. Failure-recovery test injects Nav2 abort and checks abort/detach behavior. `FailsWhenObstacleBlocksArm` waits for a result but **does not assert collision failure or `success == false`**, despite its name. Several test bodies exist and are CMake-registered; neither their presence nor my source reading establishes a passing build or a physically successful mission. [test_end_to_end_mission.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/pick_place_orchestrator/test/test_end_to_end_mission.cpp) [test_payload_attachment.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/pick_place_orchestrator/test/test_payload_attachment.cpp) [test_failure_recovery.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/pick_place_orchestrator/test/test_failure_recovery.cpp) [test_optimizer.cpp](https://github.com/Mostafasaad1/ros2-mur5e-mobile-manipulator-stack/blob/a35e3e865e399f9ac7087934f2c334ee0bbbbc82/src/base_placement_optimizer/test/test_optimizer.cpp)

Missing for robot-learning/generalization assessment: local demonstration/episode contracts, policy training/evaluation interfaces, held-out environment splits, variable object properties, leakage controls, measured success distribution, perceptual identity/uncertainty and independently observed placement/retention. Do not graft a policy onto a scripted mission and call generalization verified.

**Decision on A–D:** reject A as primary capstone; B is a substantial adaptation project, not a cheap substitution; C remains a candidate if a simpler integrated platform passes clean testing (the official TB3 manipulation source has a static gap); choose D now. Preserve a six-DOF MUR5e branch as optional advanced comparison for base placement/task planning rather than claiming a four-axis replacement has equal reach/pose capability.

### 6. Proposed reference architecture and simulator strategy

Three layers, with shared semantic contracts rather than shared simulator internals:

1. **Analytical entry:** parameterized 2R planar arm, rigid transforms, differential-drive SE(2) and grid worlds. Own simple primitive geometry and formulas; deterministic headless checks, CPU, no account. Browser visuals consume recorded frames/results or existing visual components; no simulator execution through HTTP. These are bounded learning models, not robot twins.
2. **Physics skills:** optional standalone MuJoCo for fixed-arm tracking, sensing/contact and data. Try the ROBOTIS X/TB3 models after version/license/model-load smoke. Use a single tested model per track; do not grade “physics truth” against the same model both estimator and verifier use. No GPU needed for the small proposed tasks, but performance targets require a benchmark. Original primitive meshes avoid initial asset redistribution risk.
3. **System integration:** pinned Ubuntu 24.04 + Jazzy + Harmonic, Nav2 base actions, MoveIt 2 arm, ros2_control where appropriate, a BT/state-machine mission. The selected profile is an optional advanced Linux environment; Windows/macOS users retain CoreLab and numerical labs natively. WSL2/VM graphics/USB and macOS ROS combinations are untested routes, not advertised native equivalence. Docker optional for maintainers, never a prerequisite for the first milestone.

Define frames (`map`, `odom`, `base_link`, arm base, tool, camera optical), SI units/radians, timestamp and clock source, joint order/limits, command validity/timeout and collision/observation policies. Separate geometric path, time law, controller, perception and executive. Deterministic finite scenes first; no ROS-reinvention framework, cloud backend, authentication service, heavy orchestration layer or universal simulator conversion service.

A base and arm may be used separately forever; mounting adds tipping/mass/power/reach/cabling/stop risks. Four-axis X cannot reach arbitrary SE(3) goals, so constrain the capstone to top-down/allowed-orientation reachable objects and document that reduced task. LeKiwi is an interesting inexpensive teleoperation/data alternative with omni kinematics; do not reuse differential-drive/Nav2 assumptions without an adapter and odometry assessment.

### 8. First five specifications for pilot authoring

**P01, frames.** Inputs: a declared frame graph with finite 2D/3D transforms, point/direction tag and source/target frames. Output: transformed object with a declared convention, or a typed invalid/disconnected error. Implement compose, inverse and transform without calling the assessed library equivalent. Use at least noncommuting rotations, nonzero translation and a point/direction pair; compare independent manually anchored examples and matrix properties. PASS: all mandatory tests, invalid inputs rejected, fresh parameters/mount, separate C/M explanation of order/units. I alone cannot prove understanding. A transform is not a calibration certification. Beginner effort estimate 2–4 active hours after placement, unmeasured; lower to SE(2) first if 3D readiness fails. Visual: frame axes and step-through point path. No MuJoCo/ROS.

**P02, planar FK.** Inputs: positive link lengths, finite joint angles in radians, optional typed tool transform. Output: endpoint/pose with joint convention documented. Implement direct trig and compose supplied elementary transforms; the grader's oracle is independently derived, not the learner's second function. Tests: unequal lengths, nonzero mixed angles, negative angles, wrap-equivalent angles, tool offset, invalid dimensions/lengths and independent reach bounds. No every-joint-pose enumeration can establish all FK competence; this is a two-link scope. PASS: all critical tests plus reviewed derivation/shape/convention probes; unfamiliar tool-frame reasoning needs reviewer. Estimate 2–5 hours; interactive two-link model with predict-before-run, trace/save artifact. No hardware equivalence.

**P03, endpoint Jacobian and numerical IK.** Separate J and IK subcontracts so a valid Jacobian isn't erased by slow solver convergence. J oracle uses directional central differences at multiple scales/nonzero configurations and independently known symbolic cases. IK input includes target, limits, tolerance and iteration budget; output is a candidate q with residual/limit checks or explicit failure, never inferred success from action completion. Include singular straight arm, unreachable target, near-singular reachable target, multiple IK solutions and adversarial initial states. Do not require returning one special joint vector when several are valid. Damped-SVD extension needs M17; base analytic J or a bounded transpose update has narrower math needs. PASS: analytic J validity plus feasible residual/limits on declared solvable cases and honest failure otherwise; human checks singularity explanation. Estimate 4–8 hours, novices may split across sessions; no full six-axis planning.

**P04, trajectory and toy tracking.** Declare plant `dq/dt=u` with command limit, timestep and joint bounds; begin with one joint and separately apply independent joint time laws. This plant is not a torque-controlled arm. Inputs start/end/time or speed/accel constraints; implement triangular/trapezoidal time law and bounded P tracking. Satisfy zero-distance, reverse motion, impossible-duration and finite-step cases; central-difference checks of sampled acceleration need explicit treatment at profile corners. Analytic segments/reference integrator and refined-step comparison are independent checks. PASS: exact endpoint constraints, predeclared numerical tolerances and command bounds, plus C/M saturation/time-law explanation; changed timestep/limits are transfer practice. **P05, differential-drive odometry.** Inputs wheel radius/separation, wheel velocities or encoder increments, dt and initial pose; declare angle wrapping and tick/radian units.
