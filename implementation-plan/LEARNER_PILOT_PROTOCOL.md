# CoreLab V2 learner pilot protocol

**Prepared, not executed.** No participants have been recruited, contacted or observed. This document does not approve S1/S2 release or claim learning benefits.

## Entry gates

- Owner accepts scope/capacity/recovery policy (D1/D11) and names the technical, adversarial and pedagogical reviewers (D5).
- S1/S2 acceptance and recovery rehearsal pass on the declared pilot OSes (D6). Forms/retrieval pools have genuine independent review and explicit S2 release activation. Synthetic test approvals do not qualify.
- Prepare a current backup for each volunteer. Explain local storage, optional external videos/tutor handoff, voluntary participation and how to stop. Collect only information the volunteer chooses to share; keep personal progress/exports outside Git.

## Participants and activities

Invite 3–8 volunteers only after owner authorization. Record prior mathematics/programming experience, chosen goal and device/OS/browser. No hardware, GPU, simulator or paid API is needed. Offer the optional radians bridge, Frames and Planar FK; allow any activity order and every alternative route.

An example 80-minute first session:

| Minutes | Activity | Observe |
| --- | --- | --- |
| 0–10 | Optional diagnostic and learner goal | Existing knowledge and prerequisite confusion |
| 10–25 | Learn/watch/visualize; predict a result | Units, frame conventions and independent explanation |
| 25–40 | Reconstruct equations and choose a practice route | Difficulty, hint use and recurring mistakes |
| 40–60 | Implement a trusted manual kit locally | Input/output contracts, tests and debugging; no I evidence |
| 60–70 | Optional fresh C/M check after release gates | Assistance declaration, scoped results, false accepts/rejects |
| 70–80 | Explain a gap, record notes and plan review | Separation of practice, topic level and objective evidence |

If live verification is unavailable, use practice only and label the session an interface rehearsal, not the S2 learning trial. Never enable a gate for a volunteer to bypass a missing review.

## Follow-up over at least 21 days

Observe actual due reviews using the implemented relative intervals (initial +1 day, then +3/+7/+21 from each successful due review). Separately predeclare day-7 and day-21 observation tasks with distinct reviewed inputs. Those observations are not automatically admissible retention and must not override due dates or exhaustion rules. Early, assisted and repeated retrieval remains useful practice. Record missed sessions honestly; do not invent a completed follow-up.

Record active minutes, assistance A0–A3, selected route, format errors, mathematical misconceptions, claimed false failures, hint usefulness, keyboard/matrix-entry issues and confusion between legacy topic levels and V2 objective results. Ask volunteers to explain one result in their own words. External help is self-declared, not detectable authorship proof.

## Stop, review and decisions

Stop the affected activity on data loss, failed recovery/export, unexpected evidence admission, a security-boundary violation or an unfair critical item. Preserve history and file a minimal reproducible issue without private exports. Use Settings recovery or a verified current SQLite copy; never silently rewrite signed history or change an immutable item version.

Summarize individual cases, missing observations and limitations. A small pilot cannot establish an effect size, calibrated difficulty or improved learning. Decide whether to continue, revise content/contracts with new versions, simplify the workflow, or stop. Report verified I and transfer as unavailable throughout this pilot; any isolated runner is a separate reviewed project.
