## Why this matters

Writing a controller for one motor is easy. Running several controllers on a robot with many joints, where a trajectory controller, a teleop controller and a state broadcaster all want to read the same joints and some want to *write* them, is a coordination problem. ROS 2 control (`ros2_control`) answers it with a few strict rules: hardware exposes named **interfaces**, controllers **claim** the command interfaces they write to (one owner at a time), and a controller manager runs a fixed-rate **read, update, write** loop. If you understand the rules you can predict, before running anything, which controller combinations are legal, how much timing budget you have, and what invariants a mock interface must satisfy (commands within limits, reported state consistent with actual motion). This lesson also builds the discrete controller that lives inside `update()`, with the details that make it behave on real hardware: the true period, saturation and integrator windup.

## Intuition

Think of the robot as a switchboard. Each joint offers **state interfaces** (position, velocity, effort: things you can read) and **command interfaces** (position, velocity, effort: things you can write). Reading is harmless and can be shared by many controllers. Writing is not: two controllers writing the same joint command would fight, so the system allows only one *active* owner per command interface. Switching controllers is a transaction: either the new set of claims is valid and the swap happens, or nothing changes.

![Diagram of the controller manager loop read, update, write at a fixed rate, with hardware component, resource manager showing joint command interfaces owned by one controller each, and a timeline of a 10 ms period with a read, update and write budget and an overrun](/lesson-figures/S10.svg)

*Each cycle is read hardware state, run the controllers, write the commands; the whole cycle must finish inside the period, and command interfaces have exactly one owner.*

The loop gives each controller the **actual period** since its last call, not a nominal number you typed. Controllers that hardcode $dt$ are the most common source of "it was tuned in simulation and misbehaves at a different rate".

## Theory and derivation

### Components

- **Hardware component** (system, actuator or sensor): talks to the device (S06). `read()` fills state interface values; `write()` sends command interface values. It declares what it offers, for example `joint1/position`, `joint1/velocity` (state) and `joint1/velocity` (command).
- **Resource manager**: owns all interfaces, tracks which are *available* and which are *claimed*.
- **Controller manager**: loads controllers, manages their lifecycle (unconfigured, inactive, active), checks claims on activation, and runs the update loop at `update_rate`.
- **Controller**: reads state interfaces, computes, writes command interfaces. Examples: `joint_state_broadcaster` (read only, publishes `/joint_states`), `forward_command_controller` (pass-through), `joint_trajectory_controller` (follows a trajectory), `diff_drive_controller`.

### Resource ownership rules

1. A command interface can be claimed by at most one active controller.
2. State interfaces can be shared by any number of controllers.
3. A controller can only claim interfaces that exist (unknown names fail activation).
4. A switch request lists controllers to deactivate and to activate; deactivations are applied first, then claims are checked. The request must be **atomic** in strict mode: on any conflict no controller changes state. (A best-effort mode may activate the subset that can succeed.)

### The update loop and timing

With `update_rate` $f$ the period is $T=1/f$. One cycle does: `read(time, period)`, each active controller `update(time, period)`, `write(time, period)`. The cycle is on time if $t_{\text{read}}+t_{\text{update}}+t_{\text{write}}\le T$; otherwise it is an **overrun** and the next cycle starts late. Utilization $=t_{\text{cycle}}/T$; keep it well below 1 (a common target is below 50 to 70 %) because worst-case time is what matters.

### Inside `update()`: a discrete PID

For a velocity-commanded joint with error $e=r-y$ and period $dt$ (the real one):
$$u=\operatorname{sat}\Big(k_pe+k_i\!\int e\,dt+k_d\dot e\Big),\qquad I_{k+1}=I_k+e\,dt\ \ (\text{if not wound up}).$$
- Use **derivative on measurement** ($-\dot y$) so a jump in the reference does not produce a spike.
- **Anti-windup** by conditional integration: when the output is saturated and the error pushes further into saturation, do not accumulate. Without it the integral keeps growing during a long saturation and the output stays pinned long after the error changes sign.
- Reject $dt\le0$.

### Mock hardware invariants

A mock joint with velocity limit $v_{\max}$ and range $[\ell,h]$ defines a contract to test:
- command clamped: $|v_{\text{applied}}|\le v_{\max}$; position never leaves $[\ell,h]$;
- **state consistency**: reported velocity is the actual displacement over the period, $\hat v=(p_{k+1}-p_k)/dt$, so $\sum\hat v\,dt=p_N-p_0$ exactly; it is not the commanded velocity (at a limit the command may be 1 rad/s while the joint is not moving);
- refuse non-finite commands.

## Worked example

### A ros2_control loop: timing, PID, saturation, state, windup and ownership

**Problem.** A mock joint has range $[-1,0.8]$ rad and $v_{\max}=1$ rad/s. Its controller has $k_p=2$, $k_i=1$ and output limit 1 rad/s; the loop period is $dt=10$ ms unless stated. Solve six sub-problems. (1) `update_rate: 100` with read 0.5 ms, update 1.2 ms, write 0.7 ms: cycle time and utilization; what if the update grows to 9 ms? (2) With $dt=0.1$ s, reference 1 and measurements 0 then 0.5, find the outputs and the integral after each step with a large limit and with limit 1.0 (with and without conditional integration). (3) Step of 1 rad, $k_p=2$, no integral, $v_{\max}=1$: time to enter the 2 % band. (4) Joint at $p=0.79$, command 1.0 rad/s, $dt=0.1$: new position and reported velocity. (5) Reference 1.0 (beyond the limit 0.8) held until the integral has wound up for 11.5 s, then reference 0: how many steps until the output reverses, with and without conditional integration? (6) Controllers `a` (j1) and `b` (j2) are active; a switch request activates `d` (needs j1 and j2) and deactivates only `c`: result?

**Solution.**

1. Timing. $T=1/f=1/100=10$ ms. Cycle $=0.5+1.2+0.7=2.4$ ms, utilization $=2.4/10=24\,\%$. With update 9 ms: $0.5+9+0.7=10.2$ ms $>10$ ms, so every cycle is an overrun.
2. PID numbers with $u=k_pe+k_i I$, $I_{k+1}=I_k+e\,dt$. Step 1: $e=1$, $I=0+1\cdot0.1=0.1$, $u=2\cdot1+1\cdot0.1=2.1$. Step 2: $e=1-0.5=0.5$, $I=0.1+0.5\cdot0.1=0.15$, $u=2\cdot0.5+0.15=1.15$. With limit 1.0 both outputs are clipped to 1.0. With conditional integration the output is saturated and $e\,u>0$, so $I$ is not accumulated: $I=0$ after step 1, and at step 2 the trial $u=1+0.05=1.05>1$ again, so $I$ stays 0. Without it $I=0.1$ then $0.15$.
3. Settling with a velocity limit. While $k_pe>v_{\max}$, i.e. $2e>1$, $e>0.5$, the output is 1 rad/s and $e$ falls linearly: from $e=1$ to $0.5$ takes $0.5/1=0.5$ s. Then the loop is linear: $\dot e=-2e$, $e=0.5e^{-2t'}$. Reaching $e=0.02$: $e^{-2t'}=0.04$, $t'=\ln(25)/2=1.609$ s. Total $t=0.5+1.609=2.11$ s.
4. State consistency. Commanded displacement $1.0\cdot0.1=0.1$ rad would give $0.89$, but the range ends at $0.8$, so the position is clamped to $0.8$ (actual displacement $0.8-0.79=0.01$ rad). Reported velocity $=\Delta p/dt=0.01/0.1=0.1$ rad/s, not the commanded 1.0.
5. Windup against a hard stop. The joint sits at $0.8$ with $e=1-0.8=0.2$. Without anti-windup the integral grows $0.2\cdot0.01=0.002$ per step, so after $11.5$ s ($1150$ steps) $I=0.2\cdot11.5=2.3$. The reference jumps to 0: $e=-0.8$, $u=2(-0.8)+I=-1.6+I$, and $I$ falls by $0.8\cdot0.01=0.008$ per step. The output stays positive (stuck at the stop) until $I<1.6$: $(2.3-1.6)/0.008=87.5$, so reversal at step 88 ($\approx0.9$ s). With conditional integration $I$ stops growing as soon as the output saturates ($0.4+I>1$, so $I\approx0.6$): $u=-1.6+0.6=-1.0<0$ and the output reverses at step 1.
6. Ownership. Deactivations are applied first, but `c` was not active, so nothing is freed. `d` needs j1 (owned by `a`) and j2 (owned by `b`): conflict. Strict mode is atomic, so the whole request is refused and `a` and `b` keep their claims.

**Check.** Units: $T$ in ms, utilization is a ratio, velocities in rad/s. A Python model of the PID (the `pid_step` of the reference implementation) reproduces $(2.1,\,I=0.1)$, $(1.15,\,I=0.15)$ and $(1.0,\,I=0)$; a simulation of the saturated step gives $2.109$ s against the analytic $0.5+\ln(25)/2=2.109$ s; the windup simulation gives $I=2.3$ and reversal at step 88 without anti-windup, and step 1 with it.

**Takeaway.** Limits, the real period and single ownership of command interfaces make the mock loop predictable: saturation adds a linear phase before the exponential, reported velocity is displacement over the period, and an integrator without anti-windup delays reversal by tens of steps.

`ros2 control list_hardware_interfaces` shows each interface with `[available]` and `[claimed]`; `ros2 control list_controllers` shows states; `ros2 control switch_controllers --activate forward_velocity_controller` claims the command interface.

A runnable model of the ownership rule and the PID core:

```python
class Owners:
    def __init__(self):
        self.owner = {}
    def claim(self, ctrl, ifaces):
        busy = [i for i in ifaces if i in self.owner]
        if busy:
            raise RuntimeError("already claimed: " + ", ".join(sorted(busy)))
        for i in ifaces:
            self.owner[i] = ctrl

def pid_step(integral, e, dt, kp, ki, limit):
    """Returns (output, new_integral) with conditional-integration anti-windup."""
    trial = integral + e * dt
    u = kp * e + ki * trial
    out = max(-limit, min(limit, u))
    return out, (trial if (u == out or e * u < 0) else integral)

o = Owners()
o.claim("a", ["j1/velocity"])
try:
    o.claim("b", ["j1/velocity"]); raise SystemExit("must refuse")
except RuntimeError:
    pass
out, I = pid_step(0.0, 1.0, 0.1, 2, 1, 10.0)
assert abs(out - 2.1) < 1e-12 and abs(I - 0.1) < 1e-12
out, I = pid_step(0.0, 1.0, 0.1, 2, 1, 1.0)
assert out == 1.0 and I == 0.0
print("reference ok")
```

## Independent practice

### Goal
Build and test a mock ROS 2 control stack: resource ownership with atomic switching, a limited mock joint with consistent state, a discrete PID with anti-windup, and cycle timing accounting.

### Setup
Python 3 standard library. Save starter and tests as `s10_lab.py`. Optional ROS 2 with `ros2_control_demos` for the real commands.

### Tasks
1. `ResourceManager.claim/release`: unknown interface is a `KeyError`, claimed interface a `RuntimeError`, refused claims change nothing.
2. `ResourceManager.switch(activate, deactivate, requirements)`: deactivate first, then claim; atomic on failure.
3. `MockJoint.write/read`: clamp the command to $\pm v_{\max}$, clamp the position, reported velocity is actual displacement over `dt`, reject non-finite commands.
4. `PID.update` with derivative on measurement and conditional anti-windup (`dt <= 0` raises).
5. `run_loop` (read, update, write) and `overruns`.
6. Write assumptions, baseline, boundary case and a rejecting observation.

```python
        raise NotImplementedError

        raise NotImplementedError
    def read(self):
        """(pos, vel)."""
        raise NotImplementedError

        raise NotImplementedError
```

### Tests
```python
rm = ResourceManager({"j1/velocity", "j2/velocity"}, {"j1/position", "j2/position"})
rm.claim("a", {"j1/velocity"}, {"j1/position"})
before = dict(rm.owner)
try:
    rm.claim("b", {"j1/velocity", "j2/velocity"}); raise SystemExit("must refuse a claimed interface")
except RuntimeError:
    pass
assert rm.owner == before                                  # a refused claim changes nothing
rm.claim("b", {"j2/velocity"})
try:
    rm.claim("c", {"j3/velocity"}); raise SystemExit("unknown interface must be rejected")
except KeyError:
    pass
req = {"c": {"j1/velocity"}, "d": {"j1/velocity", "j2/velocity"}}
rm.switch(["c"], ["a"], req)                               # hand over j1 from a to c
assert rm.owner == {"j1/velocity": "c", "j2/velocity": "b"}
snap = (dict(rm.owner), {k: set(v) for k, v in rm.claims.items()})
try:
    rm.switch(["d"], ["c"], req); raise SystemExit("d needs j2 which b still owns")
except RuntimeError:
    pass
assert (rm.owner, rm.claims) == snap                       # atomic: nothing changed
rm.switch(["d"], ["c", "b"], req)
assert rm.owner == {"j1/velocity": "d", "j2/velocity": "d"}

j = MockJoint(-1.0, 1.0, 1.0)
j.write(2.0, 0.1)
assert abs(j.pos - 0.1) < 1e-12 and abs(j.vel - 1.0) < 1e-12      # command clamped to vmax
j = MockJoint(-1.0, 0.8, 1.0, pos=0.79)
j.write(1.0, 0.1)
assert abs(j.pos - 0.8) < 1e-12 and abs(j.vel - 0.1) < 1e-9       # reported velocity is the ACTUAL motion
try:
    j.write(float("nan"), 0.1); raise SystemExit("NaN command must be rejected")
except ValueError:
    pass
import random
rng = random.Random(3)
j = MockJoint(-1.0, 1.0, 2.0); p0 = j.pos; dist = 0.0
for _ in range(500):
    j.write(rng.uniform(-5, 5), 0.01)
    assert -1.0 <= j.pos <= 1.0 and abs(j.vel) <= 2.0 + 1e-9
    dist += j.vel * 0.01
assert abs(dist - (j.pos - p0)) < 1e-9                              # state consistency: integral of velocity = displacement

p = PID(2, 1, 0, 10.0)
assert abs(p.update(1, 0.0, 0.1) - 2.1) < 1e-12
assert abs(p.update(1, 0.5, 0.1) - 1.15) < 1e-12 and abs(p.integral - 0.15) < 1e-12
a, b = PID(2, 1, 0, 1.0, anti_windup=True), PID(2, 1, 0, 1.0, anti_windup=False)
assert a.update(1, 0, 0.1) == 1.0 and b.update(1, 0, 0.1) == 1.0
assert a.integral == 0.0 and abs(b.integral - 0.1) < 1e-12
k = PID(0, 0, 1, 100.0)
assert k.update(5.0, 0.0, 0.1) == 0.0 and abs(k.update(9.0, 0.1, 0.1) + 1.0) < 1e-12   # derivative on measurement: no kick on ref change
try:
    k.update(0, 0, 0.0); raise SystemExit("dt <= 0 must be rejected")
except ValueError:
    pass

jt = MockJoint(-1.0, 1.0, 1.0)
log = run_loop(PID(2, 0, 0, 1.0), jt, 0.5, 0.01, 2000)
assert abs(jt.pos - 0.5) < 1e-6 and max(abs(v) for _, v, _ in log) <= 1.0 + 1e-9

def leave_steps(aw):
    jj = MockJoint(-1.0, 0.8, 1.0); pid = PID(2, 1, 0, 1.0, aw)
    run_loop(pid, jj, 1.0, 0.01, 1000)                 # pushes into the hard stop at 0.8
    lg = run_loop(pid, jj, 0.0, 0.01, 1000)
    return next(i for i, (pp, _, _) in enumerate(lg) if pp < 0.79)
assert leave_steps(True) < 10 and leave_steps(False) > 50      # windup against the stop delays the reversal

print("all checks passed")
```

## Failure modes

- Hardcoded `dt` instead of the manager's `period`: integral and derivative gains silently change when the rate changes (a factor 2 in the exercise).
- State velocity copied from the command: the controller believes the joint moves while it sits at a stop.
- Integrator windup against output saturation or a hard stop: delayed reversal (106 steps in the worked example).
- Derivative on error: a spike each time the reference jumps.
- Two controllers on one command interface in an unchecked system: oscillating or random commands.
- Partial switch: first controller deactivated, second fails to activate, the joint is left uncontrolled. Atomic strict switching avoids it.
- Cycle time close to the period: sporadic overruns appear only under load.
- Unknown interface names (typos in YAML): activation fails with a missing interface.

## Alternatives and trade-offs

A forward command controller is the simplest: pass-through of a setpoint stream to an interface. A trajectory controller adds interpolation and tolerance checks. Chained controllers separate loops (position on top of velocity) but increase the claim and ordering complexity. Enforcing limits in the hardware interface protects against any controller, while limits in controllers give better behavior (smooth saturation) and error reporting; use both and test each. Real-time execution (priority scheduling, memory locking) is needed for tight rates, the mock here tests logic but not determinism. For simple projects a single node with a timer is easier than the full framework; ros2_control pays off when you share hardware between several controllers and need standard interfaces.
