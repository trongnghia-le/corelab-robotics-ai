## Why this matters

Write small functions whose behavior you can explain and test. This lesson develops the core calculation before asking you to apply it in a new setting. Start with the diagnostic if you think you already know it; prior tool use is not evidence of understanding.

## Intuition

A program is a sequence of state changes. Reading code means predicting what each statement does before running it. A function packages a calculation behind an input/output contract; a printed message is for a person, while a returned value lets other code use the result.

Picture the running program as a lab notebook that is rewritten one line at a time. At any instant the notebook holds a set of *objects* (the number 0.8, a list of three range readings, a function) and a set of *names*, sticky labels that point at objects. Executing a statement either moves a label to a different object or changes an object in place. Reading code well means holding that picture in your head and updating it by hand before the machine does. Everything in this lesson (aliasing, default arguments, early `return`, even floating-point surprises) is a statement about which label points where and what an object contains at that moment.

A concrete case. A robot logs speeds in a list called `speeds`, and a teammate writes `backup = speeds` "to keep a copy" before appending a new reading. Predict first, on paper, what the last line prints.

```python
speeds = [0.5, 0.8]
backup = speeds
speeds.append(1.2)
print(backup)
```

The output is `[0.5, 0.8, 1.2]`. There was never a second list: `backup = speeds` attached a second sticky note to the same object, so appending through one name is visible through the other. If you predicted `[0.5, 0.8]` you were using the most common wrong intuition about variables, "a variable is a box that holds a value, and assignment copies the contents". That picture is harmless for numbers, because numbers cannot be changed in place, and it breaks the moment the object is a list, a dictionary or an array, which are exactly the objects robot code is made of. The correct picture is "a name is a label on an object", and a copy has to be requested explicitly (`list(speeds)`, `speeds.copy()`, `copy.deepcopy(...)`).

The second picture is the function as a sealed machine: arguments go in, one value comes out. Anything else it does, such as printing, writing a file or changing the list you handed it, is a *side effect* and belongs in its written contract. The second common mistake follows from mixing the two outputs: a function that only prints looks fine at the terminal and silently returns `None` to the code that called it. Before you run `scaled(3)` in the exercises, ask two questions: what value comes back, and what else changed? The pictures of the next sections (a shallow copy, a number line of floats, a loop checked by an invariant) are all ways of answering these two questions without running anything.

Predict before you compute: for each snippet in this lesson, write the output down first. The habit costs thirty seconds and is the cheapest debugger there is, because every wrong prediction points to a wrong picture of the program, which is the thing you actually want to fix.

## Theory and derivation

Python names refer to objects. `x = 3` binds a name; `x == 3` asks a question. An `if` selects a branch, and a `for` visits items in an iterable. `range(3)` produces 0, 1, 2; the stop bound is excluded. Indentation defines blocks, so moving a `return` inside a loop can stop processing after the first item.

To calculate a mean, track a running total s and count n, then return s/n. For an empty input, n=0, so define a failure contract rather than divide by zero. Avoid mutable default arguments such as `items=[]`: the same default object persists across calls. A pure function does not mutate its input and returns the same result for the same values.

Lists hold ordered references. `b=a` aliases one list; `b=list(a)` creates a shallow copy. A shallow copy does not duplicate nested lists. State whether your function reads, mutates, or owns the data it receives. Small contracts make debugging much easier than inspecting a long script with hidden global state.

### Names, objects, and aliasing

Every Python value is an object with three properties: an *identity* (what `id(x)` returns and what `is` compares), a *type*, and a *value* (Python reference, Data model §3.1 "Objects, values and types"). The assignment `name = expression` evaluates the expression to an object and binds the name to it; it never copies the object. Objects are either *immutable* (`int`, `float`, `str`, `tuple`, `None`) or *mutable* (`list`, `dict`, `set`, most user classes). An immutable object cannot change, so rebinding is the only way a name can appear to change, and sharing is harmless. A mutable object can be changed through any name that refers to it, and every other name sees the change: that is *aliasing*.

Two operators answer two different questions: `a == b` asks whether the *values* are equal; `a is b` asks whether both names point at the *same object*. Use `is` for the singleton `None` only (`if x is None`). A subtle trap is augmented assignment: for a list `a += [5]` calls the in-place method and mutates the object, while `a = a + [5]` builds a new list and rebinds `a`. Both look like "add 5 to the list" and behave differently when another name is attached.

Copies come in two depths (Python docs, `copy` module). `list(a)`, `a[:]` and `copy.copy(a)` make a *shallow copy*: a new outer list holding references to the same elements, cost $O(n)$ for $n$ elements. `copy.deepcopy(a)` recursively duplicates the elements as well and uses a memo table so that cyclic structures terminate; it costs time proportional to the whole structure, and it can fail on objects that cannot be copied (open files, locks). The rule of thumb: a shallow copy is enough when every element is immutable; use a deep copy, or better, redesign so that nothing mutable is shared, when you will edit nested elements. A tuple holding a list is only "shallowly" immutable: you cannot replace the list, but you can still change it.

**Example.** Two names, one list, then a rebind. What does the code below print, and how many list objects exist at the end?

```python
p = [0, 0]
q = p
p += [5]
r = p
p = p + [7]
print(p, q, r)
```

**Solution.** Trace the names one line at a time. `p = [0, 0]` creates list $L_1$ and binds `p` to it. `q = p` binds a second name to the same $L_1$ (assignment never copies). `p += [5]` calls the in-place method, so $L_1$ itself becomes `[0, 0, 5]`; `r = p` binds a third name to $L_1$. `p = p + [7]` builds a new list $L_2=$ `[0, 0, 5, 7]` and moves only the label `p`. The print therefore shows `[0, 0, 5, 7] [0, 0, 5] [0, 0, 5]`: `q` and `r` still point at $L_1$, which the `+=` had already mutated. Four statements on three names leave two objects.

### Functions as contracts: parameters, defaults, return values

A call `f(a)` binds the parameter name to the *same object* the caller passed (the documentation calls this "call by object reference"; Python tutorial §4.8). So a function that mutates a list parameter changes the caller's list, while a function that rebinds the parameter (`x = x + 1`) changes only its own local label. A function that reaches the end without `return` returns `None`; `print(...)` writes characters to the terminal and returns `None`, which is why a function that only prints cannot be composed with other code.

Default values are evaluated *once*, when the `def` statement runs, not at each call (Python tutorial §4.9.1). For an immutable default (`k=2`) the difference is invisible; for a mutable default (`acc=[]`) the same object is reused by every call, which is why such defaults leak state. The idiom is `acc=None` and `if acc is None: acc = []` inside the body.

Names are resolved by scope: local, then enclosing functions, then module (global), then built-ins. An assignment anywhere inside a function makes that name local for the whole function, so reading it before assigning raises `UnboundLocalError` even if a global of the same name exists. A written *contract* has four parts: the preconditions on the inputs (types, ranges, non-empty), the postcondition on the returned value, the side effects (none, for a pure function), and the exceptions raised when a precondition is violated. Code that states these is testable; code that does not is only a guess about what the author meant.

**Example.** A default is frozen at definition time, and print is not return. What do the two `print` calls below output, and what is `r`?

```python
n = 2
def scaled(x, k=n):
    return x * k

n = 10
print(scaled(3))

def show_double(x):
    print(2 * x)

r = show_double(4)
print(r)
```

**Solution.** The default `k=n` is evaluated once, when `def` runs, and `n` is 2 at that moment, so `k` is bound to the value 2. Reassigning `n = 10` afterwards does not touch it: `scaled(3)` returns `3 * 2 = 6`, printed as `6`. `show_double(4)` evaluates `2 * 4` and prints `8` (a side effect), but it has no `return`, so the call returns `None` and `r` is `None`; `print(r)` prints `None`. The output is `6`, then `8`, then `None`.

### Control flow: iteration, `range`, and early exit

`range(start, stop, step)` yields `start`, `start+step`, ... while the value is below `stop` (for a positive step) or above it (for a negative step); the stop bound is never produced (Python tutorial §4.3). Its length is $\max\!\bigl(0,\lceil (stop-start)/step\rceil\bigr)$. A `range` is a lazy sequence that stores only three integers, so `range(10**9)` costs no memory until you iterate. A `for` loop asks the iterable for an iterator and calls `next` until it raises `StopIteration`; `enumerate(xs)` yields pairs `(index, item)` and `zip(a, b)` walks two iterables together and stops at the shorter one.

`break` leaves the loop; `continue` skips to the next item; the `else` clause of a loop runs only if the loop ended without `break` (Python tutorial §4.4-§4.5). A `while` loop needs a quantity that strictly decreases (a *variant*, for example `n - i`) so that you can argue it terminates. Two classic hazards: a `return` placed inside the loop body ends the whole function at the first item (the indentation, not the intention, defines the block), and changing a list while iterating over it makes the iterator skip items, because it walks by index and the indices shift.

**Example.** A descending range, a search with `for ... else`, and the mutate-while-iterating trap. What does the code below print, and why is the last result wrong?

```python
print(list(range(10, 0, -3)))

for i, v in enumerate([4, 7, -3, 5]):
    if v < 0:
        print("first negative at", i)
        break
else:
    print("none")

xs = [1, 2, 2, 3]
for x in xs:
    if x == 2:
        xs.remove(x)
print(xs)
```

**Solution.** `range(10, 0, -3)` yields $10, 7, 4, 1$ and stops before $0$; its length is $\lceil (0-10)/(-3)\rceil=\lceil 3.33\rceil=4$, so the first line is `[10, 7, 4, 1]`. In the search, `enumerate` yields $(0,4)$, $(1,7)$, $(2,-3)$; the third pair satisfies `v < 0`, so it prints `first negative at 2` and `break` skips the `else`. In the last loop the iterator walks by index: at index 1 it sees `2` and removes it, so the list becomes `[1, 2, 3]` and the second `2` slides into index 1; the iterator then moves to index 2 (value `3`), so the second `2` is never examined and the result is `[1, 2, 3]`. The output is `[10, 7, 4, 1]`, `first negative at 2`, `[1, 2, 3]`. The last result is wrong on purpose; iterate over a copy (`for x in list(xs)`) or build a new list instead.

### Floating-point summation: where the error comes from and how large it can be

A Python `float` is an IEEE 754 binary64 number: a stored binary fraction $m\cdot 2^{e}$ with a 53-bit significand. Most decimal fractions are not of this form, so `0.1` is stored as the nearest representable value. `(0.1).as_integer_ratio()` returns `(3602879701896397, 36028797018963968)`, i.e. $3602879701896397/2^{55}$, which exceeds $1/10$ by about $5.55\times10^{-18}$ (Python tutorial, §15.1 "Representation Error").

Every arithmetic operation then rounds. Write $u=2^{-53}$ for the unit roundoff of round-to-nearest. The standard model is $\mathrm{fl}(a+b)=(a+b)(1+\delta)$ with $|\delta|\le u$. Apply it to the loop `s += x` with $\hat s_1=x_1$ and $\hat s_k=(\hat s_{k-1}+x_k)(1+\delta_k)$. Unrolling gives

$$\hat s_n = x_1\prod_{j=2}^{n}(1+\delta_j)+\sum_{i=2}^{n}x_i\prod_{j=i}^{n}(1+\delta_j),$$

so $x_1$ and $x_2$ are each multiplied by $n-1$ rounding factors and $x_i$ by $n-i+1$. Since each product lies between $(1-u)^{n-1}$ and $(1+u)^{n-1}$, to first order in $u$

$$|\hat s_n-s|\;\lesssim\;(n-1)\,u\sum_{i=1}^{n}|x_i|.$$

This is a worst-case bound and it is proportional to $\sum|x_i|$, not to $|s|$: when large terms cancel, the relative error of the result can be enormous even though every single addition was accurate to $u$. The tutorial's own example sums six numbers whose exact total is about $8.04\times10^{-13}$ and shows that plain left-to-right `+=` returns $-0.00516$, "no correct digits", while `math.fsum` returns the correctly rounded value. `math.fsum` "tracks multiple intermediate partial sums" and rounds once at the end (Python tutorial §15; `math.fsum` in the standard library reference). The built-in `sum` is not the same thing: its handling of floats changed between versions, so never write a test that depends on `sum([0.1]*10) == 1.0`. On CPython 3.11.9 the result is `0.9999999999999999`; the current tutorial shows `True` for newer versions.

Consequence for the moving-average update $s_{i+1}=s_i+v_{i+k}-v_i$: the error of $s_i$ includes rounding from every earlier step, including the steps where a huge value was inside the window and absorbed the small ones. The $O(n)$ update is exact for integers and only approximately correct for floats.

**Example.** The three symptoms of floating-point arithmetic in one run. What does the code below print, and what does each line show?

```python
import math
print(1.1 + 2.2, 1.1 + 2.2 == 3.3, math.isclose(1.1 + 2.2, 3.3))
print(sum([0.01] * 100), math.fsum([0.01] * 100))
print(float(2**53) + 1 == float(2**53))
```

**Solution.** Line 1: `1.1 + 2.2` rounds to `3.3000000000000003`, one unit in the last place above the stored `3.3`, so `==` gives `False`, while `math.isclose` accepts it with its default relative tolerance of $10^{-9}$ (`True`): representation error. Line 2: the naive sum of a hundred `0.01` accumulates rounding errors and gives `1.0000000000000007`, off by $7\times10^{-16}$, while `math.fsum` rounds once at the end and returns `1.0`. Line 3: $2^{53}=9\,007\,199\,254\,740\,992$ is the first integer after which the spacing of floats is 2, so `float(2**53) + 1` rounds back to `float(2**53)` and the comparison is `True`: absorption. The output is `3.3000000000000003 False True`, then `1.0000000000000007 1.0`, then `True`.

The hollow integers $2^{53}+1$, $+3$, $+5$ have no float of their own and round to the nearest one, ties to the even significand, so $+1\to 0$ and $+3,+5\to+4$. This is the picture behind "the 1.0 was absorbed".*

### Loop invariants: proving a loop correct instead of testing it

A **loop invariant** is a statement $I$ about the variables that is true before the loop, stays true after each iteration, and, together with the exit condition, implies the postcondition. A proof has three parts: *initialization* ($I$ holds before iteration 0), *maintenance* ($I$ before an iteration implies $I$ after it), and *termination* (what $I$ says when the loop ends).

For `mean`: let $I_k$ be "`total` equals $x_0+\dots+x_{k-1}$ (in exact arithmetic)". Initially $k=0$ and the empty sum is 0; the body adds $x_k$; after the loop $k=n$, so `total/len(values)` is the mean. The invariant also explains the classic bug: with `return` inside the loop, the exit happens at $k=1$, where $I$ says only $x_0$ has been added, which does not imply the postcondition.

For a search with early exit, the invariant is negative: "no element of `values[:i]` satisfies the predicate". Early `return i` is justified because the predicate holds at $i$ and the invariant says all smaller indices fail, so $i$ is the *first*. Falling off the end gives $i=n$, and the invariant says no element satisfies it, so `-1` is correct. Python's `for ... else` expresses exactly this: the `else` clause runs only when the loop ended without `break` (Python tutorial §4.5; language reference, the `for` statement). The buggy `first_negative` of exercise 8 fails *maintenance of the exit step*: its `return -1` is inside the loop, reached after one failed test, which does not imply that all of `values` has been checked.

**Example.** Prove `total_even` with a loop invariant, then run it on `[3, 8, 5, 6]`. What are the invariant and the printed value?

```python
def total_even(values):
    total = 0
    for v in values:
        if v % 2 == 0:
            total += v
    return total

print(total_even([3, 8, 5, 6]))
```

**Solution.** Take $I_k$: "`total` is the sum of the even elements of `values[:k]`". Initialization: for $k=0$ the slice is empty and `total` is 0. Maintenance: the body adds $v_k$ to `total` exactly when it is even, so $I_k$ implies $I_{k+1}$. Termination: after $n$ iterations $I_n$ says `total` is the sum of the even elements of `values`, the postcondition. On `[3, 8, 5, 6]` the invariant takes the values 0, 0, 8, 8, 14 after $k=0,\dots,4$ elements, the evens being 8 and 6, so the run prints `14` ($8+6$).

### Statistics under bad data: outliers and NaN

The mean is a linear statistic: changing one value by $\Delta$ changes the mean by $\Delta/n$, so a single corrupted reading can move it anywhere. The median of $n$ values (odd $n$) is the $\tfrac{n+1}{2}$-th smallest; if fewer than $\tfrac{n+1}{2}$ values are corrupted, then at least one corrupted-free value lies on each side of it, so the median stays inside the range of the clean values. That is the precise sense of the standard library's remark that the median "is a robust measure of central location" (Python docs, `statistics.median`) and that the mean "is strongly affected by outliers" (`statistics.mean`).

Missing data bring a different failure. A NaN compares false with everything (`nan < 1`, `nan > 1`, `nan == nan` are all `False`), so comparison-based algorithms silently depend on the order of the data. The `statistics` documentation warns that `median()` and friends have "undefined" behaviour on NaN and tells you to strip them first. The contract rule: decide at the boundary of your code (as `parse_readings` in the lab does) what a NaN means, and reject or remove it there.


**Example.** Five temperature readings in °C from one sensor, one of them a glitch (`99.0`). Compute the mean and the median with and without the glitch. How far does each statistic move?

```python
import statistics
data = [20.1, 19.8, 20.3, 99.0, 20.0]
print(sum(data) / len(data), statistics.median(data))
clean = [20.1, 19.8, 20.3, 20.0]
print(sum(clean) / len(clean), statistics.median(clean))
```

**Solution.** With the glitch, the mean is $(20.1+19.8+20.3+99.0+20.0)/5=179.2/5=35.84$ and the median is the third smallest value, $20.1$. Without it, the four clean readings give a mean $80.2/4=20.05$ and a median $(20.0+20.1)/2=20.05$. The output is `35.839999999999996 20.1`, then `20.05 20.05`. One corrupted reading ($\Delta\approx 79$) moves the mean by $\Delta/5\approx 15.8$ °C, from 20.05 to 35.84, while the median moves only from 20.05 to 20.1 and stays inside the range of the clean values 19.8 to 20.3.

### Testing a function: contract, cases, and properties

A test is an executable piece of the contract. Choose cases by *equivalence class* rather than at random: a typical input, each boundary (smallest and largest legal, the exact value where behaviour switches), the empty or singleton input, and one input per documented error. Add *properties* that must hold for every input and are cheap to check: the input is not mutated, the output lies between the minimum and maximum, a window of size 1 is the identity, applying a normalising function twice equals applying it once. When a fast version replaces a slow one, run both on many random inputs and compare (differential testing); the slow, obviously correct version is the oracle.

Two Python-specific points. Compare floats with `math.isclose(a, b, rel_tol=1e-9, abs_tol=0.0)`; the relative tolerance alone can never accept a difference from exactly 0, so comparing against zero needs an explicit `abs_tol` (Python docs, `math.isclose`). And `assert` statements are removed when Python runs with `-O`, so use `assert` for tests and internal invariants, never to validate user input: raise `ValueError` for that (Python reference, "The assert statement").

**Example.** A heading in degrees is wrapped to $[0, 360)$ with `deg % 360` and tested at the boundary. What does the code below print, why is `math.fmod` not a substitute, and which tolerance accepts a difference of $10^{-12}$ from zero?

```python
import math
def wrap(deg):
    return deg % 360

print(wrap(360), wrap(-90), wrap(725), math.fmod(-90, 360))
print(math.isclose(1e-12, 0.0), math.isclose(1e-12, 0.0, abs_tol=1e-9))
```

**Solution.** `360 % 360` is `0`, `-90 % 360` is `270` (270 is the representative in $[0,360)$ of $-90+360$) and `725 % 360` is `5` ($725-2\cdot360$). `math.fmod(-90, 360)` follows the sign of the dividend and returns `-90.0`, outside $[0,360)$, so it would violate the contract; Python's `%` follows the sign of the divisor, which is what the contract needs. The first line is `0 270 5 -90.0`. For the second line, the relative bound $10^{-9}\cdot\max(|a|,|b|)=10^{-21}$ is far below the difference $10^{-12}$ (a relative tolerance alone never accepts a difference from exactly 0), so `math.isclose(1e-12, 0.0)` is `False`, while `abs_tol=1e-9` admits $10^{-12}$ and gives `True`. The test cases (boundary 360, negative $-90$, multi-turn 725) came from the contract before any code.

## Worked example

### Case 1: tracing `mean` and the misplaced `return`

**Problem.** `values = [2, 4, 6]`. Using the reference `mean` (running total, then divide by the count), (a) trace `total` through the loop and return the mean; (b) show what the function returns if the line `return total/len(values)` is indented into the loop body.

**Solution.**
1. *Contract and invariant* (theory, "Loop invariants"). The postcondition is $\text{result}=\frac1n\sum x_i$ with $n=3$. The invariant is $I_k$: `total` equals $x_0+\dots+x_{k-1}$.
2. *Initialization.* Before the loop, `total = 0` is the empty sum, so $I_0$ holds.
3. *Iterations.* Each pass adds the current element: $k=1$: $0+2=2$; $k=2$: $2+4=6$; $k=3$: $6+6=12$. After the loop $I_3$ says `total` $=12$.
4. *Return.* $12/\text{len(values)}=12/3=4$, so `mean([2, 4, 6])` is $4.0$.
5. *The misplaced return.* With `return` inside the loop the function exits in the first pass, where $I_1$ says only $x_0=2$ has been added: it returns $2/3=0.667$. The invariant holds, but it no longer implies the postcondition, because the loop did not run to $k=n$.

**Check.** Python gives `mean([2, 4, 6]) = 4.0`, and the indented version gives `0.6666666666666666`. Sanity: the mean of 2, 4, 6 must lie between the minimum 2 and the maximum 6, which 4 does and 0.667 does not.

**Takeaway.** An invariant tells you what is true after each iteration; the loop is correct only if it is allowed to run until the invariant plus the exit condition imply the result.

### Case 2: a messy sensor log, from text to a robust summary

**Problem.** A range sensor writes the lines `["4.2", " 5.0", "bad", "nan", "4.8", "61.0", "5.1"]` (metres). (a) Parse them with the lab's policy (strip spaces, skip anything that is not a finite number). (b) Compute the mean and the median of the result. (c) Compute the moving average with window $k=3$ directly and with the running-sum update, and decide which statistic to report.

**Solution.**
1. *Parse* (theory, "Statistics under bad data"). `"4.2"`, `" 5.0"` (after stripping), `"4.8"`, `"61.0"`, `"5.1"` become floats; `"bad"` raises a conversion error and is skipped; `"nan"` converts to `nan` but is not finite, so the boundary rejects it. The clean list is `[4.2, 5.0, 4.8, 61.0, 5.1]`, so $n=5$.
2. *Mean.* $\sum x_i=4.2+5.0+4.8+61.0+5.1=80.1$, so the mean is $80.1/5=16.02$ m.
3. *Median.* Sort: $4.2,\ 4.8,\ 5.0,\ 5.1,\ 61.0$. For odd $n=5$ the median is the $\tfrac{n+1}{2}=3$rd value, $5.0$ m.
4. *Moving average, direct.* The number of windows is $n-k+1=3$. Window sums: $4.2+5.0+4.8=14.0$; $5.0+4.8+61.0=70.8$; $4.8+61.0+5.1=70.9$. Divide by $k=3$: $4.667$, $23.600$, $23.633$ m.
5. *Moving average, running sum* ($s_{i+1}=s_i+v_{i+k}-v_i$, theory on loop invariants). Start $s_0=14.0$. Then $s_1=14.0+61.0-4.2=70.8$ and $s_2=70.8+5.1-5.0=70.9$, the same sums with 2 additions instead of 6.
6. *Decision.* The glitch 61.0 sits in two of the three windows and drags both to about 23.6 m, so the moving average is not robust either. The mean (16.02) is three times the typical reading, while the median (5.0) is inside the cluster of the four clean readings (4.2 to 5.1). Report the median, and report that one value was far from the rest.

**Check.** Python reproduces `16.02`, `5.0`, `[4.666666666666667, 23.599999999999998, 23.63333333333333]` and the running sums `70.8`, `70.89999999999999` (the last one carries the float rounding of 70.9, as expected from the summation theory). Independent check by the bound: removing 61.0 gives the clean mean $19.1/4=4.775$, and the shift of the mean caused by the outlier is $(61.0-4.775)/5=11.245$, and indeed $4.775+11.245=16.02$.

**Takeaway.** Validate and clean at the boundary, then choose the statistic by how a bad value can move it: one bad value moved the mean by 11.2 m and the median by only 0.1 m.

The built-in `max` gives `nan, 2, 2`, the same, because it also uses `>` comparisons starting from the first item. So the answer depends on the position of the NaN. (b) Computed: `statistics.median([1, 2, 3, nan]) == 2.5` and `statistics.median([nan, 1, 2, 3]) == 1.5`: it sorts the data and `sorted` with NaN does not produce a sorted list (`sorted([3, nan, 1, 2])` is `[3, nan, 1, 2]`), so the middle elements depend on input order, exactly the "undefined" behaviour the docs warn of. (c) Let $n=2m+1$; the median $M$ is the $(m+1)$-th smallest value, so exactly $m$ values come before it in sorted order and $m$ after it. Suppose at most $m$ values are corrupted, so at least $m+1$ clean values exist. If $M>\max(\text{clean})$, all $m+1$ clean values would be smaller than $M$ and so sit before it, but only $m$ values do: contradiction. Symmetrically $M<\min(\text{clean})$ is impossible, hence $\min(\text{clean})\le M\le\max(\text{clean})$. With $m+1$ corrupted values all set to $L>\max(\text{clean})$, at most $m$ clean values remain and they fill positions $1..m$, so positions $m+1,\dots,n$ all hold $L$ and $M=L$, which is arbitrary. For the mean, changing one value by $\Delta$ changes $\frac1n\sum x_i$ by exactly $\Delta/n$, unbounded in $\Delta$. Example: `statistics.median([3,4,5,100,200])` is 5 while the mean is 62.4. (d) Reject at the boundary: in `parse_readings` skip non-finite values (as the lab does) and, in `summarize`, raise `ValueError` if any `math.isnan(x)`, or count and report the number of rejected values in the result so the loss is visible.
