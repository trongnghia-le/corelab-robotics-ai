## Why this matters

Robotics and ML code constantly handles data that is too large, too slow, or too live to hold in memory: a 17 GB lidar log, a camera stream, a dataset that must be shuffled and batched every epoch. Python's answer is the iterator protocol: values are produced on demand, one at a time. The same data model that powers `for` also powers attribute access (descriptors: `property`, methods, dataclass fields, ORM columns, `torch.nn.Parameter` registration) and class creation (`__init_subclass__`, decorators, metaclasses). Libraries you use daily (PyTorch `DataLoader`, ROS 2 `rclpy`, `dataclasses`, `pydantic`) are built from these three mechanisms. If you understand them you can read that code, and you can avoid the classic failures: an iterator that silently yields nothing the second time, a validator shared by every instance, or a registry that is empty because a module was never imported.

## Intuition

Think of an iterable as a *recipe* and an iterator as a *cook currently working through it*. A list is a recipe that can be handed to many cooks. A file object or a generator is a single cook: once the cook has finished, asking again yields nothing. `for x in obj` first asks the recipe for a fresh cook (`iter(obj)`), then repeatedly says "next" until the cook raises `StopIteration`.

A descriptor is a *customs officer* standing on an attribute. When you write `joint.angle`, Python does not just look in `joint.__dict__`; it first checks whether the *class* attribute `angle` is an object with `__get__`, `__set__` or `__delete__`. If so, that object decides what happens.

Metaprogramming is code that runs *when a class is defined*, rather than when an instance is made. The class statement is executed once, so it is the right moment to validate, register, or wrap things.

## Theory and derivation

### The iterator protocol

An **iterator** has `__next__()` (return the next value or raise `StopIteration`) and `__iter__()` returning itself. An **iterable** has `__iter__()` returning an iterator. The loop `for x in obj: body` is equivalent to

```python
it = iter(obj)
while True:
    try:
        x = next(it)
    except StopIteration:
        break
    body
```

Consequences you must remember: (1) iterators are *one-shot*: after `StopIteration` they keep raising it, so `list(it)` the second time is `[]`; (2) a class that returns `self` from `__iter__` is an iterator, a class that returns a fresh iterator each time is a re-iterable collection; (3) consuming one item of a `zip` or `islice` over a shared iterator advances it for everyone.

A **generator function** (any function with `yield`) returns a generator object *without running any of its body*. The body runs on `next()` until the next `yield`, then freezes with its local variables (the frame). That gives laziness for free, and a lifetime rule: the frame, and everything it references (open files, large lists), stays alive until the generator is exhausted, closed with `.close()`, or garbage collected. `close()` raises `GeneratorExit` at the paused `yield`, so a `try/finally` in the generator runs.

Cost model: a lazy pipeline over $N$ items with batch size $b$ holds $O(b)$ items at once instead of $O(N)$. For $N=2\times10^6$ scans of 1081 doubles each, the whole log is $2\times10^6\cdot1081\cdot8 = 17.296\times10^9$ bytes, but a batch of 64 scans is $64\cdot1081\cdot8=553{,}472$ bytes.

Be careful with *eager validation*: a generator function raises its `ValueError` only at the first `next()`. If you want errors at call time, validate in a normal function and return an inner generator, as the reference implementation does.

### Descriptors

A descriptor is an object stored as a **class attribute** whose type defines any of:

- `__get__(self, obj, owner)` - called for `obj.attr` (`obj` is `None` for `Class.attr`);
- `__set__(self, obj, value)` - called for `obj.attr = value`;
- `__delete__(self, obj)`;
- `__set_name__(self, owner, name)` - called once at class creation so the descriptor learns its attribute name.

A descriptor with `__set__` or `__delete__` is a **data descriptor**; one with only `__get__` is a **non-data descriptor**. The attribute lookup order for `obj.name` is:

1. a data descriptor found on `type(obj)` (searching the MRO);
2. otherwise `obj.__dict__["name"]`;
3. otherwise a non-data descriptor or plain class attribute found on the type;
4. otherwise `AttributeError`.

Plain functions are non-data descriptors: `f.__get__(obj, type)` returns a bound method. That is why `r.method` works and why assigning `r.method = 5` simply shadows it in the instance dictionary. `property` is a data descriptor, so it cannot be shadowed.

The key rule for writing one: **the descriptor object is shared by all instances**, so per-instance state must be stored *on the instance* (for example in `obj.__dict__`), never on `self`.

### Metaprogramming

Everything in Python is created by a call: a class is an instance of `type`. Three tools, in increasing power and decreasing readability:

1. **Decorators** (`@register`) wrap or record a function or class after creation.
2. **`__init_subclass__`** runs on the base class every time a subclass is defined, receiving class keyword arguments (`class Cam(Sensor, kind="rgb")`). Use it for registries and validation.
3. **Metaclasses** (`class M(type)`) control the creation of the class object itself. Use only when the first two cannot do the job.

A registry made this way depends on the subclass being *imported*: a plugin module that nobody imports never registers.

## Worked example

Goal: a joint angle that must stay in $[-1, 1]$ rad, and a lazy reader that hands a controller 3 samples at a time.

*Step 1, the descriptor.* Define `Bounded(-1.0, 1.0)` as a class attribute `angle` in `Joint`. At class creation Python calls `Bounded.__set_name__(Joint, "angle")`, so the descriptor stores the slot name `"_angle"`.

*Step 2, assignment.* `a = Joint(); a.angle = 0.5` finds a data descriptor on the class, so Python calls `Bounded.__set__(descriptor, a, 0.5)`. Check: $-1 \le 0.5 \le 1$ is true, so `a.__dict__["_angle"] = 0.5`.

*Step 3, a second instance.* `b = Joint()`; `b.__dict__` is still `{}`, so `b.angle` raises `AttributeError("angle")`. The state lives per instance.

*Step 4, a rejected value.* `a.angle = 1.2`: the check $-1\le1.2\le1$ is false, `ValueError`, and `a.__dict__["_angle"]` is still `0.5`. For `float("nan")` every comparison is false, so the condition `not (lo <= v <= hi)` is true and NaN is rejected; writing `if v < lo or v > hi: raise` would wrongly let NaN through.

*Step 5, the lazy reader.* `batched(range(7), 3)`: nothing executes at the call. First `next` pulls items 0,1,2 with `islice`, yields `[0,1,2]`. Second yields `[3,4,5]`. Third `islice` returns just `[6]`, which is yielded. The fourth returns `[]`, so the generator returns and `StopIteration` follows. Total items held at once: at most 3.

## Reference implementation

This file is runnable with `python3 ref.py`. It contains the four building blocks used in the lab and a self-test.

```python
"""PY10 reference: lazy batching, sliding mean, a validated descriptor, a subclass registry."""
from collections import deque
from itertools import islice


def batched(iterable, n):
    """Lazily yield lists of up to n items. Validates n eagerly (at call time)."""
    if n < 1:
        raise ValueError("n must be >= 1")

    def gen():
        it = iter(iterable)
        while True:
            chunk = list(islice(it, n))
            if not chunk:
                return
            yield chunk

    return gen()


def sliding_mean(iterable, n):
    """Lazily yield the mean of each full window of n consecutive items."""
    if n < 1:
        raise ValueError("n must be >= 1")

    def gen():
        window = deque(maxlen=n)
        for x in iterable:
            window.append(x)
            if len(window) == n:
                yield sum(window) / n

    return gen()


class Bounded:
    """Data descriptor: stores a number in the instance, rejects values outside [lo, hi]."""

    def __init__(self, lo, hi):
        self.lo, self.hi = lo, hi

    def __set_name__(self, owner, name):
        self._name = name
        self._slot = "_" + name

    def __get__(self, obj, owner=None):
        if obj is None:
            return self
        try:
            return obj.__dict__[self._slot]
        except KeyError:
            raise AttributeError(self._name) from None

    def __set__(self, obj, value):
        if not (self.lo <= value <= self.hi):  # also rejects NaN
            raise ValueError(f"{self._name}={value!r} outside [{self.lo}, {self.hi}]")
        obj.__dict__[self._slot] = value


class Sensor:
    """Base class: every subclass registers itself under `kind` (default: lowercase class name)."""

    registry = {}

    def __init_subclass__(cls, kind=None, **kwargs):
        super().__init_subclass__(**kwargs)
        key = kind or cls.__name__.lower()
        if key in Sensor.registry:
            raise ValueError(f"duplicate sensor kind {key!r}")
        Sensor.registry[key] = cls


# ---- self-test
if __name__ == "__main__":
    from itertools import count

    assert list(batched(range(7), 3)) == [[0, 1, 2], [3, 4, 5], [6]]
    assert list(batched([], 3)) == []
    try:
        batched([1], 0)
        raise SystemExit("batched must reject n=0 at call time")
    except ValueError:
        pass
    assert next(batched(count(), 2)) == [0, 1]          # infinite source: still lazy
    assert list(sliding_mean([1, 2, 3, 4], 2)) == [1.5, 2.5, 3.5]
    assert list(sliding_mean([1, 2], 3)) == []

    class Joint:
        angle = Bounded(-1.0, 1.0)

    a, b = Joint(), Joint()
    a.angle = 0.5
    assert b.__dict__ == {} and a.angle == 0.5
    try:
        a.angle = float("nan")
        raise SystemExit("NaN accepted")
    except ValueError:
        pass
    assert isinstance(Joint.angle, Bounded)

    class Lidar(Sensor):
        pass

    class Cam(Sensor, kind="rgb"):
        pass

    assert Sensor.registry == {"lidar": Lidar, "rgb": Cam}
    print("PY10 reference self-test passed")
```

## Verification

- Run each lazy function on `itertools.count()`. If it hangs or uses growing memory, it is eager somewhere.
- Use a noisy source (a generator that appends to a list) to count how many items were pulled after one `next`. For `batched(src, 4)` exactly 4 is correct; 0 means you built the generator before validating, 5 or more means look-ahead.
- For descriptors, create two instances, set different values, then read both. Equal values prove the state is on the descriptor.
- Check `Class.attr` returns the descriptor and not an exception: tools such as `help()` and `inspect` rely on this.
- For registries, assert on the registry contents after import, and add a test that a duplicate raises.

## Failure modes

| Mistake | Symptom | Cause |
|---|---|---|
| Iterating a generator twice | second pass is silently empty, so a mean over 0 items or `ZeroDivisionError` | iterators are one-shot |
| `__iter__` returns `self` for a container | `sum(s)` then `sum(s)` gives 6, 0 | container is also its own iterator |
| State kept on `self` in a descriptor | every instance shows the last value written | descriptor object is shared by the class |
| `if v < lo or v > hi` | NaN passes validation | all comparisons with NaN are false |
| Validation inside a generator function | `ValueError` appears on first `next`, far from the call | body does not run until iteration |
| Registering via `__init_subclass__` for a module not imported | `KeyError` at config load | class statement never executed |
| `list(huge_generator)` for convenience | memory spike of the full dataset | defeats laziness |
| Assuming `finally` in a generator runs promptly when abandoned | file handle stays open | CPython closes on garbage collection, other implementations may not |

## Alternatives and trade-offs

- **Generator function vs iterator class.** Use a generator function for linear pipelines (shorter, fewer bugs). Use a class when you need to expose state (position, `reset()`), support `len`, or be re-iterable.
- **Lazy vs eager.** Lazy saves memory and lets you stop early; eager is simpler to debug and allows random access and multiple passes. For data that fits in memory and is reused every epoch, materialize it once.
- **Descriptor vs `property` vs `__setattr__`.** `property` is perfect for one attribute in one class; a descriptor class wins when the same rule is reused across many attributes or classes (bounds, types, units); `__setattr__` is a blunt tool that intercepts everything.
- **`__init_subclass__` vs decorator vs metaclass.** Prefer `__init_subclass__` or a decorator; a metaclass changes the class creation protocol and conflicts with other metaclasses (for example in multiple inheritance with ABCs).
- **Dataclasses and `__slots__`.** `__slots__` are themselves implemented as descriptors, and they remove the instance `__dict__`, so the `obj.__dict__` storage trick used here will not work for slotted classes.

For launch files, the explicit import-and-register at a package `__init__` (or entry points for external plugins) plus a test that checks every configured name resolves is the most robust.

After `r.scaled = 5` the output is `5`: `Bind` has no `__set__`, so the assignment goes into the instance dict, and a non-data descriptor loses to it. With `property` (a data descriptor), assignment would call its setter or raise `AttributeError` if none exists.
10. `open`, `closed`, `done`. `close()` throws `GeneratorExit` at the `yield`, which runs the `finally`. Without it, CPython runs the same cleanup when the generator object is garbage collected, which is usually immediate by reference counting but is not guaranteed on other implementations, and a reference held in a list would keep it open. A `with` block (or `contextlib.closing`) makes the release deterministic.
