## Why this matters

A result you cannot regenerate is an anecdote. In research code the number that ends up in a figure depends on much more than the algorithm: the version of the code, the hyperparameters, the random seed, the dataset snapshot, the library versions, even the order in which a set is iterated. When these are scattered in your head, in a Jupyter cell history, or in a filename like `results_final2.json`, a rerun months later disagrees and nobody knows why. **Research programming** is the discipline of making the whole experimental setup explicit, recorded and re-runnable: configuration as data, logging instead of print statements, controlled randomness, and an automated check that a clean checkout reproduces the same output.

## Intuition

Think of an experiment as a pure function: `result = run(code, config, data, environment, seed)`. If you can name every argument, store it next to the result, and call the function again to get the same value, the experiment is reproducible. Problems arise from **hidden arguments**: the global random generator state, the current working directory, wall-clock time, hash randomization of strings, unpinned library versions, files you edited by hand. The workflow below turns hidden arguments into recorded ones.

## Theory and derivation

### Configuration as data

Put every tunable in a **config object** instead of in module-level constants and scattered literals. A frozen `dataclass` gives defaults, names, and immutability; a loader validates unknown keys and types so typos fail fast (`learning_rat` should be an error, not silently ignored). Save the **resolved** config (defaults plus overrides) in the run directory. A **config hash** (sha256 of the canonical JSON: sorted keys, no spaces) identifies a configuration regardless of key order; for `Config(seed=42)` the canonical string is `{"n_samples":10000,"seed":42,"sensors":["a","b","c"]}`. Command-line parsing with `argparse` should only select a config file and a few overrides; the result must depend on the resolved config, not on argv text.

### Logging

`print` writes text with no level, no timestamp and no destination control. The `logging` module separates **what** is logged (a level: DEBUG, INFO, WARNING, ERROR, CRITICAL; default threshold WARNING) from **where** it goes (handlers: console, file) and **how** it looks (formatters). A logger is obtained by name (`logging.getLogger("exp")`); handlers attach to loggers; calling the setup code twice must not add a second handler, or every message appears twice (three calls give three copies). Log the config hash, seed, git commit and key metrics at INFO; details at DEBUG; never log secrets.

### Randomness and determinism

Pseudo-random generators are deterministic given a seed. Use a **local generator** (`rng = random.Random(seed)`, `numpy.random.default_rng(seed)`, `torch.Generator`) passed explicitly, not the module-global one: with the global `random`, calling function B before A changes A's numbers. Remaining sources of nondeterminism:

- **Hash randomization**: `str` hashes are salted per process unless `PYTHONHASHSEED` is fixed, so `list(set_of_strings)` can have a different order each run. Sort before iterating when the order matters.
- **Floating-point non-associativity**: $(0.1+0.2)+0.3=0.6000000000000001$ but $0.1+(0.2+0.3)=0.6$; parallel reductions, multithreaded BLAS and GPU kernels change the order of additions. Compare results with a tolerance, or force deterministic algorithms and record thread counts.
- **Time, hostname, paths and environment variables** leaking into outputs.
- **Unpinned dependencies**: a library upgrade changes numerical routines.
- **Data**: files changing under the same name; store a checksum.

### The clean-checkout test

A reproducibility claim is a prediction that can fail. Procedure: `git clone` the repository to a new directory (so untracked files, local edits and relative-path accidents disappear), create a fresh environment from the lock file, run the experiment with the saved config, and compare `sha256sum result.json` with the original. Timestamps and hostnames belong in `env.json`, not `result.json`, so that the hash covers only what must be identical.

## Worked example

The experiment estimates $\pi$ by Monte Carlo: draw $N$ points in the unit square, count those with $x^2+y^2\le1$; $\hat\pi=4\cdot\text{inside}/N$. It also draws a per-sensor offset estimate (mean of 100 Gaussian values per sensor).

1. **Config.** `Config(seed=42, n_samples=10000, sensors=("a","b","c"))`; canonical JSON `{"n_samples":10000,"seed":42,"sensors":["a","b","c"]}`; config hash `a0af821358e4` (seed 43 gives `b4a0398f835d`).
2. **Run.** With a local `random.Random(42)`: $\hat\pi=3.126$ and offsets `{'a': 0.040318, 'b': 0.123098, 'c': -0.02628}`. A second run in the same process gives exactly the same dictionary; seed 43 gives $\hat\pi=3.1504$.
3. **Result hash.** `write_run` serializes the result with sorted keys; the sha256 of `result.json` starts with `b76d3b43dc9c` for seed 42, on every run.
4. **Nondeterminism trap.** If the sensor loop is `for s in set(cfg.sensors)` the offsets get assigned from the RNG stream in the set's order. Run `PYTHONHASHSEED=1 python -c "print(list({'imu','gps','lidar'}))"` and `PYTHONHASHSEED=3 ...`: the first prints `['imu', 'gps', 'lidar']`, the second `['imu', 'lidar', 'gps']`. Result: different offsets per run for the same seed. The code uses `sorted(set(...))` to remove the dependence.
5. **How noisy is $\hat\pi$?** Each estimate has standard deviation $4\sqrt{p(1-p)/N}$ with $p=\pi/4$: $4\sqrt{0.7854\cdot0.2146/10^4}=0.0164$. Over 20 seeds the mean has standard error $0.0164/\sqrt{20}=0.0037$. A single seed such as 3.126 is $(\pi-3.126)/0.0164\approx0.95$ standard deviations from $\pi$ and can be reported honestly only with that uncertainty.

## Reference implementation

```python
import hashlib, json, logging, os, platform, random, sys
from dataclasses import dataclass, asdict

@dataclass(frozen=True)
class Config:
    seed: int = 0
    n_samples: int = 10000
    sensors: tuple = ("a", "b", "c")

def config_from_dict(d):
    allowed = {"seed": int, "n_samples": int, "sensors": (list, tuple)}
    for k, v in d.items():
        if k not in allowed:
            raise ValueError("unknown config key: %s" % k)
        if isinstance(v, bool) or not isinstance(v, allowed[k]):
            raise ValueError("bad type for %s" % k)
    kw = dict(d)
    if "sensors" in kw:
        kw["sensors"] = tuple(kw["sensors"])
    cfg = Config(**kw)
    if cfg.n_samples < 1:
        raise ValueError("n_samples must be >= 1")
    return cfg

def config_hash(cfg):
    s = json.dumps(asdict(cfg), sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(s.encode()).hexdigest()[:12]

def run_experiment(cfg):
    rng = random.Random(cfg.seed)
    inside = 0
    for _ in range(cfg.n_samples):
        x, y = rng.random(), rng.random()
        inside += x * x + y * y <= 1.0
    offsets = {}
    for s in sorted(set(cfg.sensors)):
        offsets[s] = round(sum(rng.gauss(0, 1) for _ in range(100)) / 100, 6)
    return {"pi_hat": 4 * inside / cfg.n_samples, "n": cfg.n_samples, "offsets": offsets}

def setup_logger(name, logfile=None, level=logging.INFO):
    log = logging.getLogger(name)
    log.setLevel(level)
    log.propagate = False
    if not log.handlers:
        fmt = logging.Formatter("%(asctime)s %(levelname)s %(name)s %(message)s")
        h = logging.StreamHandler(); h.setFormatter(fmt); log.addHandler(h)
        if logfile:
            fh = logging.FileHandler(logfile); fh.setFormatter(fmt); log.addHandler(fh)
    return log

def write_run(dirpath, cfg, result):
    os.makedirs(dirpath, exist_ok=True)
    with open(os.path.join(dirpath, "config.json"), "w") as f:
        json.dump(asdict(cfg), f, sort_keys=True, indent=2)
    data = json.dumps(result, sort_keys=True, indent=2).encode()
    with open(os.path.join(dirpath, "result.json"), "wb") as f:
        f.write(data)
    with open(os.path.join(dirpath, "env.json"), "w") as f:
        json.dump({"python": sys.version.split()[0], "platform": platform.platform(),
                   "config_hash": config_hash(cfg)}, f, sort_keys=True, indent=2)
    return hashlib.sha256(data).hexdigest()

# self-test
c = Config(seed=42)
r = run_experiment(c)
assert r == run_experiment(c) and config_hash(c) == "a0af821358e4"
assert abs(r["pi_hat"] - 3.126) < 1e-12 and run_experiment(Config(seed=43))["pi_hat"] == 3.1504
print(r)
```

## Independent practice

### Goal

Build a tiny but complete reproducible experiment and prove its reproducibility with a clean-copy test.

### Setup

Python 3.9+ standard library and `git`. Create a folder `repro_lab/`, save the code as `repro_lab/exp.py` (starter, then tests at the bottom).

### Tasks

1. Implement `Config`, `config_from_dict` (reject unknown keys, wrong types, `n_samples < 1`) and `config_hash`.
2. Implement `run_experiment(cfg)` with a local `random.Random(cfg.seed)` and sorted sensors.
3. Implement `setup_logger` that never adds duplicate handlers, and `write_run`.
4. Put the code under git: `git init && git add exp.py && git commit -m "experiment"`, then `git clone . ../clean && cd ../clean`.
5. In the clean clone run `PYTHONHASHSEED=1 python exp.py` and `PYTHONHASHSEED=3 python exp.py` (the tests print the result hash on success) and confirm the hashes match.
6. Introduce one bug at a time (global `random.seed`, `for s in set(...)`, a timestamp inside the result) and note which checks fail.

### Tests

```python
import tempfile
c = Config(seed=42)
assert config_hash(c) == "a0af821358e4" and config_hash(Config(seed=43)) != config_hash(c)
assert config_hash(config_from_dict({"sensors": ["a", "b", "c"], "seed": 42})) == config_hash(c)
for bad in ({"seed": 1, "typo": 3}, {"seed": "1"}, {"seed": True}, {"n_samples": 0}):
    try:
        config_from_dict(bad); raise AssertionError("must raise: %r" % (bad,))
    except ValueError:
        pass
r1 = run_experiment(c)
assert r1 == run_experiment(c)                                    # same config, same result
assert abs(r1["pi_hat"] - 3.126) < 1e-12 and set(r1["offsets"]) == {"a", "b", "c"}
assert run_experiment(Config(seed=43)) != r1                       # a different seed changes the result
assert run_experiment(Config(seed=42, sensors=("c", "a", "b"))) == r1   # sensor order must not matter
random.seed(123); before = random.random()
random.seed(123); run_experiment(c); assert random.random() == before   # does not touch the global RNG
lg1 = setup_logger("lab", None)
lg2 = setup_logger("lab", None)
assert lg1 is lg2 and len(lg1.handlers) == 1
d = tempfile.mkdtemp()
lg = setup_logger("lab2", os.path.join(d, "run.log"))
lg.info("config=%s", config_hash(c))
for h in lg.handlers:
    h.flush()
assert "config=a0af821358e4" in open(os.path.join(d, "run.log")).read()
h1 = write_run(os.path.join(d, "r1"), c, r1)
h2 = write_run(os.path.join(d, "r2"), c, run_experiment(c))
assert h1 == h2 and all(os.path.exists(os.path.join(d, "r1", f)) for f in ("config.json", "result.json", "env.json"))
assert "timestamp" not in open(os.path.join(d, "r1", "result.json")).read()
print("result hash", h1[:12])
print("all tests passed")
```

## Verification

Reproducibility is verified by experiments that could fail. (1) Same config twice in one process: identical results. (2) Same config in separate processes with different `PYTHONHASHSEED`: identical `result.json` hash. (3) A fresh `git clone` in a new directory with a fresh environment: identical hash. (4) Different seed: the result must change (else the seed is ignored). (5) Statistical sanity: results across seeds scatter around the truth with the predicted standard error (0.0164 per run here). (6) Inspect the logs: config hash and git commit are present. A check that could reject your claim of reproducibility is any of (2) or (3) failing.

## Failure modes

- Global RNG shared by several functions: call order changes results; a library that reseeds the global RNG breaks your seed.
- Iterating over a `set` or relying on `dict` order from an unordered source: output changes with `PYTHONHASHSEED` (orders `['imu','gps','lidar']` versus `['imu','lidar','gps']`).
- Timestamps, hostnames or absolute paths inside the result file: hashes never match.
- Silent config typos: `{"learning_rat": 0.1}` accepted and ignored, so the run uses the default.
- Mutating a config after hashing it, or storing the defaults in code but not in the saved config.
- `print` for diagnostics: no levels, lost on redirect, mixed with results; and duplicated log lines when handlers are added repeatedly.
- Tests that compare floating results bit-exactly across machines or thread counts.
- Running from a dirty working tree: the commit hash does not describe the code that ran.
- Unpinned dependencies: a minor-version upgrade changes numerical output.

## Alternatives and trade-offs

For configs, a frozen dataclass plus JSON is simple and dependency-free; YAML is more readable but easier to get wrong (implicit type conversions); frameworks such as Hydra add composition and sweeps at the price of complexity; `argparse` alone makes runs hard to reproduce from a file. For tracking, a plain run directory with JSON files is enough for one person; experiment trackers (MLflow, Weights and Biases) add search, comparison and sharing. For environments, a `requirements.txt` with pinned versions, a lock file (`pip-tools`, `uv`, `poetry`) or a container give increasing levels of isolation. Bit-exact reproducibility is cheap for single-threaded CPU code, expensive for GPU and multi-thread code; in those cases record versions and thread counts and compare within a tolerance. Seeds make runs repeatable, not representative: report results over several seeds.

## Transfer and retention

- A robot-learning paper's table is only credible if the training run can be regenerated from a commit and a config; the same applies to your own thesis chapters.
- A ROS launch file is a configuration; `ros2 bag` records inputs for replay, which is the data-side of reproducibility.
- From memory: list the five inputs of an experiment and the three outputs you always save. In a week, run your own earlier experiment from a clean clone and report the hash.

## Exercise answers

1. Result: validation accuracy. Configuration: random seed, learning rate, path of the data file (better: a dataset name plus checksum). Environment metadata: Python version, git commit hash, hostname, wall-clock time. Wall-clock time and hostname should be saved but kept out of the result that is hashed.
2. Only `WARNING:root:b` is printed. `logging.info("a")` is silent because the root logger's default threshold is WARNING. The module-level functions call `basicConfig()` automatically when the root logger has no handler, so that first call installs a handler; the later `basicConfig(level=logging.INFO)` is then a no-op (it does nothing if handlers already exist, unless `force=True`), so `logging.info("c")` is also silent. Configure logging once, before the first message.
3. Three times. Fix: add the handler only when none exist (`if not log.handlers:`), or configure logging once at program start.
4. Not equal: with the global generator the first draw after seeding is `0.1343...` for whichever function runs first, so `x` is 0.134 in the first order and 0.847 in the second. Redesign: each function accepts an `rng` (or a seed) argument and uses its own `random.Random`, so results depend only on explicit inputs.
5. `set` iteration order of strings depends on the per-process hash salt, so the RNG stream is consumed in a different order each run, giving different offsets per sensor. Fix: `for s in sorted(set(sensors))`. Test: run `run_experiment` with the sensors tuple in different orders and assert equal results; or run a subprocess with two `PYTHONHASHSEED` values and compare.
6. `{"n_samples":10000,"seed":42,"sensors":["a","b"]}`. `str(dict)` depends on insertion order and spacing, so equal configs could hash differently, and `repr` of floats and nested types is not a stable interchange format.
7. Commands: `git clone path/to/repo /tmp/clean && cd /tmp/clean && python -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt && python run.py --config config.json --out out1 && PYTHONHASHSEED=3 python run.py --config config.json --out out2 && sha256sum out1/result.json out2/result.json` (the two hashes must match; also compare with the hash recorded from the original run). May differ: timestamps, hostname/path, log line order timing. Must not differ: `result.json`, resolved `config.json`, the config hash, the code commit.
8. `0.6000000000000001` versus `0.6`. A parallel reduction adds partial sums in a different order depending on the number of threads, and floating-point addition is not associative. Policy: `math.isclose(a, b, rel_tol=1e-9, abs_tol=1e-12)` or `numpy.allclose`; demand bit-exactness only for integer/deterministic single-thread pipelines and for hashes of data files.
9. One run: $4\sqrt{p(1-p)/N}$ with $p=\pi/4$: $0.0164$. Mean of 20 seeds: $0.0164/\sqrt{20}=0.0037$. Seed 42's $3.126$ is $0.0156$ below $\pi$, about $0.0156/0.0164=0.95$ standard deviations. A rejecting check: run many seeds and test that the mean error is within $\pm2$ standard errors of zero, and that the variance matches $0.0164^2$; a biased estimator (for example using `<` and a wrong radius) would fail.
10. Expected: identical hashes for clean clones with different hash seeds when the code uses `sorted`. Bug 1 (global RNG): results change when another function draws first; caught by "does not touch the global RNG" or order-swap tests. Bug 2 (set order): caught by the sensor-order test and by differing `PYTHONHASHSEED` runs (not always: seeds 1 and 2 happen to give the same order, 3 differs, so try several). Bug 3 (timestamp in result): hashes differ every run; caught by the repeat test.
