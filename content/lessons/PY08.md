## Why this matters

A result you cannot regenerate is an anecdote. In research code the number that ends up in a figure depends on much more than the algorithm: the version of the code, the hyperparameters, the random seed, the dataset snapshot, the library versions, even the order in which a set is iterated. When these are scattered in your head, in a Jupyter cell history, or in a filename like `results_final2.json`, a rerun months later disagrees and nobody knows why. **Research programming** is the discipline of making the whole experimental setup explicit, recorded and re-runnable: configuration as data, logging instead of print statements, controlled randomness, and an automated check that a clean checkout reproduces the same output.

## Intuition

Think of an experiment as a pure function: `result = run(code, config, data, environment, seed)`. If every argument can be named, stored next to the result, and passed again to get the same value, the experiment is reproducible. Problems arise from **hidden arguments**: the global random generator state, the current working directory, wall-clock time, hash randomization of strings, unpinned library versions, files edited by hand. The workflow below turns hidden arguments into recorded ones.

![A block diagram: code, config, seed, data and environment feed a run step, which writes result.json, run.log and env.json; a banner states the clean-checkout test](/lesson-figures/PY08.svg)

*Figure: inputs on the left are pinned; outputs on the right are saved per run. The clean-checkout test compares hashes of result.json.*

A lab notebook is the everyday counterpart. A measurement without its units, instrument and date cannot be reused, and a result without its code version, parameters, data and random seed cannot be regenerated. Nobody doubts that a chemist must write down the temperature; the same standard applies to the learning rate and the seed of a robot-learning run.

A robot makes the cost concrete. A grasp-success rate of 0.88 appears in a paper draft, and a rerun a month later gives 0.84 with "the same" repository. Nothing was edited on purpose, yet the numbers differ, and the first hours go into guessing which hidden argument moved. **Predict before you compute.** With the random seed fixed, which of these four can still change the reported number: (a) iterating over a `set` of sensor names, (b) a second function drawing from the global random generator before the first one, (c) summing the results on 8 threads instead of 4, (d) writing the current time into the log file? Write down the answers before reading on.

The answer: (a), (b) and (c) can change numbers. A `set` of strings is iterated in an order that depends on a per-process hash salt; the global generator hands out its values in the order of the calls; and floating-point addition is not associative, so a different grouping of the same summands changes the last digits. Case (d) changes only the log, and it harms reproducibility only when the timestamp is written into the file that is hashed to compare runs. The common thread is that the seed fixes one input, not the whole function.

Four intuitions are tempting and wrong. First, "a fixed seed makes the run reproducible": it fixes the stream of random numbers, but not the order in which the code consumes them, the order of iteration, or the order of additions. Second, "it reproduces on one machine, so it is reproducible": a machine carries untracked files, cached results and installed packages that a collaborator does not have, which is why the test runs from a fresh clone. Third, "one run is a result": a run is one draw from a distribution over seeds, and a reader needs to know how wide that distribution is. Fourth, "reproducible means bit-identical everywhere": that is expensive for multi-threaded and GPU code, and often the right goal is agreement within a justified tolerance plus a recorded environment. The sections below make each of these precise: what to record, how to control randomness, how to test the claim, and how many seeds a reported number needs.

## Theory and derivation

### Configuration as data

Put every tunable in a **config object** instead of in module-level constants and scattered literals. A frozen `dataclass` gives defaults, names, and immutability; a loader validates unknown keys and types so typos fail fast (`learning_rat` should be an error, not silently ignored). Save the **resolved** config (defaults plus overrides) in the run directory. A **config hash** (sha256 of the canonical JSON: sorted keys, no spaces) identifies a configuration regardless of key order; for `Config(seed=42)` the canonical string is `{"n_samples":10000,"seed":42,"sensors":["a","b","c"]}`. Command-line parsing with `argparse` should only select a config file and a few overrides; the result must depend on the resolved config, not on argv text.

**Example.** A training config has two fields, `lr` and `batch`. The loader rejects unknown keys, and the canonical JSON gives the same string and hash whatever the key order. Python 3.11.9:

```python
import hashlib, json
from dataclasses import dataclass, asdict

@dataclass(frozen=True)
class TrainCfg:
    lr: float = 0.01
    batch: int = 32

def load(d):
    unknown = set(d) - {"lr", "batch"}
    if unknown:
        raise ValueError("unknown config key(s): %s" % sorted(unknown))
    return TrainCfg(**d)

def chash(cfg):
    s = json.dumps(asdict(cfg), sort_keys=True, separators=(",", ":"))
    return s, hashlib.sha256(s.encode()).hexdigest()[:12]

a = load({"lr": 0.05, "batch": 64})
b = load({"batch": 64, "lr": 0.05})
print(chash(a))
print(chash(a) == chash(b))
try:
    load({"lr": 0.05, "bach": 64})
except ValueError as e:
    print(e)
```

Output:

```text
('{"batch":64,"lr":0.05}', 'afba9a442772')
True
unknown config key(s): ['bach']
```

The misspelt `bach` stops the run before any training starts, instead of silently training with the default batch size of 32.

### Logging

`print` writes text with no level, no timestamp and no destination control. The `logging` module separates **what** is logged (a level: DEBUG, INFO, WARNING, ERROR, CRITICAL; default threshold WARNING) from **where** it goes (handlers: console, file) and **how** it looks (formatters). A logger is obtained by name (`logging.getLogger("exp")`); handlers attach to loggers; calling the setup code twice must not add a second handler, or every message appears twice (three calls give three copies). Log the config hash, seed, git commit and key metrics at INFO; details at DEBUG; never log secrets.

**Example.** A `setup` function called once from the training module and once from the data module. Without a guard each call adds a handler; with the guard the second call finds the existing one. Python 3.11.9:

```python
import logging, sys

def setup_bad(name):
    log = logging.getLogger(name)
    log.setLevel(logging.INFO)
    h = logging.StreamHandler(sys.stdout)
    h.setFormatter(logging.Formatter("%(levelname)s %(name)s %(message)s"))
    log.addHandler(h)                    # a new handler on every call
    return log

def setup_ok(name):
    log = logging.getLogger(name)
    if not log.handlers:                 # only the first call adds one
        log.setLevel(logging.INFO)
        h = logging.StreamHandler(sys.stdout)
        h.setFormatter(logging.Formatter("%(levelname)s %(name)s %(message)s"))
        log.addHandler(h)
    return log

for setup in (setup_bad, setup_ok):
    setup("train"); log = setup("train")           # called from two modules
    log.info("epoch=3 loss=%.3f", 0.412)
    print(len(log.handlers))
    log.handlers.clear()
```

Output:

```text
INFO train epoch=3 loss=0.412
INFO train epoch=3 loss=0.412
2
INFO train epoch=3 loss=0.412
1
```

The unguarded version prints every message twice and holds two handlers; the guarded one prints it once.

### Randomness and determinism

Pseudo-random generators are deterministic given a seed. Use a **local generator** (`rng = random.Random(seed)`, `numpy.random.default_rng(seed)`, `torch.Generator`) passed explicitly, not the module-global one: with the global `random`, calling function B before A changes A's numbers. Remaining sources of nondeterminism:

- **Hash randomization**: `str` hashes are salted per process unless `PYTHONHASHSEED` is fixed, so `list(set_of_strings)` can have a different order each run. Sort before iterating when the order matters.
- **Floating-point non-associativity**: $(0.1+0.2)+0.3=0.6000000000000001$ but $0.1+(0.2+0.3)=0.6$; parallel reductions, multithreaded BLAS and GPU kernels change the order of additions. Compare results with a tolerance, or force deterministic algorithms and record thread counts.
- **Time, hostname, paths and environment variables** leaking into outputs.
- **Unpinned dependencies**: a library upgrade changes numerical routines.
- **Data**: files changing under the same name; store a checksum.

**Example.** Three noise values for a simulated sensor, once from a local generator and once from the global one. Between the two calls other code draws once from the global generator. Python 3.11.9:

```python
import random

def noise(seed, n=3):
    rng = random.Random(seed)                       # local generator
    return [round(rng.gauss(0, 1), 4) for _ in range(n)]

random.seed(0)
a = noise(7)
random.random()                                     # other code draws from the global RNG
print(noise(7) == a, a)

def noise_global(n=3):
    return [round(random.gauss(0, 1), 4) for _ in range(n)]

random.seed(7); first = noise_global()
random.seed(7); random.random(); second = noise_global()   # one unrelated draw in between
print(first == second, first, second)
```

Output:

```text
True [-0.2559, 0.5114, -0.2261]
False [-0.2559, 0.5114, -0.2261] [0.8465, 1.1783, 1.1129]
```

The local generator ignores the stranger draw; the global one shifts every later value by one position.

### The clean-checkout test

A reproducibility claim is a prediction that can fail. Procedure: `git clone` the repository to a new directory (so untracked files, local edits and relative-path accidents disappear), create a fresh environment from the lock file, run the experiment with the saved config, and compare `sha256sum result.json` with the original. Timestamps and hostnames belong in `env.json`, not `result.json`, so that the hash covers only what must be identical.

**Example.** `run.py` reads a calibration file `calib.json` that `.gitignore` excludes, so it was never committed. In the working directory the run succeeds; in a fresh clone it fails. Transcript from a scratch repository (git 2.34, Python 3.11.9):

```text
$ python3 run.py                 # in the working directory
result 3.0
$ git clone work clean && cd clean && python3 run.py
FileNotFoundError: [Errno 2] No such file or directory: 'calib.json'
```

The first run hid an input that the repository did not contain. After the file is tracked (or its checksum and download step are recorded), the clone must print `result 3.0` and the hashes must agree.

### Seeds, streams and why `seed + i` is not a design

A single integer seed is enough for one generator, but experiments need many *independent* streams: one per run in a sweep, one per trial, one per worker. Three naive schemes fail in different ways.

*Random seeds drawn from a small space collide.* If $k$ runs each draw a seed uniformly from $M$ values, the probability that all seeds are distinct is $\prod_{i=0}^{k-1}(1-i/M)$. Using $1-x\le e^{-x}$ and $\sum_{i<k}i=k(k-1)/2$,
$$P(\text{some collision})\;\approx\;1-\exp\!\Big(-\frac{k(k-1)}{2M}\Big),$$
and the collision probability reaches $1/2$ near $k\approx\sqrt{2M\ln2}=1.1774\sqrt M$ (the birthday bound). For $M=2^{32}$ this is about $77{,}000$ runs; for $k=10^4$ it is already $1.2\%$, a silent duplicated run in a large sweep. With $M=2^{128}$ the same $k$ gives about $10^{-31}$. NumPy's documentation therefore recommends drawing seeds with $128$ bits of entropy (`secrets.randbits(128)`) when they are not chosen by hand ("Parallel random number generation", NumPy docs).

*Adjacent seeds can give related streams.* The same page explains that a naive initialisation, such as copying a 32-bit seed into the last word of the 624-word Mersenne Twister state and leaving the rest zero, yields a valid but poor state, and that two adjacent integer seeds ($12345$ and $12346$) would then produce very similar streams. `SeedSequence` repairs this by hashing the seed with functions of good avalanche behaviour (flipping any input bit flips each output bit with probability about $1/2$), so nearby seeds give initial states that are far apart with very high probability.

*Streams must not depend on the executor.* `SeedSequence.spawn(n)` creates $n$ children whose `spawn_key` records their position in the tree, $(0,),(1,),\dots$; each child's stream is determined by the parent entropy and that key. Two facts matter for reproducibility, both checkable by running code:

- Child $i$ does not depend on how many siblings were requested: `SeedSequence(42).spawn(3)[2]` and `SeedSequence(42).spawn(12)[2]` generate identical numbers, and so does the stateless construction `SeedSequence(42, spawn_key=(2,))`.
- But `spawn` is stateful: calling it twice on the *same* object returns children $(0,1,2)$ and then $(3,4,5)$, because the object counts how many children it has already issued. Results then depend on how often a function was called.

The design rule that follows is to derive a stream from the identity of the **task** (the trial index $i$), never from the identity of the executor (worker number or process id), so that running on 1, 4 or 64 workers gives the same numbers.

**Example.** A sweep of $k=1000$ runs draws each seed uniformly from $M=2^{24}$ values. The approximation gives $1-\exp(-1000\cdot999/2^{25})=0.02933$, equal to the exact product to five digits, and one half is reached near $k=\sqrt{2M\ln2}=4823$. Python 3.11.9:

```python
import math

M, k = 2 ** 24, 1000
approx = 1 - math.exp(-k * (k - 1) / (2 * M))
exact = 1 - math.prod(1 - i / M for i in range(k))
print(round(approx, 5), round(exact, 5))
print(round(math.sqrt(2 * M * math.log(2))))
```

Output:

```text
0.02933 0.02933
4823
```

So 2.9 % of such sweeps contain a repeated seed, which is a silent duplicated run.

### Reproducible parallel reductions

Floating-point addition is not associative, so a parallel sum is a different expression for every partition of the work. Quantifying the damage uses the same recursion as in the testing lesson: for a left-to-right sum, $\hat s_n=\sum_j x_j(1+\theta_j)$ with $|\theta_j|\le(n-j+1)u$, hence $|\hat s_n-s_n|\le(n-1)u\sum|x_j|$ to first order (Goldberg, "What Every Computer Scientist Should Know About Floating-Point Arithmetic", §"Errors in Summation", eq. 31). Now compare reduction shapes. Each summand passes through some number of additions, and each addition multiplies it by one factor $(1+\delta)$:

- **Sequential**: the first summand passes through $n-1$ additions, so the bound is $(n-1)\,u\sum|x_j|$.
- **Balanced binary tree** (pairwise): every summand passes through exactly $\lceil\log_2n\rceil$ additions, so the bound is $\lceil\log_2n\rceil\,u\sum|x_j|$. NumPy's `np.sum` uses a blocked pairwise scheme for this reason.
- **$t$ workers, sequential inside each chunk, then a sequential combination**: at most $(n/t-1)+(t-1)$ additions on any path, so the bound is $(n/t+t-2)\,u\sum|x_j|$. The bound *and the rounded bits* depend on $t$.
- **Fixed blocks**: cut the array into blocks of a fixed size $B$ (independent of $t$), sum each block sequentially, then add the block sums in block order. Any assignment of whole blocks to workers produces exactly the same block sums and the same combination order, so the result is bitwise independent of $t$. The bound is $(B-1+n/B-1)\,u\sum|x_j|$, minimised near $B=\sqrt n$, and a pairwise combination of the block sums reduces it further.

Kahan's compensated summation (Goldberg, Theorem 8) attacks the same problem from the other side: it replaces the $n$-dependent factor by the constant $2$, whatever the order. In practice choose by the guarantee you need. If bitwise reproducibility across machines is required, fix the reduction tree; if you only need agreement within rounding, compare with a tolerance derived from the bounds above.

**Example.** 5000 values of mixed magnitude ($10^{-2}$ to $10^{2}$) are summed by $t=1,2,4$ simulated workers in $t$ equal chunks, and by the fixed-block scheme with $B=100$ whose blocks are dealt to the $t$ workers. Python 3.11.9 with NumPy 2.4.6:

```python
import math
import numpy as np

rng = np.random.default_rng(5)
x = rng.standard_normal(5000) * 10.0 ** rng.integers(-2, 3, 5000)

def seq(a):                                   # left-to-right sum
    s = 0.0
    for v in a.tolist():
        s += v
    return s

def chunked(a, t):                            # t workers, one chunk each
    return seq(np.array([seq(c) for c in np.array_split(a, t)]))

def fixed_blocks(a, t, B=100):                # blocks of fixed size B, dealt to t workers
    starts = list(range(0, len(a), B))
    sums = [0.0] * len(starts)
    for w in range(t):
        for j in range(w, len(starts), t):
            sums[j] = seq(a[starts[j]:starts[j] + B])
    return seq(np.array(sums))                # combined in block order

print("fsum", repr(math.fsum(x.tolist())))
for t in (1, 2, 4):
    print("t =", t, repr(chunked(x, t)), repr(fixed_blocks(x, t)))
```

Output:

```text
fsum 2720.4837860537373
t = 1 2720.4837860537373 2720.483786053738
t = 2 2720.4837860537323 2720.483786053738
t = 4 2720.4837860537345 2720.483786053738
```

The chunked sums differ from one another in the 16th significant digit, the fixed-block sum is the same number for all three; both lie within $6\times10^{-12}$ of the correctly rounded `math.fsum`.

### How many seeds? The variance of a reported result

Fixing a seed makes one run repeatable; it does not make it representative. A reported number $\hat\theta$ (an accuracy, an error, an estimate of $\pi$) is one draw from a distribution over seeds, and a reader needs the width of that distribution. Henderson et al. ("Deep Reinforcement Learning that Matters", §"Random Seeds and Trials") ran ten trials of one configuration, differing only in the seed, split them into two groups of five, and found learning curves that were statistically different; averaging a handful of runs, or selecting the best ones, can therefore mislead.

Model: runs with different seeds are independent draws $\hat\theta_1,\dots,\hat\theta_N$ with mean $\mu$ and variance $\sigma^2$. The empirical mean and standard deviation are $\bar\theta=\frac1N\sum_i\hat\theta_i$ and $s=\sqrt{\frac1{N-1}\sum_i(\hat\theta_i-\bar\theta)^2}$ (Colas, Sigaud & Oudeyer 2018, Eq. 1). Because the runs are independent, the variance of a sum is the sum of the variances, so
$$\operatorname{Var}(\bar\theta)=\frac{1}{N^2}\sum_{i=1}^{N}\sigma^2=\frac{\sigma^2}{N},\qquad \mathrm{SE}=\frac{\sigma}{\sqrt N}\approx\frac{s}{\sqrt N}.$$
An approximate $95\,\%$ interval for $\mu$ is $\bar\theta\pm t_{0.975,N-1}\,s/\sqrt N$, where $t_{0.975,N-1}$ is the Student quantile: $2.776$ for $N=5$, $2.020$ for $N=42$, and $1.96$ in the limit. To reach a half-width $h$, plan $N\ge(z\sigma/h)^2$ with $z=1.96$ and $\sigma$ taken from a pilot study; when $N$ comes out small, replace $z$ by $t$ and iterate. Halving the interval costs four times the seeds, because the width falls only as $1/\sqrt N$.

The assumptions can fail. The seeds must produce independent streams (the previous subsections); runs that share an initial checkpoint or a data order are correlated and the true standard error is larger. The mean of $N$ runs must be close to normal, which is doubtful for heavy-tailed outcomes such as occasional training collapses; Colas et al. then use a bootstrap interval. And the interval describes the mean over seeds of the *procedure*, not the quality of one trained model.

**Example.** Policy returns scatter with $\sigma=4.2$ points across seeds (a pilot estimate). To report the mean to within $\pm1.0$ point at 95 %, $N=\lceil(1.96\cdot4.2/1.0)^2\rceil=68$ seeds are needed. With only $N=5$ the Student half-width is $2.776\cdot4.2/\sqrt5=5.21$ points, wider than the scatter itself. Python 3.11.9:

```python
import math
from statistics import NormalDist

z = NormalDist().inv_cdf(0.975)
sigma, h = 4.2, 1.0
print(round(z, 2), math.ceil((z * sigma / h) ** 2))
print(round(z * sigma / math.sqrt(5), 2))
```

Output:

### How the pieces connect

Configuration as data and the run directory record the arguments of the experiment function; logging records what happened; local generators and task-derived streams control the random arguments; the clean-checkout test and the result hash check the claim; the reduction analysis says when bit-identical results are possible and when a tolerance is the honest criterion; and the seed count says how wide the reported number really is. The tolerance reasoning is the one derived in the testing lesson (PY07), and the standard-error formula is the same one that sets the confidence interval of any measured quantity.

## Worked example

### Case 1: configuration, run and result hash

**Problem.** The experiment estimates $\pi$ by Monte Carlo: draw $N$ points in the unit square, count those with $x^2+y^2\le1$, and report $\hat\pi=4\cdot\text{inside}/N$. It also draws a per-sensor offset estimate (the mean of 100 Gaussian values per sensor). With `Config(seed=42, n_samples=10000, sensors=("a","b","c"))`, find the config hash, $\hat\pi$ and the offsets, show that a rerun gives the same result file, and say how noisy $\hat\pi$ is.

**Solution.**

1. Canonical config: `json.dumps` of the dataclass dictionary with sorted keys and no spaces gives `{"n_samples":10000,"seed":42,"sensors":["a","b","c"]}`; the first 12 hex digits of its sha256 are `a0af821358e4` (seed 43 gives `b4a0398f835d`, so the hash does depend on the seed).
2. Run with a local `random.Random(42)`: 7815 of the 10 000 points fall inside, so $\hat\pi=4\cdot7815/10\,000=3.126$; the offsets, drawn afterwards from the same generator in sorted sensor order, are `{'a': 0.040318, 'b': 0.123098, 'c': -0.02628}`. A second run in the same process gives exactly the same dictionary; seed 43 gives $\hat\pi=3.1504$.
3. Serialise the result with sorted keys; the sha256 of `result.json` starts with `b76d3b43dc9c` for seed 42 on every run. Timestamps and hostnames go to `env.json`, so they cannot change this hash.
4. Noise of one estimate: each point is inside with probability $p=\pi/4$, so the count is binomial and $\mathrm{sd}(\hat\pi)=4\sqrt{p(1-p)/N}=4\sqrt{0.7854\cdot0.2146/10^4}=0.0164$. Over 20 seeds the mean has standard error $0.0164/\sqrt{20}=0.0037$.
5. The single value 3.126 lies $(\pi-3.126)/0.0164=0.95$ standard deviations below $\pi$: ordinary scatter, and it should be reported with that uncertainty.

**Check.** Running the experiment twice, and once from a clean clone with `PYTHONHASHSEED` set to 1 and 3, gives the same `result.json` hash `b76d3b43dc9c`; seed 43 gives a different hash, so the seed is not ignored.

**Takeaway.** The config hash names the experiment, the result hash tests the claim, and the standard error says how much of a difference between two numbers is just seed noise.

### Case 2: the set-order trap (harder)

**Problem.** The per-sensor offsets of the experiment are drawn from one generator, `random.Random(7)`, 100 Gaussian values averaged per sensor and rounded to 6 decimals, for the sensors `("imu", "gps", "lidar")`. The loop is written `for s in set(sensors)`. Run with `PYTHONHASHSEED=1` and `PYTHONHASHSEED=3` and compare the result hashes; then fix the loop and explain why the hashes differed.

**Solution.**

1. The stream of `random.Random(7)` is fixed: the three offsets it produces, in order, are $g_1=-0.058178$, $g_2=0.080740$, $g_3=-0.010933$, whatever the hash seed.
2. Python salts the hash of `str` per process, so the iteration order of a set of strings is not fixed. With `PYTHONHASHSEED=1`, `list(set(sensors))` is `['imu', 'gps', 'lidar']`: imu takes $g_1$, gps takes $g_2$, lidar takes $g_3$. The result `{"gps": 0.08074, "imu": -0.058178, "lidar": -0.010933}` has sha256 prefix `0ed87f825838`.
3. With `PYTHONHASHSEED=3` the order is `['imu', 'lidar', 'gps']`: lidar now takes $g_2=0.08074$ and gps takes $g_3=-0.010933$, giving sha256 prefix `b0c220eb2a2e`.
4. Same seed, same config, two different hashes: the only difference between the runs is a hidden argument, the hash salt. The "same hash on every run" check is exactly what detects it.
5. Fix: iterate in an order defined by the data, `for s in sorted(set(sensors))`. The order is `['gps', 'imu', 'lidar']`: gps takes $g_1$, imu takes $g_2$, lidar takes $g_3$, and the hash is `82abb5841065` for every `PYTHONHASHSEED`.

![Table of three runs: the stream draws g1, g2, g3 are assigned to different sensors when a set is iterated under two hash seeds, giving two different result hashes, while the sorted loop gives one hash](/lesson-figures/PY08-4.svg)

*Figure: the draws are the same in all three columns; only the assignment to sensors changes, and with it the result hash. The sorted loop gives a result that differs from both set runs (it is just another fixed order), so the expected value must be regenerated once after the fix.*

**Check.** Running the script four times, under `PYTHONHASHSEED` 1 and 3 with the set loop and with the sorted loop (Python 3.11.9), printed the hashes `0ed87f825838`, `b0c220eb2a2e`, `82abb5841065` and `82abb5841065`.

**Takeaway.** A fixed seed controls the stream, not who consumes it; make the consumption order a function of the data.

### Case 3: how many seeds? (harder)

**Problem.** The estimator $\hat\pi$ with $N=10\,000$ points has a per-run standard deviation $\sigma$. A 95 % interval of half-width $0.005$ is wanted. How many seeds are needed, and does a real batch of that size deliver the target?

**Solution.**

1. Per-run standard deviation: $p=\pi/4=0.785398$, $p(1-p)=0.168548$, so $\sigma=4\sqrt{0.168548/10^4}=0.016422$.
2. Plan with the normal approximation of the theory: $N\ge(1.96\cdot0.016422/0.005)^2=6.4373^2=41.44$, so 42 seeds.
3. For a small $N$ the Student quantile replaces 1.96: for 42 seeds $t_{0.975,41}=2.0195$ and the half-width is $2.0195\cdot0.016422/\sqrt{42}=0.005117>0.005$; for 44 seeds $t_{0.975,43}=2.0167$ and the half-width is $0.004993$. The normal approximation plans 42, the Student correction asks for 44.
4. Run 42 seeds, each estimate from its own child stream `SeedSequence(2024).spawn(42)[i]` (a function of the task index only): mean $\bar\theta=3.1426$, $s=0.01663$, $\mathrm{SE}=0.01663/\sqrt{42}=0.002566$, half-width $2.0195\cdot0.002566=0.005182$, interval $[3.1374,\,3.1477]$. It contains $\pi=3.14159$.
5. The half-width, 0.0052, misses the target 0.005 slightly because this batch has $s=0.01663$, a little above $\sigma$, and $t>1.96$: the planning step gave the right order of magnitude, not a guarantee.

![Left: half-width 1.96 sigma over root N against the number of seeds, falling to 0.0072 at 20 seeds and 0.0050 at 42 seeds. Right: 42 estimates of pi, their mean 3.1426 and the 95 percent interval 3.1374 to 3.1477 around pi = 3.1416](/lesson-figures/PY08-5.svg)

*Figure: left, the planning curve with the 20-seed and 42-seed points; right, the 42 simulated estimates, one dot each, with the interval they give.*

**Check.** A simulation of 20 000 batches of 42 seeds (binomial counts with $N=10\,000$, $p=\pi/4$, seed 1) gave an interval that contained $\pi$ in $0.94915$ of the batches, consistent with a 95 % interval.

**Takeaway.** The number of seeds grows as $1/h^2$: plan it from a pilot $\sigma$, then verify with the Student interval, and report the interval, not only the mean.

## Reference implementation

```python
import hashlib, json, logging, os, platform, random, sys
from dataclasses import dataclass, asdict

@dataclass(frozen=True)
class Config:
    seed: int = 0
    n_samples: int = 10000
    sensors: tuple = ("a", "b", "c")

def config_from_dict(d):
    allowed = {"seed": int, "n_samples": int, "sensors": (list, tuple)}
    for k, v in d.items():
        if k not in allowed:
            raise ValueError("unknown config key: %s" % k)
        if isinstance(v, bool) or not isinstance(v, allowed[k]):
            raise ValueError("bad type for %s" % k)
    kw = dict(d)
    if "sensors" in kw:
        kw["sensors"] = tuple(kw["sensors"])
    cfg = Config(**kw)
    if cfg.n_samples < 1:
        raise ValueError("n_samples must be >= 1")
    return cfg

def config_hash(cfg):
    s = json.dumps(asdict(cfg), sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(s.encode()).hexdigest()[:12]

def run_experiment(cfg):
    rng = random.Random(cfg.seed)
    inside = 0
    for _ in range(cfg.n_samples):
        x, y = rng.random(), rng.random()
        inside += x * x + y * y <= 1.0
    offsets = {}
    for s in sorted(set(cfg.sensors)):
        offsets[s] = round(sum(rng.gauss(0, 1) for _ in range(100)) / 100, 6)
    return {"pi_hat": 4 * inside / cfg.n_samples, "n": cfg.n_samples, "offsets": offsets}

def setup_logger(name, logfile=None, level=logging.INFO):
    log = logging.getLogger(name)
    log.setLevel(level)
    log.propagate = False
    if not log.handlers:
        fmt = logging.Formatter("%(asctime)s %(levelname)s %(name)s %(message)s")
        h = logging.StreamHandler(); h.setFormatter(fmt); log.addHandler(h)
        if logfile:
            fh = logging.FileHandler(logfile); fh.setFormatter(fmt); log.addHandler(fh)
    return log

def write_run(dirpath, cfg, result):
    os.makedirs(dirpath, exist_ok=True)
    with open(os.path.join(dirpath, "config.json"), "w") as f:
        json.dump(asdict(cfg), f, sort_keys=True, indent=2)
    data = json.dumps(result, sort_keys=True, indent=2).encode()
    with open(os.path.join(dirpath, "result.json"), "wb") as f:
        f.write(data)
    with open(os.path.join(dirpath, "env.json"), "w") as f:
        json.dump({"python": sys.version.split()[0], "platform": platform.platform(),
                   "config_hash": config_hash(cfg)}, f, sort_keys=True, indent=2)
    return hashlib.sha256(data).hexdigest()

# self-test
c = Config(seed=42)
r = run_experiment(c)
assert r == run_experiment(c) and config_hash(c) == "a0af821358e4"
assert abs(r["pi_hat"] - 3.126) < 1e-12 and run_experiment(Config(seed=43))["pi_hat"] == 3.1504
print(r)
```

### Library track

The same discipline with the numerical libraries you will actually use. Save as `repro_libs.py` (needs `numpy` and `torch`; compare with the stdlib `random.Random` approach above).

```python
import numpy as np
import torch

# 1. Local generators: the stream depends only on the seed, not on global state
def noise_np(seed, n=3):
    return np.random.default_rng(seed).normal(size=n)

np.random.seed(999); np.random.rand(10)            # touching the legacy global RNG changes nothing
assert np.array_equal(noise_np(42), noise_np(42)) and not np.array_equal(noise_np(42), noise_np(43))

def noise_torch(seed, n=3):
    g = torch.Generator().manual_seed(seed)
    return torch.randn(n, generator=g)
```

## Verification

Reproducibility is verified by experiments that could fail. (1) Same config twice in one process: identical results. (2) Same config in separate processes with different `PYTHONHASHSEED`: identical `result.json` hash. (3) A fresh `git clone` in a new directory with a fresh environment: identical hash. (4) Different seed: the result must change (else the seed is ignored). (5) Statistical sanity: results across seeds scatter around the truth with the predicted standard error (0.0164 per run here). (6) Inspect the logs: config hash and git commit are present. A check that could reject your claim of reproducibility is any of (2) or (3) failing.

## Failure modes

- Global RNG shared by several functions: call order changes results; a library that reseeds the global RNG breaks your seed.
- Iterating over a `set` or relying on `dict` order from an unordered source: output changes with `PYTHONHASHSEED` (orders `['imu','gps','lidar']` versus `['imu','lidar','gps']`).
- Timestamps, hostnames or absolute paths inside the result file: hashes never match.
- Silent config typos: `{"learning_rat": 0.1}` accepted and ignored, so the run uses the default.
- Mutating a config after hashing it, or storing the defaults in code but not in the saved config.
- `print` for diagnostics: no levels, lost on redirect, mixed with results; and duplicated log lines when handlers are added repeatedly.
- Tests that compare floating results bit-exactly across machines or thread counts.
- Running from a dirty working tree: the commit hash does not describe the code that ran.
- Unpinned dependencies: a minor-version upgrade changes numerical output.

## Alternatives and trade-offs

For configs, a frozen dataclass plus JSON is simple and dependency-free; YAML is more readable but easier to get wrong (implicit type conversions); frameworks such as Hydra add composition and sweeps at the price of complexity; `argparse` alone makes runs hard to reproduce from a file. For tracking, a plain run directory with JSON files is enough for one person; experiment trackers (MLflow, Weights and Biases) add search, comparison and sharing. For environments, a `requirements.txt` with pinned versions, a lock file (`pip-tools`, `uv`, `poetry`) or a container give increasing levels of isolation. Bit-exact reproducibility is cheap for single-threaded CPU code, expensive for GPU and multi-thread code; in those cases record versions and thread counts and compare within a tolerance. Seeds make runs repeatable, not representative: report results over several seeds.

## Transfer and retention

- A robot-learning paper's table is only credible if the training run can be regenerated from a commit and a config; the same applies to your own thesis chapters.
- A ROS launch file is a configuration; `ros2 bag` records inputs for replay, which is the data-side of reproducibility.
- From memory: list the five inputs of an experiment and the three outputs you always save. In a week, run your own earlier experiment from a clean clone and report the hash.

(vi) The docs note that keys become strings; with `sort_keys=True` the mixed keys raise `TypeError: '<' not supported between instances of 'str' and 'int'`, and without sorting the output `{"1": "a", "1": "b"}` has a duplicate key that collapses on reload: reject non-string keys. Solution:
    ```python
    import json, math
    def canonical(cfg):
        def norm(o):
            if isinstance(o, dict):
                if not all(isinstance(k, str) for k in o):
                    raise TypeError("non-string key")
                return {k: norm(v) for k, v in o.items()}
            if isinstance(o, (list, tuple)):
                return [norm(v) for v in o]
            if isinstance(o, (bool, str)) or o is None or isinstance(o, int):
                return o
            if isinstance(o, float):
                if not math.isfinite(o):
                    raise ValueError("non-finite")
                return 0.0 if o == 0 else (int(o) if o.is_integer() and abs(o) < 2**53 else o)
            raise TypeError(type(o))
        return json.dumps(norm(cfg), sort_keys=True, separators=(",", ":"),
                          ensure_ascii=True, allow_nan=False)
    ```
