## Why this matters

A robot's software is mostly data moving between producers and consumers: a camera produces frames at 30 Hz, a planner reads the latest map, a logger records every message, a filter needs the last 20 readings. The same Python code can be 100 times slower than necessary, or silently lose messages, because the wrong container was chosen. Data structures are a set of contracts that trade access speed, update speed, order and memory. Knowing the costs lets you predict, before running anything, whether a design survives 10,000 messages per second.

## Intuition

A **list** is a row of numbered boxes: jumping to box $i$ is instant, appending at the right end is instant (most of the time), but removing the first box forces every other box to slide one place left. A **hash map** (dict) is a coat-check: the key is hashed into a bucket number so you go straight to the slot instead of scanning, but the key must be something whose hash never changes. A **queue** keeps arrival order: the oldest item leaves first. A **deque** (double-ended queue) is a row of boxes with a movable start, so removing from the front only moves a pointer.

![Top: list pop(0) shifts all 5 remaining messages left; bottom: deque popleft moves only the head pointer; a note gives 15 moves versus 6 for n=6 and 50 million versus 10 thousand for n=10,000](/lesson-figures/PY02.svg)

*Draining a FIFO of n messages: a list pays n(n−1)/2 element moves; a deque pays n pointer updates.*

## Theory and derivation

### Costs at a glance

| Operation | list | dict / set | deque |
|---|---|---|---|
| index / lookup by key | $O(1)$ | $O(1)$ average | $O(n)$ in the middle, $O(1)$ at the ends |
| append at end | $O(1)$ amortized | insert $O(1)$ average | $O(1)$ |
| pop from end | $O(1)$ | delete $O(1)$ average | $O(1)$ |
| insert/pop at front | $O(n)$ | n/a | $O(1)$ |
| membership `x in c` | $O(n)$ | $O(1)$ average | $O(n)$ |
| iterate | $O(n)$ | $O(n)$ | $O(n)$ |

### Amortized append

A dynamic array over-allocates. When full, it allocates a bigger block and copies. If the capacity doubles, the copies for $n=2^k$ appends total $1+2+4+\dots+2^{k-1}=2^k-1<n$, so the **amortized** cost per append is $<2$ copies plus the write itself: $O(1)$. Python grows by roughly 12.5% instead (so a few more copies per append, about 9, still constant); the reallocation steps are visible with `sys.getsizeof`: the size jumps at lengths 1, 5, 9, 17, 25, 33 in the CPython build I tested. Amortized means the average over a sequence of operations; an individual append can still be slow.

### Hash maps

A dict computes `hash(key)`, maps it to a slot, and compares keys on a collision. The expected cost is $O(1)$ if the hash spreads keys well and the table is not too full (the table resizes as it grows); the worst case is $O(n)$. Two requirements follow: keys must be **hashable** (immutable in the sense that `hash` and `==` never change: ints, strings, tuples of hashables; lists and dicts are not), and objects that compare equal must hash equally. Since Python 3.7 a dict preserves insertion order. A **set** is a dict without values and is the right tool for "have I seen this?".

### Queues and bounded buffers

FIFO order means enqueue at one end and dequeue at the other. `collections.deque` supports both ends in $O(1)$. A **bounded** queue (`deque(maxlen=k)`, or a ring buffer) must have a **drop policy** when full: drop the oldest (keep the freshest data, right for perception), drop the newest (keep history, right for logging a burst), or block the producer (applies backpressure, can deadlock a real-time loop). If a producer is faster than a consumer, an unbounded queue grows without limit: with arrival rate $\lambda$ and service rate $\mu<\lambda$ the backlog grows by $\lambda-\mu$ per second, and the latency of the newest message after $T$ seconds is $(\lambda-\mu)T/\mu$.

### Monotonic deque

To maintain the maximum of the last $k$ values in a stream, keep a deque of **indices** whose values are decreasing from front to back. On a new value $x$: pop from the back while the back value is $\le x$ (they can never be a maximum again); append the new index; pop from the front if it left the window. The front is the window maximum. Each index is appended and removed at most once, so the whole pass is $O(n)$, not $O(nk)$.

## Worked example

A range sensor stream is processed by three consumers. Messages are tuples `(sensor, seq, value)`.

**Queue cost.** Draining $n=6$ messages with `list.pop(0)`: the pops move $5+4+3+2+1+0=15$ elements; `deque.popleft()` does 6 pointer updates. For $n=10{,}000$ the list moves $10^4\cdot(10^4-1)/2=49{,}995{,}000$ elements. A measured run draining $n=50{,}000$ items took 0.30 s with a list and 0.0033 s with a deque (about 90 times).

**Ring buffer, capacity 3,** pushing 1 through 7: pushes 1, 2, 3 fill it and drop nothing; push 4 drops 1; push 5 drops 2; push 6 drops 3; push 7 drops 4. Dropped sequence: `[None, None, None, 1, 2, 3, 4]`; final contents `[5, 6, 7]`.

**Latest per sensor.** Messages `("a",1,0.5), ("b",1,2.0), ("a",3,0.7), ("a",2,0.6)`. A dict keyed by sensor with the max sequence number keeps `a -> (3, 0.7)`, `b -> (1, 2.0)`; the late message `("a",2,0.6)` is correctly ignored. The result: `{"a": 0.7, "b": 2.0}`.

**Sliding-window maximum**, $k=3$, $x=[2,1,4,3,6,5,2,7]$. Deque of indices (values in brackets):
- $i=0$: push 0 `[0(2)]`. $i=1$: 1 < 2 stays: `[0(2),1(1)]`. $i=2$: pop 1, pop 0 (both ≤ 4); push 2: `[2(4)]`, window full, output 4.
- $i=3$: 3 < 4: `[2(4),3(3)]`, output 4. $i=4$: pop 3, pop 2; push 4: `[4(6)]`, output 6. $i=5$: `[4(6),5(5)]`, output 6.
- $i=6$: `[4(6),5(5),6(2)]`; index 4 is still in the window $[4,6]$, output 6. $i=7$: pop 6, 5 (≤ 7), and 4 (6 ≤ 7): `[7(7)]`, output 7.
Result `[4, 4, 6, 6, 6, 7]`.

## Reference implementation

```python
from collections import deque

class RingBuffer:
    """Bounded FIFO that drops the oldest item when full."""
    def __init__(self, capacity):
        if capacity < 1:
            raise ValueError("capacity must be >= 1")
        self.capacity = capacity
        self._q = deque()
    def push(self, item):
        dropped = None
        if len(self._q) == self.capacity:
            dropped = self._q.popleft()
        self._q.append(item)
        return dropped
    def pop_oldest(self):
        if not self._q:
            raise IndexError("empty buffer")
        return self._q.popleft()
    def __len__(self):
        return len(self._q)
    def to_list(self):
        return list(self._q)

def latest_by_sensor(messages):
    out = {}
    for sensor, seq, value in messages:
        if sensor not in out or seq > out[sensor][0]:
            out[sensor] = (seq, value)
    return {s: v for s, (q, v) in out.items()}

def dedupe(messages):
    seen, out = set(), []
    for m in messages:
        key = (m[0], m[1])
        if key not in seen:
            seen.add(key)
            out.append(m)
    return out

def sliding_window_max(xs, k):
    if k < 1 or k > len(xs):
        raise ValueError("bad window")
    dq, out = deque(), []
    for i, x in enumerate(xs):
        while dq and xs[dq[-1]] <= x:
            dq.pop()
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()
        if i >= k - 1:
            out.append(xs[dq[0]])
    return out

# self-test
r = RingBuffer(3)
assert [r.push(i) for i in range(1, 8)] == [None, None, None, 1, 2, 3, 4]
assert r.to_list() == [5, 6, 7]
assert latest_by_sensor([("a", 1, .5), ("b", 1, 2.0), ("a", 3, .7), ("a", 2, .6)]) == {"a": .7, "b": 2.0}
assert sliding_window_max([2, 1, 4, 3, 6, 5, 2, 7], 3) == [4, 4, 6, 6, 6, 7]
print("ok")
```

Add a `priority` field and implement a bounded priority queue with `heapq` that drops the lowest-priority item when full; compare its per-operation cost ($O(\log n)$) with the ring buffer.

## Verification

Check structure choices with three tests. (1) A model oracle: compare each fast implementation with an obviously correct brute force (the sliding-window oracle above). (2) Invariants: a ring buffer never exceeds capacity and returns items in arrival order; `latest_by_sensor` never returns a lower sequence number than one seen. (3) A measurement: time the operation for doubling $n$ and read the growth factor (about 2 for linear, 4 for quadratic). A check that could reject you: if the deque benchmark grows 4 times per doubling, you are not using a deque (or the loop copies the container).

## Failure modes

- `list.pop(0)` or `list.insert(0, x)` in a loop: $n^2/2$ moves; 50 million moves for 10,000 items.
- `x in some_list` inside a loop: 200,000 messages cost up to $2\times10^{10}$ comparisons in the worst case (a set needs 200,000 hash lookups).
- Unhashable keys: `{[1,2]: 3}` raises `TypeError: unhashable type: 'list'`; use tuples.
- Mutating a key's contents after insertion (for example a custom class with a changing `__hash__`): the entry becomes unreachable.
- Unbounded queue with a slow consumer: the backlog grows $(\lambda-\mu)T$ items and latency grows linearly (600 items, 60 s stale after 60 s at 20 Hz in, 10 Hz out).
- Treating dict order as sorted order: it is insertion order.
- Modifying a dict or list while iterating over it: skipped items or `RuntimeError: dictionary changed size during iteration`.
- Silent drops: a bounded buffer without a counter hides data loss; always count dropped messages.

## Alternatives and trade-offs

A `deque(maxlen=k)` gives a drop-oldest ring buffer in one line, at the cost of silent drops (no dropped item returned). A preallocated array with head and tail indices (a real ring buffer) avoids allocation in latency-critical code. `queue.Queue` adds thread safety and blocking with timeouts but is slower than a plain deque; `asyncio.Queue` suits asynchronous code. `heapq` provides a priority queue with $O(\log n)$ push and pop when order is by priority, not arrival. `collections.OrderedDict` and `dict` both preserve insertion order; `OrderedDict` adds `move_to_end` for LRU caches. For numeric streams, NumPy arrays (PY04) beat lists in memory and speed but have fixed size and no cheap front removal. Sorted-key lookups need `bisect` or a tree; hash maps give no ordering by key.

## Transfer and retention

- A ROS 2 subscriber's history depth and reliability policies are bounded-queue policies in disguise: depth 1 with best effort is "keep only the latest".
- A path planner's open set is a priority queue; its closed set is a hash set; its path reconstruction uses a dict of parents.
- Reproduce from memory the cost table row by row and the monotonic-deque invariant. In a week, redo the queue cost model for a producer at 50 Hz and a consumer at 30 Hz.
