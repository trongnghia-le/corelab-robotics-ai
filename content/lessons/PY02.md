## Why this matters

A robot's software is mostly data moving between producers and consumers: a camera produces frames at 30 Hz, a planner reads the latest map, a logger records every message, a filter needs the last 20 readings. The same Python code can be 100 times slower than necessary, or silently lose messages, because the wrong container was chosen. Data structures are a set of contracts that trade access speed, update speed, order and memory. Knowing the costs lets you predict, before running anything, whether a design survives 10,000 messages per second.

## Intuition

A **list** is a row of numbered boxes: jumping to box $i$ is instant, appending at the right end is instant (most of the time), but removing the first box forces every other box to slide one place left. A **hash map** (dict) is a coat-check: the key is hashed into a bucket number so you go straight to the slot instead of scanning, but the key must be something whose hash never changes. A **queue** keeps arrival order: the oldest item leaves first. A **deque** (double-ended queue) is a row of boxes with a movable start, so removing from the front only moves a pointer.

Picture a robot's message pipeline on a busy afternoon. A lidar callback delivers a scan 20 times a second, a planner wants "the newest scan, now", a logger wants "every scan, in order", and a safety check asks "have I already seen obstacle number 4312?" for every point of every scan. Four questions, four different containers. The newest scan per sensor is a dict lookup by name. Every scan in order is a queue. "Have I seen it?" is a set membership test. Keeping only the last 20 gyro samples is a bounded deque. Choosing the wrong one does not usually crash anything: it makes the code a hundred or a hundred thousand times slower than it needs to be, or silently drops the data you needed, and the symptom (a robot that reacts late) shows up far from the cause.

Predict before you compute. A planner has 1,000 known obstacle ids in a list and checks 1,000 new ids against it, one `in` test each. In the worst case, how many comparisons is that? (Each test scans the whole list: $1000\times1000=10^6$.) Now keep the ids in a set instead: about 1,000 hash lookups, a thousand times fewer, and the gap widens with every extra id because the list cost grows with the size of the container while the set cost does not. If you guessed "a few thousand comparisons" you used the most common wrong intuition about containers, "membership is a quick operation because Python is fast". Python's C loop is fast per element, roughly 7 ns, but it still touches every element.

The opposite wrong intuition is "a dict is always better". A dict pays for its speed with memory (the table is kept less than two-thirds full), with the requirement that keys be hashable, and with a build cost: filling a set of $n$ items costs about three or four list scans of those items. For a handful of lookups a plain list is faster; for thousands, the set wins by orders of magnitude. The same trade-off exists between a list and a deque: a list is perfect while you only touch the right end, and quadratic as soon as you drain from the left. The pictures in this lesson put these trade-offs on the same axes so that you can see where each curve bends.

## Theory and derivation

### Costs at a glance

| Operation | list | dict / set | deque |
|---|---|---|---|
| index / lookup by key | $O(1)$ | $O(1)$ average | $O(n)$ in the middle, $O(1)$ at the ends |
| append at end | $O(1)$ amortized | insert $O(1)$ average | $O(1)$ |
| pop from end | $O(1)$ | delete $O(1)$ average | $O(1)$ |
| insert/pop at front | $O(n)$ | n/a | $O(1)$ |
| membership `x in c` | $O(n)$ | $O(1)$ average | $O(n)$ |
| iterate | $O(n)$ | $O(n)$ | $O(n)$ |

**Example.** Count the comparisons instead of timing them. `Id` is an `int` that counts every `==` call. How many comparisons does `Id(499) in ids` cost for a list of 500 ids, and how many for a set built from them?

```python
class Id(int):
    calls = 0
    def __eq__(self, other):
        Id.calls += 1
        return int.__eq__(self, other)
    __hash__ = int.__hash__

ids = [Id(i) for i in range(500)]
Id.calls = 0
print(Id(499) in ids, Id.calls)
s = set(ids)
Id.calls = 0
print(Id(499) in s, Id.calls)
```

**Solution.** A list scans from the front and compares each element with the target until it matches, and `Id(499)` is the last element, so all 500 elements are compared: `Id.calls` is 500. The set hashes the value, goes to one slot and finds the equal key with a single `==`: `Id.calls` is 1. The output is `True 500` then `True 1`. That is the table row "membership $O(n)$ against $O(1)$ average" with real counts.

### Amortized append

A dynamic array over-allocates. When full, it allocates a bigger block and copies. If the capacity doubles, the copies for $n=2^k$ appends total $1+2+4+\dots+2^{k-1}=2^k-1<n$, so the **amortized** cost per append is $<2$ copies plus the write itself: $O(1)$. Python grows by roughly 12.5% instead (so a few more copies per append, about 9, still constant); the reallocation steps are visible with `sys.getsizeof`: the size jumps at lengths 1, 5, 9, 17, 25, 33 in the CPython build I tested. Amortized means the average over a sequence of operations; an individual append can still be slow.

**Example.** Count how often a list reallocates while 1,000 readings are appended, using the size reported by `sys.getsizeof`. How many appends change the size, and what does the final size mean?

```python
import sys
data = []
last = sys.getsizeof(data)
jumps = 0
for i in range(1000):
    data.append(i)
    size = sys.getsizeof(data)
    if size != last:
        jumps += 1
        last = size
print(jumps, len(data), sys.getsizeof(data))
```

**Solution.** The loop counts every append after which `sys.getsizeof(data)` differs from the previous value. Output (CPython 3.11.9, 64-bit): `28 1000 8856`. Only 28 of the 1,000 appends reallocated; the other 972 wrote into spare capacity. A strict doubling rule would have reallocated about $\lceil\log_2 1000\rceil=10$ times; CPython's gentler growth does so more often but wastes less memory. The 8,856 bytes are the 56-byte list header plus 1,100 pointers of 8 bytes ($56+1100\cdot8=8856$), so the final capacity (1,100) is only 10% above the length.

### Hash maps

A dict computes `hash(key)`, maps it to a slot, and compares keys on a collision. The expected cost is $O(1)$ if the hash spreads keys well and the table is not too full (the table resizes as it grows); the worst case is $O(n)$. Two requirements follow: keys must be **hashable** (immutable in the sense that `hash` and `==` never change: ints, strings, tuples of hashables; lists and dicts are not), and objects that compare equal must hash equally. Since Python 3.7 a dict preserves insertion order. A **set** is a dict without values and is the right tool for "have I seen this?".

**Example.** A latest-value table keyed by sensor name, and a key that cannot be used. What does the code below print for the three readings, for the list key and for the tuple key?

```python
latest = {}
for sensor, v in [("imu", 0.1), ("gps", 5.2), ("imu", 0.3)]:
    latest[sensor] = v
print(latest, len(latest))
try:
    {[1, 2]: 0}
except TypeError as e:
    print(e)
grid = {(2, 5): "wall"}
print(grid[(2, 5)])
```

**Solution.** Each assignment `latest[sensor] = v` stores or replaces by key; the second `imu` reading replaces the first because equal keys are the same key, leaving two entries: `{'imu': 0.3, 'gps': 5.2} 2`. The key `[1, 2]` is rejected with `unhashable type: 'list'` because its hash could change when the list is edited. The tuple `(2, 5)` is hashable, so it is a valid key for a grid cell and `grid[(2, 5)]` prints `wall`.

### Queues and bounded buffers

FIFO order means enqueue at one end and dequeue at the other. `collections.deque` supports both ends in $O(1)$. A **bounded** queue (`deque(maxlen=k)`, or a ring buffer) must have a **drop policy** when full: drop the oldest (keep the freshest data, right for perception), drop the newest (keep history, right for logging a burst), or block the producer (applies backpressure, can deadlock a real-time loop). If a producer is faster than a consumer, an unbounded queue grows without limit: with arrival rate $\lambda$ and service rate $\mu<\lambda$ the backlog grows by $\lambda-\mu$ per second, and the latency of the newest message after $T$ seconds is $(\lambda-\mu)T/\mu$.

**Example.** A camera callback delivers 25 frames per second but the detector handles only 20 per second. How much does an unbounded queue grow over $T=8$ s, how long does the newest frame wait, and what changes with `deque(maxlen=3)` (drop-oldest)?

**Solution.** With $\lambda=25$ and $\mu=20$ the unbounded queue grows by $(\lambda-\mu)T=(25-20)\cdot8=40$ frames, and the newest frame waits $(\lambda-\mu)T/\mu=40/20=2.0$ s before it is processed, which a robot driving at 1 m/s turns into 2 m of blind travel. With `deque(maxlen=3)` the queue never holds more than 3 frames, so the wait is at most $3/20=0.15$ s and the price is that the 40 surplus frames are dropped instead of delayed. The code below prints `deque(['c', 'd', 'e'], maxlen=3)`: the two oldest frames, `a` and `b`, fell out silently.

```python
from collections import deque
frames = deque(maxlen=3)
for f in "abcde":
    frames.append(f)
print(frames)
```

### Monotonic deque

To maintain the maximum of the last $k$ values in a stream, keep a deque of **indices** whose values are decreasing from front to back. On a new value $x$: pop from the back while the back value is $\le x$ (they can never be a maximum again); append the new index; pop from the front if it left the window. The front is the window maximum. Each index is appended and removed at most once, so the whole pass is $O(n)$, not $O(nk)$.

**Example.** Wheel speeds in cm/s, window of $k=3$ samples, $x=[9,7,8,5,6,4,10]$. What does `window_max` return, and how much work does the deque do?

```python
from collections import deque

def window_max(x, k):
    dq, out = deque(), []
    for i, v in enumerate(x):
        while dq and x[dq[-1]] <= v:
            dq.pop()
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()
        if i >= k - 1:
            out.append(x[dq[0]])
    return out

print(window_max([9, 7, 8, 5, 6, 4, 10], 3))
```

**Solution.** Trace the deque of indices after each sample: $i=0$: `[0]`; $i=1$: `[0,1]` (7 < 9); $i=2$: value 8 pops index 1, giving `[0,2]`, and the first window outputs $x_0=9$; $i=3$: `[2,3]`, index 0 expires, output 8; $i=4$: value 6 pops index 3, giving `[2,4]`, output 8; $i=5$: `[4,5]`, index 2 expires, output $x_4=6$; $i=6$: value 10 pops everything, giving `[6]`, output 10. The result is `[9, 8, 8, 6, 10]`, equal to `max` over each of the five windows, but each index entered and left the deque at most once. The deque never held more than 2 indices on this data, so the work per step was a couple of comparisons rather than a scan of $k$ values.

### Dynamic arrays in general: growth factor, shrinking, and CPython's rule

Let the capacity be multiplied by a factor $g>1$ whenever the array is full. Right after a resize from capacity $c$ to $gc$ the array holds $c$ elements and has $(g-1)c$ free slots. Charge each of the next $(g-1)c$ appends an extra $\tfrac{1}{g-1}$ units of "credit"; by the time the array is full again the credit totals $c$, exactly enough to pay for copying $c$ elements at the next resize. Hence every append costs at most $1+\tfrac1{g-1}=\tfrac{g}{g-1}$ element writes amortized: $2$ for $g=2$ and $9$ for $g=9/8$. Larger $g$ buys fewer copies for more wasted memory (up to a fraction $1-1/g$ of the array can be empty). This is the amortized argument of MIT 6.006 Lecture 2 ("any sequence of $\Theta(n)$ operations takes $\Theta(n)$ time"), made quantitative.

CPython does not use a pure factor. In `list_resize` the new allocation is `(newsize + (newsize >> 3) + 6) & ~3`, i.e. about $\tfrac98\,\text{newsize}$ plus a constant, rounded down to a multiple of 4; the source comment lists the growth pattern as `0, 4, 8, 16, 24, 32, 40, 52, 64, 76, ...` (CPython `Objects/listobject.c`, 3.11). The $+6$ makes small lists grow quickly, the $\tfrac18$ term gives the geometric growth $g\approx 9/8$ for large ones, and the bound above predicts about $1/(g-1)=8$ copies per append.

**Shrinking is where naive rules fail.** Suppose a deletion halves the array as soon as the fill ratio drops to $1/2$. Take an array that is exactly full ($n=c$). An append doubles it (copy $n$); the following pop leaves ratio $\tfrac{n}{2n}=\tfrac12$ and halves it again (copy $n$). Alternating push/pop then costs $\Theta(n)$ per operation forever. The fix in MIT 6.006 Lecture 2 is hysteresis: shrink only when the fill ratio falls below $r_d=\tfrac14$, and shrink to ratio $r_i=\tfrac12$. After any resize the array is exactly half full, so at least $\min(c/2,\,c/4)=c/4$ cheap operations must occur before the next resize, and each resize costs $\Theta(c)$: amortized $O(1)$ again. In general, resizing thresholds must be separated by a constant gap $r_d<r_i$ so that a resize leaves $\Theta(n)$ slack in *both* directions.

**Example.** Why the shrink threshold needs a gap. A buffer of capacity 16 is exactly full and then receives three append/pop pairs. Policy A halves the capacity as soon as the fill ratio is $\le\frac12$; policy B only when it is $<\frac14$. How many element copies does each policy make?

**Solution.** Under A each append doubles the capacity (copying 16 elements) and each pop leaves ratio $\tfrac{16}{32}=\tfrac12$ and halves it again (copying 16): $3\times(16+16)=96$ copies. Under B the first append copies 16 and the array then stays at capacity 32 with 16 or 17 elements, ratio at least $\tfrac12\ge\tfrac14$, so no further resize occurs and the total is 16. A short simulation reproduces `96` and `16`. Growth by $g=2$ costs at most $\tfrac{g}{g-1}=2$ writes per append amortized, and the same array with a bad shrink rule costs 32 copies per pair, an unbounded multiple of that.

*Figure: cumulative copies divided by the number of appends. Both curves peak right after a resize and stay below the geometric-series bound $g/(g-1)$ (dashed: 2 for doubling, 9 for $g=9/8$; CPython's measured peak reaches 8.99 for a list of a million). Doubling costs at most 2 copies per append but may leave half the array empty; CPython's rule costs up to about 9 and wastes at most about $1/9$ of the array.*

### Hash tables: why lookups are $O(1)$ in expectation, and how CPython probes

*Chaining and universal hashing (MIT 6.006, Lecture 4).* Store each key in a bucket chosen by $h(k)\in\{0,\dots,m-1\}$ and keep collisions in a chain. For a fixed hash function an adversary who knows $h$ can pick $n$ keys with the same hash, making one chain of length $n$. A hash *family* $\mathcal H$ is **universal** if $\Pr_{h\in\mathcal H}[h(k_i)=h(k_j)]\le 1/m$ for all $k_i\ne k_j$; the lecture uses $h_{ab}(k)=((ak+b)\bmod p)\bmod m$ with $p>u$ prime. Choose $h$ at random from $\mathcal H$ and let $X_{ij}$ be the indicator that $k_j$ lands in the bucket of $k_i$. The expected chain length at $h(k_i)$ is
$$\mathbb E\Big[\sum_j X_{ij}\Big]=1+\sum_{j\ne i}\Pr[h(k_i)=h(k_j)]\le 1+\frac{n-1}{m}=1+\alpha ,$$
with load factor $\alpha=n/m$. If the table is resized to keep $m=\Omega(n)$, a lookup is $O(1)$ **in expectation over the choice of $h$**, not for every input.

*Open addressing, as CPython does it.* CPython stores entries in a table of size $2^i$ and resizes when it is two-thirds full (`USABLE_FRACTION`, `Objects/dictobject.c`). Instead of chains it probes: starting at $j=\text{hash}\bmod 2^i$ it visits $j\leftarrow(5j+1+\text{perturb}) \bmod 2^i$ with `perturb >>= 5` before each step, where `perturb` starts as the full hash. Two facts justify this design. (1) Without the perturbation term the recurrence $T(j)=5j+1 \bmod 2^i$ visits **every** slot exactly once in $2^i$ steps, from any start, so a probe always finds the free slot the table guarantees. *Proof.* Unrolling over the integers, $T^k(j)=5^kj+\tfrac{5^k-1}{4}$, so $4T^k(j)+1=5^k(4j+1)$. Put $y=4j+1$, which is odd. Then $T^k(j)\equiv j \pmod{2^i}$ iff $4T^k(j)+1\equiv 4j+1 \pmod{2^{i+2}}$ iff $(5^k-1)y\equiv0 \pmod{2^{i+2}}$ iff $5^k\equiv 1\pmod{2^{i+2}}$, because $y$ is odd. Now $5^{2^t}=1+2^{t+2}q_t$ with $q_t$ odd: true for $t=0$ ($5=1+4\cdot1$), and squaring gives $1+2^{t+3}(q_t+2^{t+1}q_t^2)$ with an odd bracket. For $k=2^s w$ with $w$ odd, $5^k=(1+2^{s+2}q_s)^w=1+2^{s+2}\cdot\text{odd}$, which is $\equiv1 \pmod{2^{i+2}}$ iff $s\ge i$. The smallest such $k$ is $2^i$, so the orbit of every start has length exactly $2^i$ and therefore contains every slot once. $\square$ (2) With the perturbation, the probe sequence depends on all hash bits, which breaks up clusters of keys that share their low bits; since `perturb` is eventually 0, the plain recurrence takes over and (1) guarantees termination (comments in `Objects/dictobject.c`). Ints hash to themselves, so a set of keys such as `i << 16` all share the same initial slot in tables smaller than $2^{16}$, yet the perturbation keeps insertion close to linear.

**Example.** An 8-slot table where slots 0, 1, 2, 6 and 7 are taken (5 entries, the most CPython allows in 8 slots). In which order is a key with home slot $1$ probed with the recurrence $j\leftarrow(5j+1)\bmod 8$, and where is it stored?

**Solution.** Start at $j=1$, which is taken. Then $5\cdot1+1=6$ (taken), $5\cdot6+1=31\bmod8=7$ (taken) and $5\cdot7+1=36\bmod8=4$, which is free. The probe order is $1\to6\to7\to4$: three collisions, then the key is stored in slot 4. Run on its own the recurrence visits `[1, 6, 7, 4, 5, 2, 3, 0]`, all eight slots exactly once, as the proof guarantees.

*Figure: the probe sequence $j\leftarrow(5j+1)\bmod 8$ from home slot 1 with the perturbation left out. Occupied slots are filled; the key is stored in the first free slot reached, slot 4.*

### Why the monotonic deque is correct

Let the deque hold indices $q_1<q_2<\dots<q_r$ of the current window $[i-k+1,i]$ with $x_{q_1}>x_{q_2}>\dots>x_{q_r}$. **Claim:** after processing $x_i$ the front $q_1$ is an index of the maximum of the window, and $q_r=i$. *Initialization* is the empty deque. *Maintenance:* appending $i$ after popping every back element with $x_q\le x_i$ keeps the values strictly decreasing and the indices increasing; popping the front when $q_1\le i-k$ removes the only element that can have left the window (indices are increasing, and at most one index leaves per step). *Why nothing needed is discarded:* an index $q$ popped because $x_q\le x_i$ with $q<i$ can never be the unique maximum of any window that contains both, and every window that contains $q$ and later windows contain $i$ for as long as $q$ stays (since $i>q$ leaves the window later than $q$). *The front is the maximum:* every index of the window is either in the deque or was popped by a later index with an at-least-as-large value, so by induction on pops some deque element is $\ge$ every window element, and the deque is decreasing, so that element is the front. Each index is appended once and popped at most once, so the total number of deque operations is at most $2n$, with $O(1)$ per end operation (Python docs, `collections.deque`).

**Example.** What breaks if the front is never expired? Drop the line `if dq[0] <= i - k: dq.popleft()` and run $x=[8,1,2,3]$ with $k=2$. What does each version return?

**Solution.** The correct version takes the maxima of the windows $[8,1]$, $[1,2]$, $[2,3]$ and returns `[8, 2, 3]`. In the broken version the deque after $i=1$ is `[0,1]` and the first output is $x_0=8$; at $i=2$ value 2 pops index 1, leaving `[0,2]` with index 0 (value 8) still at the front although it has left the window $[1,2]$, so the output is 8 again; at $i=3$ value 3 pops index 2, `[0,3]`, and the output is 8 once more. It prints `[8, 8, 8]`, because the claim "the front is an index inside the window" is no longer true. The invariant is what the missing line maintains.

## Worked example

A range sensor stream is processed by three consumers. Messages are tuples `(sensor, seq, value)`.

### Case 1: draining a FIFO with a list and with a deque

**Problem.** A logger drains $n$ queued messages in arrival order. Count the element moves of `list.pop(0)` and the pointer updates of `deque.popleft()` for $n=6$ and $n=10{,}000$, and compare with a measured run of $n=50{,}000$.

**Solution.**
1. *Cost of one `list.pop(0)`* (theory, "Costs at a glance"): removing the first element shifts every other element one place left, so with $m$ elements left it moves $m-1$.
2. *Sum over the drain.* For $n=6$ the pops move $5+4+3+2+1+0=15$ elements; in general $\sum_{m=1}^{n}(m-1)=n(n-1)/2$. For $n=10{,}000$ this is $10^4\cdot(10^4-1)/2=49{,}995{,}000$.
3. *Cost of `deque.popleft()`*: it only advances the head pointer, so one update per message: 6 for $n=6$ and $10{,}000$ for $n=10{,}000$.
4. *Measured* (best of three runs, CPython 3.11.9, this machine). Draining $n=25{,}000$, $50{,}000$ and $100{,}000$ messages took 0.037 s, 0.158 s and 0.599 s with a list, and 0.00071 s, 0.00123 s and 0.00155 s with a deque. At $n=50{,}000$ that is about 130 times faster. The move counts differ by a factor of about $n/2=25{,}000$, but each move is one pointer copy inside a single `memmove`, so the observed gap is smaller than the count ratio.

**Check.** A counting simulation returns 15 and 49,995,000 moves. Doubling $n$ should quadruple the list time (quadratic) and roughly double the deque time (linear): the list times above grow by factors 4.2 and 3.8, while the deque times grow by factors 1.7 and 1.3 (close to linear, with timer noise at this size).

**Takeaway.** The structure that looks the same in code (`pop(0)` versus `popleft()`) differs by a factor that grows with $n$; choose the container from the access pattern, not from habit.

### Case 2: a ring buffer of capacity 3

**Problem.** A drop-oldest ring buffer of capacity 3 receives the values 1 to 7. Which value does each push drop, and what does the buffer finally hold?

**Solution.**
1. *Rule* (theory, "Queues and bounded buffers"): if the buffer is full, remove the oldest, then append the new value.
2. *Pushes 1, 2, 3* find room (length 0, 1, 2 < 3), drop nothing: contents `[1, 2, 3]`.
3. *Push 4*: full, drop 1, contents `[2, 3, 4]`. *Push 5*: drop 2, `[3, 4, 5]`. *Push 6*: drop 3, `[4, 5, 6]`. *Push 7*: drop 4, `[5, 6, 7]`.
4. *Result.* Dropped sequence `[None, None, None, 1, 2, 3, 4]`, final contents `[5, 6, 7]`.

**Check.** Seven values in, three kept, four dropped: $7=3+4$. The dropped values are the four oldest and the kept ones are the three newest.

**Takeaway.** A bounded drop-oldest queue always holds the last $k$ items, and the loss is explicit: here exactly $n-k=4$ values.

### Case 3: the latest reading per sensor, with a late message

**Problem.** The messages `("a",1,0.5), ("b",1,2.0), ("a",3,0.7), ("a",2,0.6)` arrive in this order (the last one is late). Keep the value with the highest sequence number for each sensor.

**Solution.**
1. *Structure*: a dict keyed by sensor name that stores `(seq, value)`, so each update is one $O(1)$ lookup (theory, "Hash maps").
2. *Message 1*: `a` is new, store `a -> (1, 0.5)`. *Message 2*: store `b -> (1, 2.0)`.
3. *Message 3*: `a` exists with seq 1 and $3>1$, so replace: `a -> (3, 0.7)`.
4. *Message 4*: `a` exists with seq 3 and $2<3$, so ignore the late message.
5. *Result*: `{"a": 0.7, "b": 2.0}`.

**Check.** The final dict has one entry per sensor (2 keys for 2 sensors) and each stored seq is the maximum seen for it: 3 for `a`, 1 for `b`. A list scan of the four messages gives the same answer.

**Takeaway.** The rule "newest sequence number wins" is what makes the result independent of arrival order; the dict only makes each update cheap.

### Case 4: sliding-window maximum, step by step

**Problem.** For $x=[2,1,4,3,6,5,2,7]$ and window $k=3$, compute the maximum of every window with the monotonic deque and count the pushes and pops.

**Solution.**
1. *Rule* (theory, "Monotonic deque"): the deque stores indices with decreasing values; on a new $x_i$ pop from the back while $x_{\text{back}}\le x_i$, append $i$, pop the front if its index is $\le i-k$, and output $x_{\text{front}}$ once $i\ge k-1$.
2. *$i=0$*: push 0, deque `[0(2)]`. *$i=1$*: $1<2$, deque `[0(2), 1(1)]`. *$i=2$*: pop 1 and 0 (both $\le 4$), push 2: `[2(4)]`; the window is full, output 4.
3. *$i=3$*: $3<4$, `[2(4), 3(3)]`, output 4. *$i=4$*: pop 3 and 2, push 4: `[4(6)]`, output 6. *$i=5$*: `[4(6), 5(5)]`, output 6.
4. *$i=6$*: `[4(6), 5(5), 6(2)]`; index 4 is still inside the window $[4,6]$, output 6. *$i=7$*: pop 6, 5 and 4 (all $\le 7$), push 7: `[7(7)]`, output 7.
5. *Result*: `[4, 4, 6, 6, 6, 7]`. Counting: 8 pushes and 7 pops in total (index 7 stays), at most $2n$ operations.

**Check.** Direct maximum of each slice of three: $\max(2,1,4)=4$, $\max(1,4,3)=4$, $\max(4,3,6)=6$, $\max(3,6,5)=6$, $\max(6,5,2)=6$, $\max(5,2,7)=7$, the same list. Python gives `[4, 4, 6, 6, 6, 7]` from both versions.

**Takeaway.** Each index is pushed once and popped at most once, so the pass is $O(n)$ regardless of $k$, and the front is always the window maximum because the deque holds only the candidates that can still win.

## Reference implementation

```python
from collections import deque

class RingBuffer:
    """Bounded FIFO that drops the oldest item when full."""
    def __init__(self, capacity):
        if capacity < 1:
            raise ValueError("capacity must be >= 1")
        self.capacity = capacity
        self._q = deque()
    def push(self, item):
        dropped = None
        if len(self._q) == self.capacity:
            dropped = self._q.popleft()
        self._q.append(item)
        return dropped
    def pop_oldest(self):
        if not self._q:
            raise IndexError("empty buffer")
        return self._q.popleft()
    def __len__(self):
        return len(self._q)
    def to_list(self):
        return list(self._q)

def latest_by_sensor(messages):
    out = {}
    for sensor, seq, value in messages:
        if sensor not in out or seq > out[sensor][0]:
            out[sensor] = (seq, value)
    return {s: v for s, (q, v) in out.items()}

def dedupe(messages):
    seen, out = set(), []
    for m in messages:
        key = (m[0], m[1])
        if key not in seen:
            seen.add(key)
            out.append(m)
    return out

def sliding_window_max(xs, k):
    if k < 1 or k > len(xs):
        raise ValueError("bad window")
    dq, out = deque(), []
    for i, x in enumerate(xs):
        while dq and xs[dq[-1]] <= x:
            dq.pop()
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()
        if i >= k - 1:
            out.append(xs[dq[0]])
    return out

# self-test
r = RingBuffer(3)
assert [r.push(i) for i in range(1, 8)] == [None, None, None, 1, 2, 3, 4]
assert r.to_list() == [5, 6, 7]
assert latest_by_sensor([("a", 1, .5), ("b", 1, 2.0), ("a", 3, .7), ("a", 2, .6)]) == {"a": .7, "b": 2.0}
assert sliding_window_max([2, 1, 4, 3, 6, 5, 2, 7], 3) == [4, 4, 6, 6, 6, 7]
print("ok")
```

## Verification

Check structure choices with three tests. (1) A model oracle: compare each fast implementation with an obviously correct brute force (the sliding-window oracle above). (2) Invariants: a ring buffer never exceeds capacity and returns items in arrival order; `latest_by_sensor` never returns a lower sequence number than one seen. (3) A measurement: time the operation for doubling $n$ and read the growth factor (about 2 for linear, 4 for quadratic). A check that could reject you: if the deque benchmark grows 4 times per doubling, you are not using a deque (or the loop copies the container).

## Failure modes

- `list.pop(0)` or `list.insert(0, x)` in a loop: $n^2/2$ moves; 50 million moves for 10,000 items.
- `x in some_list` inside a loop: 200,000 messages cost up to $2\times10^{10}$ comparisons in the worst case (a set needs 200,000 hash lookups).
- Unhashable keys: `{[1,2]: 3}` raises `TypeError: unhashable type: 'list'`; use tuples.
- Mutating a key's contents after insertion (for example a custom class with a changing `__hash__`): the entry becomes unreachable.
- Unbounded queue with a slow consumer: the backlog grows $(\lambda-\mu)T$ items and latency grows linearly (600 items, 60 s stale after 60 s at 20 Hz in, 10 Hz out).
- Treating dict order as sorted order: it is insertion order.
- Modifying a dict or list while iterating over it: skipped items or `RuntimeError: dictionary changed size during iteration`.
- Silent drops: a bounded buffer without a counter hides data loss; always count dropped messages.

## Alternatives and trade-offs

A `deque(maxlen=k)` gives a drop-oldest ring buffer in one line, at the cost of silent drops (no dropped item returned). A preallocated array with head and tail indices (a real ring buffer) avoids allocation in latency-critical code. `queue.Queue` adds thread safety and blocking with timeouts but is slower than a plain deque; `asyncio.Queue` suits asynchronous code. `heapq` provides a priority queue with $O(\log n)$ push and pop when order is by priority, not arrival. `collections.OrderedDict` and `dict` both preserve insertion order; `OrderedDict` adds `move_to_end` for LRU caches. For numeric streams, NumPy arrays (PY04) beat lists in memory and speed but have fixed size and no cheap front removal. Sorted-key lookups need `bisect` or a tree; hash maps give no ordering by key.

## Transfer and retention

- A ROS 2 subscriber's history depth and reliability policies are bounded-queue policies in disguise: depth 1 with best effort is "keep only the latest".
- A path planner's open set is a priority queue; its closed set is a hash set; its path reconstruction uses a dict of parents.

Trace: i=0 `[0]`; i=1 `[0,1]`; i=2 pop 1 (3≤4) → `[0,2]` output 5; i=3 `[0,2,3]`, then index 0 leaves the window, `[2,3]`, output 4; i=4 pop 3 (1≤2), `[2,4]`, output 4; i=5 pop 4 and 2, `[5]`, output 6. Each index is pushed once and popped at most once: $\le2n$ operations.
9. (a) Backlog grows $(20-10)=10$ scans/s: 600 scans after 60 s; the newest scan waits $600/10=60$ s: hopelessly stale. (b) Depth 5, drop-oldest: at most 5 scans wait, worst-case wait $5\times0.1=0.5$ s before processing starts and the consumer sees only every second scan (50% dropped, 10 Hz processed). (c) Drop-newest preserves history (useful for logging a burst); blocking is right when losing a message is unacceptable and the producer can slow down (offline processing), but it is dangerous in a real-time control loop.
10. Predicted slopes: about 2 for the list and about 1 for the deque. Doubling $n$ multiplies the list time by about 4 (measured: 50,000 items in 0.30 s) and the deque time by about 2. Cache effects may make the list slope appear lower than 2 for small $n$.
11. Computed: policy A costs $1024000$ copies for the 500 pairs ($2048$ per pair: the append at full capacity copies $1024$, and the pop leaves ratio exactly $1/2$ and copies $1024$ again), ending at $n=1024$, capacity $1024$. Policy B costs $1024$ copies in total (one doubling at the first append; after that the array has capacity $2048$ and ratio about $1/2$, so no later operation triggers a resize). Proof for B: grow happens when $n=c_{old}$ and sets $c=2c_{old}$, so right after it $n=c/2+1$; shrink happens when a pop leaves $n<c_{old}/4$ and sets $c=c_{old}/2$, so right after it $n\approx c/2-1$. In both cases the new fill ratio is within one element of $1/2$. To trigger the next grow the size must rise from $\approx c/2$ to $c$: at least $c/2-1$ appends; to trigger the next shrink it must fall below $c/4$: at least $c/4-1$ pops. A resize copies at most $c$ elements, and it is preceded (since the previous resize) by at least $c/4-1\ge c/8$ ordinary $O(1)$ operations for $c\ge8$ (with a minimum capacity of 8 so that no shrink applies below it). Charging the $c$ copies to those operations gives at most $8$ extra units each, so $m$ operations cost $O(m)$ in total. The invariant is: after every resize the fill ratio is within one element of $1/2$, so both thresholds ($1$ for growth, $1/4$ for shrinkage) are $\Theta(c)$ operations away. Policy A violates it: after a resize the ratio sits exactly on a threshold. Random check: for 100000 random push/pop operations from $n=4$, $c=8$ (Python 3.11.9, `random.seed(1)`, minimum capacity 8) policy A copies 166488 elements, policy B 2581.
12. (a) Capacities at which the list grows (size at which growth happens, new capacity): $(1,4),(5,8),(9,16),(17,24),(25,32),(33,40),(41,52),(53,64),(65,76),(77,92)$, then $(93,108),(109,128)$; there are $66$ resizes for $100\,000$ appends. `sys.getsizeof` on 3.11.9 jumps at the same lengths (1, 5, 9, 17, 25, 33, 41, 53, 65, 77, 93) with capacities $(s-56)/8=4,8,16,24,32,40,52,64,76,92,108$, as the source comment states. (b) Total copies $798\,128$, i.e. $7.98$ per append, vs. the bound $1/(g-1)=8$ for $g=9/8$: the simulation agrees (plus the one write per append gives about $9$ units, as derived). (c) For short lists the term $\text{newsize}/8$ is below 5, so the constant dominates: `+6` and rounding to a multiple of 4 give the first capacities $4, 8, 16, 24, 32, 40$ (ratios $2, 2, 1.5, 1.33, 1.25$), so the first few appends do not each trigger a reallocation, and as the list grows the ratio tends to $9/8$. The result is never below `newsize` because `& ~3` removes at most 3 and the added $+6$ exceeds that.
13. (a) The brute-force maximum over all pairs is $2/11\approx0.182$, below $1/m=0.25$ (computed). (b) Keys $0,4,8,\dots,36$ all map to bucket $0$: one chain of length 10; inserting them one by one (searching the chain before each insertion) costs $0+1+\dots+9=45$ comparisons, quadratic in the number of keys. (c) Measured on 3.11.9 (best of 5): $N=20\,000$: $1.12$ ms for `i << 16` against $0.23$ ms for `range`, ratio $\approx4.9$; $N=40\,000$ gave $2.0$ ms for `i << 16`. Doubling $N$ roughly doubles the time, so the behaviour is not quadratic. All keys `i << 16` share their low 15 bits (zero) so every key starts at the same slot, but `perturb` feeds the high bits into the sequence from the first step, spreading the keys over different probe sequences. Absolute times depend on the machine; the ratio and the near-linear growth are the point. A fixed bucket function like `k mod 4` has no such escape, so the adversarial input is a real attack on chaining with a fixed $h$.
14. (a) Start 5: $5\to 26\bmod 8=2\to 11\bmod8=3\to16\bmod8=0\to1\to6\to7\to4\to5$, order $5,2,3,0,1,6,7,4$, a permutation of $0..7$ (same cycle as the source's $0\to1\to6\to7\to4\to5\to2\to3$). (b) See the proof in the lesson: $T^k(j)\equiv j \pmod{2^i}$ iff $5^k\equiv1 \pmod{2^{i+2}}$, and the order of $5$ modulo $2^{i+2}$ is $2^i$ because $5^{2^t}=1+2^{t+2}\cdot\text{odd}$; therefore the first return to $j$ is after exactly $2^i$ steps, independent of $j$. A cycle of length $2^i$ in a set of $2^i$ residues visits each residue once. (c) Modulus $12$: $0\to1\to6\to7\to0$, a cycle of length $4$ (checked), so slots $2,3,4,\dots$ are never probed from slot $0$. The proof breaks at the last equivalence: for modulus $M$ the return condition is $(5^k-1)(4j+1)\equiv0 \pmod{4M}$; for $M=12$ and $j=0$ it reads $5^k\equiv1 \pmod{48}$, and the order of $5$ modulo $48$ is $4$ ($5^4=625=13\cdot48+1$), not $12$. With $M=2^i$ the order of 5 modulo $4M$ equals $M$, which is why only powers of two work. (d) Once `perturb` reaches 0 (after at most $\lceil\text{bits}/5\rceil$ shifts, 13 for 64-bit hashes) the recurrence is $5j+1$ again, which by (b) visits every slot; since the table always keeps at least one empty slot (it is resized at $2/3$ load), the probe terminates.
