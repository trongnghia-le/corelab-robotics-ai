## Why this matters

A numerical algorithm is useful only when there is evidence that its implementation matches its contract. Testing should constrain behavior, errors, and reproducibility, rather than reward a green indicator. An independent reference implementation is often the most valuable first tool.

## Intuition and definitions

Declare the input domain, output meaning, invalid-input behavior, precision, and side effects. For a vector norm, inputs are finite real coordinates and the output is nonnegative. For a projection, the direction must be nonzero and both vectors must have equal dimensions. These assumptions should become explicit checks or clearly documented caller obligations.

![A stack of test layers (examples, properties, integration, regression) and a tolerance plot showing where atol and rtol dominate](/lesson-figures/T04.svg)

*Figure: different layers catch different bugs, and the tolerance atol + rtol*|b| switches from absolute to relative at b = atol/rtol.*

## Reasoning and assumptions

Floating comparisons often use $|a-b|\le atol+rtol|b|$. Near zero the absolute tolerance dominates; at large scale the relative tolerance dominates. Choose both using measurement scale and numerical conditioning. A single loose tolerance can accept an implementation that is systematically wrong. For exact identifiers, counts, and exception types, use exact checks.

## Worked example

A norm implementation returning the coordinate sum passes [1,0] but fails [−1,0] because the output becomes negative. It also fails [3,4], where the correct result is 5 instead of 7. A suite of zero vectors and axis-aligned positive unit vectors would miss much of this error. Test cases must separate plausible wrong implementations from the intended one.

## Exercises

1. **(Easy)** For the functions `dot`, `norm` and `project(a, b)` (projection of `a` onto `b`), write the expected value of `norm([-3, 4])`, `norm([0, 0, 0])`, `dot([1, 2, 3], [4, -5, 6])` and `project([2, 2], [1, 0])`, and list three invalid calls with the behaviour you require.
2. **(Easy, tolerances)** *(Adapted from: Python docs, unittest, `assertAlmostEqual`)* A result 2.01 is compared with the expected 2. Does it pass with `rtol=1e-3, atol=0`? With `rtol=0, atol=0.02`? What is the tolerance when the expected value is 0 and `rtol=1e-3, atol=0`? Choose settings for a position in metres measured by a sensor with 1 mm resolution.
3. **(Easy, discriminating tests)** An implementation of `norm` returns (A) the coordinate sum, (B) the largest absolute coordinate, (C) the squared norm, (D) the sum of absolute values. Find the smallest set of test vectors that distinguishes the correct function from all four. Which of $[1,0]$, $[3,4]$, $[-3,4]$ do you need?
4. **(Medium, applied)** A fixture file holds `{"unit": "mm", "vectors": [[3000, 4000]]}` but the robot code works in metres. Write an integration test that would catch a missing unit conversion, and say what output you expect for the norm in metres.
5. **(Medium, find the bug)** This test never fails, even against `norm = lambda v: 0.0`. Explain why, and rewrite it.
   ```python
   def test_small_norm(self):

   ```
6. **(Medium, predict)** *(Adapted from: Goldberg, What Every Computer Scientist Should Know About Floating-Point Arithmetic, 1991, overflow and underflow)* Predict `math.sqrt(sum(x*x for x in v))` for `v = [3e200, 4e200]` and for `v = [3e-200, 4e-200]`. What are the true norms, and how does scaling by the largest component fix it?
7. **(Medium-hard, properties)** List five properties that must hold for any correct `project(a, b)` and, for each, name a plausible bug that it would catch (e.g. forgetting to divide by $b\cdot b$).
8. **(Medium-hard, reduction)** A random test fails on `[5, 1e154, 2, 3, 7, 9, 1e154, 4]` because the naive norm overflows. Show how halving (delta debugging) reduces it to a minimal failing input, and say which seed/command should be stored with the report.
9. **(Hard, oracles)** *(Adapted from: Python docs, `decimal` and `math.fsum`)* Rank these oracles for `norm` by independence: (a) a copy of the same formula in the test, (b) `math.hypot`, (c) `decimal.Decimal(sum of squares).sqrt()` at 50 digits, (d) a hand-calculated table of Pythagorean triples. Which could share a bug with your code?
10. **(Hard, conditioning)** `dot([1e16, 1, -1e16], [1, 1, 1])` should be 1 but a left-to-right float sum returns 0. Explain this, say whether the test `is_close(result, 1, rtol=1e-9)` is reasonable for a plain sum, and propose a scale for the tolerance and an alternative implementation.
11. **(Hard, design)** Design the test architecture for a small vector library used by robot code: which layers (examples, properties, integration, regression), what lives in fixtures, how seeds are reported, and the single command that runs everything from a clean checkout.
12. **(Mini-project)** Write a `unittest` suite (`python3 -m unittest -v`) for `dot`, `norm`, `project` and a JSON loader with unit handling. Create six mutants, produce a table of which test kills which mutant, add tests until all die, and record the one gap you found in your own first version.

## Implementation and verification

Use three layers: examples with independently calculated outputs, properties such as norm scaling and nonnegativity, and integration checks for boundaries such as serialization or units. Keep randomized test seeds in failure reports and reduce a failing random case to the smallest useful example. Preserve the failing case as a regression test.

## Misconceptions and alternatives

Mutation checking deliberately breaks code to inspect the suite. Remove a square, reverse a sign, or accept a mismatched dimension. At least one relevant test should fail for each mutation. Line coverage helps find unexecuted paths, but a line can run without an assertion checking its effect. A copied reference function in both the implementation and expected result is not an independent oracle.

## Independent practice and transfer

### Goal

Write a small, trustworthy vector module (`dot`, `norm`, `project`, and a JSON loader with unit handling) together with the tests that make it trustworthy: hand-computed examples, invalid-input checks, scale tests (overflow/underflow), properties with a recorded seed, and a fixture-based integration test.

### Setup

Python 3 standard library only. Save the starter code and the tests in one file, `vector_lab.py`, and run `python3 vector_lab.py`. For the extension you will move the checks into a `unittest.TestCase` and run `python3 -m unittest -v`.

### Tasks

1. Implement `is_close(a, b, rtol, atol)` and use it for every floating comparison.
2. Implement `dot` (use `math.fsum`), `norm` (scale by the largest coordinate) and `project(a, b)`, all raising `ValueError` for empty vectors, non-finite values, mismatched dimensions and a zero direction.
3. Implement `load_vectors(text)` for JSON of the form `{"unit": "m" | "mm", "vectors": [[...], ...]}`; return coordinates in metres and raise `ValueError` for any other unit.
4. Run the tests and read each assertion: which kind of bug does it catch?
5. Break `norm` on purpose (sum instead of norm; naive formula) and confirm which test fails.
6. Add one test of your own for a bug you can imagine, then try to write an implementation that passes the tests but is still wrong.

### Tests

```python
import random

def raises(f, *args):
    try:
        f(*args)
    except ValueError:
        return True
    return False

# examples with independently calculated outputs
assert is_close(norm([-3, 4]), 5.0) and norm([0, 0, 0]) == 0.0
assert dot([1, 2, 3], [4, -5, 6]) == 12
assert all(is_close(x, y, atol=1e-12) for x, y in zip(project([2, 2], [1, 0]), [2.0, 0.0]))
assert all(is_close(x, y, atol=1e-12) for x, y in zip(project([1, 2, 3], [0, 0, 2]), [0.0, 0.0, 3.0]))
assert is_close(0.0, 1e-10, atol=1e-9) and not is_close(0.0, 1e-10, rtol=1e-3)
# invalid inputs
assert raises(dot, [1, 2], [1]) and raises(norm, []) and raises(norm, [1.0, float("nan")])
assert raises(project, [1, 2], [0, 0]) and raises(project, [1, 2], [1])
# scale: naive sqrt(sum(x*x)) gives inf / 0.0 here
assert is_close(norm([3e200, 4e200]), 5e200, rtol=1e-12)
assert is_close(norm([3e-200, 4e-200]), 5e-200, rtol=1e-12)
# cancellation: plain left-to-right float summation returns 0.0
assert dot([1e16, 1, -1e16], [1, 1, 1]) == 1.0
# properties (the seed is part of the failure report)
SEED = 20240607
rng = random.Random(SEED)
for _ in range(200):
    n = rng.randint(1, 6)
    a = [rng.uniform(-10, 10) for _ in range(n)]
    b = [rng.uniform(-10, 10) for _ in range(n)]
    c = rng.uniform(-5, 5)
    msg = f"seed={SEED} a={a} b={b} c={c}"
    assert abs(dot(a, b)) <= norm(a) * norm(b) * (1 + 1e-12) + 1e-12, msg
    assert is_close(norm([c * x for x in a]), abs(c) * norm(a), rtol=1e-12, atol=1e-12), msg
    if norm(b) > 1e-3:
        p = project(a, b)
        assert abs(dot([x - y for x, y in zip(a, p)], b)) <= 1e-9 * (1 + norm(a) * norm(b)), msg
        q = project(p, b)
        assert all(is_close(x, y, rtol=1e-9, atol=1e-9) for x, y in zip(p, q)), msg
        assert norm(p) <= norm(a) * (1 + 1e-12), msg
# integration with a fixture, including units
text = '{"unit": "mm", "vectors": [[3000, 4000], [0, 1]]}'
vs = load_vectors(text)
assert is_close(norm(vs[0]), 5.0) and is_close(vs[1][1], 0.001)
assert raises(load_vectors, '{"unit": "inch", "vectors": [[1, 2]]}')
print("norm of the fixture vector in metres:", norm(vs[0]))
print("all tests passed")
```

### Library track

Use the standard tools around your lab (`pip install numpy pytest hypothesis`). Save the lab module as `vector_lab.py` (without the test code at the bottom) and the following as `test_vector_lib.py` next to it; run `python3 -m pytest -q`. NumPy and `math.hypot` act as independent oracles, and Hypothesis generates the random cases and shrinks a failure to a minimal input (the library version of exercise 8). Note what the run teaches: `np.linalg.norm` itself underflows on `[3e-200, 4e-200]`, so it is only a valid oracle in a moderate range.

```python
import math
import numpy as np
import pytest
from hypothesis import given, strategies as st
from vector_lab import dot, norm, project

# keep away from underflow, which NumPy's own norm does not handle
finite = st.floats(min_value=-1e6, max_value=1e6, allow_nan=False, allow_infinity=False).filter(
    lambda x: x == 0 or abs(x) > 1e-100)
pair = st.integers(1, 6).flatmap(lambda n: st.tuples(st.lists(finite, min_size=n, max_size=n),
                                                      st.lists(finite, min_size=n, max_size=n)))

@given(pair)
def test_against_numpy(ab):
    a, b = ab
    scale = float(np.dot(np.abs(a), np.abs(b)))                    # natural scale of the sum
    assert dot(a, b) == pytest.approx(float(np.dot(a, b)), abs=1e-12 * (1 + scale))
    assert norm(a) == pytest.approx(math.hypot(*a), rel=1e-12, abs=0.0)
    np.testing.assert_allclose(norm(a), np.linalg.norm(a), rtol=1e-12)

@given(pair)
def test_cauchy_schwarz(ab):
    a, b = ab
    assert abs(dot(a, b)) <= norm(a) * norm(b) * (1 + 1e-12) + 1e-12

@given(pair)
def test_projection_residual_orthogonal(ab):
    a, b = ab
    if norm(b) < 1e-3:
        return
    p = project(a, b)
    assert abs(dot([x - y for x, y in zip(a, p)], b)) <= 1e-9 * (1 + norm(a) * norm(b))

def test_extreme_scale_needs_hypot_not_numpy():
    v = [3e-200, 4e-200]
    assert norm(v) == pytest.approx(5e-200, rel=1e-12, abs=0.0)
    assert math.hypot(*v) == pytest.approx(5e-200, rel=1e-12, abs=0.0)
    assert np.linalg.norm(v) != pytest.approx(5e-200, rel=1e-6, abs=0.0)   # NumPy norm underflows: a weaker oracle

@pytest.mark.parametrize("v, expected", [([-3, 4], 5.0), ([0, 0, 0], 0.0), ([3e200, 4e200], 5e200)])
def test_examples(v, expected):
    assert norm(v) == pytest.approx(expected, rel=1e-12)

def test_invalid():
    with pytest.raises(ValueError):
        project([1, 2], [0, 0])
```

Expected: `8 passed`. Mutation check: replace the body of `norm` by `math.sqrt(sum(x*x for x in v))`; `test_examples` (the `3e200` case) and `test_against_numpy` must fail. Hypothesis stores failing examples in a local `.hypothesis` directory and replays them first on the next run.

## Exercise answers

1. `norm([-3, 4]) = 5`; `norm([0, 0, 0]) = 0`; `dot = 4 - 10 + 18 = 12`; `project([2, 2], [1, 0]) = [2, 0]` (component of `a` along `b`). Invalid: `dot([1, 2], [1])` and `project([1, 2], [1])` raise `ValueError` (dimension mismatch); `project([1, 2], [0, 0])` raises `ValueError` (zero direction); `norm([])` raises `ValueError`; `nan`/`inf` coordinates raise `ValueError`.
2. $|2.01-2|=0.01$. With `rtol=1e-3` the allowed error is $0.002$: fail. With `atol=0.02`: pass. For expected 0 and `atol=0`, the allowed error is 0, so only an exact zero passes: relative tolerance alone is useless at zero. For 1 mm resolution use `atol` about $5\times10^{-4}$ m (half the resolution) plus a small `rtol` like $10^{-9}$ for numerical noise.
3. $[1,0]$ is useless: every candidate returns 1, the same as the correct norm. $[3,4]$ alone separates all four: A gives 7, B gives 4, C gives 25, D gives 7, while the correct value is 5. $[-3,4]$ also kills all four (A gives 1, B 4, C 25, D 7) and additionally shows that the sign is handled. Axis-aligned unit vectors distinguish none of the bugs.
4. Load the fixture, convert, and assert `is_close(norm(v), 5.0)` (metres). With the missing conversion the code returns 5000. Also assert the unit is recorded and that an unknown unit raises `ValueError`. The test must use hand-computed expected values, not values produced by the loader.
5. `assertAlmostEqual` rounds the difference to 7 decimal places; the difference is $2\times10^{-9}$, which rounds to 0.0, so any value in $(-5\times10^{-8}, 5\times10^{-8})$ passes: even 0. Use a relative comparison: `assertTrue(math.isclose(norm([1e-9, 2e-9]), 2.2360679775e-9, rel_tol=1e-9))` (expected value computed independently, e.g. $\sqrt5\times10^{-9}$).
6. First: `inf` (the squares $9\times10^{400}$ overflow). Second: `0.0` (the squares $9\times10^{-400}$ underflow). True: $5\times10^{200}$ and $5\times10^{-200}$. Scale by $m=\max|x_i|$: $m\sqrt{\sum(x_i/m)^2}$ keeps the squared terms in $[0,n]$, so no overflow or underflow. `math.hypot` does this for you.
7. For example: (i) $b\cdot(a-p)=0$ (residual orthogonal to $b$; catches a wrong scalar); (ii) idempotence $p(p(a,b),b)=p(a,b)$ (catches a missing division by $b\cdot b$); (iii) $p$ is parallel to $b$ (catches adding components of $a$); (iv) $\|p\|\le\|a\|$ (catches scale errors); (v) $p(a,cb)=p(a,b)$ for $c\ne0$ (catches normalising $b$ incorrectly or using $\|b\|$ in place of $\|b\|^2$); also $p(a,b)=a$ if $a$ is parallel to $b$.
8. Each of the two halves, `[5, 1e154, 2, 3]` and `[7, 9, 1e154, 4]`, passes (a single $10^{154}$ squares to $10^{308}$, which is still finite), so halving alone cannot reduce it: the failure needs both large values. Then remove single elements and keep the removal whenever the failure persists: dropping 5, 2, 3, 7, 9, 4 all keep the failure, leaving the minimal case `[1e154, 1e154]` (the squares sum to $2\times10^{308}>1.8\times10^{308}$). Store the seed, the exact command (`python3 -m unittest module.Class.test`) and this minimal input as a regression test.
9. Most independent: (c) at 50 digits and (d) hand-calculated triples ($3,4,5$; $5,12,13$). (b) `math.hypot` is an independent implementation but may differ in the last bit, so compare with a relative tolerance. (a) shares every bug with the code (it checks nothing). The oracle in (c) can fail if the sum of squares was computed in floats before being passed to Decimal: build it from `Decimal` inputs.
10. Floating addition is not associative: $10^{16}+1=10^{16}$ (1 is below half a unit in the last place, which is 2), so the 1 is lost and the final sum is $0$. The problem is ill-conditioned relative to the result: the natural scale is $\sum|a_ib_i|=2\times10^{16}$, so a correct float implementation can have an absolute error of about $10^{16}\varepsilon\approx2$. Scale the tolerance by $\sum|a_ib_i|$ for tests of such cancellation, or use `math.fsum` (exact summation of the products, returns 1.0).
11. Layers: (1) example tests with hand-computed values (norm 5, dot 12, projection $[2,0]$); (2) property tests (Cauchy-Schwarz $|a\cdot b|\le\|a\|\|b\|$, scaling, orthogonality of residual) with a recorded seed; (3) integration tests that read fixtures (JSON with units) and check types and values; (4) regression tests holding every reduced failing case. Fixtures are small JSON files under `tests/fixtures/`. Report seeds in the failure message. Command: `python3 -m unittest discover -s tests -v`.
12. A good answer includes the mutation table (e.g. rows = mutants such as missing square, wrong sign, missing dimension check, missing zero check, wrong unit scale, in-place modification; columns = tests), shows each mutant killed by a named test, and states a real gap found (typically: no test for the zero direction or for mismatched dimensions, or the tolerance too loose).
