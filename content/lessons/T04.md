## Why this matters

A numerical algorithm is useful only when there is evidence that its implementation matches its contract. Testing should constrain behavior, errors, and reproducibility, rather than reward a green indicator. An independent reference implementation is often the most valuable first tool.

## Intuition

Declare the input domain, output meaning, invalid-input behavior, precision, and side effects. For a vector norm, inputs are finite real coordinates and the output is nonnegative. For a projection, the direction must be nonzero and both vectors must have equal dimensions. These assumptions should become explicit checks or clearly documented caller obligations.

![A stack of test layers (examples, properties, integration, regression) and a tolerance plot showing where atol and rtol dominate](/lesson-figures/T04.svg)

*Figure: different layers catch different bugs, and the tolerance atol + rtol*|b| switches from absolute to relative at b = atol/rtol.*

**The picture first.** A test is a question you ask a program together with the answer you already trust. The only way a test teaches you something is if a *wrong* program would have given a different answer. So the useful mental image is not "green means correct" but a net: every test is a hole in a net, and a bug is a fish that has to be too big to slip through any hole. Examples with hand-computed values are large holes in a few places; properties are many small holes everywhere; integration tests check that the net is tied to the real world (units, files, types); regression tests patch holes where a fish once escaped.

**A robot example.** A mobile robot computes the distance to a waypoint with `norm(p - q)`. A unit test on `[3, 4]` passes; in the field the robot stops 1000 times too early because the odometry is in millimetres and the planner expects metres. No arithmetic test could catch this: the fault lives at the boundary between two components, which is exactly what the integration layer with a unit-tagged fixture is for. Another case: a drone sums $10^6$ range readings and the total is off in the ninth digit; that is not a bug but the rounding behaviour of floating-point sums, and a test that demands bit equality would be wrong while a test with no tolerance reasoning would be useless.

**Predict before you compute.** Before reading the theory, guess: (1) how large can the error of adding $10^3$ numbers in $[0,1)$ be, relative to their sum, in double precision? (2) What does `math.isclose(1e-12, 0.0)` return, and why might that surprise you? (3) For `dot([1e16, 1, -1e16], [1, 1, 1])` should a test accept `0.0`? Write your three guesses down; the theory answers them with numbers.

**The common wrong intuition.** "Floating-point error is random noise, so a loose tolerance like `1e-6` is always safe." Two things are wrong. Error is not noise: it is a deterministic function of the operation order, and in an ill-conditioned problem it can be as large as the result itself. And a tolerance chosen without looking at the scale either rejects correct code (too tight for a cancelling sum) or accepts wrong code (too loose for a norm of order $10^{-9}$, where `1e-6` accepts zero). The tolerance is part of the contract and must be derived, not guessed.


## Theory and derivation

Floating comparisons often use $|a-b|\le atol+rtol|b|$. Near zero the absolute tolerance dominates; at large scale the relative tolerance dominates. Choose both using measurement scale and numerical conditioning. A single loose tolerance can accept an implementation that is systematically wrong. For exact identifiers, counts, and exception types, use exact checks.

### The floating-point error model

All of the numerical claims below rest on one assumption, the **standard model** of rounding: for a basic operation $\circ\in\{+,-,\times,\div\}$ whose exact result lies in the normal range, the computed result is $\mathrm{fl}(x\circ y)=(x\circ y)(1+\delta)$ with $|\delta|\le u$, where $u=2^{-53}\approx1.11\times10^{-16}$ is the unit roundoff of IEEE double precision with round-to-nearest. (Goldberg calls the corresponding bound $\varepsilon$ and shows, in the section on rounding error, that exactly rounded operations satisfy it; his Theorem 2 gives a relative error below $2\varepsilon$ for subtraction with a guard digit.) The model fails in three places that a test suite must treat separately: when the exact result exceeds the largest finite double ($\approx1.8\times10^{308}$), the result is `inf`; when it is below the smallest normal number the relative error bound is lost (subnormals have fewer digits); and when an operand is already `nan` or `inf`. Overflow and underflow are therefore *contract* questions (what inputs are allowed?), not tolerance questions.

### Error of a sum and the condition number

Take $s_1=x_1$ and $s_k=\mathrm{fl}(s_{k-1}+x_k)=(s_{k-1}+x_k)(1+\delta_k)$ with $|\delta_k|\le u$, $k=2,\dots,n$. Unrolling gives
$$s_n=\sum_{j=1}^{n}x_j\prod_{k=\max(j,2)}^{n}(1+\delta_k),$$
so each summand $x_j$ is multiplied by a product of at most $n-1$ factors $(1+\delta_k)$. Using $\prod(1+\delta_k)\le(1+u)^{m}=1+mu+O(u^2)$ and the analogous lower bound, every factor lies within $(n-1)u+O(u^2)$ of $1$. Subtracting the exact sum,
$$|s_n-\textstyle\sum x_j|\le(n-1)\,u\sum_j|x_j|+O(u^2).$$
This is the first-order bound; Goldberg states the same comparison when he notes that the naive sum perturbs each summand by up to $ne$ while Kahan summation perturbs each by about $2e$ (Goldberg, Theorem 8 and the discussion that follows it). Dividing by $|\sum x_j|$ gives the relative error bound $(n-1)u\,\kappa$ with the **condition number of the sum**
$$\kappa=\frac{\sum_j|x_j|}{\left|\sum_jx_j\right|}\ge1.$$
When all $x_j$ have the same sign, $\kappa=1$ and the relative error is at most about $nu$, harmless. When terms cancel, $\kappa$ is large and *no* relative tolerance fixed in advance is safe. For a dot product the same argument adds one rounding per product, giving $|\mathrm{fl}(a\cdot b)-a\cdot b|\le n\,u\sum_i|a_ib_i|+O(u^2)$. The practical rule: scale the tolerance of a sum or dot product by $\sum|a_ib_i|$, not by the result. The bound is a worst case: for $1000$ numbers drawn uniformly from $[0,1)$ (`random.seed(1)`) the actual error was $1.66\times10^{-13}$ against a bound of $5.70\times10^{-11}$, about $343$ times smaller, because the rounding errors have mixed signs. A test should use the bound (it must never fail for a correct implementation), while a benchmark may use the typical error.

### Compensated and exact summation

If a sum is ill-conditioned you can change the algorithm instead of the tolerance. **Kahan summation** keeps a running correction $C$: for each $x_j$ compute $Y=x_j-C$, $T=S+Y$, $C=(T-S)-Y$, $S=T$. The quantity $(T-S)-Y$ is the part of $Y$ that was lost when $T$ was rounded, so subtracting it from the next term feeds the lost digits back. Goldberg's Theorem 8 shows that the computed sum equals $\sum x_j(1+\delta_j)+O(Nu^2)\sum|x_j|$ with $|\delta_j|\le2u$, so the error no longer grows with $n$. It is **not exact**: the correction relies on $T-S$ being computed without error, which can fail when $|S|$ is much smaller than $|Y|$. For $[1,10^{100},1,-10^{100}]$ the loop returns $0$, while the exact sum is $2$; the lost $1$ is never recovered because at the moment $10^{100}$ is added the partial sum $1$ is smaller than the term. `math.fsum` tracks several partial sums and returns the correctly rounded sum for such inputs (Python documentation, `math.fsum`; it notes that the result depends on IEEE-754 behaviour and can be off in the last bit on some builds). Note a trap: in the Python 3.14.7 used here the built-in `sum` of floats is itself compensated, so `sum([1e16, 1.0, -1e16])` returns $1.0$; to reproduce the naive behaviour, write the explicit loop `s += x`.

### Tolerances: absolute, relative, symmetric

The lesson's test $|a-b|\le atol+rtol\,|b|$ treats $b$ (the expected value) differently from $a$. `math.isclose` uses a symmetric rule: $|a-b|\le\max(rel\_tol\cdot\max(|a|,|b|),abs\_tol)$, with defaults `rel_tol=1e-9`, `abs_tol=0` (Python documentation, `math.isclose`). With $abs\_tol=0$ and $rel\_tol<1$, `isclose(a, b)` is true exactly when *either* asymmetric test passes, because $\max(rtol|a|,rtol|b|)$ is the larger of the two bounds. Three consequences: (1) it is symmetric in its arguments; (2) it is **not transitive**: with $rel\_tol=0.1$, $1$ is close to $1.1$ and $1.1$ is close to $1.21$ but $1$ is not close to $1.21$; (3) comparing with $0$ is only true for exactly $0$, since $\max(rtol\cdot|x|,0)<|x|$, so a test of a quantity that can be zero needs a positive $abs\_tol$ chosen from the physical scale (for a position, half the sensor resolution). Combine the two: take $abs\_tol$ from measurement scale and $rel\_tol$ from $c\,n\,u\,\kappa$ with a small safety factor $c$.

### Scaling and the norm

For a vector norm the dangerous step is squaring. If $\max|x_i|\ge10^{154}$ the square overflows even though the norm $\sqrt{\sum x_i^2}$ may be representable; below $10^{-154}$ the squares underflow. Factor out $m=\max|x_i|$: $\|x\|=m\sqrt{\sum(x_i/m)^2}$. Every term $(x_i/m)^2\le1$, so the sum lies in $[1,n]$ and cannot overflow. The division costs one rounding per coordinate unless $m$ is a power of two, in which case it is exact (barring subnormal results). In a measurement against a $60$-digit `Decimal` oracle over $20{,}000$ random vectors (lengths $2$ to $6$, magnitudes from $10^{-150}$ to $10^{150}$), the worst relative error was $2.29\,u$ for scaling by $\max|x_i|$, $1.50\,u$ for a power-of-two scale, and $0.98\,u$ for `math.hypot` (Python documentation, `math.hypot`). For tests this means two things: the oracle for a norm should be an independent high-precision computation, and the tolerance for a norm should be a few $u$ relative, not $10^{-6}$.

### Properties as tests: derive them, then derive their tolerance

A property test replaces "this input gives this output" by a statement that must hold for every input in the domain, checked on many generated inputs (by default Hypothesis generates $100$ random inputs per test and lets you change this with `max_examples`; Hypothesis documentation, Quickstart). The statements come from mathematics, so derive them. For the projection of $a$ onto a nonzero $b$, minimise $\|a-tb\|^2$ over $t$: the derivative $-2\,b\cdot(a-tb)=0$ gives $t=\frac{a\cdot b}{b\cdot b}$ and $p=tb$. Three properties follow at once. (i) *Orthogonal residual*: $b\cdot(a-p)=b\cdot a-t\,b\cdot b=0$. (ii) *Idempotence*: $p$ is a multiple of $b$, so projecting it again gives $t'=\frac{(tb)\cdot b}{b\cdot b}=t$ and $p'=p$. (iii) *Scale invariance in $b$*: replacing $b$ by $cb$ ($c\ne0$) gives $t'=t/c$ and $p'=t'cb=p$. A fourth, $\|p\|\le\|a\|$, follows from (i) by Pythagoras, $\|a\|^2=\|p\|^2+\|a-p\|^2$, and the Cauchy-Schwarz inequality $|a\cdot b|\le\|a\|\|b\|$ is equivalent to $\|p\|\le\|a\|$ after substituting $\|p\|=|a\cdot b|/\|b\|$.

Each exact identity becomes a floating-point test only after a tolerance is derived. In (i) the computed residual is not zero but of order $u$ times the *scale of the terms*, $\|a\|\|b\|$, not times $b\cdot(a-p)$ itself, which is the cancelling quantity. In a run of $10{,}000$ random $4$-vectors with magnitudes from $10^{-3}$ to $10^{3}$ (`random.seed(5)`), the worst measured $|b\cdot(a-p)|/(\|a\|\|b\|)$ was $3.53\,u$, so a tolerance of $c\,n\,u\|a\|\|b\|$ with $c=1$ and $n=4$ would have passed every correct case, whereas `abs_tol=1e-12` would have failed for large vectors and accepted wrong answers for tiny ones. Properties do not replace examples: a property can be satisfied by a wrong function (the zero vector satisfies (i), (ii) and (iv)), which is why the example layer keeps hand-computed values such as $\mathrm{project}([2,2],[1,0])=[2,0]$.

### Test strength: what a tolerance can and cannot detect

A test kills a wrong implementation $f$ at input $v$ when $f(v)$ and the oracle value differ by more than the tolerance. Two limits follow directly. First, **separation**: an input only helps if wrong candidates give different outputs there; the vectors $[1,0]$ and $[0,1]$ give $1$ for the correct norm and for the coordinate sum, the largest coordinate and the sum of absolute values alike, so they kill none of those mutants, while $[-3,4]$ gives $5$ against $1$, $4$, $7$. Second, **resolution**: a mutant whose output differs from the oracle by a relative amount $\delta$ survives whenever $\delta\le rtol$. For instance, an implementation that silently rounds each coordinate to single precision before squaring has relative error up to $2^{-24}\approx5.96\times10^{-8}$ per coordinate (measured worst case over $10^5$ random values in $[1,1000]$: $5.94\times10^{-8}$; for the vector $[3.1,4.7]$ the norm differed by $3.76\times10^{-8}$). Such a mutant passes `rel_tol=1e-6` and is killed only by a tolerance of a few $u$. So the tolerance is not just protection against false alarms; it is also the *smallest bug you promise to detect*, and it should be justified from the error analysis above. Finally, an oracle that shares code with the implementation shares its bugs; the more independent the oracle (hand-computed values, a $60$-digit `Decimal` computation, `math.fsum`), the more mutants it can kill.

### From theory to test design

Putting the pieces together gives a procedure. State the domain (finite inputs; no overflow beyond a stated bound). Choose the oracle (hand values, `Decimal`, `math.fsum`, `math.hypot`) and note which share code with the implementation. Derive the tolerance from the error bound and conditioning of the specific operation. Test the boundaries explicitly (zero vectors, mismatched lengths, extreme magnitudes, cancellation). Keep every failure as a minimal regression test, with the seed (T03 shows how to reduce a failing run by bisection), and pin the environment that produced it (T05).

## Worked example

### Basic case

**Problem.** A norm implementation returns the sum of the coordinates, $f(v)=v_0+v_1$, instead of $\sqrt{v_0^2+v_1^2}$. Which of the test vectors $[1,0]$, $[-1,0]$, $[3,4]$ expose it, and would a suite made only of zero vectors and axis-aligned positive unit vectors expose it?

**Solution.**

1. For $[1,0]$ the implementation returns $1+0=1$ and the correct norm is $1$: the test passes.
2. For $[-1,0]$ it returns $-1+0=-1$, but a norm is never negative and the correct value is $1$: the test fails.
3. For $[3,4]$ it returns $3+4=7$ and the correct norm is $\sqrt{9+16}=5$: the test fails, with $7$ instead of $5$.
4. For a zero vector it returns $0$ (correct) and for an axis-aligned positive unit vector $e_i$ it returns $1$ (correct). Such a suite agrees with the intended function on every input it contains, so the wrong implementation passes the whole suite.

**Check.** Running the three vectors in Python gives $1$, $-1$, $7$ against $1$, $1$, $5$; the implementation also equals the true norm on every non-negative axis-aligned vector tried ($[0,0],[1,0],[0,1],[2,0],[0,5]$).

**Takeaway.** Test cases must separate plausible wrong implementations from the intended one: include negative coordinates and a non-axis-aligned vector such as the $3$-$4$-$5$ triangle.

### A harder case: deriving a tolerance for a cancelling dot product

**Problem.** Test `dot([1e16, 1.0, -1e16], [1.0, 1.0, 1.0])`, whose exact value is $1$. (a) What error bound does the theory section give? (b) What does a plain left-to-right loop return? (c) Is `isclose(result, 1, rel_tol=1e-9)` a reasonable test for it? Is the bound-based tolerance? (d) Design a better test. (e) Show how Kahan summation fails on $[1,10^{100},1,-10^{100}]$ (exact sum $2$), with the trace.

**Solution.**

1. The products $10^{16}\cdot1$, $1\cdot1$, $-10^{16}\cdot1$ are exact, so the problem is the sum $10^{16}+1-10^{16}=1$. Then $\sum|a_ib_i|=10^{16}+1+10^{16}\approx2\times10^{16}$ and the condition number is $\kappa=\sum|a_ib_i|/|\sum a_ib_i|\approx2\times10^{16}$.
2. The bound $n\,u\sum|a_ib_i|$ with $n=3$ and $u=2^{-53}\approx1.11\times10^{-16}$ gives $3\times1.11\times10^{-16}\times2\times10^{16}\approx6.66$ (computed $6.661$): an absolute error up to $6.66$ is allowed, on an exact value of $1$.
3. The loop computes $0+10^{16}=10^{16}$, then $10^{16}+1$. The spacing of doubles near $10^{16}$ is $2$ (since $2^{53}\approx9.0\times10^{15}<10^{16}<2^{54}$), so $1$ is half a spacing and the sum rounds back to $10^{16}$. Then $10^{16}-10^{16}=0.0$. The error is $1$, well inside the bound $6.66$.
4. `isclose(result, 1, rel_tol=1e-9)` demands $|{\rm result}-1|\le10^{-9}$ where the bound allows $6.66$, so the correct plain loop fails it: not a reasonable test.
5. The tolerance $6.66$ (from the bound) accepts every result in $[-5.66,\,7.66]$, including $0$, $1$ and $7$, hence almost any wrong implementation: also a poor test.
6. The better design changes the algorithm: `math.fsum(x * y for x, y in zip(a, b))` returns exactly $1.0$, so the test can demand equality (or a tiny tolerance).
7. Kahan on $[1,10^{100},1,-10^{100}]$, with $Y=x-C$, $T=S+Y$, $C=(T-S)-Y$, $S=T$:
   - start: $S=1$, $C=0$;
   - add $10^{100}$: $Y=10^{100}$, $T=10^{100}$, $C=0$ (the $1$ is absorbed and not captured);
   - add $1$: $Y=1$, $T=10^{100}$, $C=-1$;
   - add $-10^{100}$: $Y=-10^{100}-(-1)=-10^{100}$, $T=0$, $C=0$.
8. The final result $0$ is wrong by the full $2$, whereas `fsum` returns the exact $2.0$.

**Check.** Python gives: loop result $0.0$, `fsum` $1.0$, `math.ulp(1e16)` $=2.0$, `1e16 + 1 == 1e16` is `True`, bound $6.661$; for the second input a Kahan loop returns $0.0$ and `fsum` $2.0$, with the trace above reproduced term by term.

**Takeaway.** Pick the oracle (`fsum`) and the implementation by conditioning, and test the cancelling case explicitly.

## Implementation and verification

Use three layers: examples with independently calculated outputs, properties such as norm scaling and nonnegativity, and integration checks for boundaries such as serialization or units. Keep randomized test seeds in failure reports and reduce a failing random case to the smallest useful example. Preserve the failing case as a regression test.

## Misconceptions and alternatives

Mutation checking deliberately breaks code to inspect the suite. Remove a square, reverse a sign, or accept a mismatched dimension. At least one relevant test should fail for each mutation. Line coverage helps find unexecuted paths, but a line can run without an assertion checking its effect. A copied reference function in both the implementation and expected result is not an independent oracle.

## Independent practice and transfer

### Goal

Write a small, trustworthy vector module (`dot`, `norm`, `project`, and a JSON loader with unit handling) together with the tests that make it trustworthy: hand-computed examples, invalid-input checks, scale tests (overflow/underflow), properties with a recorded seed, and a fixture-based integration test.

### Setup

Python 3 standard library only. Save the starter code and the tests in one file, `vector_lab.py`, and run `python3 vector_lab.py`. For the extension you will move the checks into a `unittest.TestCase` and run `python3 -m unittest -v`.

### Library track

Use the standard tools around your lab (`pip install numpy pytest hypothesis`). Save the lab module as `vector_lab.py` (without the test code at the bottom) and the following as `test_vector_lib.py` next to it; run `python3 -m pytest -q`. NumPy and `math.hypot` act as independent oracles, and Hypothesis generates the random cases and shrinks a failure to a minimal input (the library version of exercise 8). Note what the run teaches: `np.linalg.norm` itself underflows on `[3e-200, 4e-200]`, so it is only a valid oracle in a moderate range.

```python
import math
import numpy as np
import pytest
from hypothesis import given, strategies as st
from vector_lab import dot, norm, project

# keep away from underflow, which NumPy's own norm does not handle
finite = st.floats(min_value=-1e6, max_value=1e6, allow_nan=False, allow_infinity=False).filter(
    lambda x: x == 0 or abs(x) > 1e-100)
pair = st.integers(1, 6).flatmap(lambda n: st.tuples(st.lists(finite, min_size=n, max_size=n),
                                                      st.lists(finite, min_size=n, max_size=n)))

@given(pair)
def test_against_numpy(ab):
    a, b = ab
    scale = float(np.dot(np.abs(a), np.abs(b)))                    # natural scale of the sum
    assert dot(a, b) == pytest.approx(float(np.dot(a, b)), abs=1e-12 * (1 + scale))
    assert norm(a) == pytest.approx(math.hypot(*a), rel=1e-12, abs=0.0)
    np.testing.assert_allclose(norm(a), np.linalg.norm(a), rtol=1e-12)

@given(pair)
def test_cauchy_schwarz(ab):
    a, b = ab
    assert abs(dot(a, b)) <= norm(a) * norm(b) * (1 + 1e-12) + 1e-12

@given(pair)
def test_projection_residual_orthogonal(ab):
    a, b = ab
    if norm(b) < 1e-3:
        return
    p = project(a, b)
    assert abs(dot([x - y for x, y in zip(a, p)], b)) <= 1e-9 * (1 + norm(a) * norm(b))

def test_extreme_scale_needs_hypot_not_numpy():
    v = [3e-200, 4e-200]
    assert norm(v) == pytest.approx(5e-200, rel=1e-12, abs=0.0)
    assert math.hypot(*v) == pytest.approx(5e-200, rel=1e-12, abs=0.0)
    assert np.linalg.norm(v) != pytest.approx(5e-200, rel=1e-6, abs=0.0)   # NumPy norm underflows: a weaker oracle

@pytest.mark.parametrize("v, expected", [([-3, 4], 5.0), ([0, 0, 0], 0.0), ([3e200, 4e200], 5e200)])
def test_examples(v, expected):
    assert norm(v) == pytest.approx(expected, rel=1e-12)

def test_invalid():
    with pytest.raises(ValueError):
        project([1, 2], [0, 0])
```

Expected: `8 passed`. Mutation check: replace the body of `norm` by `math.sqrt(sum(x*x for x in v))`; `test_examples` (the `3e200` case) and `test_against_numpy` must fail. Hypothesis stores failing examples in a local `.hypothesis` directory and replays them first on the next run.

## Exercise answers

1. `norm([-3, 4]) = 5`; `norm([0, 0, 0]) = 0`; `dot = 4 - 10 + 18 = 12`; `project([2, 2], [1, 0]) = [2, 0]` (component of `a` along `b`). Invalid: `dot([1, 2], [1])` and `project([1, 2], [1])` raise `ValueError` (dimension mismatch); `project([1, 2], [0, 0])` raises `ValueError` (zero direction); `norm([])` raises `ValueError`; `nan`/`inf` coordinates raise `ValueError`.
2. $|2.01-2|=0.01$. With `rtol=1e-3` the allowed error is $0.002$: fail. With `atol=0.02`: pass. For expected 0 and `atol=0`, the allowed error is 0, so only an exact zero passes: relative tolerance alone is useless at zero. For 1 mm resolution use `atol` about $5\times10^{-4}$ m (half the resolution) plus a small `rtol` like $10^{-9}$ for numerical noise.
3. $[1,0]$ is useless: every candidate returns 1, the same as the correct norm. $[3,4]$ alone separates all four: A gives 7, B gives 4, C gives 25, D gives 7, while the correct value is 5. $[-3,4]$ also kills all four (A gives 1, B 4, C 25, D 7) and additionally shows that the sign is handled. Axis-aligned unit vectors distinguish none of the bugs.
4. Load the fixture, convert, and assert `is_close(norm(v), 5.0)` (metres). With the missing conversion the code returns 5000. Also assert the unit is recorded and that an unknown unit raises `ValueError`. The test must use hand-computed expected values, not values produced by the loader.
5. `assertAlmostEqual` rounds the difference to 7 decimal places; the difference is $2\times10^{-9}$, which rounds to 0.0, so any value in $(-5\times10^{-8}, 5\times10^{-8})$ passes: even 0. Use a relative comparison: `assertTrue(math.isclose(norm([1e-9, 2e-9]), 2.2360679775e-9, rel_tol=1e-9))` (expected value computed independently, e.g. $\sqrt5\times10^{-9}$).
6. First: `inf` (the squares $9\times10^{400}$ overflow). Second: `0.0` (the squares $9\times10^{-400}$ underflow). True: $5\times10^{200}$ and $5\times10^{-200}$. Scale by $m=\max|x_i|$: $m\sqrt{\sum(x_i/m)^2}$ keeps the squared terms in $[0,n]$, so no overflow or underflow. `math.hypot` does this for you.
7. For example: (i) $b\cdot(a-p)=0$ (residual orthogonal to $b$; catches a wrong scalar); (ii) idempotence $p(p(a,b),b)=p(a,b)$ (catches a missing division by $b\cdot b$); (iii) $p$ is parallel to $b$ (catches adding components of $a$); (iv) $\|p\|\le\|a\|$ (catches scale errors); (v) $p(a,cb)=p(a,b)$ for $c\ne0$ (catches normalising $b$ incorrectly or using $\|b\|$ in place of $\|b\|^2$); also $p(a,b)=a$ if $a$ is parallel to $b$.
8. Each of the two halves, `[5, 1e154, 2, 3]` and `[7, 9, 1e154, 4]`, passes (a single $10^{154}$ squares to $10^{308}$, which is still finite), so halving alone cannot reduce it: the failure needs both large values. Then remove single elements and keep the removal whenever the failure persists: dropping 5, 2, 3, 7, 9, 4 all keep the failure, leaving the minimal case `[1e154, 1e154]` (the squares sum to $2\times10^{308}>1.8\times10^{308}$). Store the seed, the exact command (`python3 -m unittest module.Class.test`) and this minimal input as a regression test.
9. Most independent: (c) at 50 digits and (d) hand-calculated triples ($3,4,5$; $5,12,13$). (b) `math.hypot` is an independent implementation but may differ in the last bit, so compare with a relative tolerance. (a) shares every bug with the code (it checks nothing). The oracle in (c) can fail if the sum of squares was computed in floats before being passed to Decimal: build it from `Decimal` inputs.
10. Floating addition is not associative: $10^{16}+1=10^{16}$ (1 is below half a unit in the last place, which is 2), so the 1 is lost and the final sum is $0$. The problem is ill-conditioned relative to the result: the natural scale is $\sum|a_ib_i|=2\times10^{16}$, so a correct float implementation can have an absolute error of about $10^{16}\varepsilon\approx2$. Scale the tolerance by $\sum|a_ib_i|$ for tests of such cancellation, or use `math.fsum` (exact summation of the products, returns 1.0).

13. *Derivation.* Assumptions: round-to-nearest double arithmetic, each addition satisfies $\mathrm{fl}(x+y)=(x+y)(1+\delta)$ with $|\delta|\le u$ (the standard model), and no overflow or underflow. With $s_1=x_1$ and $s_k=(s_{k-1}+x_k)(1+\delta_k)$, induction gives $s_n=\sum_jx_j\prod_{k=\max(j,2)}^n(1+\delta_k)$: the step $k$ multiplies everything accumulated so far, and the new term, by $(1+\delta_k)$. Each summand carries at most $n-1$ factors. For $|\delta_k|\le u$ and $m\le n-1$ factors, $(1-u)^m\le\prod(1+\delta_k)\le(1+u)^m$ and $(1\pm u)^m=1\pm mu+O(m^2u^2)$, so $|\prod-1|\le(n-1)u+O(u^2)$. Hence $|s_n-\sum x_j|\le\sum_j|x_j|\,|\prod-1|\le(n-1)u\sum|x_j|+O(u^2)$. *Dot product.* Each product $a_ib_i$ is rounded once more, $\mathrm{fl}(a_ib_i)=a_ib_i(1+\eta_i)$, so each term carries at most $n$ factors (one product rounding and at most $n-1$ additions): bound $n\,u\sum|a_ib_i|+O(u^2)$. *Signs.* Dividing by $|\sum x_j|$ gives relative error $\le(n-1)u\kappa$ with $\kappa=\sum|x_j|/|\sum x_j|$. If all terms have one sign, $\kappa=1$ and a relative tolerance of a few $nu$ is right; if terms cancel, $\kappa$ can be huge and a relative tolerance fixed in advance either fails correct code or hides errors, so use $n\,u\sum|x_j|$ as an absolute tolerance. *Numbers (computed).* Actual error $1.663\times10^{-13}$, bound with $n-1=999$ and $\sum|x_j|$ from the same data $5.702\times10^{-11}$, ratio $342.9$ (so the bound is about $343$ times larger than the error observed; the errors have mixed signs). The correctly rounded sum from `math.fsum` equals the correctly rounded value of the exact `Decimal` sum for this data.
14. Implementation: `s = xs[0]; c = 0.0` then for each remaining `x`: `y = x - c; t = s + y; c = (t - s) - y; s = t`. Results (computed with Python 3.14.7): $[10^{16},1,1,-10^{16}]$: explicit loop $0.0$, Kahan $2.0$, `fsum` $2.0$. $[10^{16},1,-10^{16}]$: loop $0.0$, Kahan $0.0$, `fsum` $1.0$. $[1,10^{100},1,-10^{100}]$: loop $0.0$, Kahan $0.0$, `fsum` $2.0$. Trace for the last input $(S,C)$: initial $(1,0)$; add $10^{100}$: $Y=10^{100}$, $T=10^{100}$, $C=(10^{100}-1)-10^{100}=0$ because $10^{100}-1$ rounds to $10^{100}$, so the $1$ is invisible: $(10^{100},0)$; add $1$: $Y=1$, $T=10^{100}$, $C=(T-S)-Y=-1$: $(10^{100},-1)$; add $-10^{100}$: $Y=-10^{100}-(-1)=-10^{100}$ after rounding, $T=0$, $C=0$: $(0,0)$. The failure is that the compensation tracks the error of an addition only when $T-S$ is exact, and here $|S|=1\ll|Y|$. Kahan improves a long sum of similar magnitudes but is not exact when terms of very different size cancel. A test oracle should be `fsum` (or `Decimal`), not Kahan.
15. (a) Let $M=\max(|a|,|b|)$. Then $\max(rel\_tol\,|a|,rel\_tol\,|b|)=rel\_tol\,M$ since $rel\_tol\ge0$, and $|a-b|\le rel\_tol\,M$ iff $|a-b|\le rel\_tol|a|$ or $|a-b|\le rel\_tol|b|$ (the maximum is attained by one of the two). (The function documents $rel\_tol<1$ as its valid range; the equivalence itself does not need it.) (b) $a=1$, $b=1.15$, $rel\_tol=0.14$: $|a-b|=0.15\le0.14\cdot1.15=0.161$ passes with $b$ as reference but $0.15\le0.14\cdot1=0.14$ fails with $a$ as reference; `isclose` returns True (computed). (c) $\mathrm{isclose}(1,1.1)$ and $\mathrm{isclose}(1.1,1.21)$ are True while $\mathrm{isclose}(1,1.21)$ is False (computed): $0.21>0.1\cdot1.21=0.121$. So "close" is not an equivalence relation, and a chain of comparisons can drift. (d) For $b=0$ the bound is $rel\_tol\cdot\max(|a|,0)=rel\_tol|a|<|a|$ for any $a\ne0$, so only exact zero is close (computed: `isclose(1e-12, 0.0)` is False, and True with `abs_tol=1e-9`). For a position with $1$ mm resolution use `abs_tol` of about $5\times10^{-4}$ m (half the resolution) plus a small `rel_tol`.
16. Procedure and results (computed): the oracle is `sqrt` of the `Decimal` sum of squares at precision $60$; vectors: length uniformly in $2..6$, each coordinate $\mathrm{uniform}(0.5,1)\cdot10^{\mathrm{uniform}(-150,150)}$, `random.seed(3)`, $20{,}000$ vectors. Worst relative error in units of $u=2^{-53}$: scaling by $\max|x_i|$: $2.29$; scaling by a power of two: $1.50$; `math.hypot`: $0.98$. Why the power of two adds no rounding: a double is $\pm f\cdot2^e$ with $1\le f<2$; multiplying or dividing by $2^k$ only changes $e$, and $f$ is unchanged as long as the result stays in the normal range, so the operation is exact. (Dividing by an arbitrary $m$ is not exact: it rounds each $x_i/m$, adding up to $u$ per coordinate, which explains the larger error.) A reasonable test tolerance is `rel_tol` about $4\times10^{-16}$ (a few $u$, here $4u\approx4.4\times10^{-16}$) for vectors of length up to $6$; for longer vectors scale it with $n$. The oracle must be independent of the formula under test: `Decimal`, not a second copy of the scaling code.
