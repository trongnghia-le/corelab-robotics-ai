## Why this matters

A robot is many programs: a driver reading wheel encoders, a localizer, a planner, a safety monitor, a logger. ROS 2 is the glue that lets them exchange typed messages without knowing about each other. Most early ROS problems are not algorithmic: a topic name differs by one slash, two nodes disagree on units, a publisher and subscriber have different message types and silently never connect, a timer period is in seconds when you thought Hz. This lesson gives you the vocabulary and, more importantly, a checklist for making the communication layer explicit and testable before you build anything on it.

## Intuition

A **node** is a process (or a component inside one) with a single job and a name. A **topic** is a named, typed, many-to-many channel: any number of publishers can write, any number of subscribers can read, and neither knows about the others. A **message** is a typed record defined in a `.msg` file; its type is part of the contract, and so are the units and the frame of each field. The graph is built at run time by discovery, so the same node can run on a laptop, in a simulator, or on a robot.

![Diagram of a ROS 2 graph: a teleop node and a planner publishing Twist on /cmd_vel, a base node subscribing to it and publishing Odometry on /odom, with a table of units for each field and a note that mismatched types do not connect](/lesson-figures/S03.svg)

*Nodes connect only through named, typed topics; the units live in the contract, not in the wire.*

Compare topics, services and actions. A topic is a stream ("here is my latest speed", fire and forget). A service is a request-response call ("set the speed limit to 0.4"). An action is a long-running goal with feedback and cancel ("navigate to this pose"). Choosing the wrong one is a design bug: a service for a 100 Hz sensor, or a topic for a command that needs an acknowledgment.

## Theory and derivation

### Names, types and matching

- A topic name is a path such as `/robot1/cmd_vel`. Rules (from the ROS 2 naming design): letters, digits, underscore, `/`; no empty tokens (`//`), no trailing `/`, and no token may start with a digit. Relative names (`cmd_vel`) are resolved inside the node's namespace, and remapping changes the name at launch without code changes.
- A publisher and a subscriber connect only if the **topic name** (after remapping) and the **type** agree (and their QoS is compatible, see S05). A type mismatch is not an exception in your code: the endpoints simply do not match, and no data flows. `ros2 topic info -v /cmd_vel` lists each endpoint with its type.

### Units and frames are conventions, not checks

Message fields are numbers; nothing enforces meters versus millimeters. REP 103 fixes the conventions: SI units (meters, seconds, kilograms), angles in radians, right-handed frames with $x$ forward, $y$ left, $z$ up for a robot body. `geometry_msgs/Twist` has `linear` in m/s and `angular` in rad/s; it carries no stamp and no frame, whereas a `Header` supplies `stamp` (seconds and nanoseconds) and `frame_id`. Document every field you publish: "`range` is in meters, measured from `frame_id`".

### Rates, periods, stamps

A timer with period $T$ seconds fires at rate $f=1/T$ Hz. Timestamps should be integers in nanoseconds (as in `builtin_interfaces/Time`); converting to float seconds loses resolution at large times (a double has about 16 digits, so a time near $1.7\times10^9$ s has resolution of roughly 0.2 microseconds). The measured rate from $n$ stamps spanning $\Delta t$ is $(n-1)/\Delta t$, because $n$ stamps bound $n-1$ intervals. A gap in the stamps larger than $1.5$ periods indicates lost or delayed messages; the number missing across a gap $g$ is $\mathrm{round}(g/T)-1$.

### Message size

A `Twist` has 6 doubles, 48 bytes of payload, plus a few bytes of serialization header. At 50 Hz it costs about $48\cdot50=2.4$ kB/s plus overhead. This matters when you move images or point clouds, not for velocity commands.

## Worked example

A teleop node publishes `geometry_msgs/Twist` on `/cmd_vel` at 10 Hz with `linear.x = 0.5` m/s for 2 s. An odometer node subscribes and integrates $x\mathrel{+}=v\,\Delta t$, with $\Delta t$ taken from message stamps.

1. A 10 Hz timer has $T=0.1$ s. Stamps $0,0.1,\dots,2.0$ s give 21 messages (if the first fires at 0), hence 20 intervals.
2. Integrate each interval with the speed of the message that ends it: $x=20\cdot0.5\cdot0.1=1.0$ m. The first message has no predecessor and contributes no distance.
3. A common off-by-one: using $\Delta t=0.1$ for all 21 messages gives $21\cdot0.5\cdot0.1=1.05$ m, a 5 % error from a counting mistake.
4. A rate check: $(21-1)/2.0=10$ Hz. If three messages are lost in the middle, 18 stamps span the same 2 s and $(18-1)/2=8.5$ Hz, and `missing_count` reports 3.
5. Units: if the sender publishes 50 meaning cm/s, the receiver integrates $50\cdot2=100$ m instead of $1$ m. The topic name and type are correct, yet the result is wrong by 100: types cannot catch unit errors.
6. Bandwidth: 48 B $\times$ 10 Hz $=480$ B/s (payload only).

## Reference implementation

First the real ROS 2 node (needs a ROS 2 installation; shown for reference, not run here):

```py
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import Twist

class Teleop(Node):
    def __init__(self):
        super().__init__("teleop")
        self.pub = self.create_publisher(Twist, "cmd_vel", 10)   # depth-10 keep-last
        self.timer = self.create_timer(0.1, self.tick)           # period in SECONDS: 10 Hz
    def tick(self):
        msg = Twist()
        msg.linear.x = 0.5          # m/s, REP 103
        self.pub.publish(msg)

def main():
    rclpy.init()
    rclpy.spin(Teleop())
```

Commands to inspect it: `ros2 topic list -t`, `ros2 topic info -v /cmd_vel`, `ros2 topic hz /cmd_vel`, `ros2 topic echo --once /cmd_vel`, `ros2 interface show geometry_msgs/msg/Twist`.

Now a runnable model of the contract: delivery needs name and type, and a stamp-based integrator.

```python
class Bus:
    def __init__(self):
        self.subs = {}
    def subscribe(self, topic, mtype, cb):
        self.subs.setdefault(topic, []).append((mtype, cb))
    def publish(self, topic, mtype, msg):
        n = 0
        for t, cb in self.subs.get(topic, []):
            if t == mtype:
                cb(msg); n += 1
        return n

def integrate(stamps_ns, speed):
    """Distance from stamps: each interval uses the speed of the message ending it."""
    return sum(speed * (b - a) * 1e-9 for a, b in zip(stamps_ns, stamps_ns[1:]))

bus, got = Bus(), []
bus.subscribe("/cmd_vel", "Twist", got.append)
assert bus.publish("/cmd_vel", "Twist", {"vx": 0.5}) == 1
assert bus.publish("/cmd_vel", "String", {}) == 0          # mismatch: nothing delivered
stamps = [k * 100_000_000 for k in range(21)]
assert abs(integrate(stamps, 0.5) - 1.0) < 1e-9
print("reference ok")
```

## Independent practice

### Goal
Build and test a small model of the ROS 2 pub/sub contract (names, types, remapping, stamps, rates) so that the same checks guide you when you run real nodes.

### Setup
Python 3 standard library. Optional real ROS 2 (Jazzy or later): the commands in the reference section. Save the starter and the tests as `s03_lab.py`.

### Tasks
1. `Bus.subscribe/publish` with remapping; publish returns the number of deliveries; a type mismatch delivers nothing and raises nothing.
2. `OdomNode.on_twist` integrates `vx` over stamp differences (integer ns) and ignores out-of-order stamps.
3. `rate_hz(stamps_ns)` using $(n-1)/\Delta t$; reject fewer than two stamps.
4. `missing_count(stamps_ns, period_ns)`.
5. `valid_topic_name(name)` following the naming rules above.
6. Write in a comment: the units of every message field you used, a baseline, the boundary case, and one observation that would reject the result.

assert bus.publish("/cmd_vel", "Twist", {"vx": 0.5}) == 1 and got == [{"vx": 0.5}]

### Library track

ROS 2 is the "library" here. If you have a ROS 2 install (this was run on Humble with Python 3.10; Jazzy or later behaves the same), run the real `rclpy` version of the lab: a 10 Hz teleop node, an odometer that integrates `Twist` between arrival times, and a second process that subscribes to the same topic name with the wrong type.

```python
# Run with a sourced ROS 2 install (e.g. `source /opt/ros/<distro>/setup.bash`).
import subprocess, sys, time
import rclpy
from rclpy.node import Node
from rclpy.executors import SingleThreadedExecutor
from geometry_msgs.msg import Twist, TwistStamped

class Teleop(Node):
    def __init__(self):
        super().__init__("teleop")
        self.pub = self.create_publisher(Twist, "cmd_vel", 10)
        self.timer = self.create_timer(0.1, self.tick)           # seconds: 10 Hz
    def tick(self):
        msg = Twist(); msg.linear.x = 0.5                        # m/s
        self.pub.publish(msg)

class Odom(Node):
    def __init__(self):
        super().__init__("odom")
        self.stamps_ns, self.x, self.last = [], 0.0, None
        self.create_subscription(Twist, "cmd_vel", self.on_twist, 10)
    def on_twist(self, msg):
        now = self.get_clock().now().nanoseconds                 # Twist has no stamp: use arrival time
        if self.last is not None:
            self.x += msg.linear.x * (now - self.last) * 1e-9
        self.last = now
        self.stamps_ns.append(now)

WRONG = """
import rclpy, time
from rclpy.node import Node
from geometry_msgs.msg import TwistStamped
rclpy.init(); n = Node("wrong"); got = []
n.create_subscription(TwistStamped, "cmd_vel", got.append, 10)   # same name, other type
t = time.time() + 2.6
while time.time() < t: rclpy.spin_once(n, timeout_sec=0.05)
print("WRONG_RECEIVED", len(got))
"""

rclpy.init()
proc = subprocess.Popen([sys.executable, "-c", WRONG], stdout=subprocess.PIPE, text=True)
tele, odo = Teleop(), Odom()
ex = SingleThreadedExecutor()
for n in (tele, odo):
    ex.add_node(n)
time.sleep(1.0)                                   # let discovery finish
t_end = time.time() + 2.05
while time.time() < t_end:
    ex.spin_once(timeout_sec=0.01)

s = odo.stamps_ns
rate = (len(s) - 1) / ((s[-1] - s[0]) * 1e-9)
print("messages: %d, measured rate: %.2f Hz, distance: %.2f m" % (len(s), rate, odo.x))
assert 9.0 < rate < 11.0                          # ros2 topic hz would report about 10
assert abs(odo.x - 0.5 * (s[-1] - s[0]) * 1e-9) < 1e-9
out = proc.communicate()[0]
print(out.strip())
assert "WRONG_RECEIVED 0" in out                  # type mismatch: both nodes run, nothing is delivered
for n in (tele, odo): n.destroy_node()
rclpy.shutdown()
print("library track ok")
```

Run it with `source /opt/ros/<distro>/setup.bash && ROS_LOCALHOST_ONLY=1 python3 s03_ros.py` (use the system Python that ROS was built for). Expected: `messages: 21`, a measured rate near 10 Hz, distance `1.00 m`, `WRONG_RECEIVED 0` and `library track ok`. The wrong-type subscriber must be a separate process: creating two types on one topic name inside a single process raises an `RCLError` instead of failing silently. The arrival-time stamps jitter by about a millisecond, so the rate is 10.0 Hz only to about 1 %, unlike the exact stamps of the stdlib bus.

## Verification

Check the worked example numerically: 21 stamps, 20 intervals, 1.0 m, 10 Hz. Then check the boundary cases: one message (no distance, no rate), duplicate stamps, a stamp going backwards. On a real system verify names and types with `ros2 topic list -t`, matching endpoints with `ros2 topic info -v`, rate with `ros2 topic hz`, and one message with `echo --once`. Confirm every numeric field against its documented unit by publishing a known value (0.5 m/s) and reading it back where it is used.

## Failure modes

- Type mismatch: `Twist` published, `TwistStamped` expected; both nodes run, nothing is delivered. Check `ros2 topic info -v`.
- Name mismatch by one character or namespace: `/robot1/cmd_vel` vs `/cmd_vel`; use remapping or relative names deliberately.
- Timer period in seconds taken as Hz: `create_timer(10, ...)` runs at 0.1 Hz.
- Counting messages instead of intervals: 5 % error in the worked example.
- Unit disagreement (cm/s vs m/s): 100-fold error with no warning.
- Float seconds for stamps in long logs: resolution loss; use integer nanoseconds.
- Starting a subscriber after the data was published: with the default volatile durability it never sees old data.

## Alternatives and trade-offs

Topics are best for continuous streams; services for short request-reply with a clear result; actions for long goals with feedback; parameters for configuration that changes rarely. A single large message reduces the number of endpoints but couples unrelated consumers and makes every change a breaking one; several small messages are easier to evolve and to replay. A custom type is only worth it if existing types (`geometry_msgs`, `sensor_msgs`, `nav_msgs`) do not fit, because standard types work with every tool, bag file and visualizer. Plain function calls inside one process are simpler than topics; use topics when decoupling, introspection or distribution is worth the overhead.
