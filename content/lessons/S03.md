## Why this matters

A robot is many programs: a driver reading wheel encoders, a localizer, a planner, a safety monitor, a logger. ROS 2 is the glue that lets them exchange typed messages without knowing about each other. Most early ROS problems are not algorithmic: a topic name differs by one slash, two nodes disagree on units, a publisher and subscriber have different message types and silently never connect, a timer period is in seconds when it was meant as Hz. This lesson gives the vocabulary and, more importantly, a checklist for making the communication layer explicit and testable before anything is built on it.

## Intuition

A **node** is a process (or a component inside one) with a single job and a name. A **topic** is a named, typed, many-to-many channel: any number of publishers can write, any number of subscribers can read, and neither knows about the others. A **message** is a typed record defined in a `.msg` file; its type is part of the contract, and so are the units and the frame of each field. The graph is built at run time by discovery, so the same node can run on a laptop, in a simulator, or on a robot.

![Diagram of a ROS 2 graph: a teleop node and a planner publishing Twist on /cmd_vel, a base node subscribing to it and publishing Odometry on /odom, with a note that a connection needs the same name, the same type and compatible QoS](/lesson-figures/S03.svg)

*Nodes connect only through named, typed topics; the units live in the contract, not in the wire.*

Compare topics, services and actions. A topic is a stream ("here is my latest speed", fire and forget). A service is a request-response call ("set the speed limit to 0.4"). An action is a long-running goal with feedback and cancel ("navigate to this pose"). Choosing the wrong one is a design bug: a service for a 100 Hz sensor, or a topic for a command that needs an acknowledgment.

Three questions decide whether a topic works, and each has a physical picture. *Do the two ends fit?* Think of two radios: they must be tuned to the same channel (the name), speak the same language (the type) and agree on the service level (QoS: a caller who demands guaranteed delivery cannot be served by a transmitter that only broadcasts). *How heavy is the stream?* Every message has a weight in bytes, and the load on a wire is weight times rate, so a 30 Hz camera is a river and a velocity command is a trickle. *What happens while a message waits?* A subscription is a mailbox with room for $N$ letters and a reader who opens one letter per callback. If letters arrive faster than the reader can open them, the mailbox fills, the oldest letter is thrown away to make room, and the reader always holds a stack of old letters.

The common wrong intuition is that `RELIABLE` and a deep queue mean "nothing is ever lost and the data is always current". Reliability protects against loss on the network, not against a reader slower than the writer; and a deeper queue creates no processing capacity, it only turns thrown-away letters into old letters.

*Predict before computing.* A camera publishes at 30 Hz with the default depth of 10. The detector callback takes 50 ms per frame. After one minute, what fraction of the frames did the callback never see, and about how many frames old is the frame it is working on? Write down both numbers, and check them against the derivation in the theory section and the second worked case. The point to look for: the letters the reader opens are about $N$ periods old, so the robot acts on a world that has moved on.

## Theory and derivation

The quantitative core of ROS 2 messaging is small. An *endpoint* is a publisher or a subscription, and it carries four things: a resolved topic name, a message type, a QoS profile and a queue. Everything that follows is a consequence of three questions: which endpoints are connected (names, types, QoS), how many bytes flow (size times rate), and what happens to a message while it waits (queue depth against rates). Each question gets a definition, a result with a proof, and a case where the result stops being true. Sources: the ROS 2 Jazzy concept pages (Topics, Nodes, Discovery, Executors, Quality of Service settings), the ROS 2 design article on topic names, the OMG DDSI-RTPS specification, and measurements made with `rclpy` on ROS 2 Humble (the wire format and the QoS rules are those documented for Jazzy; the measurements themselves were made on Humble and not repeated on Jazzy).

### Names, types and matching

**Definition.** An endpoint is a tuple $e=(\tau,\,T,\,q)$ of a fully qualified topic name $\tau$, a message type $T$ (such as `geometry_msgs/msg/Twist`) and a QoS profile $q$. A publisher $p$ and a subscription $s$ are *connected* if and only if

$$\tau_p=\tau_s,\qquad T_p=T_s,\qquad q_p\text{ is compatible with }q_s .$$

The relation is decided pair by pair; the Jazzy QoS page states that the compatibility of a pair "is unaffected by the presence of other publishers and subscriptions". Consequently a topic with $P$ publishers and $S$ subscriptions has up to $PS$ connections, a subscription receives the interleaved messages of all publishers connected to it, and its input rate is the sum of their rates. The ROS 2 documentation calls the system "strongly-typed, anonymous publish/subscribe": the type of every field is enforced when messages are built and (de)serialized, but nothing checks the meaning of the numbers (next subsection).

Names are resolved before matching. A relative name such as `cmd_vel` is prefixed by the node's namespace, a private name `~/cmd_vel` by the namespace and node name, and a remapping rule replaces a name at launch time. The naming rules (design article "ROS 2 Topic and Service Name Mapping") allow letters, digits, underscores and `/`; a name may not be empty, may not start with a digit, may not end with `/`, and may not contain repeated `/` or repeated underscores. Only when names agree do the type and QoS comparison start, and a failure in any of the three means the pair is simply not connected.

**Example.** A teleop node in namespace `/robot1` publishes `Twist` on the relative name `cmd_vel`. A base driver subscribes to `/robot1/cmd_vel` with `Twist`, and a logger subscribes to the same name with `TwistStamped`. Later a planner in the same namespace publishes `Twist` on `cmd_vel` at 20 Hz while the teleop publishes at 10 Hz. Which subscribers connect, and how many messages per second does the base driver receive?

**Solution.** The relative name resolves to `/robot1/cmd_vel`, and a connection needs the same resolved name and the same type. The base driver matches on both: connected. The logger has the same name but `TwistStamped` instead of `Twist`: not connected, and no exception is raised in either node. After the planner starts, the base driver has two connections and receives $10+20=30$ messages per second, interleaved. A mismatch in type is silent, so a missing connection must be looked for in the name and type.

### Units and frames are conventions, not checks

Message fields are numbers; nothing enforces meters versus millimeters. REP 103 fixes the conventions: SI units (meters, seconds, kilograms), angles in radians, right-handed frames with $x$ forward, $y$ left, $z$ up for a robot body. `geometry_msgs/Twist` has `linear` in m/s and `angular` in rad/s; it carries no stamp and no frame, whereas a `Header` supplies `stamp` (seconds and nanoseconds) and `frame_id`. Document every field that is published: "`range` is in meters, measured from `frame_id`". The consequence for design is that a unit error is invisible to every mechanism in the previous subsection: name, type and QoS all match, so only tests, naming and review can catch it.

**Example.** A joystick node holds a stick position that means 40 cm/s and writes it into `linear.x`, while the base driver expects m/s and clips at 0.8 m/s. What speed does the robot get if the node publishes 40, and what must be published to get the intended speed?

**Solution.** The field is in m/s, so 40 cm/s $=0.4$ m/s and the node must divide by 100 before publishing. If it publishes 40, the driver clips to 0.8 m/s, which is $0.8/0.4=2$ times too fast, and `ros2 topic info -v` still shows a healthy connection. The unit is a convention that no connection check enforces.

### Rates, periods, stamps and latency

A timer with period $T$ seconds fires at rate $f=1/T$ Hz. Timestamps should be integers in nanoseconds (as in `builtin_interfaces/Time`); converting to float seconds loses resolution at large times (a double has about 16 digits, so a time near $1.7\times10^9$ s has resolution of roughly 0.2 microseconds). The measured rate from $n$ stamps spanning $\Delta t$ is $(n-1)/\Delta t$, because $n$ stamps bound $n-1$ intervals.

Two clocks matter. The *stamp* $s_k$ of message $k$ is written by the publisher and should be the acquisition time of the data (the `Image` message definition says the header stamp "should be acquisition time of image"). The *arrival time* $r_k$ is read by the subscriber when the callback runs. The latency $\lambda_k=r_k-s_k$ is meaningful only if both come from the same clock; across two computers it contains their clock offset. The latency is a sum of stages, $\lambda=\lambda_{\text{acq}}+\lambda_{\text{ser}}+\lambda_{\text{net}}+\lambda_{\text{queue}}+\lambda_{\text{cb}}$ (driver and exposure, serialization, transport at size divided by bandwidth, waiting in the subscription queue, the callback itself). Writing a latency budget means assigning a number to every stage and checking that the total fits the control loop. The queue term is the one that can grow without limit, and the later subsection on queues bounds it.

A gap in the stamps larger than $1.5$ periods indicates lost or delayed messages; the number missing across a gap $g$ is $\mathrm{round}(g/T)-1$. This rule needs a condition on the jitter, which is exactly what the following statement says.

**Proof.** (Claim: if message $k$ is stamped $s_k=kT+e_k$ with $|e_k|\le\varepsilon$ and $\varepsilon<T/4$, then for two consecutively *received* messages with indices $a<b$ the rule $\mathrm{round}(g/T)-1$ returns exactly the number $b-a-1$ of lost messages in between, where $g=s_b-s_a$.) Put $m=b-a$. Then $g=mT+(e_b-e_a)$ and $|e_b-e_a|\le2\varepsilon<T/2$, so $g/T\in(m-\tfrac12,\,m+\tfrac12)$ and $\mathrm{round}(g/T)=m$; hence the rule returns $m-1=b-a-1$. $\square$ The bound is sharp: with $\varepsilon=0.3T$, a pair with $e_a=-0.3T$ and $e_b=+0.3T$ and no loss ($m=1$) has $g=1.6T$, so $\mathrm{round}(g/T)-1=1$ and the rule reports a message that was never lost. A publisher whose timer jitters by more than a quarter period cannot be audited by gap counting alone; use the sequence number of the message (or a counter field) instead.

**Example.** A 10 Hz sensor ($T=100$ ms) has stamp errors within $\pm20$ ms, below $T/4=25$ ms. Four received stamps are 12, 95, 218 and 480 ms. How many messages are missing before each received one, which messages were lost, and what rate is measured?

**Solution.** The gaps are $95-12=83$, $218-95=123$ and $480-218=262$ ms. Dividing by $T=100$ ms gives 0.83, 1.23 and 2.62, which round to 1, 1 and 3, so the rule (rounded ratio minus one) reports $0$, $0$ and $2$ missing messages. Both lost messages sit in the last gap: the messages with indices 3 and 4 were lost. The measured rate is $(4-1)/(0.480-0.012)=3/0.468=6.41$ Hz, which is the delivered rate, not the nominal 10 Hz.

### Message size and bandwidth

A message on the wire is its serialized form. ROS 2 serializes with the CDR (Common Data Representation) rules used by DDS. The payload starts with a 4-byte header (representation identifier and options, DDSI-RTPS 2.5, §10.2); the alignment of every following value is measured from the first byte after that header. The rules needed here are these:

- a primitive of size $s$ bytes (1, 2, 4 or 8) starts at an offset that is a multiple of $s$, so up to $s-1$ padding bytes are inserted before it;
- a `string` is a `uint32` length (counting the terminating NUL), the characters and the NUL;
- a sequence (`type[]`) is a `uint32` count followed by the elements, each aligned to its own size; a fixed array (`type[9]`) has no count;
- a nested message is the concatenation of its fields, with no header of its own.

These are the PLAIN_CDR (XCDR1) rules that the ROS 2 middleware layers use. XCDR2 aligns every primitive to at most 4 bytes, so a `float64` would not be 8-aligned and the sizes below would differ.

Let $S$ be the serialized size in bytes and $f$ the publication rate in Hz. The data rate that one connection needs is
$$B=S\,f\quad[\text{bytes/s}],$$
and the same number must be paid again for each subscription connected to a different host (each connection is a separate delivery unless the middleware multicasts or uses shared memory). The formula is a lower bound: RTPS adds its own headers to every datagram and fragments large samples, which is not modelled here.

Applying the rules to `sensor_msgs/Image` (fields `header`, `height`, `width`, `encoding`, `is_bigendian`, `step`, `data`) with `frame_id` "camera", encoding "rgb8" and a 640×480 frame: after the 4-byte header, `stamp` takes 8 bytes (offset 8); `frame_id` takes $4+7=11$ bytes (offset 19); `height` is aligned from 19 to 20 and takes 4 (24); `width` 4 (28); `encoding` takes $4+5=9$ (37); `is_bigendian` 1 (38); `step` is aligned from 38 to 40 and takes 4 (44); the sequence count takes 4 (48) and the $640\cdot480\cdot3=921600$ data bytes bring the total to 921648, plus the 4-byte header: **921 652 bytes**. All of this was checked against `rclpy.serialization.serialize_message` on ROS 2 Humble: it returned 921 652 for that image, 324 for an `Imu` with `frame_id` "imu_link", 1 860 for a `LaserScan` with 450 ranges and `frame_id` "laser" (empty intensities), and 52 for a `Twist` (the 48-byte payload plus the header).

| Message | Layout reasoning | $S$ (bytes) | Rate | $B=Sf$ |
|---|---|---|---|---|
| `Twist` | 6 float64 | 52 | 50 Hz | 2.6 kB/s |
| `Imu`, `frame_id` "imu_link" | 3 float64 vectors, a quaternion, 3 covariances of 9 float64 | 324 | 200 Hz | 64.8 kB/s |
| `LaserScan`, 450 ranges | 7 float32 plus 450 float32 | 1 860 | 15 Hz | 27.9 kB/s |
| `Image` 640×480 rgb8 | 921 600 data bytes | 921 652 | 30 Hz | 27.6 MB/s |
| `Image` 1920×1080 rgb8 | 6 220 800 data bytes | 6 220 852 | 30 Hz | 186.6 MB/s |

A 1 Gbit/s Ethernet link carries at most 125 MB/s, so the last row cannot be sent uncompressed over it even once. This is the first reason that cameras are streamed as compressed images, or processed on the host that owns them.

**Example.** A depth camera streams 1280×720 rgb8 frames at 30 Hz with the same header strings. Find the message size, the bandwidth and its share of a 125 MB/s (1 Gbit/s) link, whether a second identical camera fits, and the time to send one frame alone.

**Solution.** The size is the pixel data plus the 52 header bytes: $S=1280\cdot720\cdot3+52=2\,764\,800+52=2\,764\,852$ bytes. The bandwidth is $B=2\,764\,852\cdot30=82.9$ MB/s, which is $82.9/125=66$ % of the link. A second identical camera would exceed the link ($2\cdot82.9=165.9>125$ MB/s), so only one fits. Sending one frame alone takes $2\,764\,852\cdot8/10^9=22.1$ ms at line rate.

The quantity $S$ also decides how long a callback needs to copy and convert a message, which feeds the queue model below.

### Four views: message size and bandwidth

**Algebra.** $S=4+\sum_i\big(\text{pad}_i+\text{size}_i\big)$ with $\text{pad}_i=(-\text{offset}_i)\bmod\text{align}_i$, and $B=Sf$. For a sequence the size term is $4+\text{pad}+n\,s$, which is why the cost of an `Image` is the pixel count times bytes per pixel, plus a constant of about 52 bytes.

**Geometry.** Picture the serialized message as a strip of bytes with a ruler marked in multiples of 4 and 8. Each field is a block that must start on a mark of its own size; the gaps between blocks are the padding (the 1-byte gaps before `height` and `step` above). The bandwidth figure draws the sizes of five common messages to scale on a logarithmic axis, against the 125 MB/s limit of a gigabit link.

![Horizontal bars on a logarithmic axis for the data rates of five messages: Twist at 50 Hz 2.6 kB/s, LaserScan 27.9 kB/s, Imu 64.8 kB/s, VGA Image 27.6 MB/s and 1080p Image 186.6 MB/s, with a vertical line at the 125 MB/s of a gigabit link](/lesson-figures/S03-2.svg)

*Figure: data rate $B=Sf$ of five messages on a logarithmic axis. Four orders of magnitude separate a velocity command from an uncompressed 1080p camera, and only the camera crosses the 125 MB/s limit of a 1 Gbit/s link.*

**Code.** The reference implementation below contains a `cdr_size` function that walks a message definition with exactly the rules above; with it the numbers of the table are:

```python
from s03_pubsub import Image, cdr_size, blank       # the module of the reference implementation
vga = blank(Image, frame_id=6, encoding=4, data=640 * 480 * 3)
S = cdr_size(Image, vga)
print(S, S * 30 / 1e6)                              # 921652 bytes, 27.6 MB/s at 30 Hz
```

**Physical meaning.** $B$ is the load on a wire (bytes per second), on a memory bus (every copy of a message costs $S$ bytes of memory traffic) and on a CPU (serialization and copying scale with $S$). The unit conversion to remember: a link of $x$ Gbit/s carries at most $125x$ MB/s.

**Example.** A 450-beam lidar at 15 Hz has messages of 1 860 bytes, and a 900-beam lidar at 40 Hz with 4 bytes per range and no intensities has messages of 3 660 bytes. Compare their bandwidths and find the larger one as a share of a gigabit link (125 MB/s).

**Solution.** The first needs $1\,860\cdot15=27\,900$ B/s $=27.9$ kB/s. The second needs $3\,660\cdot40=146\,400$ B/s $=146.4$ kB/s, which is $146.4/27.9=5.2$ times more. Against the link, $146\,400/125\,000\,000=0.12$ %. So for lidar the CPU cost of the callback matters long before the wire does.

### Quality of service: request versus offered

A QoS profile is a bundle of policies. For compatibility four of them matter, and each is a *chain*, a set of values ordered by strength. The Jazzy QoS page states the rule in words: a subscription requests the "minimum quality" it will accept, a publisher offers the "maximum quality" it can provide, and "connections are only made if every policy of the requested QoS profile is not more stringent than that of the offered QoS profile". The next result derives that rule and the table that follows from it.

| Policy | Values from weakest to strongest | Meaning of the stronger value |
|---|---|---|
| Reliability | `BEST_EFFORT` < `RELIABLE` | samples are retransmitted instead of lost |
| Durability | `VOLATILE` < `TRANSIENT_LOCAL` | the publisher stores samples for late-joining subscriptions |
| Deadline | $\infty$ (default) > $d$ | a new sample appears at least every $d$ seconds (a smaller $d$ is stronger) |
| Liveliness | `AUTOMATIC` < `MANUAL_BY_TOPIC` | the publisher must assert it is alive itself; with a lease duration $\lambda$ (smaller is stronger) |

**Proof.** (Claim: for each ordered policy, the pair (offered $o$, requested $r$) is safe if and only if $o\ge r$ in the strength order; the connection is made if and only if all policies are safe.) Model a *behaviour* as everything a subscriber can observe from one publisher: which samples arrive, when, and whether old samples are replayed. An offer $o$ is a promise: the publisher can only produce behaviours in a set $\mathrm{Poss}(o)$. A request $r$ is a requirement: the subscriber's code is correct only for behaviours in a set $\mathrm{Ok}(r)$. The connection is *safe* when every behaviour that can occur is one the subscriber tolerates: $\mathrm{Poss}(o)\subseteq\mathrm{Ok}(r)$. Check each policy.

*Reliability.* $\mathrm{Poss}(\text{RELIABLE})$ and $\mathrm{Ok}(\text{RELIABLE})$ are the runs in which every sample still held in the history is delivered, in order; call this set $C$. $\mathrm{Poss}(\text{BEST\_EFFORT})$ and $\mathrm{Ok}(\text{BEST\_EFFORT})$ are all runs, $\mathcal A\supsetneq C$ (losses allowed). The four inclusions are $C\subseteq C$, $C\subseteq\mathcal A$, $\mathcal A\subseteq\mathcal A$, all true, and $\mathcal A\subseteq C$, false (a run that loses one sample). So only (offered BEST_EFFORT, requested RELIABLE) is unsafe.

*Durability.* A volatile publisher produces runs without replay, $N_0$; a transient-local publisher produces runs in which a late joiner receives the stored samples, $R$. A volatile request tolerates both, $\mathrm{Ok}(\text{VOLATILE})=N_0\cup R$; a transient-local request requires the replay, $\mathrm{Ok}(\text{TRANSIENT\_LOCAL})=R$. Then $N_0\subseteq N_0\cup R$, $R\subseteq N_0\cup R$, $R\subseteq R$ hold and $N_0\subseteq R$ fails (a late joiner that receives nothing). *Liveliness.* A publisher with `AUTOMATIC` liveliness is kept alive by the system whenever any publisher of its node publishes; call the runs of such a publisher $A$. A publisher with `MANUAL_BY_TOPIC` must be asserted by the application for each topic; call its runs $M$. A request for `AUTOMATIC` tolerates both, $\mathrm{Ok}(\text{AUTOMATIC})=A\cup M$; a request for `MANUAL_BY_TOPIC` requires the per-topic assertion, $\mathrm{Ok}(\text{MANUAL\_BY\_TOPIC})=M$. Then $A\subseteq A\cup M$, $M\subseteq A\cup M$ and $M\subseteq M$ hold and $A\subseteq M$ fails, so only (offered `AUTOMATIC`, requested `MANUAL_BY_TOPIC`) is unsafe. The lease duration bounds the gap between assertions and is treated exactly like the deadline.

*Deadline.* Let $\mathrm{Poss}(d_o)$ and $\mathrm{Ok}(d_r)$ be the runs in which every gap between consecutive samples is at most $d_o$, respectively $d_r$ (with $d=\infty$ allowing every run). If $d_o\le d_r$ every gap bounded by $d_o$ is bounded by $d_r$, so the inclusion holds. If $d_o>d_r$, take a run whose gaps all equal a value $g$ with $d_r<g\le d_o$ (any $g>d_r$ if $d_o=\infty$): it belongs to $\mathrm{Poss}(d_o)$ and not to $\mathrm{Ok}(d_r)$, so the inclusion fails. Hence safe if and only if $d_o\le d_r$, and the lease duration is identical.

*Several policies.* A behaviour is a tuple of one component per policy, and the sets above are products over the policies. A product of non-empty sets is contained in another product if and only if each factor is contained, so the connection is safe if and only if every policy is safe. $\square$ (The "request versus offered" model is the DDS rule that the ROS 2 page documents; the Jazzy page states the table and the "not more stringent" principle but does not derive them; the proof shows that the table follows from this reading of offer and request.)

The result gives the 2×2 tables of the Jazzy page. Reliability and durability each have exactly one failing cell; for deadline, offered "default" ($\infty$) against a requested finite $x$ fails, offered $x$ against requested $y$ passes iff $x\le y$. The compatibility matrix figure below shows the four reliability and four durability cells and the deadline rule.

![Two 2 by 2 compatibility matrices, reliability and durability, with publisher offers on one axis and subscription requests on the other: only best-effort offered with reliable requested, and volatile offered with transient-local requested, are crossed out; a number line shows that an offered deadline of 0.2 seconds fails a request of 0.1 seconds](/lesson-figures/S03-3.svg)

*Figure: compatibility is "offered at least as strong as requested". The two red cells fail for reliability and durability; on the deadline line, an offer of 0.2 s fails a request of 0.1 s because a run with 0.2 s gaps is possible but not tolerated.*

**Counterexamples and limits.** Compatibility is about the *declared* profiles, not about the real behaviour. A 5 Hz publisher that offers a 0.1 s deadline is compatible with a subscription that requests 0.1 s, yet it misses its own deadline at every sample (the "offered deadline missed" event of the QoS page). Compatibility also does not say that data flows well: a connected pair with `RELIABLE` still loses samples when the subscription queue overflows, as the next subsection shows. In `rclpy` a duration field equal to `Duration()` (0) means "not set", that is $\infty$, not a deadline of 0 s. Finally, an incompatible pair is not an error in either node; on ROS 2 Humble, with a best-effort publisher and a reliable subscription on `std_msgs/String`, both nodes logged a warning of the form "New subscription discovered on topic ..., requesting incompatible QoS. No messages will be sent to it. Last incompatible policy: RELIABILITY", the publisher reported 0 matched subscriptions and 0 of 5 messages arrived; swapping the two profiles delivered 5 of 5.

**Example.** A camera driver publishes with the sensor-data profile (`BEST_EFFORT`, depth 5, `VOLATILE`) and a node subscribes with the default profile (`RELIABLE`, depth 10, `VOLATILE`). Do they connect? What fixes it, and would a requested 0.1 s deadline change the result?

**Solution.** The publisher offers `BEST_EFFORT` and the subscription requests `RELIABLE`. Offered reliability is weaker than requested, so the pair is incompatible and the image topic looks empty. Changing the subscription to the sensor-data profile makes every policy safe. If the subscription also requested a 0.1 s deadline, the pair would still fail because the driver offers the default $\infty$, which is weaker than 0.1 s.

### Four views: QoS compatibility

**Algebra.** Encode each policy as a number in its strength order (BEST_EFFORT 0, RELIABLE 1; VOLATILE 0, TRANSIENT_LOCAL 1; deadlines compared by $d_o\le d_r$). The pair is connected iff $o_i\ge r_i$ for every policy $i$, a conjunction of inequalities.

**Geometry.** For two policies the possibilities form a grid whose cells are (offer, request); the safe cells lie on and below the diagonal in the strength order. The matrix figure draws it. For the deadline the picture is a number line with the offered value to the left of the requested one.

**Code.** The compatibility test is a loop of comparisons; this is the version used by the reference implementation:

```python
REL = {"BEST_EFFORT": 0, "RELIABLE": 1}
def reliability_ok(offered, requested):
    return REL[offered] >= REL[requested]

print(reliability_ok("BEST_EFFORT", "RELIABLE"), reliability_ok("RELIABLE", "BEST_EFFORT"))   # False True
```

**Physical meaning.** The policies encode physical needs: a controller that must not miss a command asks for `RELIABLE`; a camera that must not fall behind offers `BEST_EFFORT`; a map server that must give its map to nodes that start later offers `TRANSIENT_LOCAL`; a safety watchdog requests a deadline because silence from a sensor is itself a fault.

**Example.** A lidar offers `BEST_EFFORT` and `VOLATILE`. Three subscribers request (`BEST_EFFORT`, `VOLATILE`), (`RELIABLE`, `VOLATILE`) and (`BEST_EFFORT`, `TRANSIENT_LOCAL`). Which of them connect?

**Solution.** Each pair is checked policy by policy against the offer. The first requests nothing stronger than offered: connected. The second requests `RELIABLE` but `BEST_EFFORT` is offered: reliability fails. The third requests `TRANSIENT_LOCAL` but `VOLATILE` is offered: durability fails. Only the first connects, and the verdict for each pair does not depend on the others.

### Queues, depth and drops

A subscription has a queue of depth $N$ (history `KEEP_LAST`, depth $N$; the ROS 2 default is 10). The Jazzy page on executors states that an incoming message "is not stored in a queue on the Client Library layer but kept in the middleware until it is taken for processing by a callback function", and this lesson identifies that middleware queue with the queue of the model (assumption (v) below).

**Model.** The publisher writes sample $k=0,1,2,\dots$ at time $kT_p$, with $T_p=1/f_p$. When a sample arrives and the queue already holds $N$ samples, the *oldest* is discarded (dropped). The consumer, an executor thread running a callback, takes the *oldest* queued sample at the times $mT_c$, $m=1,2,\dots$, where $T_c=1/f_c$ is the time one callback occupies the executor when the queue is never empty. Assume $f_c<f_p$, that is $T_c>T_p$, and when a take and an arrival coincide, the take comes first. Samples are stamped when written, so the *age* of a delivered sample is the time of its take minus its write time, with zero transport delay.

**Assumptions.** (i) The first take is at $T_c$; another phase shifts the bound on the first drop but not the age bounds. (ii) The periods are deterministic; with jitter the lemma and the bounds shift by up to the size of the jitter. (iii) The age is measured at the take, so callback time is not included: in Case 2 the callback adds 0.05 s, giving 0.350 to 0.383 s and 0.383 m of motion when the processing ends. (iv) The transport delay is zero; a 2.76 MB frame takes about 22 ms at gigabit line rate (see the message-size subsection). (v) Taking the reader history of depth $N$ in the middleware as the queue of the model is the reading used in this lesson, supported by the measurements below, not a sentence of the ROS 2 documentation.

**Lemma.** The queue is never empty at a take. *Proof.* Induction over the takes. Before take 1 at time $T_c>T_p$ the samples written at 0 and $T_p$ have arrived and nothing was taken; an arrival never leaves the queue empty (a full queue drops one and adds one, so it stays at $N\ge1$), so the queue holds at least one sample. If take $m$ found a sample and removed it, the open interval $(mT_c,(m+1)T_c)$ is longer than $T_p$ and therefore contains an arrival, after which the queue is non-empty again; so take $m+1$ also finds a sample. $\square$

**Proof.** (Claim 1, no drops at first and a bound on the first drop; Claim 2, the long-run drop fraction.) Let $r=f_c/f_p<1$. Just after arrival $k$ and before any drop, the queue length is $L_k=(k+1)-\lfloor kr\rfloor$: $k+1$ arrivals so far, and $\lfloor kT_p/T_c\rfloor=\lfloor kr\rfloor$ takes. The first drop happens at the first $k$ with $L_k>N$, that is $k-\lfloor kr\rfloor\ge N$. From $kr-1<\lfloor kr\rfloor\le kr$ we get $k(1-r)\le k-\lfloor kr\rfloor<k(1-r)+1$. If $k-\lfloor kr\rfloor\ge N$ then $k(1-r)+1>N$, so $k>(N-1)/(1-r)$; if $k(1-r)\ge N$ then $k-\lfloor kr\rfloor\ge N$. Hence the first drop is at an index $k^*$ with $(N-1)/(1-r)<k^*<N/(1-r)+1$, and since $T_p/(1-r)=1/(f_p-f_c)$ its time satisfies
$$\frac{N-1}{f_p-f_c}<t^*=k^*T_p<\frac{N}{f_p-f_c}+T_p .$$
For the long run, every take delivers a sample (Lemma), so by time $t$ exactly $C(t)=\lfloor tf_c\rfloor$ samples have been delivered. If $A(t)=\lfloor tf_p\rfloor+1$ samples were written and $L(t)\in[0,N]$ remain queued, conservation gives $D(t)=A(t)-C(t)-L(t)$ dropped samples. Dividing by $A$ and letting $t\to\infty$: $C/A\to f_c/f_p$ and $L/A\le N/A\to0$, so
$$\frac{D}{A}\to1-\frac{f_c}{f_p},$$
and the delivered rate is $f_c$, independent of $N$. More precisely $|D/A-(1-f_c/f_p)|<(N+2)/A$, because $0\le A\,f_c/f_p-C<1+f_c/f_p<2$ and $0\le L\le N$. $\square$

The depth $N$ does not change the long-run loss. It only delays the first drop: the queue gains $f_p-f_c$ samples per second, so it fills in about $N/(f_p-f_c)$ seconds ($1$ s for the numbers of the explore block below).

**Proof.** (Claim 3: once drops have started, every delivered sample has age $a$ with $(N-1)T_p<a\le NT_p$.) Right after the first drop the queue holds $N$ samples. At a take one is removed, leaving $N-1$; the next take is $T_c>T_p$ later, and the open interval between two takes is longer than $T_p$ and contains at least one arrival, so the queue is back at $N$ at the next take. By induction every take finds $N$ queued samples, the $N$ most recent writes, say with indices $j-N+1,\dots,j$, where $j$ is the last arrival strictly before the take time $\tau$. The consumer takes the oldest, index $j-N+1$, whose age is $\tau-(j-N+1)T_p=(\tau-jT_p)+(N-1)T_p$. Since $j$ is the last arrival before $\tau$, $0<\tau-jT_p\le T_p$, which gives the bounds. $\square$

So a deep queue on a slow consumer turns *drops* into *delay*: the loss fraction is unchanged but every sample processed is about $N$ periods old. For $N=1$ the age is at most one period. The product of age and speed is a position error: at $v=1$ m/s a consumer that sees samples $0.333$ s old acts on a world that has moved $0.333$ m.

**Counterexamples.** (a) If $f_c\ge f_p$ there are no drops and no standing queue: in the simulation with $f_p=20$ Hz, $f_c=30$ Hz and depth 5 the drop count is 0 and every age is at most $T_c=0.033$ s (for a consumer that polls at its own rate; an event-driven executor wakes at the arrival and the age is close to 0). The claims above need $f_c<f_p$. (b) With `KEEP_ALL` (no bound) nothing is dropped but the backlog grows by $(f_p-f_c)$ samples per second, and the age of the delivered sample grows by $(T_c-T_p)$ per take: a 30 Hz producer and a 20 Hz consumer gives a delivered age of $1200\cdot(0.05-1/30)=20$ s after one minute, and memory grows without limit. (c) A depth buys tolerance of a *stall*: a consumer blocked for $\tau$ seconds with an empty queue loses $\max(0,\,f_p\tau-N)$ samples. With a stall of $\tau=0.5$ s at 30 Hz and depth 10, $15-10=5$ samples are lost. Freshness requires $N/f_p\le\lambda_{\max}$ and surviving the stall requires $N\ge f_p\tau$; both hold only if $\tau\le\lambda_{\max}$, so no queue depth can absorb a stall longer than the latency the application tolerates. (d) The proofs assume the consumer takes the oldest sample; a consumer that drains the queue and keeps only the newest behaves like $N=1$.

**Example.** A 40 Hz producer feeds a callback that takes 0.1 s ($f_c=10$ Hz) with depth 5. Find the drop fraction, the time of the first drop and the range of delivered ages, and compare them with real `rclpy` nodes at depths 1, 5 and 20.

**Solution.** The drop fraction tends to $1-10/40=75\,\%$. The first drop occurs between $(5-1)/30=0.133$ s and $5/30+0.025=0.192$ s; the exact simulation gives 0.150 s (the first $k$ with $k-\lfloor k/4\rfloor\ge5$ is 6, and $6/40=0.15$). Delivered ages lie in $(0.100,\,0.125]$ s. Real `rclpy` nodes on ROS 2 Humble (publisher in another process, reliable, 8 s of publishing; the script `queue_probe.py` is in the Library track) agree in steady state, with the start-up and the drain after the publisher stops excluded: depth 1 gives a mean age of 0.013 s (0.001 to 0.025 s; model $(0,0.025]$), depth 5 gives 0.112 s (0.101 to 0.125 s; model $(0.100,0.125]$) and depth 20 gives 0.488 s (0.476 to 0.501 s; model $(0.475,0.500]$). The delivered counts (81, 84 and 99, against about 80 expected from $f_c$) include the drain: after the publisher stops, the callback still takes the up to $N$ samples left in the queue, so the count grows with the depth. These runs support the identification of the model's queue with the reader history of depth $N$.

### Four views: the KEEP_LAST queue

**Algebra.** Rates give the whole story: loss $1-f_c/f_p$, first drop at about $N/(f_p-f_c)$, age between $(N-1)/f_p$ and $N/f_p$. The only free design choices are $N$ (and, through the callback, $f_c$).

**Geometry.** Plot the number of queued samples against time: it climbs with slope $f_p-f_c$ from the first sample, reaches $N$ at $t^*$, and then stays at the ceiling $N$ while the cumulative drop count grows with slope $f_p-f_c$. The worked-example figure draws this staircase for the numbers of Case 2 and marks the age of a delivered sample.

**Code.** The simulation of the reference implementation reproduces all three numbers:

```python
from s03_pubsub import simulate
r = simulate(30, 20, 10, 60)
print(r["dropped"] / r["published"])               # 0.3282 (591 of 1801), tends to 1 - 20/30 = 0.3333
print(r["first_drop_s"])                           # 0.9333, inside (0.900, 1.033)
ages = [a for t, a in r["ages"] if t > r["first_drop_s"]]
print(min(ages), max(ages))                        # 0.3167 0.3333, inside (0.300, 0.333]
```

**Physical meaning.** $f_c$ is set by the callback duration (image processing, a service call, a lock) and the executor; $N$ is memory spent on holding old data. Age is seconds of delay between the world and the robot's decision, so $N/f_p$ is added to every other term of the latency budget.

**Example.** A lane-detection callback needs 80 ms per camera frame and the camera runs at 30 Hz. Find the fraction of dropped frames, the age of the processed frame with the default depth 10 and with depth 1, and the resulting lag at 0.5 m/s.

**Solution.** The callback rate is $f_c=1/0.08=12.5$ Hz, so $1-12.5/30=58.3\,\%$ of the frames are dropped regardless of $N$. With the default depth 10 the processed frame is between $9/30=0.300$ s and $10/30=0.333$ s old; with depth 1 it is at most $1/30=0.033$ s old. At 0.5 m/s that is a lag of $0.5\cdot0.033=1.7$ cm instead of $0.5\cdot0.333=16.7$ cm.

### How the pieces connect

Discovery (Jazzy page "Discovery") is the process that finds endpoints and applies the matching rule of the first subsection, repeatedly, so a node started later is connected too; S05 continues from here with executors, callback groups and measured delay and loss. Stamps and latency matter wherever data from different sensors is combined, for example transforms between the frames of S04, which are stamped and looked up by time. Message sizes lead to rosbag recording rates and to choosing compressed transports. The queue results are the first example of a general rule of data-flow systems: a stage with service rate below the arrival rate either loses data or accumulates delay, and a buffer only chooses which of the two happens first.

## Worked example

### Case 1: counting stamps in an odometer

**Problem.** A teleop node publishes `geometry_msgs/Twist` on `/cmd_vel` at 10 Hz with `linear.x = 0.5` m/s for 2 s; the first message is published at $t=0$. An odometer node subscribes and integrates $x\mathrel{+}=v\,\Delta t$ with $\Delta t$ taken from message stamps. Find the distance, the measured rate, the rate and missing count if three messages in the middle are lost, the effect of a unit error (50 meaning cm/s) and the payload bandwidth.

**Solution.**

1. A 10 Hz timer has $T=1/f=0.1$ s (the Rates subsection). Stamps $0,0.1,\dots,2.0$ s give 21 messages, hence $n-1=20$ intervals.
2. Integrate each interval with the speed of the message that ends it: $x=20\cdot0.5\ \text{m/s}\cdot0.1\ \text{s}=1.0$ m. The first message has no predecessor and contributes no distance.
3. The measured rate is $(n-1)/\Delta t=(21-1)/2.0=10$ Hz.
4. If three messages in the middle are lost, 18 stamps span the same 2 s: $(18-1)/2=8.5$ Hz. The gap in the stamps is $4T=0.4$ s, so the rule gives $\mathrm{round}(0.4/0.1)-1=3$ missing.
5. If the sender publishes 50 meaning cm/s into a field documented as m/s, the receiver computes $50\cdot2=100$ m instead of $1$ m, a factor of 100, with the name, type and QoS all matching.
6. Payload bandwidth: 48 B $\times$ 10 Hz $=480$ B/s; with the 4-byte CDR header, $S=52$ B and $B=520$ B/s.

**Check.** The common off-by-one, $\Delta t=0.1$ s for all 21 messages, gives $21\cdot0.5\cdot0.1=1.05$ m, a $5\,\%$ error (21/20 = 1.05), so the counting of intervals matters. A Python run of the lesson's `integrate` gives exactly 1.0 for 21 integer-nanosecond stamps.

**Takeaway.** $n$ stamps bound $n-1$ intervals, and no type system can detect a wrong unit.

### Case 2: a 30 Hz camera and a 50 ms callback

**Problem.** A camera publishes `sensor_msgs/Image` 1280×720, `rgb8`, `frame_id` "camera", at $f_p=30$ Hz. A subscription with the default depth $N=10$ runs a callback that takes 50 ms per frame (so $f_c=20$ Hz) on a robot driving at 1 m/s. Find (a) the bandwidth, (b) the long-run fraction of dropped frames and the delivered rate, (c) the time of the first drop, (d) the age of the frame being processed and the distance the robot moved meanwhile, (e) the effect of depth 1.

**Solution.**

1. *Size and bandwidth.* With the CDR rules of the message-size subsection, $S=4+8+11+1+4+4+9+1+2+4+4+2\,764\,800$ (header, stamp, `frame_id`, one pad byte, `height`, `width`, `encoding`, `is_bigendian`, two pad bytes, `step`, the sequence count, the data); the fixed part is 52 bytes, so $S=1280\cdot720\cdot3+52=2\,764\,852$ B and $B=Sf=2\,764\,852\cdot30=82.9$ MB/s, which is 66 % of a 125 MB/s link.
2. *Which regime.* $f_c=1/0.05=20$ Hz is below $f_p=30$ Hz, so the queue claims apply.
3. *Loss.* The drop fraction tends to $1-f_c/f_p=1-20/30=33.3\,\%$ and the delivered rate is $f_c=20$ Hz, whatever the depth. In a 60 s exact simulation 591 of 1801 samples were dropped, 32.8 %, within the bound $(N+2)/A=12/1801=0.7\,\%$ of the limit.
4. *First drop.* The queue gains $f_p-f_c=10$ samples/s, so it fills in about $N/(f_p-f_c)=1.0$ s; the proof gives $(N-1)/(f_p-f_c)=0.900<t^*<N/(f_p-f_c)+T_p=1.033$ s. Exactly: the first $k$ with $k-\lfloor 2k/3\rfloor\ge10$ is $k=28$, so $t^*=28/30=0.933$ s.
5. *Age.* Every delivered frame has age in $((N-1)T_p,\,NT_p]=(0.300,\,0.333]$ s; the simulation gave values between 0.317 and 0.333 s. At 1 m/s the robot moved about $0.333$ m since the image was exposed.
6. *Depth 1.* The loss stays $33.3\,\%$ (it does not depend on $N$), but the age is at most $T_p=0.033$ s, so the lag shrinks to 0.033 m.

**Check.** The simulation of the reference implementation (`simulate(30, 20, 10, 60)`) gives the numbers above; the same procedure with 40 Hz, 0.1 s and depth 5 was compared with real `rclpy` nodes in steady state (ages 0.101 to 0.125 s, mean 0.112 s, against the predicted $0.100$ to $0.125$ s). The units: samples/s times seconds gives samples, metres per second times seconds gives metres.

**Takeaway.** A deep queue on a slow subscriber loses the same fraction of frames as a shallow one, and makes every processed frame a third of a second stale.

### Case 3: a QoS mismatch on the camera topic

**Problem.** The camera driver offers the sensor-data profile: `BEST_EFFORT`, `VOLATILE`, depth 5 and no deadline. Three nodes subscribe: A with the default profile (`RELIABLE`, `VOLATILE`, depth 10), B with `BEST_EFFORT`, `VOLATILE` and a requested deadline of 0.05 s, C with `BEST_EFFORT`, `VOLATILE` and a deadline of 0.1 s. Which connect? What is the smallest change to the driver that connects B and C, and what does it promise?

**Solution.**

1. For each pair apply the rule "offered at least as strong as requested" (the QoS proof) policy by policy.
2. A: reliability offered `BEST_EFFORT` (0) against requested `RELIABLE` (1): $0<1$, unsafe. Not connected, whatever the other policies say. The depth is irrelevant to compatibility.
3. B: reliability $0\ge0$ and durability $0\ge0$ are fine; the deadline offered is $\infty$ (default) against requested $0.05$ s: $\infty>0.05$, unsafe.
4. C: the same, $\infty>0.1$, unsafe. So none connects.
5. Repair: the driver offers a deadline $d_o$ with $d_o\le0.05$ s, the strictest request, for example $0.04$ s. Then $0.04\le0.05$ and $0.04\le0.1$, so B and C connect; A still does not, and needs to change its subscription to `BEST_EFFORT` (or the driver to `RELIABLE`).
6. The promise: at 30 Hz the nominal gap is $T=33.3$ ms, inside 40 ms, so the driver is allowed 6.7 ms of jitter per sample before it reports "offered deadline missed".

**Check.** `rclpy.qos.qos_check_compatible` on ROS 2 Humble returns an error for A (best-effort publisher with reliable subscription), an error for B and C before the repair (subscription has a deadline, publisher does not) and a pass (a warning only about the unset liveliness) for B and C after it, which is the same verdict as the rule. A run with real nodes confirmed the reliability case: 0 of 5 messages arrived and both nodes logged "incompatible QoS ... RELIABILITY".

**Takeaway.** Compatibility is a check of declared promises policy by policy; the failing policy is named in the log, and the fix is to change the weakest side that can honestly make the promise.

```python
class Bus:
    def __init__(self):
        self.subs = {}
    def subscribe(self, topic, mtype, cb):
        self.subs.setdefault(topic, []).append((mtype, cb))
    def publish(self, topic, mtype, msg):
        n = 0
        for t, cb in self.subs.get(topic, []):
            if t == mtype:
                cb(msg); n += 1
        return n

def integrate(stamps_ns, speed):
    """Distance from stamps: each interval uses the speed of the message ending it."""
    return sum(speed * (b - a) * 1e-9 for a, b in zip(stamps_ns, stamps_ns[1:]))

bus, got = Bus(), []

assert bus.publish("/cmd_vel", "Twist", {"vx": 0.5}) == 1
assert bus.publish("/cmd_vel", "String", {}) == 0          # mismatch: nothing delivered
stamps = [k * 100_000_000 for k in range(21)]
assert abs(integrate(stamps, 0.5) - 1.0) < 1e-9
print("reference ok")
```

### From scratch: typed messages, QoS compatibility and KEEP_LAST queues

The module below is the whole model of the Theory section in plain Python: message types with a CDR size calculator, a `QoS` profile with the compatibility test, a graph that matches endpoints by name, type and QoS (and replays stored samples to late `TRANSIENT_LOCAL` joiners), subscription queues with `KEEP_LAST` depth, and the producer/slow-consumer experiment in exact rational time. Save it as `s03_pubsub.py`; no ROS installation is needed.

```python
from collections import deque
from dataclasses import dataclass, replace
import math

INF = math.inf
REL = {"BEST_EFFORT": 0, "RELIABLE": 1}              # ordered: a larger value is a stronger guarantee
DUR = {"VOLATILE": 0, "TRANSIENT_LOCAL": 1}
LIVE = {"AUTOMATIC": 0, "MANUAL_BY_TOPIC": 1}

@dataclass(frozen=True)
class QoS:
    depth: int = 10
    reliability: str = "RELIABLE"
    durability: str = "VOLATILE"
    deadline_s: float = INF        # offered: promised max gap between writes; requested: tolerated gap
    liveliness: str = "AUTOMATIC"
    lease_s: float = INF

def qos_compatible(offered, requested):
    """(ok, violated): the connection is safe iff, for every policy, offered is at least as strong as requested."""
    bad = []
    if REL[offered.reliability] < REL[requested.reliability]: bad.append("reliability")
    if DUR[offered.durability] < DUR[requested.durability]: bad.append("durability")
    if offered.deadline_s > requested.deadline_s: bad.append("deadline")
    if LIVE[offered.liveliness] < LIVE[requested.liveliness]: bad.append("liveliness")
    if offered.lease_s > requested.lease_s: bad.append("liveliness lease")
    return not bad, bad

# ---- typed messages and their CDR size ------------------------------------------------------
PRIM = {"uint8": 1, "int32": 4, "uint32": 4, "float32": 4, "float64": 8}   # size == alignment

class MsgType:
    def __init__(self, name, fields):
        self.name, self.fields = name, fields           # fields: [(field, type)]
    def __repr__(self): return self.name

def _align(off, a): return (off + a - 1) // a * a

def _walk(t, v, off):
    if isinstance(t, MsgType):
        for fname, ft in t.fields: off = _walk(ft, v[fname], off)
        return off
    if t == "string":
        return _align(off, 4) + 4 + len(v.encode()) + 1          # length, characters, NUL
    if isinstance(t, tuple) and t[0] == "seq":                   # variable-length sequence
        off = _align(off, 4) + 4
        return _align(off, PRIM[t[1]]) + PRIM[t[1]] * len(v) if len(v) else off
    if isinstance(t, tuple) and t[0] == "arr":                   # fixed-size array: no length prefix
        return _align(off, PRIM[t[1]]) + PRIM[t[1]] * t[2]
    return _align(off, PRIM[t]) + PRIM[t]

def cdr_size(t, v):
    """Serialized bytes: 4-byte encapsulation header, then fields aligned to their own size."""
    return 4 + _walk(t, v, 0)

Time = MsgType("builtin_interfaces/Time", [("sec", "int32"), ("nanosec", "uint32")])
Header = MsgType("std_msgs/Header", [("stamp", Time), ("frame_id", "string")])
Vec3 = MsgType("geometry_msgs/Vector3", [("x", "float64"), ("y", "float64"), ("z", "float64")])
Quat = MsgType("geometry_msgs/Quaternion", [(k, "float64") for k in "xyzw"])
Twist = MsgType("geometry_msgs/Twist", [("linear", Vec3), ("angular", Vec3)])
Imu = MsgType("sensor_msgs/Imu", [
    ("header", Header), ("orientation", Quat), ("orientation_covariance", ("arr", "float64", 9)),
    ("angular_velocity", Vec3), ("angular_velocity_covariance", ("arr", "float64", 9)),
    ("linear_acceleration", Vec3), ("linear_acceleration_covariance", ("arr", "float64", 9))])
LaserScan = MsgType("sensor_msgs/LaserScan", [
    ("header", Header)] + [(k, "float32") for k in
    ("angle_min", "angle_max", "angle_increment", "time_increment", "scan_time", "range_min", "range_max")] +
    [("ranges", ("seq", "float32")), ("intensities", ("seq", "float32"))])
Image = MsgType("sensor_msgs/Image", [
    ("header", Header), ("height", "uint32"), ("width", "uint32"), ("encoding", "string"),
    ("is_bigendian", "uint8"), ("step", "uint32"), ("data", ("seq", "uint8"))])

def blank(t, **sizes):
    """A zero-filled value of type t; sizes gives lengths of sequences and strings by field name."""
    if isinstance(t, MsgType): return {f: blank(ft, **sizes) if not (f in sizes) else _fill(ft, sizes[f]) for f, ft in t.fields}
    return "" if t == "string" else [] if isinstance(t, tuple) else 0
def _fill(ft, n): return "x" * n if ft == "string" else [0] * n

# ---- the graph: discovery by name + type + QoS, KEEP_LAST queues ------------------------------
class Subscription:
    def __init__(self, topic, mtype, qos):
        self.topic, self.mtype, self.qos = topic, mtype, qos
        self.queue, self.dropped, self.received = deque(), 0, 0
    def _push(self, item):
        self.received += 1
        if len(self.queue) == self.qos.depth:          # KEEP_LAST: discard the OLDEST sample
            self.queue.popleft(); self.dropped += 1
        self.queue.append(item)
    def take(self):
        """Oldest queued (stamp_ns, msg), or None: what an executor does before calling the callback."""
        return self.queue.popleft() if self.queue else None

class Publication:
    def __init__(self, graph, topic, mtype, qos):
        self.graph, self.topic, self.mtype, self.qos = graph, topic, mtype, qos
        self.history, self.subs = deque(maxlen=qos.depth), []
    def publish(self, msg, stamp_ns):
        if self.qos.durability == "TRANSIENT_LOCAL": self.history.append((stamp_ns, msg))
        for s in self.subs: s._push((stamp_ns, msg))
        return len(self.subs)

class Graph:
    def __init__(self, remap=None):
        self.remap, self.pubs, self.subs, self.log = remap or {}, [], [], []
    def _resolve(self, name): return self.remap.get(name, name)
    def _match(self, p, s):
        if p.topic != s.topic or p.mtype is not s.mtype: return           # name and type first
        ok, bad = qos_compatible(p.qos, s.qos)                            # then QoS
        if not ok:
            self.log.append(f"{p.topic}: incompatible QoS ({', '.join(bad)}); no messages will be sent")
            return
        p.subs.append(s)
        if s.qos.durability == "TRANSIENT_LOCAL":                         # late joiner gets the stored history
            for item in p.history: s._push(item)
    def create_publisher(self, topic, mtype, qos=QoS()):
        p = Publication(self, self._resolve(topic), mtype, qos); self.pubs.append(p)
        for s in self.subs: self._match(p, s)
        return p
    def create_subscription(self, topic, mtype, qos=QoS()):
        s = Subscription(self._resolve(topic), mtype, qos); self.subs.append(s)
        for p in self.pubs: self._match(p, s)
        return s

# ---- the producer / slow consumer experiment, in exact rational time -------------------------
from fractions import Fraction

def simulate(fp, fc, depth, duration_s):
    """Publisher writes at fp Hz from t=0; the consumer takes one message at m/fc, m=1,2,... (take first on a tie).
    fp and fc are integers (Hz). Returns counts, the first drop time and (take time, age) pairs in seconds."""
    g = Graph(); q = QoS(depth=depth, reliability="BEST_EFFORT")
    pub = g.create_publisher("/x", Header, q); sub = g.create_subscription("/x", Header, q)
    Tp, Tc, end = Fraction(1, fp), Fraction(1, fc), Fraction(duration_s)
    k, m, ages, first_drop = 0, 1, [], None
    while min(k * Tp, m * Tc) <= end:
        if m * Tc <= k * Tp:                           # consumer take
            item = sub.take()
            if item: ages.append((float(m * Tc), float(m * Tc - item[0])))
            m += 1
        else:
            before = sub.dropped
            pub.publish({}, k * Tp); k += 1
            if sub.dropped > before and first_drop is None: first_drop = float((k - 1) * Tp)
    return dict(published=k, delivered=len(ages), dropped=sub.dropped, ages=ages,
                first_drop_s=first_drop, left=len(sub.queue))
```

### What the library does differently

- **Discovery.** Here a match is computed the instant an endpoint is created. In ROS 2 the middleware (DDS or Zenoh) finds endpoints by exchanging discovery messages, and nodes "periodically advertise their presence" (Discovery page), so a match can take from milliseconds to seconds and can change while the system runs.
- **Serialization.** The real type support is generated from the `.msg` files and covers every primitive (`bool`, `int16`, `int64`, `wstring`), bounded sequences, arrays of messages and nested types; `cdr_size` handles only the subset used here, and the real wire format adds RTPS headers, fragments large samples and may use shared memory instead of the network. Measured sizes always come from `serialize_message`.
- **QoS.** The middleware checks more policies than the five modelled here, applies resource limits to history and reports the outcome as events: `rclpy.event_handler.SubscriptionEventCallbacks` has an `incompatible_qos` callback and, in Jazzy, an `incompatible_type` callback; `rclpy.qos.qos_check_compatible` returns the verdict and a message, with a "warning" result when a policy is `SYSTEM_DEFAULT` and the middleware's default decides. Lifespan, liveliness assertions and deadline events have no counterpart here.
- **Queues and executors.** The model keeps a single queue per subscription and a consumer with a fixed period. Real nodes also have a publisher-side history, a reader history inside the middleware (the executors page says messages are "kept in the middleware until it is taken for processing by a callback function"), a wait set that tells the executor which queues hold data, callback groups, and multi-threaded executors that run several callbacks at once, so $f_c$ is not simply $1/T_c$ when callbacks overlap or when other callbacks share the thread. The steady-state ages measured on Humble (depth 5: 0.101 to 0.125 s against the model's $(0.100,0.125]$ s) fit the model; the delivered counts include the drain after publication stops.
- **Intra-process communication.** In C++ (`rclcpp`) nodes that live in one process can pass messages without serializing them, which removes the cost proportional to $S$ but not the queue.

For a check against the real thing, the Library track below runs the 10 Hz teleop on `rclpy`, and the measurement used in this section is the same experiment with a slow callback.

### Library track

ROS 2 is the "library" here. With a ROS 2 install (all runs of this lesson were made on Humble with Python 3.10 and were not repeated on Jazzy), run the real `rclpy` version of the lab: a 10 Hz teleop node, an odometer that integrates `Twist` between arrival times, and a second process that subscribes to the same topic name with the wrong type.

```python
# Run with a sourced ROS 2 install (e.g. `source /opt/ros/<distro>/setup.bash`).
import subprocess, sys, time
import rclpy
from rclpy.node import Node
from rclpy.executors import SingleThreadedExecutor
from geometry_msgs.msg import Twist, TwistStamped

class Teleop(Node):
    def __init__(self):
        super().__init__("teleop")
        self.pub = self.create_publisher(Twist, "cmd_vel", 10)
        self.timer = self.create_timer(0.1, self.tick)           # seconds: 10 Hz
    def tick(self):
        msg = Twist(); msg.linear.x = 0.5                        # m/s
        self.pub.publish(msg)

class Odom(Node):
    def __init__(self):
        super().__init__("odom")
        self.stamps_ns, self.x, self.last = [], 0.0, None
        self.create_subscription(Twist, "cmd_vel", self.on_twist, 10)
    def on_twist(self, msg):
        now = self.get_clock().now().nanoseconds                 # Twist has no stamp: use arrival time
        if self.last is not None:
            self.x += msg.linear.x * (now - self.last) * 1e-9
        self.last = now
        self.stamps_ns.append(now)

WRONG = """

    ex.add_node(n)
```

### Queue probe: steady-state age of a slow subscriber

The following script, saved as `queue_probe.py`, measures the quantities of the queue model with real nodes: a publisher at 40 Hz in a child process, a callback that sleeps 0.1 s ($f_c=10$ Hz) and a chosen depth. It reports the age of the delivered messages in steady state, excluding the first and last 25 deliveries (start-up and the drain after the publisher stops). On Humble, for depths 1, 5 and 20, it printed the ages quoted in the theory section; it was not run on Jazzy.

```python
# Steady-state age of delivered messages for a slow subscriber (needs a sourced ROS 2 install).
# Usage: ROS_LOCALHOST_ONLY=1 python3 queue_probe.py DEPTH     (Jazzy: ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST)
import statistics, subprocess, sys, time
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy
from std_msgs.msg import Header

FP, SLEEP, RUN_S = 40.0, 0.1, 8.0                     # producer rate, callback duration, publishing time
depth = int(sys.argv[1]); role = sys.argv[2] if len(sys.argv) > 2 else "main"
qos = QoSProfile(depth=depth, reliability=ReliabilityPolicy.RELIABLE)
rclpy.init()
if role == "pub":
    node = Node("probe_pub"); pub = node.create_publisher(Header, "/probe", qos)
    def tick():
        msg = Header(); msg.stamp = node.get_clock().now().to_msg(); pub.publish(msg)
    time.sleep(1.5)                                    # let discovery finish before the first sample
    timer = node.create_timer(1 / FP, tick)
    end = time.time() + RUN_S
    while time.time() < end: rclpy.spin_once(node, timeout_sec=0.01)
else:
    node = Node("probe_sub"); ages = []
    def callback(msg):
        now = node.get_clock().now().nanoseconds
        ages.append((now - (msg.stamp.sec * 10**9 + msg.stamp.nanosec)) * 1e-9)
        time.sleep(SLEEP)                              # the "slow" callback: f_c = 1 / SLEEP
    node.create_subscription(Header, "/probe", callback, qos)
    child = subprocess.Popen([sys.executable, __file__, str(depth), "pub"])
    end = time.time() + 1.5 + RUN_S + 3.0
    while time.time() < end: rclpy.spin_once(node, timeout_sec=0.01)
    child.wait()
    mid = ages[25:-25]                                 # drop the start-up and the drain after the publisher stops
    print(f"depth {depth}: delivered {len(ages)}, steady-state age mean {statistics.mean(mid):.3f} s, "
          f"min {min(mid):.3f} s, max {max(mid):.3f} s, model ({(depth-1)/FP:.3f}, {depth/FP:.3f}] s")
```

Run it with `ROS_LOCALHOST_ONLY=1 python3 queue_probe.py 5` (Humble) or `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST python3 queue_probe.py 5` (Jazzy) and compare the printed range with $((N-1)/f_p,\,N/f_p]$.

## Verification

On a real system verify names and types with `ros2 topic list -t`, matching endpoints with `ros2 topic info -v`, rate with `ros2 topic hz`, and one message with `echo --once`. Confirm every numeric field against its documented unit by publishing a known value (0.5 m/s) and reading it back where it is used. For the queue and QoS results: compare `ros2 topic info -v` (the QoS profile of each endpoint) before reasoning about missing data; compute $f_c=1/T_c$ from the callback duration and compare the delivered rate (`ros2 topic hz` inside the subscriber) with $\min(f_p,f_c)$; log $\text{now}-\text{stamp}$ in the callback and check it against $N/f_p$; compute the size of each message with `serialize_message` and the product $Sf$ against the link capacity.

## Failure modes

- Type mismatch: `Twist` published, `TwistStamped` expected; both nodes run, nothing is delivered. Check `ros2 topic info -v`.
- Name mismatch by one character or namespace: `/robot1/cmd_vel` vs `/cmd_vel`; use remapping or relative names deliberately.
- Timer period in seconds taken as Hz: `create_timer(10, ...)` runs at 0.1 Hz.
- Counting messages instead of intervals: 5 % error in the worked example.
- Unit disagreement (cm/s vs m/s): 100-fold error with no warning.
- Float seconds for stamps in long logs: resolution loss; use integer nanoseconds.
- Starting a subscriber after the data was published: with the default volatile durability it never sees old data.
- QoS mismatch (a best-effort publisher, a reliable subscription, or a requested deadline the publisher does not offer): both nodes run and the topic exists, but no samples flow; read the "incompatible QoS" warning or `ros2 topic info -v`.
- A deep queue on a slow subscriber: the loss fraction is $1-f_c/f_p$ regardless of depth, and the processed samples are about $N/f_p$ old.
- Gap counting with a jittery publisher: if the stamp jitter exceeds $T/4$ the rule $\mathrm{round}(g/T)-1$ can report messages that were never lost; use a sequence counter.
- Bursts: an average rate below the consumer's rate does not prevent drops if a burst is larger than the depth.
- Streaming raw images: 1920x1080 rgb8 at 30 Hz needs 186.6 MB/s, more than a 125 MB/s gigabit link.

## Alternatives and trade-offs

Topics are best for continuous streams; services for short request-reply with a clear result; actions for long goals with feedback; parameters for configuration that changes rarely. A single large message reduces the number of endpoints but couples unrelated consumers and makes every change a breaking one; several small messages are easier to evolve and to replay. A custom type is only worth it if existing types (`geometry_msgs`, `sensor_msgs`, `nav_msgs`) do not fit, because standard types work with every tool, bag file and visualizer. Plain function calls inside one process are simpler than topics; use topics when decoupling, introspection or distribution is worth the overhead. For a slow consumer the alternatives are a shallower queue (fresher data, same loss), a faster callback or a multi-threaded executor (higher $f_c$), a lower publication rate, or `KEEP_ALL` (no loss until memory runs out, unbounded delay); for images, a compressed transport or processing on the host that owns the camera trades CPU time for bandwidth.
