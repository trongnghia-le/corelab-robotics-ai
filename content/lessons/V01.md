## Why this matters

An image is a sampled measurement, not a perfect copy of a scene. Before using a detector, understand what the array stores: axis order, coordinate origin, channel meaning, dtype, and intensity scale. An array with the right shape can still represent the wrong colors or geometry.

## Intuition and definitions

A grayscale image often has shape (H,W), while a color image often has (H,W,C). Row index usually increases downward and column index rightward; this differs from a conventional upward Cartesian y axis. A pixel coordinate (u,v) normally means column u, row v, so indexing is image[v,u]. Declare whether pixel centers are integer positions.

![A 4 by 6 RGB image grid showing column and row axes, img[row, column] indexing, marker pixels, and notes on uint8 wrap-around and resizing](/lesson-figures/V01.svg)

*Figure: pixel (u, v) lives at img[v, u]; dtype and resizing choices change the numbers.*

## Reasoning and assumptions

An 8-bit channel has $2^8=256$ representable values, conventionally 0 through 255. Dividing by 255 maps this range into [0,1], but does not undo nonlinear camera response or guarantee linear light. RGB and BGR channel orders contain the same number of entries with different meanings. Converting to grayscale uses a declared weighting and color-space convention.

## Worked example

For a two-row, three-column RGB image, shape is (2,3,3). Pixel (u=2,v=1) is the last column of the second row, indexed [1,2]. A pure red RGB pixel [255,0,0] interpreted as BGR becomes blue. A uint8 subtraction can wrap rather than represent a negative difference; cast to a suitable floating type before arithmetic.

## Misconceptions and alternatives

Resizing changes sampling. Nearest-neighbor preserves discrete labels but can look blocky for photographs; bilinear interpolation blends nearby intensities and is generally unsuitable for category IDs in a segmentation mask. Downsampling without appropriate low-pass filtering can alias fine patterns into incorrect larger patterns.

### Tests

```python
img = markers()
assert img.shape == (4, 6, 3) and img.dtype == np.uint8
# indexing: (u, v) = (column, row); non-square image makes swaps visible
assert tuple(pixel_at(img, 1, 0)) == (255, 0, 0)
assert tuple(pixel_at(img, 4, 2)) == (0, 255, 0)
assert tuple(pixel_at(img, 5, 3)) == (0, 0, 255)
for bad in ((6, 0), (0, 4), (-1, 0)):
    try:
        pixel_at(img, *bad)
    except IndexError:
        pass
    else:
        raise AssertionError("expected IndexError")
# channel order and round trip; copy semantics
bgr = rgb_to_bgr(img)
assert tuple(bgr[0, 1]) == (0, 0, 255) and np.array_equal(rgb_to_bgr(bgr), img)
bgr[0, 0, 0] = 9
assert img[0, 0, 0] == 0
# uint8 wrap-around vs safe arithmetic
a = np.array([10, 200], dtype=np.uint8); b = np.array([20, 100], dtype=np.uint8)
assert list(a - b) == [246, 100] and list(abs_diff(a, b)) == [10, 100]

# normalisation, grey, means
assert to_float01(img).max() == 1.0 and to_float01(img).dtype == np.float64
assert abs(gray(img)[0, 1] - 0.299) < 1e-12 and abs(gray(img)[2, 4] - 0.587) < 1e-12
assert np.allclose(channel_means(img), [255 / 24] * 3)
white = np.full((2, 2, 3), 255, dtype=np.uint8)
assert np.allclose(gray(white), 1.0)                              # weights sum to 1
# resizing: nearest keeps labels, aliases stripes; box average does not
mask = np.array([[0, 0, 2, 2], [0, 0, 2, 2], [1, 1, 0, 0], [1, 1, 0, 0]], dtype=np.uint8)
small = resize_nearest(mask, 2, 2)
assert small.tolist() == [[0, 2], [1, 0]] and set(np.unique(small)) <= {0, 1, 2}
stripes = np.array([[0, 255] * 4, [0, 255] * 4], dtype=np.uint8)
assert resize_nearest(stripes, 1, 4).max() == 0               # aliasing: stripes vanish
assert np.allclose(downsample_box(stripes, 2), 127.5)         # true local mean
assert resize_nearest(img, 8, 12).shape == (8, 12, 3)
print("marker channel means:", channel_means(img).round(3), "| grey of red marker:", gray(img)[0, 1])
```

## Exercise answers

1. Shape `(1080, 1920, 3)`. `uint8`: $1080\cdot1920\cdot3=6\,220\,800$ B (6.2 MB); `float32`: 24.9 MB; `float64`: 49.8 MB. At 30 fps `uint8`: 187 MB/s, which is why cameras compress or why pipelines downsample early.
2. `img[300, 700]`: the first index is the row $v$, the second the column $u$. Bottom-right: `img[1079, 1919]`. `img[700, 300]` asks for row 700, column 300, a different pixel (it is valid here only because $700<1080$ and $300<1920$, so it silently reads the wrong place).
3. 8 bit: $1/255=0.0039$ of full scale; 12 bit: $1/4095=0.00024$. Dividing by 255 only rescales the integer codes; camera response curves (gamma) are non-linear, so the values are not proportional to scene radiance unless the image is linear (RAW or gamma-decoded).
4. `[246 100]`: `uint8` arithmetic wraps modulo 256: $10-20=-10\to246$. `[-10 100]`: casting one operand to a wider signed type promotes the result, which gives the true difference. `[30 44]`: $200+100=300\to44$. Always convert to a signed or float type before subtracting.
5. OpenCV loads colour images in BGR order; matplotlib assumes RGB. A pure red pixel is `[0, 0, 255]` in BGR and `[255, 0, 0]` in RGB, so unchanged BGR data shows red as blue. Fix: `rgb = bgr[:, :, ::-1]` (or `cv2.cvtColor`). Round trip: `assert np.array_equal(rgb[:, :, ::-1], bgr)`; also check a marker pixel by explicit indexing.
6. It indexes `img[row=u, col=v]`; the convention is `img[v, u]`. For a $4\times6$ image, `pixel(img, 5, 0)` asks for row 5 and raises `IndexError`, while the valid pixel $u=5,v=0$ should exist. On square images it silently returns the transposed pixel, so the bug stays hidden. Always test with $H\ne W$.
7. Red: $0.299\cdot255=76.2$; green: $0.587\cdot255=149.7$; blue: $0.114\cdot255=29.1$; mid-grey 128: $128$ (weights sum to 1). Plain mean for pure green: $85$. The eye is most sensitive to green and least to blue, so the luma weights give a perceptually better brightness; equal weights make pure blue look as bright as pure green.
8. $(128/255-0.485)/0.229=0.074$, $(0.502-0.456)/0.224=0.205$, $(0.502-0.406)/0.225=0.426$. With BGR input, the channels are scaled with the wrong means (red is normalised as if it were blue) and the network sees colour-shifted images; with 0..255 inputs the values are about 255 times too large and saturate the network.
9. (a) Taking pixels 0, 2, 4, 6 gives $0,0,0,0$: the stripes vanish into a flat dark image (aliasing). (b) Block averaging gives $127.5$ everywhere, the correct local mean. For a label mask bilinear interpolation creates new values such as $0.5$ or $1.5$ between labels 0 and 1 or 1 and 2, which are not categories: use nearest-neighbour (and keep integer dtype).
10. $f=(W/2)/\tan(\mathrm{FOV}/2)=960/\tan45^\circ=960$ px. Box width in pixels: $0.5/3\cdot960=160$ px. One pixel covers $3/960=3.1$ mm at 3 m, so a single pixel quantisation error is up to about $\pm1.6$ mm laterally; sub-pixel methods or averaging can do better, but not beyond the optics and noise.
11. New values: $65,140,215$. Standardised: original $(-1.22,0,1.22)$ and new $(-1.22,0,1.22)$: identical, because $(aI+b-a\mu-b)/(a\sigma)=(I-\mu)/\sigma$ for $a>0$. It does not help when the change is non-linear (gamma, saturation, clipping at 255), when shadows change only part of the image, or when $a<0$.
12. A good answer predicts: marker indices `[0,1]`, `[2,4]`, `[3,5]` in `(row, col)` form, per-channel means $255/24=10.6$ each, shape `(4, 6, 3)`, dtype `uint8`, min 0, max 255; shows that the RGB-to-BGR conversion swaps the channels at the markers and that the round trip returns the original; shows that `uint8` subtraction wraps and the safe difference does not.
