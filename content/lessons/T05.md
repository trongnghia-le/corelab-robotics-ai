## Why this matters

"It worked yesterday" and "it works on my machine" are the two most expensive sentences in applied computing. A result depends on much more than your script: the Python version, every installed package and *its* dependencies, environment variables, command-line options, input data, hardware and the random seed. If any of these changes silently, the number changes, and you cannot tell whether your idea or your environment moved. A **reproducible environment** declares these inputs explicitly, installs them in an isolated place, and keeps secrets and per-machine settings out of the code. This lesson builds on version control (T02) and tooling (T03) to give you a recipe for recreating a small experiment from scratch in a clean virtual environment and proving that you got the same answer.

## Intuition

Three layers, each a place where drift creeps in.

1. **Interpreter and packages (the environment).** A *virtual environment* is a private folder with its own Python and its own installed packages, so projects do not disturb each other or the operating system's Python.
2. **Versions (the lock).** A requirement like `numpy>=1.20` describes what you *accept*; a **lock** like `numpy==1.26.4` records what you *used*. Rebuilding from the range gives whatever is newest today; rebuilding from the lock gives the same packages as last time.
3. **Configuration.** Values that change between runs or machines (seed, steps, paths, API keys) should not be edited into source files. They are supplied from outside, in layers: built-in defaults, then a config file, then environment variables, then command-line options. Secrets live only in the environment (or a secret store), never in the repository.

*Left: ranges are resolved once into exact pins that rebuild the same environment. Right: later configuration layers override earlier ones; secrets stay out of Git.*

**The picture first.** An experiment's result is a function of everything it touches: the code, the interpreter, every installed library at an exact version, the configuration, the data, the seed, and the machine. Reproducibility means being able to write all of those inputs down so that someone else (or you in a year) can feed the same inputs and get the same output. A requirements range such as `numpy>=1.20` is a recipe that says "some flour"; a lock is the same recipe with the brand, batch number and weight of each ingredient.

**An everyday and a robot example.** A lab robot's perception node ran well in March. In September a colleague builds a fresh environment from `numpy>=1.20`; the resolver now picks a newer major release whose default behaviour for an array function changed, and detections shift by a pixel. Nothing in the code changed and the commit hash is identical. A second case: the robotics setup script exports `PYTHONPATH`, so a "clean" virtual environment quietly imports 165 packages from the system installation; the experiment works on one laptop and fails in CI.

**Predict before you compute.** (1) Which of $1.3.9,\ 1.4.0,\ 1.4.7,\ 1.5.0$ does `~=1.4.2` accept, and does `~=1.4.2.0` accept the same set? (2) Defaults say `shuffle=True`, the environment says `EXP_SHUFFLE=false`; what does a program that does `bool(os.environ["EXP_SHUFFLE"])` use? (3) After `python3 -m venv .venv` you run `pip install numpy` without activating; into which interpreter does it install? Write your answers before reading the theory.

**The common wrong intuition.** "If I pin the top-level libraries in requirements.txt, the environment is reproducible." It is not: the transitive dependencies still float, files can be replaced under the same version number, and the interpreter, operating system and `PYTHONPATH` are outside the file. A second wrong belief is "activating the venv isolates me": activation only edits `PATH`; environment variables such as `PYTHONPATH` still flow into the process. Reproducibility is the property you *test by rebuilding from nothing*, not one you assume from having a file.


## Theory and derivation

### Virtual environments

`python3 -m venv .venv` creates a folder containing a copy (or link) of the interpreter, a `site-packages` directory and `bin/` scripts. *Activating* it (`source .venv/bin/activate`) only edits `PATH` and a prompt; you can instead call `.venv/bin/python` directly, which is the most explicit and least error-prone way, especially in scripts and CI. Inside a venv, `sys.prefix` differs from `sys.base_prefix`, which is how a program can check it is isolated. Use `python -m pip` (not bare `pip`) so the package manager belongs to the same interpreter. Never `sudo pip install`.

### Version specifiers

Python packaging (PEP 440) uses specifiers: `==1.4.2` exact, `>=1.4,<2` a range (clauses are ANDed), `!=` exclusion, and `~=1.4.2` the *compatible release*: $\ge1.4.2$ and $<1.5$ (for `~=1.4`: $\ge1.4$ and $<2$). Versions compare numerically per segment, so $1.10>1.9$ and `1.2` equals `1.2.0`. A **resolver** chooses, for each package, a version satisfying all constraints (real resolvers also handle the dependencies of dependencies; our model resolves each package independently). With a range, the chosen version is typically the *highest allowed*, so the answer changes when a new release appears: **drift**.

### Locking

A lock is the *complete* resolved set including transitive dependencies, ideally with file hashes (`pip install --require-hashes -r requirements.lock`) so that even a re-uploaded file with the same version is rejected. Workflow: keep a small human-written `requirements.in` (what you want), generate a machine-written `requirements.lock` (what you got; `pip freeze` is the simplest generator, tools such as `pip-tools`, `uv` or Poetry produce richer locks), commit both (T02), install from the lock. When you upgrade, you diff the old and new lock (`lock_diff`), run your tests and commit the change deliberately. Also pin the Python version (`requires-python`, `.python-version`) and system libraries (T06 covers OS-level pinning). A **fingerprint** (a hash of the normalized lock) is a compact way to record "which environment ran this" in the results.

### Configuration

The Twelve-Factor App rule: strict separation of **config** (varies between deploys) from **code** (does not). Put defaults in code, per-experiment values in a config file, machine- or run-specific overrides in environment variables (`EXP_SEED=7`), and one-off tweaks on the command line. The merge order is **defaults < file < environment < command line**. Environment variables are strings; convert them to the right type (a `bool` from `"false"` is the string `"false"`, which is truthy in Python). Log the *effective* configuration of each run, with secrets redacted. Provide `.env.example` (names, no values) and keep the real `.env` in `.gitignore`.

### What cannot be locked by pip

Operating-system libraries, the CPU/GPU, BLAS thread counts and non-deterministic kernels, the data, wall-clock time, and unseeded randomness. Record them (hardware, data checksum, seed) and treat bitwise reproducibility as a goal you verify, not an assumption.

### Verifying reproducibility

The only convincing test is to **rebuild from nothing**: delete the environment, create it from the lock in a fresh directory (or CI), run with the recorded configuration and compare outputs (here a short digest). A mismatch is information: something was not captured.

### The PEP 440 version scheme as a total order

A public version has the shape `[N!]N(.N)*[{a|b|rc}N][.postN][.devN]`: an optional epoch, a release segment of integers, then optional pre-release, post-release and development segments (PEP 440, "Version scheme"). Comparison is lexicographic on the numeric release segment after padding with zeros, which is why `1.2 == 1.2.0` and `1.10 > 1.9`; the phases order as developmental release $<$ alpha $<$ beta $<$ release candidate $<$ final $<$ post-release. PEP 440 lists a full example of the order: `1.dev0 < 1.0.dev456 < 1.0a1 < 1.0b2 < 1.0rc1 < 1.0 < 1.0+abc.5 < 1.0.post456 < 1.0.15 < 1.1.dev1` (abridged), and a quick check with the `packaging` library that pip vendors reproduces the whole listed sequence. Two consequences matter for locking. First, a **local version** `1.0+abc` sorts above `1.0` but is not selected by `>1.0`, and `>1.0` also excludes `1.0.post1` (the exclusive ordered comparison does not match post-releases or local versions of the named version, PEP 440, "Exclusive ordered comparison"). Second, **pre-releases are excluded by default** from every specifier unless they are already installed, explicitly requested, or the only candidate, so `<2.0` does not admit `2.0rc1`.

### Specifiers as intervals: deriving the compatible-release operator

Every clause denotes a set of versions, and a comma-separated specifier is the intersection of its clauses. Prefix matching `==1.4.*` is the half-open interval $[1.4,\,1.5)$ (with pre-release and post-release suffixes handled by the order above). The compatible-release operator is defined by $\sim\!=V.N\;\equiv\;{\ge}V.N,\;{=}{=}V.*$, where $V.*$ drops the *last* segment of the stated release (PEP 440, "Compatible release"). Hence $\sim\!=1.4.5$ is $[1.4.5,\,1.5)$, $\sim\!=1.4$ is $[1.4,\,2)$ and $\sim\!=2.2$ is $[2.2,\,3)$. Appending a zero narrows the range, because the stated release is longer: $\sim\!=1.4.5.0$ means ${\ge}1.4.5.0$, ${=}{=}1.4.5.*$, i.e. $[1.4.5,\,1.4.6)$. A single-segment form such as $\sim\!=1$ is forbidden, since dropping the last segment would leave nothing to match. In a check of eight candidate strings, `~=1.4.5` accepted `1.4.5`, `1.4.5.post1`, `1.4.9` and `1.4.9.3` and rejected `1.4.4`, `1.5.0` and `1.5.0.dev1`, while `~=1.4.5.0` accepted only `1.4.5` and `1.4.5.post1` (computed with `packaging`). The conclusion for design: a range bounds *which* releases may be chosen, but the *choice* inside the range is made by the resolver, so a range alone never reproduces an environment.

### Resolution is search with backtracking

For one package the resolver intersects the intervals imposed by everyone who requires it and, by default, picks the highest version in the intersection. The difficulty is that each choice brings new requirements (the dependencies of that version), so choices interact. pip's resolver explores this as a search: when an assumption made earlier turns out to be incompatible with a later requirement it backtracks and tries another candidate (pip documentation, "Dependency Resolution", Backtracking). A small model makes this concrete. The root needs `a>=1` and `b>=1`; `a 2.0` needs `c>=2`; `a 1.0` needs `c<2`; `b 1.0` needs `c<2`; `c` exists as $2.1,2.0,1.5,1.0$. The greedy first choice `a 2.0` forces `c 2.1`, which contradicts `b`'s `c<2`; the search backtracks to `a 1.0` and then picks the highest `c<2`, which is `1.5`. The result `{a 1.0, b 1.0, c 1.5}` is unique here. Two lessons follow: the answer can be *older* than the newest release of a direct dependency, and if the intersection of constraints is empty (say `a` needs `c>=2` and `b` needs `c<2` for every version of both) no resolution exists and the installer must report the conflict instead of guessing.

### Hash-checking mode: what a hash locks, and what it does not

A version identifies a release; a hash identifies bytes. In hash-checking mode every requirement in the file carries `--hash=sha256:...` and pip verifies the downloaded file against it. The mode is all-or-nothing: giving a hash for any requirement switches it on for the whole install, hashes are then required for *all* requirements and *all* dependencies, and every requirement must be pinned with `==` (or a URL or path), so that a new release cannot cause a surprising mismatch (pip documentation, "Secure installs", Hash-checking Mode). Several hashes can be listed for one package, which is needed when it offers different wheels per platform or both a wheel and a source archive; weak algorithms (md5, sha1, sha224) are rejected. The hash that PyPI itself advertises in a download URL fragment protects against corruption but not tampering and does not satisfy `--require-hashes`. This tells you exactly what is locked: the *bytes of each distribution*. It does not lock the interpreter, the operating system, the build of a source archive (a wheel compiled on your machine from an sdist can differ between machines), or the platform choice: a lock produced on one platform contains only that platform's wheel hashes unless the others are added deliberately.

### Configuration as an ordered merge

Treat each layer (defaults, file, environment, command line) as a mapping and the effective configuration as a right-biased union: later keys override earlier ones. The operation is associative with the empty mapping as identity, so you may group layers freely, but it is **not commutative** when layers share keys. In the exercise-5 style example, merging defaults $\{lr{:}0.1,epochs{:}10,shuffle{:}True\}$, file $\{epochs{:}20\}$, environment $\{lr{:}0.01\}$, command line $\{epochs{:}5\}$ gives $\{lr{:}0.01,epochs{:}5,shuffle{:}True\}$, and reversing the order gives $\{lr{:}0.1,epochs{:}10,shuffle{:}True\}$, so documenting the order is part of the contract (computed). Because environment values are strings, parsing is a separate step with its own rule: `bool("false")` and `bool("0")` are `True` and only `bool("")` is `False`, hence a parser must map accepted spellings explicitly and reject the rest (The Twelve-Factor App, "Config", for why configuration lives in the environment).

### Isolation and leaks

A virtual environment is a directory with a `pyvenv.cfg` file whose `home` key points to the base interpreter and whose `include-system-site-packages` key is `false` unless `--system-site-packages` was given (Python documentation, `venv`). That isolates *installed packages*; it does not isolate the process from environment variables. `PYTHONPATH` entries are put on `sys.path` for every interpreter, venv or not, and in an experiment a module placed on `PYTHONPATH` was imported by `.venv/bin/python` even though `sys.prefix != sys.base_prefix`. Python's isolated mode `-I` ignores all `PYTHON*` variables, the user site directory and the script directory (Python documentation, "Command line and environment", `-I`), and in the same experiment the import failed with `ModuleNotFoundError`, as it did after `env -u PYTHONPATH`. Use `-I` for verification scripts, and treat any environment that "has 165 packages with an empty venv" as leaking.

### How the pieces connect

T05 sits between three neighbours. T02 supplies the commit that records the lock and the configuration; T03 explains how the interpreter and `PYTHONPATH` decide which module an import finds; T06 extends the lock to the operating-system layer with a container image, and T04 supplies the tests that make "the rebuilt environment behaves the same" a checkable statement rather than a hope. A reproducible experiment is the conjunction of: pinned bytes (lock with hashes), a known interpreter, an explicit configuration with documented precedence, a recorded seed and data checksum, and a command that rebuilds and compares.

## Worked example

### Basic cases

**Problem.** Five short problems on pinning and configuration.

(a) Which of $\{1.3.9,1.4.0,1.4.7,1.5.0\}$ does `~=1.4.2` accept? And `>=1.4,<1.5`? Does `~=1.2` accept $1.9.9$ and $2.0$?

(b) Available `numpy`: $1.9.0, 1.26.4, 2.0.0$. What does `>=1.20` resolve to, what after adding the bound `<2`, and what does a lock `numpy==1.26.4` give when the environment is rebuilt later?

(c) Diff the old lock `{numpy 1.26.4, six 1.16.0, tqdm 4.66.0}` against the new `{numpy 2.0.0, six 1.16.0, rich 13.7.0}`.

(d) Defaults `seed=0, steps=1000, verbose=False`; file `steps=500, seed=3`; env `EXP_SEED=7, EXP_VERBOSE=True`; CLI nothing. What is the effective configuration?

(e) The lab program, run with `EXP_SEED=0 EXP_STEPS=1000`: what does it print, and does it change in a freshly rebuilt `.venv` or outside any venv?

**Solution.**

1. (a) `~=1.4.2` is the compatible-release specifier, equal to `>=1.4.2,==1.4.*`. $1.3.9$ fails the lower bound; $1.4.0<1.4.2$ fails the lower bound; $1.4.7$ passes both; $1.5.0$ fails `==1.4.*`. Only $1.4.7$ is accepted.
2. (a) `>=1.4,<1.5`: $1.3.9<1.4$ fails, $1.4.0$ and $1.4.7$ pass, $1.5.0\not<1.5$ fails. Accepted: $1.4.0$ and $1.4.7$.
3. (a) `~=1.2` is `>=1.2,==1.*`: $1.9.9$ passes, $2.0$ fails `==1.*`.
4. (b) Versions compare number by number, so $1.9.0<1.20$ ($9<20$) and is excluded; $1.26.4$ and $2.0.0$ satisfy `>=1.20` and the highest allowed is $2.0.0$. This is drift: a later rebuild takes whatever is newest.
5. (b) With `>=1.20,<2` only $1.26.4$ remains (since $2.0.0\not<2$), so the resolution is $1.26.4$. A lock `numpy==1.26.4` yields $1.26.4$ whichever versions exist at rebuild time.
6. (c) Compare the two sets by package name: `rich` is only in the new lock (added), `tqdm` only in the old (removed), `six 1.16.0` is equal in both, and `numpy` differs: $1.26.4\to2.0.0$ (changed).
7. (d) The merge order is defaults < file < environment < command line. `seed`: default $0$, file $3$, env `"7"` converted to the integer $7$, so $7$ (env beats file). `steps`: default $1000$, file $500$, no env or CLI value, so $500$. `verbose`: default `False`, env the string `"True"` converted to the boolean `True`, so `True`.
8. (e) Run 1: `python3 experiment.py` with the system Python. Run 2: `python3 -m venv .venv`, then `.venv/bin/python experiment.py`. Run 3: delete `.venv`, recreate it and run again. Each prints final position $17.849482$ and digest `7d5f7244248d` (`"in_venv"` is `false` for run 1 and `true` for runs 2 and 3). The program uses only the standard library and a seeded generator, so nothing outside the code and settings enters the result.

**Check.** (a) and (b) were checked with `packaging.specifiers.SpecifierSet` and `packaging.version.Version`: `~=1.4.2` accepts `['1.4.7']`, `>=1.4,<1.5` accepts `['1.4.0','1.4.7']`, `~=1.2` accepts `['1.9.9']` only, and the highest `numpy` is $2.0.0$ without the bound, $1.26.4$ with it. (e) The three runs of `experiment.py` printed the same digest and final position.

**Takeaway.** A range drifts with the index, a lock does not; and a value is decided by the highest layer that sets it, after conversion from string to the right type.

### A harder case: a resolution that must backtrack

**Problem.** Index: the root requires `a>=1` and `b>=1`. `a` has versions $2.0$ (needs `c>=2`) and $1.0$ (needs `c<2`); `b` has $1.0$ (needs `c<2`); `c` has $2.1,\,2.0,\,1.5,\,1.0$. (a) Find the lock, choosing highest versions first and backtracking on conflict. (b) A release `c 2.2` and a new `a 3.0` (needs `c>=2.2`) appear: does the lock change? (c) Later `b` is upgraded to a version `b 2.0` that needs `c>=2`: what does the lock diff show?

**Solution.**

1. Greedy, highest first: `a 2.0`. It needs `c>=2`, and the highest such `c` is $2.1$.
2. Next `b`: its only version `b 1.0` needs `c<2`, which contradicts `c 2.1`. No `c` can satisfy both `c>=2` and `c<2`, so the choice `a 2.0` is a dead end: backtrack.
3. Drop `a 2.0` and try `a 1.0`, which needs `c<2`. The versions of `c` below $2$ are $1.5$ and $1.0$; the highest is `c 1.5`.
4. `b 1.0` needs `c<2`, which `c 1.5` satisfies. The lock is `a==1.0`, `b==1.0`, `c==1.5`.
5. With `c 2.2` and `a 3.0` added, the highest `a` is $3.0$, which needs `c>=2.2`, hence `c 2.2`; but `b 1.0` needs `c<2`: conflict. `a 2.0` needs `c>=2`, which also conflicts with `b`. Backtracking reaches `a 1.0` and the same answer `a==1.0, b==1.0, c==1.5`: `b` still caps `c` below $2$, so drift happens only where constraints leave room.
6. After the upgrade, `b 2.0` needs `c>=2`, so `a 3.0`, `b 2.0`, `c 2.2` are all compatible and the highest versions are chosen. The lock diff is `a 1.0 -> 3.0`, `b 1.0 -> 2.0`, `c 1.5 -> 2.2`.

**Check.** A small recursive search over this index returned exactly `{a: 1.0, b: 1.0, c: 1.5}`; with `c 2.2` and `a 3.0` added it returned the same; with `b 2.0` added it returned `(a 3.0, b 2.0, c 2.2)`. Each result was also verified by re-checking every constraint.

**Takeaway.** Dependencies move in groups, which is why a lock diff, not a requirements diff, is the document to review.

## Reference implementation

A Python model of the ideas above: version specifiers, a drifting resolver, lock diffs, layered configuration with type conversion and redaction, lock fingerprints and an environment checker. (The real tools are `pip`, `venv` and a locking tool; this model lets you test your understanding of their rules.)

```python
import hashlib, re

def parse_version(s):
    """'1.26.4' -> (1, 26, 4). Release segments only."""
    return tuple(int(p) for p in s.split("."))

def _cmp(a, b):
    n = max(len(a), len(b))
    a = a + (0,) * (n - len(a)); b = b + (0,) * (n - len(b))
    return (a > b) - (a < b)

def satisfies(version, spec):
    """True if version satisfies every comma-separated clause of spec, e.g. '>=1.4,<2' or '~=1.4.2'.
    Operators: == != >= <= > < ~=  (~=X.Y.Z means >=X.Y.Z and <X.(Y+1); ~=X.Y means >=X.Y and <(X+1))."""
    v = parse_version(version)
    for clause in spec.split(","):
        m = re.fullmatch(r"\s*(==|!=|>=|<=|>|<|~=)\s*([0-9][0-9.]*)\s*", clause)
        if not m:
            raise ValueError(f"bad clause {clause!r}")
        op, ref = m.group(1), parse_version(m.group(2))
        c = _cmp(v, ref)
        if op == "==": ok = c == 0
        elif op == "!=": ok = c != 0
        elif op == ">=": ok = c >= 0
        elif op == "<=": ok = c <= 0
        elif op == ">": ok = c > 0
        elif op == "<": ok = c < 0
        else:
            upper = ref[:-2] + (ref[-2] + 1,) if len(ref) > 2 else (ref[0] + 1,)
            ok = c >= 0 and _cmp(v, upper) < 0
        if not ok:
            return False
    return True

def resolve(specs, available):
    """For each package pick the highest available version that satisfies its spec (None if none)."""
    out = {}
    for pkg, spec in specs.items():
        ok = [v for v in available.get(pkg, []) if satisfies(v, spec)]
        out[pkg] = max(ok, key=parse_version) if ok else None
    return out

def lock_diff(old, new):
    """Compare two {package: version} dicts -> {'added': [...], 'removed': [...], 'changed': {pkg: (old, new)}}."""
    return {"added": sorted(set(new) - set(old)), "removed": sorted(set(old) - set(new)),
            "changed": {p: (old[p], new[p]) for p in sorted(set(old) & set(new)) if old[p] != new[p]}}

def merge_config(defaults, file_cfg, env, cli, prefix="EXP_"):
    """Layered configuration, later layers win: defaults < file_cfg < env < cli.
    Environment variables are PREFIX + KEY.upper(); their string values are converted to the type of the default."""
    cfg = dict(defaults)
    cfg.update({k: v for k, v in file_cfg.items() if k in defaults})
    for k, d in defaults.items():
        raw = env.get(prefix + k.upper())
        if raw is not None:
            cfg[k] = (raw.lower() in ("1", "true", "yes")) if isinstance(d, bool) else type(d)(raw)
    cfg.update({k: v for k, v in cli.items() if k in defaults and v is not None})
    return cfg

def redact(cfg, secret_keys):
    """Copy of cfg with the values of secret_keys replaced by '***' (so it can be logged)."""
    return {k: ("***" if k in secret_keys else v) for k, v in cfg.items()}

def fingerprint(lock_text):
    """Stable 12-hex-digit sha256 of a requirements/lock text: ignore comments and blank lines, case, '_' vs '-' in
    names and the order of lines."""
    lines = []
    for ln in lock_text.splitlines():
        ln = ln.split("#", 1)[0].strip().lower().replace("_", "-").replace(" ", "")
        if ln:
            lines.append(ln)
    return hashlib.sha256("\n".join(sorted(lines)).encode()).hexdigest()[:12]

def check_env(lock, installed):
    """Differences between the locked and installed {package: version}: sorted list of strings
    'missing:<pkg>', 'extra:<pkg>', 'version:<pkg>:<have>!=<want>'."""
    out = [f"missing:{p}" for p in lock if p not in installed]
    out += [f"extra:{p}" for p in installed if p not in lock]
    out += [f"version:{p}:{installed[p]}!={lock[p]}" for p in lock if p in installed and installed[p] != lock[p]]
    return sorted(out)

# tiny self-test
assert satisfies("1.4.7", "~=1.4.2") and not satisfies("1.5.0", "~=1.4.2") and satisfies("1.10.0", ">1.9")
assert fingerprint("Numpy==1.26.4\n# c\n") == fingerprint("numpy==1.26.4")
```

import hashlib, json, os, platform, random, sys

def load_settings(env=os.environ):
    return {"seed": int(env.get("EXP_SEED", "0")), "steps": int(env.get("EXP_STEPS", "1000"))}

def run(seed, steps):
    rng = random.Random(seed)
    x = 0.0
    for _ in range(steps):
        x += rng.gauss(0.0, 1.0)
    return x

if __name__ == "__main__":
    cfg = load_settings()
    x = run(**cfg)

           "python": platform.python_version(), "in_venv": sys.prefix != sys.base_prefix}

## Verification

- **Same digest after a full rebuild** (delete `.venv`, recreate from the lock, rerun). This is the actual test of reproducibility.
- **Isolation:** `"in_venv": true`, `pip freeze` matches the lock exactly (`check_env == []`).
- **Hand values:** `~=1.4.2` accepts only $1.4.7$ of the list above; the config example resolves to `seed=7, steps=500, verbose=True`.
- **Invariants:** a fingerprint is unchanged by comments, order and case; adding any package changes it.
- **Falsifier:** if the digest differs after a rebuild, diff the old and new `pip freeze`, the Python versions (`python --version`), `env` settings (`PYTHONPATH`, `EXP_*`) and the data checksum, in that order.

## Failure modes

- **Installing into the wrong Python:** forgetting to activate (or using bare `pip`) installs into the user/system interpreter, or fails with an "externally managed environment" error.
- **Unpinned ranges** (`numpy>=1.20`) that change meaning when a new release appears; un-pinned *transitive* dependencies.
- **`PYTHONPATH` leakage:** sourcing a setup script (for example a robotics distribution's `setup.bash`) puts its packages on `PYTHONPATH`, so a "clean" venv imports packages that are not in your lock. Detect with `python -c "import pkg; print(pkg.__file__)"`, `python -I`, or `env -u PYTHONPATH`; fix by not exporting it globally.
- **Committing `.venv/` or `.env`:** huge, machine-specific, and secrets leak into history (T02).
- **Booleans from environment strings:** `bool("false")` is `True`.
- **Secrets in logs:** printing the effective config without redaction.
- **Assuming the lock fixes the system:** native libraries, drivers and CPU instruction sets still differ; containers (T06) address part of this.
- **Mixing `pip` and `conda`** in the same environment without a plan.

## Alternatives and trade-offs

| Tool | Gives you | Cost |
| --- | --- | --- |
| `venv` + `pip freeze` | zero extra tools; simple lock | no hashes, no resolver for conflicts, flat output |
| `pip-tools`, `uv` | hashed, resolved lock files; fast installs | one more tool and step |
| Poetry, PDM, Hatch | project metadata plus lock and build | learning curve; tool-specific files |
| `conda` / `mamba` | non-Python dependencies (BLAS, CUDA libs) | large environments; different lock formats |
| Containers (T06) | the whole user-space, OS libraries included | image build and size; kernel and drivers still shared |
| Nix/Guix | bit-for-bit reproducible builds | steep learning curve |

Results (computed with `packaging`, pre-releases allowed): `~=1.4.5` accepts `1.4.5`, `1.4.5.post1`, `1.4.9`, `1.4.9.3`, `1.4.6rc1` and rejects `1.4.4`, `1.5.0.dev1`, `1.5.0`. `~=1.4.5.0` accepts only `1.4.5` and `1.4.5.post1`. `~=1.4` accepts all eight candidates, because they all match `1.*` and are at least `1.4`. `~=1` is illegal: the definition drops the last segment to form the prefix `==V.*`, and a one-segment version leaves no prefix to match (the PEP forbids it). A project trusting only patch releases should write `~=1.4.0`, which is ${\ge}1.4.0,\ {=}{=}1.4.*$; `~=1.4` also admits `1.5`, `1.9` and so on.
12. Order (computed): `0.9 < 1.0.dev1 < 1.0a1 < 1.0b2 < 1.0rc1 < 1.0 < 1.0+local < 1.0.0.post1.dev2 < 1.0.post1 < 1.0.1`. (`1.0.0` is padded to `1.0`; a development release of a post-release sorts before that post-release.) Satisfying `>1.0`: only `1.0.1`. The PEP says the exclusive comparison `>V` must not match a post-release of `V` (unless `V` is itself a post-release) nor a local version of `V`, so `1.0.post1`, `1.0.0.post1.dev2` and `1.0+local` are all rejected. Satisfying `<1.0`: only `0.9`; pre-releases of `1.0` (`1.0.dev1`, `1.0a1`, `1.0b2`, `1.0rc1`) are rejected because `<V` must not match a pre-release of `V`. Satisfying `>=1.0rc1`: `1.0rc1`, `1.0`, `1.0+local`, `1.0.0.post1.dev2`, `1.0.post1`, `1.0.1`. Satisfying `==1.0.*`: every version with release prefix `1.0`: `1.0.dev1`, `1.0a1`, `1.0b2`, `1.0rc1`, `1.0`, `1.0+local`, `1.0.0.post1.dev2`, `1.0.post1` and `1.0.1`.
13. (a) Order of work: `a`, then `b`, then `c`. Try `a 2.0` (needs `c>=2`); choose `b 1.0` (needs `c<2`); now `c` must satisfy `>=2` and `<2`: try `c 2.1` (violates `<2`), try `c 2.0` (violates `<2`), no more candidates, so backtrack and discard `a 2.0`. Try `a 1.0` (needs `c<2`), `b 1.0`, then `c 1.5` satisfies both `<2` constraints. Result `{a 1.0, b 1.0, c 1.5}`; candidates tried in order: `a 2.0`, `b 1.0`, `c 2.1`, `c 2.0`, `a 1.0`, `b 1.0` again, `c 1.5`. A small recursive search over this index returns exactly this resolution (computed). (b) With `a 1.0` as the only `a` (needs `c<2`) and `b 1.0` needing `c>=2`, the two demands on `c` are $(-\infty,2)$ and $[2,\infty)$, whose intersection is empty. Neither `a` nor `b` has another version to try, so backtracking exhausts all alternatives and the resolver must report an unsatisfiable set of requirements instead of installing anything. (c) Independent resolution ignores that the version chosen for one package changes the requirements placed on others (here `a 2.0` demands `c>=2` while `b` demands `c<2`); only a joint search, with backtracking when a later requirement contradicts an earlier choice, finds a consistent set.
14. (a) Hash-checking is all-or-nothing (one `--hash` switches it on for everything); hashes are required for all requirements; hashes are required for all dependencies; and every requirement must be pinned (`==`, a URL or a path). (b) A missing transitive dependency is an error (it is not spelled out and hashed); a requirement with `>=` is rejected as unpinned; with only the Linux wheel hash of `numpy` the macOS install fails because the downloaded macOS wheel matches none of the listed hashes. (c) It protects against a replaced or tampered file and against a surprise new release; it does not protect against an interpreter change, an operating-system library change, a source build that differs per machine, or different platform wheels you did not list. Design: `requirements.in` (human), a compiled `requirements.lock` with one `--hash=sha256:...` per wheel for each platform (for instance generated per platform and merged, or by a tool that writes all hashes), `python -m pip install --require-hashes -r requirements.lock` in a fresh venv, and `.python-version` or `requires-python`. Hash listing for the second platform must be added deliberately, as the docs describe for multiple hashes.
15. Commands: `python3 -m venv --without-pip .venv`; `mkdir D && echo 'X=1' > D/leakmod.py`; (1) `PYTHONPATH=$PWD/D .venv/bin/python -c "import leakmod"` succeeds (`leakmod.__file__` is under `D`); (2) with `-I` it fails with `ModuleNotFoundError: No module named 'leakmod'`; (3) `env -u PYTHONPATH` also fails. In run (1) `sys.prefix != sys.base_prefix` is `True`, so it is the venv interpreter, and `sys.path` shows `D` right after the script entry. (Computed with Python 3.14.7.) `include-system-site-packages = false` (written in `pyvenv.cfg`) prevents the base installation's `site-packages` from being added; it does not stop environment variables (`PYTHONPATH`), the current directory or the script directory from adding entries. `-I` implies `-E`, `-P` and `-s`, so it ignores `PYTHON*` variables, the script directory and the user site.
