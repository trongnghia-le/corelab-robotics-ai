## Why this matters

Robotics and ML pipelines are full of performance claims: "the perception node runs at 30 Hz", "training is I/O bound", "the planner is fast enough". Each of those sentences hides a choice of resource (CPU? memory? disk?), a workload (which input, how many?), and a statistic (mean? worst case?). A control loop that is fast on average but misses its deadline once per second is broken; a data loader that keeps one core at 100% while the GPU idles is the bottleneck of the whole job.

This lesson gives you a small vocabulary and a measurement discipline. You will learn what each number means, how to measure it without fooling yourself, and how two simple laws (Little's and Amdahl's) let you predict the effect of a change before you spend a day on it. You build on timing tools from T03 and the optimisation habits from PY09, but here the focus is on **measurement**, not on making code faster.

## Intuition

Think of a pipeline as a road. **Latency** is how long one car takes to travel from entrance to exit. **Throughput** is how many cars leave per second. They are related but not the same: a long, wide motorway has high latency and high throughput. **Utilization** is the fraction of time a resource (a lane, a CPU core) is busy; **saturation** is the queue of cars waiting because the resource is full. A resource can be 100% utilized without a queue (work arrives exactly as fast as it is served), while a persistently growing queue means demand exceeds capacity; bursty arrivals also create short, temporary queues even below capacity.

![Timeline of a request showing waiting, CPU work and I/O wait, with a latency histogram that has a long tail](/lesson-figures/T07.svg)

*One request splits into queueing, CPU work and waiting; many requests form a latency distribution whose tail is far from its mean.*

Two clocks matter. **Wall-clock time** is what a stopwatch on the wall shows. **CPU time** counts only the seconds a core spent executing your process. If wall time is much bigger than CPU time, the program was waiting (disk, network, sleep, lock). If CPU time is bigger than wall time, several cores worked in parallel.
**A picture from a queue.** Stand at a coffee counter and watch for an hour. Count the people in the shop at any instant, count how many walk in per minute, and time how long each person stays. The three numbers are tied together: if ten people walk in per minute and each stays three minutes, there are about thirty inside. That is Little's law, and it holds whether the shop is a coffee bar, a Python worker pool or a GPU waiting for batches from a data loader. Now imagine a single customer who spends an hour arguing with the cashier. Nearly everyone else is served in two minutes, so the *average* wait barely moves, but the person behind the argument experiences a disaster. That customer is your $P_{99}$, and it is why a camera node with a 33 ms frame budget cannot be judged by its mean.

**Predict before you compute.** A program runs 20% serial and 80% parallel on one core. Before computing, guess the speedup on 4, 16 and 1000 cores; most people guess "roughly the number of cores" for the first and are surprised that the third is nowhere near 1000. Second, a load generator sends one request at a time and waits for each answer. The server freezes for 10 seconds in the middle of a 100-second test. Do you expect the measured $P_{99}$ to show a 10-second delay? Third, you time a function ten times and get nine values near 5 ms and one at 60 ms: which single number would you report?

**The common wrong intuition.** "Faster average means better system." Averages hide the tail; a frozen server, as above, is often *invisible* in a naive benchmark, because the tool that measures latency stops asking questions while the server is stuck. A second false belief is that more workers always help in proportion to their number: the serial fraction sets a ceiling (Amdahl), unless the problem grows with the machine (Gustafson). The answers to the three prompts are in the theory and the second worked case: the speedups are $2.5$, $4$ and $4.98$ for the 20%-serial program; a single-connection closed-loop test will show almost nothing, and the median (about 5 ms) with the tail separately is the honest report.

## Theory and derivation

### What to measure: the USE checklist

For every resource (CPU, memory, disk, network, GPU) ask three questions: its **U**tilization (how busy), its **S**aturation (how much work is queued or swapped), and its **E**rrors (dropped packets, out-of-memory kills). Measuring the wrong resource is the most common mistake: optimising arithmetic in a loop that is waiting on a file read changes nothing.

### Latency statistics

Given $n$ measured latencies, the **nearest-rank percentile** $P_p$ is the sorted value at rank $\lceil p\,n/100\rceil$ (1-indexed). With $n=10$, $P_{50}$ is the 5th smallest value and $P_{99}$ is the 10th, that is, the maximum. The mean $\bar t=\frac1n\sum t_i$ is dragged by outliers; the median $P_{50}$ describes the typical request; $P_{95},P_{99}$ describe the tail. Report at least a typical value and a tail value, and always the sample count: a $P_{99}$ from 20 samples is just the maximum.

Latencies are rarely symmetric, so "mean $\pm$ standard deviation" is a poor summary. Timing noise (other processes, frequency scaling, cache state) is almost always *positive*: it can make a run slower, never faster than the machine's true capability. That is why `timeit` recommends taking the **minimum** of several repeats for micro-benchmarks, while for service latency we keep the whole distribution.

### Throughput, wall time, CPU time

For $N$ items processed in wall time $T$: throughput $X=N/T$. If a single worker handles items one after another, $X=1/\bar t$. CPU utilization over a window is
$$U=\frac{t_{\text{cpu}}}{T\cdot c},$$
where $c$ is the number of cores available. $U\approx 1$ with one core means CPU-bound; $U\ll 1$ means the process waits.

### Little's law

For any stable system in steady state, the average number of items inside the system is the arrival rate times the average time each spends there:
$$L=\lambda W.$$
It needs no assumption about distributions. If $\lambda=200$ requests/s and $W=0.05$ s, then $L=10$ requests are in flight on average. A pool of 8 workers can then complete at most $8/0.05=160$ requests/s, so requests queue and $W$ grows: the system is saturated.

### Amdahl's law

If a fraction $p$ of the run time can be sped up by a factor $s$ and the rest cannot, the overall speedup is
$$S=\frac{1}{(1-p)+p/s}.$$
Even with $s\to\infty$ the limit is $1/(1-p)$. Derivation: new time $=(1-p)T+pT/s$, divide old time by new time.

### Measuring memory

`tracemalloc` reports bytes allocated by Python code (the peak is what matters for sizing). Operating-system numbers such as resident set size (RSS) include the interpreter, shared libraries and allocator slack, so they are larger. Say which one you report. A Python list of $10^6$ floats stores $8$ bytes of pointer plus a $24$-byte float object each, about 32 MB, while `array('d')` stores $8$ bytes each, 8 MB.
### Little's law: a proof, its exact finite-window form and when it applies

Little's law is usually quoted for stable systems in steady state, but it has a short sample-path proof that holds on any finite observation window and therefore applies directly to a measurement you took (Little, "Little's Law as Viewed on Its 50th Anniversary", Operations Research 59(3), 2011, §2.1 and §2.2). Observe a system over $[0,T]$ with $0<T<\infty$ and let $n(t)$ be the number of items in the system at time $t$. Define
$$A=\int_0^T n(t)\,dt ,\qquad N=\text{number of arrivals in }[0,T],$$
and the three averages $L=A/T$ (time average of the number in the system), $\lambda=N/T$ (arrival rate) and $W=A/N$ (the average time an item spends in the system, because $A$ is also the total of the individual times in the system, each item contributing the length of its own stay). If the system is empty at $0$ and at $T$, then
$$L=\frac AT=\frac{N}{T}\cdot\frac{A}{N}=\lambda W .$$
Nothing was assumed about the arrival process, the service times or the order in which items are served; the identity is exact for the data you have. The reason it works is that the area $A$ is counted twice: once as "people-in-the-room integrated over time" and once as "each person's waiting time added up".

Real windows are rarely empty at both ends. Let $S(T)$ be the cumulative number of items that were present at some time in $[0,T]$, which includes those already there at $0$. Redefine $\lambda=S(T)/T$ and $W=A/S(T)$, where each item contributes only the part of its stay inside the window. The same algebra gives $L=\lambda W$ exactly (Little 2011, Theorem LL.2). Two practical warnings follow. First, $W$ must be the time *inside the same boundary* that $L$ counts: if $L$ counts the requests in a pool plus its queue, $W$ is queueing plus service, not service alone. Second, if you instead average only the items that completed in the window, you leave out the long ones still in the system, and $L\ne\lambda W$ with those mismatched numbers (exercise 12 shows the size of the error). The law also needs no service operation at all, so it applies equally to a data loader holding batches, a wine cellar or a thread pool.

### Amdahl's law in general form and Gustafson's scaled speedup

For a program whose time splits into fractions $f_1,\dots,f_k$ ($\sum f_i=1$), where stage $i$ is accelerated by a factor $s_i$ (with $s_i=1$ for untouched stages), the new time is $\sum_i f_i/s_i$ and the speedup is
$$S=\frac1{\sum_i f_i/s_i},$$
of which the lesson's two-part formula is the special case $k=2$. Two conclusions follow: the stage with the largest $f_i/s_i$ after acceleration is the next bottleneck, and the speedup is bounded by $1/\sum_{i:s_i=1}f_i$, the reciprocal of the untouched fraction.

Amdahl's argument fixes the *problem size* and asks how much faster it can be done. Gustafson (J. L. Gustafson, "Reevaluating Amdahl's Law", Communications of the ACM, 1988) pointed out that in practice users enlarge the problem to fill the machine, so it is the *run time* that stays fixed. Measure on the parallel machine with $N$ processors and let $s'$ and $p'=1-s'$ be the serial and parallel fractions of the elapsed time on that machine. A single processor would need $s'+p'N$ for the same job, because the parallel part is $N$ times as long when done serially. The **scaled speedup** is
$$S_{\text{scaled}}=\frac{s'+p'N}{s'+p'}=s'+(1-s')N=N-(N-1)s',$$
a straight line in $N$ with slope $1-s'$ instead of a hyperbola. Gustafson's own check: with $N=1024$ and $s'$ between 0.4% and 0.8% the formula gives roughly $1016$ to $1020$, matching the measured speedups of $1016$ to $1021$ for three Sandia applications. The two laws are not in conflict: if you write the same job's serial fraction as measured on one processor, $s=s'/(s'+p'N)$, then Amdahl's $1/(s+(1-s)/N)$ equals $s'+p'N$ exactly. They differ in what is held fixed and which fraction you measured. The assumption that decides which one to use is whether the parallel work grows with $N$; it fails when memory, communication or I/O grow with $N$ as well, and then neither formula is a safe predictor and you must measure.

### Open-loop versus closed-loop measurement and coordinated omission

A **closed-loop** load generator sends the next request only after the previous reply arrives; an **open-loop** generator sends requests on a schedule regardless of replies. The distinction matters when the system stalls. In a closed-loop test the generator stops sending exactly when the server is slow, so the slow period contributes *one* sample instead of the many requests that would have arrived on schedule; this is called **coordinated omission** (G. Tene, wrk2 README, "A note about wrk2's latency measurement technique"). The remedy used by wrk2 is to send at a constant intended rate and to measure each latency from the time the request *should* have been sent, so that requests delayed behind a stall are charged their full waiting time.

A model makes the distortion precise. Let the intended rate be $\lambda$ requests per second, the normal service time $d$, and a stall of length $D$. The closed-loop test records about $T/d$ samples of length $d$ and one of length about $D$: a stall of 10 s in a 100-second test is $1$ slow sample in about $9\times10^4$. An open-loop test records the $\lambda D$ requests scheduled during the stall, each charged between $0$ and $D$ of waiting, plus the requests that wait behind the backlog while the server catches up at rate $1/d-\lambda$. In the second worked case this raises the $P_{99}$ from 1 ms to about 9.5 s. The lesson: measure latency against the schedule, not against the instant the tool finally got round to asking.

### Percentiles from a sample: definitions and sampling error

Different tools define "the 99th percentile" differently. The nearest-rank rule of this lesson returns an observed value. Python's `statistics.quantiles` interpolates linearly, and its default `method="exclusive"` treats the data as a sample from a population that can have more extreme values, assigning the $i$-th of $m$ sorted points the percentile $i/(m+1)$, so it may extrapolate above the observed maximum; `method="inclusive"` assigns $(i-1)/(m-1)$ and never exceeds the maximum (Python docs, `statistics.quantiles`). For $n=10$ the cut points can differ enormously, so state the method together with $n$.

A second issue is sampling error. Let $q$ be the true $99$th percentile of a continuous latency distribution. Each sample falls below $q$ with probability $0.99$, so the number of samples below $q$ is $\text{Bin}(n,0.99)$. The $r$-th order statistic is below $q$ exactly when at least $r$ samples are, hence $P(X_{(r)}\le q)=P(\text{Bin}(n,0.99)\ge r)$. For the maximum, $P(X_{(n)}<q)=0.99^n$: with $n=100$ the maximum underestimates the true $P99$ with probability $0.366$, and one needs $n\ge299$ for a 95% chance that the maximum exceeds it. The interval $[X_{(a)},X_{(b)}]$ covers $q$ with probability $P(\text{Bin}\ge a)-P(\text{Bin}\ge b)$. This is why a tail percentile needs both a sample count and a confidence statement, and why a $P_{99}$ from a few dozen samples is little more than the maximum.

## Worked example

### Basic cases

A one-worker pipeline processes 10 requests. Measured latencies in ms: 12, 11, 13, 12, 10, 11, 95, 12, 13, 11.

1. **Sum and mean.** $12+11+13+12+10+11+95+12+13+11=200$, so $\bar t=200/10=20$ ms.
2. **Sort.** 10, 11, 11, 11, 12, 12, 12, 13, 13, 95.
3. **Median.** Rank $\lceil 0.5\cdot 10\rceil=5$ gives $P_{50}=12$ ms.
4. **P90.** Rank $\lceil 0.9\cdot 10\rceil=9$ gives 13 ms.
5. **P99.** Rank $\lceil 0.99\cdot 10\rceil=10$ gives 95 ms.
6. **Throughput.** One worker, serial, so wall time is the sum of latencies: $T=200$ ms $=0.2$ s and $X=10/0.2=50$ requests/s.
7. **Interpretation.** The mean (20 ms) is 67% higher than the typical request (12 ms) because of one outlier. Reporting only the mean would send you looking for a general slowdown; the percentiles show one rare slow request (a cache miss, garbage collection, a retry).
8. **Boundary check.** If the 95 ms request were removed, $T=105$ ms, $X=9/0.105\approx 85.7$/s, mean $11.7$ ms. One outlier cost 40% of the throughput.
### A harder case: a perception service measured end to end

**Setting.** A perception service receives $\lambda=120$ requests per second. A test over $T=100$ s on 8 workers shows an average time in system of $W=80$ ms. Its run time splits into three stages: preprocessing 40% (parallel over 4 threads already), inference 50%, and I/O 10%.

**Step 1: Little's law.** $L=\lambda W=120\times0.08=9.6$ requests in the system on average. Eight workers can serve at most $8$ requests at once, so at least $1.6$ requests are waiting on average: the 80 ms contains queueing time. For the queue to be stable the mean *service* time $s$ must satisfy $8/s\ge120$, that is $s\le66.7$ ms. If the service time were really 80 ms, capacity would be $8/0.08=100$ requests/s $<120$ and $W$ would grow without bound; the measured 80 ms would then be only the average of a growing transient (the identity holds exactly for the finite window by LL.2, but extrapolating $W$ to a long run would be wrong).

**Step 2: Amdahl with several stages.** Suppose inference is accelerated 5 times (a better model runtime) and preprocessing 4 times (more threads). Then $S=1/(0.1+0.5/5+0.4/4)=1/0.3=3.33$. The untouched I/O is $0.1$ of the original time and caps any further speedup at $10$; after the change the three stages take $0.1,\,0.1,\,0.1$ of the old time each, so the three are equally the bottleneck. Speeding up inference to 10 times would give $1/(0.1+0.05+0.1)=4$, a lower return than the first step.

**Step 3: how much can you trust $P_{99}$?** You collected $n=1000$ latencies. The nearest-rank $P_{99}$ is the $\lceil0.99\times1000\rceil=990$-th smallest value. The count of samples below the true $P_{99}$ is $\text{Bin}(1000,0.99)$ with mean $990$, so the interval from the $985$-th smallest to the maximum contains the true value with probability $0.952$ (computed from the binomial distribution). The statement "$P_{99}=118$ ms" should therefore be reported with that interval, or with the number of samples, because the data only constrain the true value to within a handful of order statistics of the tail.

**Step 4: the measurement itself.** If the test used one connection in a closed loop, a 10-second stall in the middle would contribute one slow sample and leave the percentiles untouched; with a constant intended rate and latencies measured from the scheduled send time, the same stall inflates the tail as the second case of exercise 14 shows. Always check which regime your tool uses before trusting a tail percentile.

## Reference implementation

The harness below times each item with an injectable clock. The self-test uses a fake clock so the expected numbers are exact: nine 10 ms items and one 100 ms item.

```python
import math, time

def percentile(xs, p):
    """Nearest-rank percentile: smallest value with at least p% of samples <= it."""
    s = sorted(xs)
    rank = max(1, math.ceil(p / 100 * len(s)))
    return s[rank - 1]

def measure(fn, items, clock=time.perf_counter, cpu=time.process_time):
    """Run fn on every item; return latency list, wall/cpu seconds and throughput."""
    lat = []
    c0, w0 = cpu(), clock()
    for it in items:
        t = clock()
        fn(it)
        lat.append(clock() - t)
    wall, cpu_s = clock() - w0, cpu() - c0
    return {"n": len(lat), "wall_s": wall, "cpu_s": cpu_s,
            "throughput": len(lat) / wall, "mean_s": sum(lat) / len(lat),
            "p50_s": percentile(lat, 50), "p99_s": percentile(lat, 99), "max_s": max(lat)}

# --- self-test with a fake clock so the numbers are exact ---
class Fake:
    def __init__(self): self.t = 0.0
    def __call__(self): return self.t

fake = Fake()
work = [0.010] * 9 + [0.100]          # nine 10 ms items, one 100 ms outlier

def fn(dt): fake.t += dt

r = measure(fn, work, clock=fake, cpu=fake)
assert abs(r["wall_s"] - 0.190) < 1e-9
assert abs(r["throughput"] - 10 / 0.190) < 1e-9
assert abs(r["mean_s"] - 0.019) < 1e-9 and r["p50_s"] == 0.010 and r["p99_s"] == 0.100
print("T07 reference OK:", round(r["throughput"], 2), "items/s, mean", r["mean_s"], "s")
```

With real clocks, use `time.perf_counter()` for wall time (monotonic, highest resolution) and `time.process_time()` for CPU time of the current process. Never use `time.time()` for intervals: it can jump when the system clock is adjusted.

## Verification

Check a harness with a fake clock before trusting it on real code: feed known durations and compare every statistic with a hand calculation (as in the self-test). Check invariants: $P_{50}\le P_{99}\le\max$; throughput times mean latency equals the number of workers busy (Little's law) for a serial run; CPU time never exceeds wall time times the core count. Run the benchmark twice; if the two results disagree by more than the effect you want to claim, the measurement cannot support the claim. Finally state the check that could reject your result, for example "if the baseline empty function already takes 30% of the measured time, the harness overhead dominates".

## Failure modes

- **Timing a lazy object.** Timing the creation of a generator or an unsynchronised asynchronous call measures nothing; the printed value is microseconds instead of seconds.
- **Index instead of rank.** `xs[int(0.5*n)]` for $n=4$ returns the 3rd value instead of the 2nd; with `q=100` it raises `IndexError`.
- **Mean only.** A mean of 20 ms hides a 95 ms tail and invites the wrong fix.
- **Cold start.** The first call includes imports, cache misses and JIT or file-cache warm-up; it can be 10x slower than the steady state.
- **Wall time for CPU questions.** On a loaded machine, wall time includes time spent waiting for other processes; use CPU time (or isolate the machine) when comparing algorithms.
- **Measuring the harness.** For a 50 ns function, the timer call itself costs about the same. Time a loop of many calls and subtract an empty-loop baseline.
- **Different inputs.** Comparing two versions on different data measures the data.

## Alternatives and trade-offs

| Tool | Use when | Limitation |
|---|---|---|
| `timeit` | Micro-benchmarks, small functions | Not for I/O or tail latency |
| `time.perf_counter` harness | Per-item latency, custom workloads | You must handle warm-up and repeats |
| `cProfile` / sampling profiler | Find *where* time goes | Adds overhead; not a latency distribution |
| `tracemalloc` | Python allocations and peak | Slows the program; misses native allocations |
| OS tools (`top`, `/usr/bin/time -v`) | RSS, context switches, whole processes | Coarse; includes interpreter overhead |

Use a benchmark to answer "how fast?" and a profiler to answer "why?". When the code is I/O bound, parallelism (threads, async) improves throughput; when it is CPU bound in pure Python, processes or native libraries help.

## Transfer and retention
