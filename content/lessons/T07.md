## Why this matters

Robotics and ML pipelines are full of performance claims: "the perception node runs at 30 Hz", "training is I/O bound", "the planner is fast enough". Each of those sentences hides a choice of resource (CPU? memory? disk?), a workload (which input, how many?), and a statistic (mean? worst case?). A control loop that is fast on average but misses its deadline once per second is broken; a data loader that keeps one core at 100% while the GPU idles is the bottleneck of the whole job.

This lesson gives you a small vocabulary and a measurement discipline. You will learn what each number means, how to measure it without fooling yourself, and how two simple laws (Little's and Amdahl's) let you predict the effect of a change before you spend a day on it. You build on timing tools from T03 and the optimisation habits from PY09, but here the focus is on **measurement**, not on making code faster.

## Intuition

Think of a pipeline as a road. **Latency** is how long one car takes to travel from entrance to exit. **Throughput** is how many cars leave per second. They are related but not the same: a long, wide motorway has high latency and high throughput. **Utilization** is the fraction of time a resource (a lane, a CPU core) is busy; **saturation** is the queue of cars waiting because the resource is full. A resource can be 100% utilized without a queue (work arrives exactly as fast as it is served), while a persistently growing queue means demand exceeds capacity; bursty arrivals also create short, temporary queues even below capacity.

![Timeline of a request showing waiting, CPU work and I/O wait, with a latency histogram that has a long tail](/lesson-figures/T07.svg)

*One request splits into queueing, CPU work and waiting; many requests form a latency distribution whose tail is far from its mean.*

Two clocks matter. **Wall-clock time** is what a stopwatch on the wall shows. **CPU time** counts only the seconds a core spent executing your process. If wall time is much bigger than CPU time, the program was waiting (disk, network, sleep, lock). If CPU time is bigger than wall time, several cores worked in parallel.

## Theory and derivation

### What to measure: the USE checklist

For every resource (CPU, memory, disk, network, GPU) ask three questions: its **U**tilization (how busy), its **S**aturation (how much work is queued or swapped), and its **E**rrors (dropped packets, out-of-memory kills). Measuring the wrong resource is the most common mistake: optimising arithmetic in a loop that is waiting on a file read changes nothing.

### Latency statistics

Given $n$ measured latencies, the **nearest-rank percentile** $P_p$ is the sorted value at rank $\lceil p\,n/100\rceil$ (1-indexed). With $n=10$, $P_{50}$ is the 5th smallest value and $P_{99}$ is the 10th, that is, the maximum. The mean $\bar t=\frac1n\sum t_i$ is dragged by outliers; the median $P_{50}$ describes the typical request; $P_{95},P_{99}$ describe the tail. Report at least a typical value and a tail value, and always the sample count: a $P_{99}$ from 20 samples is just the maximum.

Latencies are rarely symmetric, so "mean $\pm$ standard deviation" is a poor summary. Timing noise (other processes, frequency scaling, cache state) is almost always *positive*: it can make a run slower, never faster than the machine's true capability. That is why `timeit` recommends taking the **minimum** of several repeats for micro-benchmarks, while for service latency we keep the whole distribution.

### Throughput, wall time, CPU time

For $N$ items processed in wall time $T$: throughput $X=N/T$. If a single worker handles items one after another, $X=1/\bar t$. CPU utilization over a window is
$$U=\frac{t_{\text{cpu}}}{T\cdot c},$$
where $c$ is the number of cores available. $U\approx 1$ with one core means CPU-bound; $U\ll 1$ means the process waits.

### Little's law

For any stable system in steady state, the average number of items inside the system is the arrival rate times the average time each spends there:
$$L=\lambda W.$$
It needs no assumption about distributions. If $\lambda=200$ requests/s and $W=0.05$ s, then $L=10$ requests are in flight on average. A pool of 8 workers can then complete at most $8/0.05=160$ requests/s, so requests queue and $W$ grows: the system is saturated.

### Amdahl's law

If a fraction $p$ of the run time can be sped up by a factor $s$ and the rest cannot, the overall speedup is
$$S=\frac{1}{(1-p)+p/s}.$$
Even with $s\to\infty$ the limit is $1/(1-p)$. Derivation: new time $=(1-p)T+pT/s$, divide old time by new time.

### Measuring memory

`tracemalloc` reports bytes allocated by Python code (the peak is what matters for sizing). Operating-system numbers such as resident set size (RSS) include the interpreter, shared libraries and allocator slack, so they are larger. Say which one you report. A Python list of $10^6$ floats stores $8$ bytes of pointer plus a $24$-byte float object each, about 32 MB, while `array('d')` stores $8$ bytes each, 8 MB.

## Worked example

A one-worker pipeline processes 10 requests. Measured latencies in ms: 12, 11, 13, 12, 10, 11, 95, 12, 13, 11.

1. **Sum and mean.** $12+11+13+12+10+11+95+12+13+11=200$, so $\bar t=200/10=20$ ms.
2. **Sort.** 10, 11, 11, 11, 12, 12, 12, 13, 13, 95.
3. **Median.** Rank $\lceil 0.5\cdot 10\rceil=5$ gives $P_{50}=12$ ms.
4. **P90.** Rank $\lceil 0.9\cdot 10\rceil=9$ gives 13 ms.
5. **P99.** Rank $\lceil 0.99\cdot 10\rceil=10$ gives 95 ms.
6. **Throughput.** One worker, serial, so wall time is the sum of latencies: $T=200$ ms $=0.2$ s and $X=10/0.2=50$ requests/s.
7. **Interpretation.** The mean (20 ms) is 67% higher than the typical request (12 ms) because of one outlier. Reporting only the mean would send you looking for a general slowdown; the percentiles show one rare slow request (a cache miss, garbage collection, a retry).
8. **Boundary check.** If the 95 ms request were removed, $T=105$ ms, $X=9/0.105\approx 85.7$/s, mean $11.7$ ms. One outlier cost 40% of the throughput.

## Reference implementation

The harness below times each item with an injectable clock. The self-test uses a fake clock so the expected numbers are exact: nine 10 ms items and one 100 ms item.

```python
import math, time

def percentile(xs, p):
    """Nearest-rank percentile: smallest value with at least p% of samples <= it."""
    s = sorted(xs)
    rank = max(1, math.ceil(p / 100 * len(s)))
    return s[rank - 1]

def measure(fn, items, clock=time.perf_counter, cpu=time.process_time):
    """Run fn on every item; return latency list, wall/cpu seconds and throughput."""
    lat = []
    c0, w0 = cpu(), clock()
    for it in items:
        t = clock()
        fn(it)
        lat.append(clock() - t)
    wall, cpu_s = clock() - w0, cpu() - c0
    return {"n": len(lat), "wall_s": wall, "cpu_s": cpu_s,
            "throughput": len(lat) / wall, "mean_s": sum(lat) / len(lat),
            "p50_s": percentile(lat, 50), "p99_s": percentile(lat, 99), "max_s": max(lat)}

# --- self-test with a fake clock so the numbers are exact ---
class Fake:
    def __init__(self): self.t = 0.0
    def __call__(self): return self.t

fake = Fake()
work = [0.010] * 9 + [0.100]          # nine 10 ms items, one 100 ms outlier

def fn(dt): fake.t += dt

r = measure(fn, work, clock=fake, cpu=fake)
assert abs(r["wall_s"] - 0.190) < 1e-9
assert abs(r["throughput"] - 10 / 0.190) < 1e-9
assert abs(r["mean_s"] - 0.019) < 1e-9 and r["p50_s"] == 0.010 and r["p99_s"] == 0.100
print("T07 reference OK:", round(r["throughput"], 2), "items/s, mean", r["mean_s"], "s")
```

With real clocks, use `time.perf_counter()` for wall time (monotonic, highest resolution) and `time.process_time()` for CPU time of the current process. Never use `time.time()` for intervals: it can jump when the system clock is adjusted.

### Library track

Check your `percentile` against NumPy and use the standard `timeit.repeat` for task 6. NumPy's default `np.percentile` interpolates linearly, which is a different definition; `method="inverted_cdf"` is the nearest-rank rule from this lesson. Install with `pip install numpy` (in a virtual environment).

```python
import timeit, random
import numpy as np
# reuse percentile and summarize from your perf_lab.py solution

random.seed(7)
xs = [random.lognormvariate(0, 0.8) for _ in range(997)]
for p in (50, 90, 95, 99, 100):
    assert percentile(xs, p) == float(np.percentile(xs, p, method="inverted_cdf"))
print("default (interpolated) P99:", float(np.percentile(xs, 99)),
      "nearest-rank P99:", percentile(xs, 99))

times = timeit.repeat("sorted(range(200000, 0, -1))", number=1, repeat=30)
s = summarize(times)
assert min(times) <= s["p50"] <= s["p99"] <= s["max"]
print("min", min(times), "median", s["p50"], "max-min", s["max"] - min(times))
```

The asserts must pass (nearest rank equals `inverted_cdf`); the two P99 values differ slightly, which shows why you must state the percentile definition when you report a tail number. `timeit.repeat` returns one total per repeat, so with `number=1` its list is directly comparable to your `timed` output.

## Verification

Check a harness with a fake clock before trusting it on real code: feed known durations and compare every statistic with a hand calculation (as in the self-test). Check invariants: $P_{50}\le P_{99}\le\max$; throughput times mean latency equals the number of workers busy (Little's law) for a serial run; CPU time never exceeds wall time times the core count. Run the benchmark twice; if the two results disagree by more than the effect you want to claim, the measurement cannot support the claim. Finally state the check that could reject your result, for example "if the baseline empty function already takes 30% of the measured time, the harness overhead dominates".

## Failure modes

- **Timing a lazy object.** Timing the creation of a generator or an unsynchronised asynchronous call measures nothing; the printed value is microseconds instead of seconds.
- **Index instead of rank.** `xs[int(0.5*n)]` for $n=4$ returns the 3rd value instead of the 2nd; with `q=100` it raises `IndexError`.
- **Mean only.** A mean of 20 ms hides a 95 ms tail and invites the wrong fix.
- **Cold start.** The first call includes imports, cache misses and JIT or file-cache warm-up; it can be 10x slower than the steady state.
- **Wall time for CPU questions.** On a loaded machine, wall time includes time spent waiting for other processes; use CPU time (or isolate the machine) when comparing algorithms.
- **Measuring the harness.** For a 50 ns function, the timer call itself costs about the same. Time a loop of many calls and subtract an empty-loop baseline.
- **Different inputs.** Comparing two versions on different data measures the data.

## Alternatives and trade-offs

| Tool | Use when | Limitation |
|---|---|---|
| `timeit` | Micro-benchmarks, small functions | Not for I/O or tail latency |
| `time.perf_counter` harness | Per-item latency, custom workloads | You must handle warm-up and repeats |
| `cProfile` / sampling profiler | Find *where* time goes | Adds overhead; not a latency distribution |
| `tracemalloc` | Python allocations and peak | Slows the program; misses native allocations |
| OS tools (`top`, `/usr/bin/time -v`) | RSS, context switches, whole processes | Coarse; includes interpreter overhead |

Use a benchmark to answer "how fast?" and a profiler to answer "why?". When the code is I/O bound, parallelism (threads, async) improves throughput; when it is CPU bound in pure Python, processes or native libraries help.

## Transfer and retention

Apply the same discipline to any robot or ML pipeline: a camera node at 30 Hz has a 33.3 ms budget per frame, so you need $P_{99}$ and the maximum, not the mean. A data loader feeding a GPU is a queue; Little's law tells you how many batches must be in flight to hide a 200 ms disk latency at 50 batches/s (10). ## Exercise answers

1. Mean $=115/10=11.5$ ms. Sorted data already; median rank 5, so 6 ms. $P_{99}$ rank $\lceil 9.9\rceil=10$, so 60 ms. Quote the median (6 ms) as typical and $P_{99}$ (60 ms) as the tail; the mean describes neither.
2. $X=1200/4.8=250$ items/s. Serial mean latency $=1/250=4$ ms.
3. CPU time sums over cores, so $3.6/1.2=3$ cores were busy on average (multi-process or native threads). `cpu_s=0.1`, `wall_s=5.0` means the process was 2% busy and waited on I/O, sleep, locks or other processes; optimising arithmetic will not help.
4. $L=200\times0.05=10$ requests in flight. Eight workers give at most $8/0.05=160$ requests/s. At 200/s arrivals exceed capacity, the queue grows without bound and latency rises over time (saturation); the system is unstable.
5. A generator expression is lazy: no `f(x)` has run. Fix: materialise it (`out = [f(x) for x in data]`) or consume it (`sum(1 for _ in gen)`) between the two timer calls.
6. `sorted` gives `[1,2,3,4]`. First call: index `int(0.5*4)=2`, value 3 (prints `3`). Second call: index 4 is out of range: `IndexError`. Nearest rank for $p=50$, $n=4$: rank $\lceil 2\rceil=2$, value 2.
7. List: $10^6\times(8+24)\approx32$ MB. `array('d')`: $10^6\times8=8$ MB. Factor 4. `tracemalloc` counts the Python-allocated bytes (for the array it counts the buffer); RSS additionally includes the interpreter, loaded libraries and allocator slack, so it is larger and moves in coarse steps.
8. $S=1/(0.6+0.4/4)=1/0.7\approx1.43$. Limit $1/0.6\approx1.67$. A 2x speedup is impossible because it would need $0.5$ of the time, but the serial part alone is 0.6.
9. Variance of a sum of independent terms adds: $\mathrm{Var}(\bar t)=n\sigma^2/n^2=\sigma^2/n$, so SD $=\sigma/\sqrt n$. One quarter needs $\sqrt n=4$, $n=16$. The minimum is not an average: with positive-only noise it estimates the noise-free floor and does not shrink like $1/\sqrt n$, but it is sensitive to a single lucky run and says nothing about tail latency.
10. A good answer states: identical, representative log files (include one large and one pathological), the same process/machine state and Python build, warm-up discarded, at least 20-30 alternating runs of each (to avoid drift), median and spread (or min for micro-benchmarks), and the rejection rule, e.g. "if the median difference is smaller than the run-to-run spread, or the new parser is slower on the large file, reject". Also verify both parsers return identical output.
11. A good project has: fake-clock tests of the statistics, a real run reporting CPU, wall, peak memory, $P_{50}/P_{95}/P_{99}$ and throughput per stage, an empty-function baseline to estimate overhead, an empty input and a 100x input, a stated rejection check (linear scaling within 20%, or $P_{99}<$ the deadline), and a note of the machine and Python version.
