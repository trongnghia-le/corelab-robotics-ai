## Why this matters

Most programming time is spent not writing code but understanding why code does not do what you expected. Development tools exist to shorten that path from a symptom to a reproducible fix: an **editor** that shows errors as you type and navigates code, a **debugger** that lets you stop a running program and inspect it, and an **environment** (interpreter, working directory, variables) that is the same whenever you run the program. The most common beginner failure is not a logic bug at all: the program works from one terminal and fails from the editor's run button because the *working directory* or *interpreter* differs. This lesson gives you the vocabulary and the habits to configure one debug launch properly, to document where it runs, and to find a bug by narrowing rather than guessing.

## Intuition

Treat your tools as three instruments.

- The **editor** is a typing aid with a model of your code (a language server): it knows names, types and imports, and can rename, jump to definitions, lint and format.
- The **debugger** pauses execution. At a **breakpoint** the program freezes with all variables intact; you can read them, step one line at a time, and see the **call stack** (who called whom). That replaces guessing with observation.
- The **environment** is everything the program silently depends on: which interpreter and packages, the current directory, environment variables, command-line arguments. A **launch configuration** is a saved description of that environment so that pressing F5 does the same thing every time.

![Left: a VS Code workspace tree and launch.json fields (program, args, env, cwd) feeding a debug session with a breakpoint, call stack and variables panel. Right: the same relative path resolved against two different working directories, one succeeding and one failing.](/lesson-figures/T03.svg)

*A launch configuration fixes the environment (left); the same relative path means different files under different working directories (right).*

**A picture to hold on to.** A running program is a film; a debugger is a remote control with pause, frame-advance and rewind-by-restart. The fault is the frame where the state first becomes wrong; the failure is the later frame where you notice. They are usually different frames, and debugging is the art of walking from the failure back to the fault. Bisection is the fast-forward button: instead of watching every frame you jump to the middle and ask one question, "is the state already wrong here?", and halve the film each time.

**An everyday and a robot example.** Imagine a recipe that says "open the notebook". Which notebook you get depends on which kitchen you stand in: the working directory is the kitchen, the relative path is the instruction, and the script's own folder is the cookbook's shelf. A robot arm's calibration file read as `open("calib.yaml")` behaves the same: on the lab PC (started from the project root) it finds the file, from a systemd service started in `/` it does not. A launch configuration is the written note that says which kitchen to stand in.

**Predict before you compute.** A loop of one million steps corrupts a value at some unknown step and every later step sees the corrupted value. Before reading on, guess how many questions of the form "is it wrong yet?" you need, then compare with $\lceil\log_2(10^6+1)\rceil=20$. Next: a file `util.py` sits both next to your script and at the project root. Which one does `import util` pick when you press F5, and which when you type `python -m pkg.script`? Write your guess down, then check the theory section.

**The common wrong intuition.** "The bug is at the line where the program crashed." The crash line only shows where the wrong state was *finally used*; the fault may be millions of steps earlier. The second wrong intuition is "relative paths are relative to the script": they are relative to the process's working directory, and only `import` searches the script's folder first. Keep these two sentences; they remove most "works on my machine" mysteries.


## Theory and derivation

### What the debugger gives you

A debugger controls execution of a process. Core operations (names in VS Code / `pdb`):

| Action | VS Code | pdb | Meaning |
| --- | --- | --- | --- |
| Continue | F5 | `c` | run until the next breakpoint |
| Step over | F10 | `n` | execute this line; do not enter called functions |
| Step into | F11 | `s` | enter the function called on this line |
| Step out | Shift+F11 | `r` | run until the current function returns |
| Inspect | Variables, Watch | `p expr`, `pp expr` | evaluate an expression in the current frame |
| Call stack | Call Stack panel | `w`, `u`, `d` | where am I and who called me; move up/down frames |
| Breakpoint | click gutter | `b file:line` | stop here |
| Conditional breakpoint | right-click, expression | `b file:line, cond` | stop only when cond is true |
| Logpoint | right-click, message | (add a print) | print without stopping |

A **conditional breakpoint** evaluates its condition at every pass and stops only when it is true; with a large loop it is slow but exact. A **hit count** stops on the $k$-th pass. A **post-mortem** session (`python -m pdb script.py`, then `c`) stops at the line of an uncaught exception with all variables still available.

### A method for finding a bug

1. **Reproduce** deterministically (fix seeds, inputs, arguments, working directory).
2. **Minimize**: delete everything not needed to trigger the failure.
3. **Narrow** with a monotone predicate. If some check is true after the bug appears and stays true (a corrupted value, a failing assertion), a **binary search** finds the first bad step in $\lceil\log_2 n\rceil$ probes instead of $n$; $n=10^6$ needs about $20$. This is the idea behind `git bisect` (T02).
4. **Observe** state at the boundary with a breakpoint, not by editing code repeatedly.
5. **Fix and pin** with a regression test that fails before the fix.

### Environment: interpreter, directory, variables

Four facts decide whether "works here" transfers:

- **Interpreter.** `python -c "import sys; print(sys.executable)"` shows which Python runs. An editor can use a different interpreter than your terminal, with different installed packages. A project environment (T05) and the editor's *Select Interpreter* command fix this.
- **Working directory (cwd).** Relative paths such as `open("config.json")` are resolved against the process's cwd, **not** the script's folder. A debug launch with no `cwd` uses the workspace folder; running `python path/to/script.py` from another terminal uses that terminal's directory.
- **Arguments and variables.** `args` is a **list** of strings; `env` values must be strings. Secrets belong in an environment file that is not committed (T05).
- **Variable substitution.** Launch files accept variables such as `${workspaceFolder}` (the opened folder), `${file}` (the active file), `${fileDirname}`, `${fileBasename}`, `${fileBasenameNoExtension}` and `${env:NAME}`. They are expanded by the editor; an unknown name is an error.

Robust code does not rely on the cwd: build paths from the module's own location (`Path(__file__).parent / "config.json"`) or take the path as an argument. A launch configuration then documents rather than fixes the dependency.

### A minimal launch configuration

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "sumsq: run from the project root",
      "type": "debugpy",
      "request": "launch",
      "program": "${workspaceFolder}/sumsq.py",
      "args": [],
      "env": {"PYTHONHASHSEED": "0"},
      "cwd": "${workspaceFolder}",
      "console": "integratedTerminal",
      "justMyCode": true
    }
  ]
}
```

(Older versions of the Python extension use `"type": "python"`; the fields are the same.) Document the choice of `cwd` next to it, for example in the README: "Debug configs run with the project root as the working directory because `config.json` is resolved relative to it."

### Bisection: exact cost, optimality and when it fails

Model the run as steps $1,\dots,n$ with step $0$ known good. A predicate $\text{bad}(k)$ is **monotone** if $\text{bad}(k)\Rightarrow\text{bad}(k+1)$. The unknown is the first bad step $f\in\{1,\dots,n\}$, or $f=n+1$ if no step is bad: $n+1$ possible answers. Keep the invariant "`lo` is good, `hi` is bad", starting from $lo=0$, $hi=n+1$ (a virtual bad end), and probe $m=\lfloor(lo+hi)/2\rfloor$. If $m$ is bad set $hi=m$, otherwise $lo=m$. The gap $L=hi-lo$ becomes $\lfloor L/2\rfloor$ or $\lceil L/2\rceil$, so after $t$ probes it is at most $\lceil (n+1)/2^t\rceil$; the search ends when $L=1$, and then $f=hi$. Hence $t=\lceil\log_2(n+1)\rceil$ probes suffice.

This is **optimal**. A deterministic strategy that only learns one bit per probe is a binary decision tree whose leaves must separate all $n+1$ answers; a tree of depth $d$ has at most $2^d$ leaves, so $2^d\ge n+1$, i.e. $d\ge\lceil\log_2(n+1)\rceil$. For $n=10^6$ that is $20$: probing the last stage first, as in the worked example, costs one extra probe ($21$) but exits early when nothing is bad. The same invariant is what Python's `bisect` module maintains on a sorted list (Python documentation, `bisect`).

Three conditions break the guarantee.

- **Non-monotone predicate.** The invariant still guarantees an adjacent pair ($lo$ good, $lo+1$ bad) when the loop ends, so the search returns *a* good-to-bad transition, but not necessarily the first one. A bug that appears, disappears and reappears (a state corrupted and later overwritten) produces several transitions.
- **Untestable steps.** `git bisect run <cmd>` reads the exit status of `<cmd>`: $0$ means good, $1$ to $127$ except $125$ means bad, $125$ means "cannot be tested, skip", and anything else aborts the session (an `exit(-1)` becomes $255$ and aborts). If a skipped commit is adjacent to the culprit, git cannot tell exactly which commit is the first bad one and reports a candidate range (Git documentation, `git-bisect`, "Bisect skip" and "Bisect run"). Formally, if $a$ is the largest testable good step and $b$ the smallest testable bad step, the answer is only known to lie in $\{a+1,\dots,b\}$.
- **Flaky failures.** If a bad step shows the symptom with probability $q<1$ in a single run, a "good" verdict is unreliable. Declare *good* only after $r$ clean runs: a bad step is then misjudged with probability $(1-q)^r$. With at most $\lceil\log_2(n+1)\rceil$ probes, all verdicts on bad steps are right with probability at least $\bigl(1-(1-q)^r\bigr)^{\lceil\log_2(n+1)\rceil}$ (a lower bound, because not every probe lands on a bad step). The cost grows only by the factor $r$.

### Which module does `import` find? `sys.path` and the launch mode

When Python starts it builds `sys.path`. Its first entry is the directory that contains the input script if there is one; otherwise (interactive shell, `-c`, or `-m module`) it is the current directory. Then come `PYTHONPATH`, the standard library and `site-packages` (Python documentation, "The initialization of the sys.path module search path"). Two consequences matter when you debug.

1. The **same file** can import different modules depending on how it is launched. `python tools/run.py` puts `tools/` first; `python -m tools.run` puts the *cwd* first. VS Code's `"program"` corresponds to the first form and `"module"` to the second (VS Code, Python debugging configurations), so the `cwd` you document decides which `util.py` is found in the second form.
2. A module that sits earlier in `sys.path` **shadows** a later one with the same name. A local file called like an installed or standard module silently wins. Since Python 3.11 the option `-P` (or `PYTHONSAFEPATH`) stops Python from prepending the script's directory or the cwd (Python documentation, "Command line and environment", `-P`).

Worked second case. Layout: `proj/util.py`, `proj/tools/util.py`, `proj/tools/run.py` (which does `import util`), `proj/tools/__init__.py`. Run from `proj`: `python tools/run.py` imports `proj/tools/util.py` (script directory first); `python -m tools.run` imports `proj/util.py` (cwd first); `python -P tools/run.py` fails with `ModuleNotFoundError` because nothing is prepended and `proj/tools` is not on the path. The lesson's rule "build paths from `__file__`" is the file-system twin of "do not rely on what happens to be first on `sys.path`": give code an explicit package structure and run it with `-m`.

### Scripted breakpoints: ignore counts and command lists

`pdb` gives each breakpoint a number and a small state machine (Python documentation, `pdb`, "Debugger commands"). `break f.py:3, cond` stops only when `cond` is true; `ignore N k` makes breakpoint $N$ skip its next $k$ crossings, where a crossing counts only if the condition is true; `tbreak` is a one-shot breakpoint; `commands N ... end` attaches commands that run when the breakpoint is hit, and `silent` as the first command suppresses the stop message. Any resuming command (`continue`, `next`, ...) ends the list. Together they turn a debugger session into a logging instrument without editing the source: a list `commands` with `p (i, total)` and `continue` is a logpoint with a condition.

Worked case. For `for i in range(10): total += i * i` with the breakpoint at the update line and condition `i % 3 == 0`, the successive hits show $(i,\text{total})=(0,0),(3,5),(6,55),(9,204)$, because `total` is printed *before* the update and equals $\sum_{j<i}j^2$. With `ignore 1 2` the first two qualifying crossings ($i=0,3$) are skipped and the first stop is at $i=6$ with $\text{total}=55$ (checked with a real `pdb` session).

### How the pieces connect

Bisection is not specific to code: `git bisect` (T02) applies it to the commit graph, where the "steps" are commits and the predicate is a test script, and the same algebra decides how many builds a regression hunt costs. The interpreter and `sys.path` facts link to T05: a virtual environment changes which `site-packages` come last on `sys.path`, while the script directory and `PYTHONPATH` still come first, which is why a stray `PYTHONPATH` can defeat an otherwise clean environment. Containers (T06) pin the operating system layer the same way a launch configuration pins `cwd` and `env`. Finally, the regression test that closes every debugging session (T04) is the monotone predicate you would feed to bisection the next time a similar failure appears: a test that is deterministic, fast and exits with a meaningful status is what makes `git bisect run` usable at all.


## Worked example

### Basic cases

**Problem.** Four short problems from a debugging session.

(a) Workspace `/home/u/proj`, active file `/home/u/proj/exp/train.py`. Expand `${workspaceFolder}/data/${fileBasenameNoExtension}.csv` and `${fileDirname}`.

(b) The script contains `open("data/input.csv")` and the file is `/home/u/proj/exp/data/input.csv`. What happens with `cwd=/home/u/proj/exp` and with `cwd=/home/u/proj` (the default for a launch without `cwd`)?

(c) In `sum_squares`, line 11 is `total += i * i`. A conditional breakpoint with the condition `i == 3` is set on it. Where does the loop stop and what does `p (i, total)` print?

(d) A pipeline of $n=1{,}000{,}000$ stages corrupts the data at stage $730{,}000$ and every later stage sees corrupted data. How many probes does bisection need, compared with a linear scan?

**Solution.**

1. (a) Each variable is replaced by the part of the context it names: `${workspaceFolder}` is `/home/u/proj`; the base name of the active file is `train.py`, and dropping the extension gives `${fileBasenameNoExtension}` $=$ `train`. Substituting: `/home/u/proj/data/train.csv`.
2. (a) `${fileDirname}` is the active file's path without its last component: `/home/u/proj/exp`.
3. (b) A relative path is resolved against the working directory. With `cwd=/home/u/proj/exp` the path becomes `/home/u/proj/exp/data/input.csv`, which exists, so `open` succeeds.
4. (b) With `cwd=/home/u/proj` the path becomes `/home/u/proj/data/input.csv`, which does not exist, so `open` raises `FileNotFoundError`. The script is identical in both runs; only the directory it is started in changed.
5. (c) The breakpoint is hit before line 11 executes. For $i=0,1,2$ the condition is false and the line runs, so `total` $=0^2+1^2+2^2=0+1+4=5$. At $i=3$ the condition is true and the loop stops, with the line not yet executed.
6. (c) In `pdb`: `break sumsq.py:11, i == 3`, then `c`, then `p (i, total)`, which prints `(3, 5)`.
7. (d) Probe the last stage first: $1$ call, and it is corrupted, so a first bad stage exists. The invariant is "a bad stage lies in the interval", and each probe halves it.
8. (d) The interval holds at most $10^6$ candidates, and $2^{19}=524\,288<10^6\le2^{20}=1\,048\,576$, so $\lceil\log_2(10^6)\rceil=20$ more probes suffice: $1+20=21$ in total, versus up to $10^6$ calls for a linear scan.

**Check.** The steps were run. In Python the expansion gives `train` and `/home/u/proj/exp`; `open("data/input.csv")` succeeds from `exp/` and raises `FileNotFoundError` from the parent folder; a `pdb` session with `break sumsq.py:11, i == 3`, `c`, `p (i, total)` printed `(3, 5)`; and $\lceil\log_2 10^6\rceil=20$.

**Takeaway.** What a launch configuration means depends on the variables it expands and on the working directory; observe the state (a conditional breakpoint) and halve the search space (bisection) instead of guessing.

### A harder case: bisection with an untestable stretch

**Problem.** A history has $n=1000$ commits and the true first bad commit is $613$. (a) How many probes does bisection need when every commit is testable? (b) Commits $611$ to $614$ do not build, so the script exits $125$ for them. Where does bisection end and how many candidates remain? (c) How can the ambiguity be resolved, at what cost? (d) What if only $613$ were unbuildable? (e) How should a crash of the harness (status $255$) be treated?

**Solution.**

1. The possible answers are "first bad is commit $k$" for $k=1,\dots,1000$, or "none": $1001$ outcomes. Each probe gives one bit, so $k$ probes distinguish at most $2^k$ outcomes: $2^9=512<1001\le1024=2^{10}$, hence $\lceil\log_2(1001)\rceil=10$ probes. A simulation of bisection with first bad commit $613$ uses exactly $10$.
2. With $611$ to $614$ untestable, bisection can only maintain the invariant "$a$ is the largest testable good commit, $b$ the smallest testable bad commit". Every testable commit up to $610$ is good and every testable commit from $615$ on is bad, so the search ends at $a=610$, $b=615$.
3. The first bad commit lies in $(a,b]=\{611,\dots,615\}$: $b-a=5$ candidates. In truth $611$ and $612$ are good and $613$ to $615$ are bad, but no test can say so.
4. Way out 1: apply a small patch so that the stretch builds, then rerun. Five candidates need $\lceil\log_2 5\rceil=3$ more probes, since $2^2=4<5\le8=2^3$. Way out 2: read the five diffs.
5. If only $613$ were unbuildable, then $a=612$ (good) and $b=614$ (bad), so the candidates are $(612,614]=\{613,614\}$: $2$ candidates.
6. Exit $125$ means "cannot test this commit, skip it". A crash of the harness (status $255$) aborts the bisection, and it must not be read as "bad": the script is fixed instead.

**Check.** A simulation with the untestable set $\{611,\dots,614\}$ ends at $a=610$, $b=615$; with $\{613\}$ it ends at $a=612$, $b=614$; with none it ends at $612,613$ after $10$ probes. Sanity bound: the number of candidates is always $b-a$, and a fully testable history gives $b-a=1$.

**Takeaway.** The cost of a skipped stretch is not extra probes but lost resolution, so a bisect script should skip only genuinely untestable commits.

## Reference implementation

A Python model of three tool behaviors: variable expansion and path resolution (what a launch configuration means), validation of a launch entry, and the breakpoint/bisection logic used to narrow a bug.

```python
import posixpath, re, math

def expand_vars(s, ctx):
    """Expand VS Code style variables: ${workspaceFolder}, ${file}, ${fileDirname}, ${fileBasename},
    ${fileBasenameNoExtension}, ${env:NAME}. ctx = {'workspaceFolder': str, 'file': str or None, 'env': dict}.
    Unknown or unavailable variables raise ValueError."""
    f = ctx.get("file")
    table = {"workspaceFolder": ctx.get("workspaceFolder")}
    if f:
        base = posixpath.basename(f)
        table.update({"file": f, "fileDirname": posixpath.dirname(f), "fileBasename": base,
                      "fileBasenameNoExtension": posixpath.splitext(base)[0]})
    def sub(m):
        name = m.group(1)
        if name.startswith("env:"):
            return ctx.get("env", {}).get(name[4:], "")
        if table.get(name) is None:
            raise ValueError(f"unresolved variable ${{{name}}}")
        return table[name]
    return re.sub(r"\$\{([^}]+)\}", sub, s)

def resolve_path(base, p):
    """Absolute normalised path of p, interpreting relative paths against base."""
    return posixpath.normpath(p if p.startswith("/") else posixpath.join(base, p))

def find_file(cwd, rel, files):
    """Where a program started in cwd finds the relative path rel: the resolved path if it exists, else None."""
    full = resolve_path(cwd, rel)
    return full if full in files else None

def validate_launch(cfg, ctx, files, dirs):
    """Return a sorted list of problem codes for a launch configuration:
    'no-target' (neither program nor module), 'unresolved-variable', 'program-missing',
    'cwd-missing' (cwd defaults to the workspace folder), 'args-not-list', 'env-not-string'."""
    problems = set()
    ws = ctx["workspaceFolder"]
    if "program" not in cfg and "module" not in cfg:
        problems.add("no-target")
    try:
        cwd = resolve_path(ws, expand_vars(cfg.get("cwd", "${workspaceFolder}"), ctx))
        if cwd not in dirs:
            problems.add("cwd-missing")
        if "program" in cfg:
            prog = resolve_path(ws, expand_vars(cfg["program"], ctx))
            if prog not in files:
                problems.add("program-missing")
    except ValueError:
        problems.add("unresolved-variable")
    a = cfg.get("args", [])
    if not isinstance(a, list) or not all(isinstance(x, str) for x in a):
        problems.add("args-not-list")
    if not all(isinstance(v, str) for v in cfg.get("env", {}).values()):
        problems.add("env-not-string")
    return sorted(problems)

def breakpoint_hits(values, cond=None):
    """Indices at which a (conditional) breakpoint inside a loop over `values` would stop."""
    return [i for i, v in enumerate(values) if cond is None or cond(v)]

def first_bad(n, is_bad):
    """Binary search for the first index in 0..n-1 where is_bad is True, assuming is_bad is monotone
    (False...False True...True). Return (index or None, number_of_probes)."""
    probes = 1
    if n == 0 or not is_bad(n - 1):
        return None, probes
    lo, hi = 0, n - 1                      # invariant: is_bad(hi) is True
    while lo < hi:
        mid = (lo + hi) // 2
        probes += 1
        if is_bad(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo, probes

# tiny self-test
assert resolve_path("/w", "../x/./y") == "/x/y"
assert first_bad(8, lambda i: i >= 5) == (5, 4)
```

## Verification

- **Same result from anywhere:** the program prints `demo 55` from the project folder, the parent folder and from the editor's launch.
- **Hand values:** `(3, 5)` at the breakpoint; `${workspaceFolder}/data/train.csv`; $\le21$ probes for $10^6$ steps.
- **Environment check:** print `sys.executable`, `os.getcwd()` and `sys.argv` at the start of a debug session; they must match what your README claims.
- **Invariants:** the launch validator returns an empty list for a correct configuration; bisection agrees with a linear scan on every monotone predicate.
- **Falsifier:** if the program works from the terminal but not under the debugger (or the reverse), the environment records differ; compare the three printed values.

## Failure modes

- **Relative paths resolved against the wrong cwd** (`FileNotFoundError`), the most frequent reason a program "only works in the terminal".
- **Wrong interpreter:** the editor runs a different Python, so imports fail or versions differ.
- **`args` as a string** instead of a list, so the whole string becomes one argument; `env` values that are numbers.
- **Misspelled variables** (`${workspace}` instead of `${workspaceFolder}`).
- **Debugging with a stale breakpoint set** (breakpoints in files not executed, or optimized code).
- **Heisenbugs:** timing or concurrency bugs that disappear under the debugger; add logging.
- **Only changing code and re-running** instead of observing state; or leaving debug prints and breakpoints in committed code.
- **Committing machine-specific launch files** with absolute paths (`/home/me/...`); use variables.
- **Skipping the regression test**, so the bug returns.

## Alternatives and trade-offs

| Need | Tool | Trade-off |
| --- | --- | --- |
| Quick look at a value | `print` / logging | no tool needed; clutter; cannot inspect other variables |
| Inspect state at a point | breakpoint and step | exact; slower for large loops |
| Failure in remote or headless code | `pdb` / `breakpoint()`, remote attach | works anywhere with a terminal; less visual |
| Intermittent or long-running failures | logging, assertions, core dumps/traces | no interactive stop; needs prior instrumentation |
| Find the change that broke it | `git bisect run` | needs a script that detects the failure |
| Performance, not correctness | profiler (`cProfile`) | different question |

Start with the cheapest tool that answers your question; escalate to the debugger when you need to see state you did not print.
