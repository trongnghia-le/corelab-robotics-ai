## Why this matters

Most programming time is spent not writing code but understanding why code does not do what you expected. Development tools exist to shorten that path from a symptom to a reproducible fix: an **editor** that shows errors as you type and navigates code, a **debugger** that lets you stop a running program and inspect it, and an **environment** (interpreter, working directory, variables) that is the same whenever you run the program. The most common beginner failure is not a logic bug at all: the program works from one terminal and fails from the editor's run button because the *working directory* or *interpreter* differs. This lesson gives you the vocabulary and the habits to configure one debug launch properly, to document where it runs, and to find a bug by narrowing rather than guessing.

## Intuition

Treat your tools as three instruments.

- The **editor** is a typing aid with a model of your code (a language server): it knows names, types and imports, and can rename, jump to definitions, lint and format.
- The **debugger** pauses execution. At a **breakpoint** the program freezes with all variables intact; you can read them, step one line at a time, and see the **call stack** (who called whom). That replaces guessing with observation.
- The **environment** is everything the program silently depends on: which interpreter and packages, the current directory, environment variables, command-line arguments. A **launch configuration** is a saved description of that environment so that pressing F5 does the same thing every time.

## Theory and derivation

### What the debugger gives you

A debugger controls execution of a process. Core operations (names in VS Code / `pdb`):

| Action | VS Code | pdb | Meaning |
| --- | --- | --- | --- |
| Continue | F5 | `c` | run until the next breakpoint |
| Step over | F10 | `n` | execute this line; do not enter called functions |
| Step into | F11 | `s` | enter the function called on this line |
| Step out | Shift+F11 | `r` | run until the current function returns |
| Inspect | Variables, Watch | `p expr`, `pp expr` | evaluate an expression in the current frame |
| Call stack | Call Stack panel | `w`, `u`, `d` | where am I and who called me; move up/down frames |
| Breakpoint | click gutter | `b file:line` | stop here |
| Conditional breakpoint | right-click, expression | `b file:line, cond` | stop only when cond is true |
| Logpoint | right-click, message | (add a print) | print without stopping |

A **conditional breakpoint** evaluates its condition at every pass and stops only when it is true; with a large loop it is slow but exact. A **hit count** stops on the $k$-th pass. A **post-mortem** session (`python -m pdb script.py`, then `c`) stops at the line of an uncaught exception with all variables still available.

### A method for finding a bug

1. **Reproduce** deterministically (fix seeds, inputs, arguments, working directory).
2. **Minimize**: delete everything not needed to trigger the failure.
3. **Narrow** with a monotone predicate. If some check is true after the bug appears and stays true (a corrupted value, a failing assertion), a **binary search** finds the first bad step in $\lceil\log_2 n\rceil$ probes instead of $n$; $n=10^6$ needs about $20$. This is the idea behind `git bisect` (T02).
4. **Observe** state at the boundary with a breakpoint, not by editing code repeatedly.
5. **Fix and pin** with a regression test that fails before the fix.

### Environment: interpreter, directory, variables

Four facts decide whether "works here" transfers:

- **Interpreter.** `python -c "import sys; print(sys.executable)"` shows which Python runs. An editor can use a different interpreter than your terminal, with different installed packages. A project environment (T05) and the editor's *Select Interpreter* command fix this.
- **Working directory (cwd).** Relative paths such as `open("config.json")` are resolved against the process's cwd, **not** the script's folder. A debug launch with no `cwd` uses the workspace folder; running `python path/to/script.py` from another terminal uses that terminal's directory.
- **Arguments and variables.** `args` is a **list** of strings; `env` values must be strings. Secrets belong in an environment file that is not committed (T05).
- **Variable substitution.** Launch files accept variables such as `${workspaceFolder}` (the opened folder), `${file}` (the active file), `${fileDirname}`, `${fileBasename}`, `${fileBasenameNoExtension}` and `${env:NAME}`. They are expanded by the editor; an unknown name is an error.

Robust code does not rely on the cwd: build paths from the module's own location (`Path(__file__).parent / "config.json"`) or take the path as an argument. A launch configuration then documents rather than fixes the dependency.

### A minimal launch configuration

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "sumsq: run from the project root",
      "type": "debugpy",
      "request": "launch",
      "program": "${workspaceFolder}/sumsq.py",
      "args": [],
      "env": {"PYTHONHASHSEED": "0"},
      "cwd": "${workspaceFolder}",
      "console": "integratedTerminal",
      "justMyCode": true
    }
  ]
}
```

(Older versions of the Python extension use `"type": "python"`; the fields are the same.) Document the choice of `cwd` next to it, for example in the README: "Debug configs run with the project root as the working directory because `config.json` is resolved relative to it."

## Worked example

**Variable expansion.** Workspace `/home/u/proj`, active file `/home/u/proj/exp/train.py`. Then `${workspaceFolder}/data/${fileBasenameNoExtension}.csv` $\to$ `/home/u/proj/data/train.csv`; `${fileDirname}` $\to$ `/home/u/proj/exp`.

**Working directory.** The script contains `open("data/input.csv")` and the file is `/home/u/proj/exp/data/input.csv`. With `cwd=/home/u/proj/exp` the open resolves to that file and succeeds; with `cwd=/home/u/proj` (the default for a launch without `cwd`) it resolves to `/home/u/proj/data/input.csv`, which does not exist: `FileNotFoundError`.

**Conditional breakpoint.** In `sum_squares`, `total += i * i` at line 11. With the condition `i == 3` the loop stops when $i=3$ and `total` $=0^2+1^2+2^2=5$. In `pdb`: `break sumsq.py:11, i == 3`, `c`, `p (i, total)` prints `(3, 5)`.

**Binary search.** A pipeline of $n=1{,}000{,}000$ stages corrupts the data at stage $730{,}000$ and every later stage sees corrupted data. First probe the last stage ($1$ call: corrupted), then bisect: at most $\lceil\log_2(10^6)\rceil=20$ more probes, so at most $21$ in total, versus up to $10^6$ for a linear scan.

## Reference implementation

A Python model of three tool behaviors: variable expansion and path resolution (what a launch configuration means), validation of a launch entry, and the breakpoint/bisection logic used to narrow a bug.

```python
import posixpath, re, math

def expand_vars(s, ctx):
    """Expand VS Code style variables: ${workspaceFolder}, ${file}, ${fileDirname}, ${fileBasename},
    ${fileBasenameNoExtension}, ${env:NAME}. ctx = {'workspaceFolder': str, 'file': str or None, 'env': dict}.
    Unknown or unavailable variables raise ValueError."""
    f = ctx.get("file")
    table = {"workspaceFolder": ctx.get("workspaceFolder")}
    if f:
        base = posixpath.basename(f)
        table.update({"file": f, "fileDirname": posixpath.dirname(f), "fileBasename": base,
                      "fileBasenameNoExtension": posixpath.splitext(base)[0]})
    def sub(m):
        name = m.group(1)
        if name.startswith("env:"):
            return ctx.get("env", {}).get(name[4:], "")
        if table.get(name) is None:
            raise ValueError(f"unresolved variable ${{{name}}}")
        return table[name]
    return re.sub(r"\$\{([^}]+)\}", sub, s)

def resolve_path(base, p):
    """Absolute normalised path of p, interpreting relative paths against base."""
    return posixpath.normpath(p if p.startswith("/") else posixpath.join(base, p))

def find_file(cwd, rel, files):
    """Where a program started in cwd finds the relative path rel: the resolved path if it exists, else None."""
    full = resolve_path(cwd, rel)
    return full if full in files else None

def validate_launch(cfg, ctx, files, dirs):
    """Return a sorted list of problem codes for a launch configuration:
    'no-target' (neither program nor module), 'unresolved-variable', 'program-missing',
    'cwd-missing' (cwd defaults to the workspace folder), 'args-not-list', 'env-not-string'."""
    problems = set()
    ws = ctx["workspaceFolder"]
    if "program" not in cfg and "module" not in cfg:
        problems.add("no-target")
    try:
        cwd = resolve_path(ws, expand_vars(cfg.get("cwd", "${workspaceFolder}"), ctx))
        if cwd not in dirs:
            problems.add("cwd-missing")
        if "program" in cfg:
            prog = resolve_path(ws, expand_vars(cfg["program"], ctx))
            if prog not in files:
                problems.add("program-missing")
    except ValueError:
        problems.add("unresolved-variable")
    a = cfg.get("args", [])
    if not isinstance(a, list) or not all(isinstance(x, str) for x in a):
        problems.add("args-not-list")
    if not all(isinstance(v, str) for v in cfg.get("env", {}).values()):
        problems.add("env-not-string")
    return sorted(problems)

def breakpoint_hits(values, cond=None):
    """Indices at which a (conditional) breakpoint inside a loop over `values` would stop."""
    return [i for i, v in enumerate(values) if cond is None or cond(v)]

def first_bad(n, is_bad):
    """Binary search for the first index in 0..n-1 where is_bad is True, assuming is_bad is monotone
    (False...False True...True). Return (index or None, number_of_probes)."""
    probes = 1
    if n == 0 or not is_bad(n - 1):
        return None, probes
    lo, hi = 0, n - 1                      # invariant: is_bad(hi) is True
    while lo < hi:
        mid = (lo + hi) // 2
        probes += 1
        if is_bad(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo, probes

# tiny self-test
assert resolve_path("/w", "../x/./y") == "/x/y"
assert first_bad(8, lambda i: i >= 5) == (5, 4)
```

```python
"""Sum of squares driven by config.json -- the config path depends on the working directory."""
import json
from pathlib import Path

def load_config(path="config.json"):
    return json.loads(Path(path).read_text())

def sum_squares(n):
    total = 0
    for i in range(n):
        total += i * i
    return total

def main():
    cfg = load_config()
    print(cfg["name"], sum_squares(cfg["n"]))

if __name__ == "__main__":
    main()
```

## Verification

- **Same result from anywhere:** the program prints `demo 55` from the project folder, the parent folder and from the editor's launch.
- **Hand values:** `(3, 5)` at the breakpoint; `${workspaceFolder}/data/train.csv`; $\le21$ probes for $10^6$ steps.
- **Environment check:** print `sys.executable`, `os.getcwd()` and `sys.argv` at the start of a debug session; they must match what your README claims.
- **Invariants:** the launch validator returns an empty list for a correct configuration; bisection agrees with a linear scan on every monotone predicate.
- **Falsifier:** if the program works from the terminal but not under the debugger (or the reverse), the environment records differ; compare the three printed values.

## Failure modes

- **Relative paths resolved against the wrong cwd** (`FileNotFoundError`), the most frequent reason a program "only works in the terminal".
- **Wrong interpreter:** the editor runs a different Python, so imports fail or versions differ.
- **`args` as a string** instead of a list, so the whole string becomes one argument; `env` values that are numbers.
- **Misspelled variables** (`${workspace}` instead of `${workspaceFolder}`).
- **Debugging with a stale breakpoint set** (breakpoints in files not executed, or optimized code).
- **Heisenbugs:** timing or concurrency bugs that disappear under the debugger; add logging.
- **Only changing code and re-running** instead of observing state; or leaving debug prints and breakpoints in committed code.
- **Committing machine-specific launch files** with absolute paths (`/home/me/...`); use variables.
- **Skipping the regression test**, so the bug returns.

## Alternatives and trade-offs

| Need | Tool | Trade-off |
| --- | --- | --- |
| Quick look at a value | `print` / logging | no tool needed; clutter; cannot inspect other variables |
| Inspect state at a point | breakpoint and step | exact; slower for large loops |
| Failure in remote or headless code | `pdb` / `breakpoint()`, remote attach | works anywhere with a terminal; less visual |
| Intermittent or long-running failures | logging, assertions, core dumps/traces | no interactive stop; needs prior instrumentation |
| Find the change that broke it | `git bisect run` | needs a script that detects the failure |
| Performance, not correctness | profiler (`cProfile`) | different question |

Start with the cheapest tool that answers your question; escalate to the debugger when you need to see state you did not print.
