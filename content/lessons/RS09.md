## Why this matters

Research code changes constantly: you tweak a threshold, regenerate a dataset, switch a library. A month later someone asks "which settings produced Figure 3?" and the honest answer is often "I am not sure". A result you cannot trace is a rumour, even if it was once correct.

The remedy is not heavy infrastructure. It is a habit: every run writes down which **code**, which **config** and which **data** produced it, using identifiers that cannot silently change (hashes). With that, you can reproduce a result, explain a difference between two runs, and notice when a file has been corrupted or edited.

## Intuition

Treat a result as the output of a function with three inputs: `result = f(code, config, data)` (plus the seed, which belongs to the config). If you can name the three inputs exactly, the result is reproducible in principle. A **hash** is a short fingerprint of an input: change one byte and the fingerprint changes completely, so comparing fingerprints is a cheap way to ask "is this exactly the same thing?".

![Three inputs, a git revision, a config hash and a data hash, feed a seeded run that writes a result and a manifest; later verification recomputes the three hashes and names which one changed.](/lesson-figures/RS09.svg)

*The manifest sits next to every result; verifying it later tells you whether the code, config or data changed.*

The manifest is deliberately boring. Its value comes from being written automatically on every run, not from being clever.

## Theory and derivation

### Organise the project

Following Good Enough Practices in Scientific Computing: keep raw data **read-only and separate** from derived data, put code in version control, keep configuration in files (not edited inline), give every run its own output folder, and keep generated results out of git unless they are small and final. A common layout:

```text
project/
  data/raw/        # never edited; hashed
  data/derived/    # produced by scripts
  configs/         # one YAML or JSON per experiment
  src/             # code, in git
  runs/<run_id>/   # result files + manifest.json
```

### Versioning code

Git identifies each commit by a hash of its content and history. Record it with `git rev-parse HEAD`. If the working tree has uncommitted edits, `HEAD` does not describe the code that ran, so check `git status --porcelain` (empty means clean) and either refuse to run on a dirty tree, or record the hash of `git diff`. Use `git tag -a v1-paper -m "code for submission"` to name important revisions, since a branch name moves but a tag does not.

### Hashing

A cryptographic hash $H$ maps bytes to a fixed-size digest (SHA-256: 256 bits, 64 hex characters). Properties you rely on: the same bytes always give the same digest; changing any input bit changes about half the output bits; finding two inputs with the same digest is computationally infeasible. In Python:

- hash **bytes**, not "text", so newline and encoding conventions cannot change the digest;
- read large files in **chunks** and call `update` for each chunk, so memory stays small and the digest equals that of the whole file.

Short prefixes are convenient but collide more easily. For $b$ bits and $k$ items, the chance of at least one collision is approximately

$$P\approx 1-\exp\!\left(-\frac{k^2}{2\cdot 2^{b}}\right).$$

### Hashing a config

Two configs that mean the same thing can serialise differently: `{"a":1,"b":2}` versus `{"b":2,"a":1}`. Dump to **canonical JSON** (sorted keys, fixed separators) before hashing, so only real changes alter the hash. Floats have one pitfall: `0.10` and `0.1` parse to the same number and hash identically, while the string `"0.1"` is a different value and hashes differently, which is correct.

### Determinism

A manifest only helps if the run is repeatable. Seed every random number generator you use; know the other sources of variation: multi-threaded reductions, non-deterministic GPU kernels, dictionary or set ordering over unhashed data, wall-clock time, library versions. The test is simple: run twice with the same manifest and compare result hashes. If they differ, the manifest is missing an ingredient.

## Worked example

A toy experiment computes the mean of a data file plus seeded noise.

**Step 1, inputs.** Data file bytes `b"x\n1\n2\n3\n"`; config `{"seed": 7, "noise": 0.1, "lr": 0.01}`; code revision `a1b2c3d`.

**Step 2, run.** The data are $1,2,3$ with mean $2.0$. A generator seeded with 7 draws noise $-0.0256$ (to 4 decimals), so the result is $1.9744$.

**Step 3, hashes.** Canonical config string is `{"lr":0.01,"noise":0.1,"seed":7}`. Its SHA-256 starts `63fac9eb4f7d...`. The SHA-256 of the data bytes starts `4bf0e63035dd...`.

**Step 4, manifest.**

```json
{"result": 1.9744, "seed": 7, "config_sha": "63fac9eb4f7d...", "data_sha": "4bf0e63035dd...", "code_rev": "a1b2c3d"}
```

**Step 5, tamper tests.** Recompute and compare against the manifest, one change at a time:

- change `lr` to `0.1`: only `config_sha` differs;
- change the last data byte (`3` to `4`): only `data_sha` differs;
- check out another commit: only `code_rev` differs;
- change nothing: nothing differs, and rerunning gives exactly $1.9744$.

**Step 6, check that could reject you.** Re-run the experiment from a fresh clone on another machine using only the manifest. If it does not give $1.9744$, an ingredient is missing (a library version, an unseeded generator, a hidden environment variable).

## Reference implementation

The Python below hashes bytes and files, canonicalises configs, runs a seeded toy experiment, writes a manifest and verifies it. Standard library only.

```python
import hashlib
import json
import random
import statistics


def sha256_bytes(data):
    """Hex SHA-256 digest of a bytes object."""
    return hashlib.sha256(data).hexdigest()


def sha256_file(path, chunk=1 << 20):
    """Hex SHA-256 of a file, read in chunks so large files fit in memory."""
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for block in iter(lambda: f.read(chunk), b""):
            h.update(block)
    return h.hexdigest()


def config_hash(cfg):
    """Hash of a config that ignores key order: canonical JSON (sorted keys, no spaces)."""
    canon = json.dumps(cfg, sort_keys=True, separators=(",", ":"))
    return sha256_bytes(canon.encode("utf8"))


def run_experiment(cfg, data):
    """A tiny seeded 'experiment': mean of the data plus seeded noise of scale cfg['noise']."""
    rng = random.Random(cfg["seed"])
    return statistics.mean(data) + rng.gauss(0, cfg["noise"])


def make_manifest(result, cfg, data_bytes, code_rev):
    """Everything needed to say which code, config and data produced a result."""
    return {"result": result, "seed": cfg["seed"], "config_sha": config_hash(cfg),
            "data_sha": sha256_bytes(data_bytes), "code_rev": code_rev}


def verify(manifest, cfg, data_bytes, code_rev):
    """Return the list of manifest fields that no longer match (empty list = intact)."""
    now = make_manifest(manifest["result"], cfg, data_bytes, code_rev)
    return [k for k in ("config_sha", "data_sha", "code_rev") if now[k] != manifest[k]]


if __name__ == "__main__":
    data_bytes = b"x\n1\n2\n3\n"
    data = [1.0, 2.0, 3.0]
    cfg = {"seed": 7, "noise": 0.1, "lr": 0.01}
    r1 = run_experiment(cfg, data)
    r2 = run_experiment(dict(reversed(list(cfg.items()))), data)
    assert r1 == r2                                  # same seed, same result
    m = make_manifest(round(r1, 4), cfg, data_bytes, "a1b2c3d")
    print(json.dumps({k: (v[:12] if isinstance(v, str) and len(v) > 12 else v) for k, v in m.items()}))
    assert verify(m, cfg, data_bytes, "a1b2c3d") == []
    assert verify(m, {**cfg, "lr": 0.1}, data_bytes, "a1b2c3d") == ["config_sha"]
    assert verify(m, cfg, b"x\n1\n2\n4\n", "a1b2c3d") == ["data_sha"]
    assert verify(m, cfg, data_bytes, "ffffff0") == ["code_rev"]
    assert sha256_bytes(b"abc").startswith("ba7816bf8f01cfea")
    print("self-test passed")
```

Running it prints:

```text
{"result": 1.9744, "seed": 7, "config_sha": "63fac9eb4f7d", "data_sha": "4bf0e63035dd", "code_rev": "a1b2c3d"}
self-test passed
```

## Independent practice

### Goal

Build the provenance toolkit (hashing, canonical config hash, manifest, verification) and use it on a small seeded experiment so that every kind of change is detected and named.

### Setup

Python 3 standard library only; `git` is optional for the extension. Create `provenance.py`, paste the starter code, then paste the tests below it and run `python3 provenance.py`.

### Tasks

1. Implement `sha256_bytes` and compare with `sha256sum` on a file of your own.
2. Implement `sha256_file` with chunked reads and test with `chunk=3`.
3. Implement `config_hash` with canonical JSON; check key-order independence.
4. Implement `make_manifest` and `verify`.
5. Run `run_experiment` twice with the same config (same result?) and with seed 8 (different result?).
6. Turn your own data file into `data/raw/`, write the manifest as JSON next to the result, and change one byte of the data to see `verify` fail.

### Starter code

```python
import hashlib
import json
import random
import statistics


def sha256_bytes(data):
    """Return the hex SHA-256 digest (64 characters) of a bytes object."""
    raise NotImplementedError


def sha256_file(path, chunk=1 << 20):
    """Return the hex SHA-256 of the file at `path`, reading `chunk` bytes at a time
    (the result must not depend on the chunk size)."""
    raise NotImplementedError


def config_hash(cfg):
    """Hash of a config dict that does NOT depend on key order: dump canonical JSON
    (sorted keys, separators (',', ':')), encode as UTF-8, and hash it."""
    raise NotImplementedError


def run_experiment(cfg, data):
    """Given: a tiny seeded experiment (mean of data plus seeded Gaussian noise)."""
    rng = random.Random(cfg["seed"])
    return statistics.mean(data) + rng.gauss(0, cfg["noise"])


def make_manifest(result, cfg, data_bytes, code_rev):
    """Return a dict with keys: result, seed (from cfg), config_sha (config_hash(cfg)),
    data_sha (sha256_bytes(data_bytes)), code_rev."""
    raise NotImplementedError


def verify(manifest, cfg, data_bytes, code_rev):
    """Return the list of field names among ['config_sha', 'data_sha', 'code_rev'] (in
    that order) whose current value differs from the manifest. [] means intact."""
    raise NotImplementedError
```

### Tests

```python
import os
import tempfile
# 1. known test vectors for SHA-256
assert sha256_bytes(b"abc") == "ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad"
assert sha256_bytes(b"").startswith("e3b0c44298fc1c14")
# 2. file hashing equals bytes hashing, for any chunk size, including an empty file
with tempfile.TemporaryDirectory() as d:
    p = os.path.join(d, "data.csv")
    open(p, "wb").write(b"x\n1\n2\n3\n")
    assert sha256_file(p) == sha256_bytes(b"x\n1\n2\n3\n") == sha256_file(p, chunk=3)
    q = os.path.join(d, "empty")
    open(q, "wb").write(b"")
    assert sha256_file(q) == sha256_bytes(b"")
# 3. config hash ignores key order but notices any value change
a = {"seed": 7, "noise": 0.1, "lr": 0.01}
assert config_hash(a) == config_hash({"lr": 0.01, "noise": 0.1, "seed": 7})
assert config_hash(a) != config_hash({**a, "lr": 0.1})
# 4. same seed -> same result; different seed -> different result
data = [1.0, 2.0, 3.0]
assert run_experiment(a, data) == run_experiment(dict(a), data)
assert run_experiment(a, data) != run_experiment({**a, "seed": 8}, data)
# 5. manifest and verification, one tampering at a time
raw = b"x\n1\n2\n3\n"
m = make_manifest(1.9744, a, raw, "a1b2c3d")
assert set(m) == {"result", "seed", "config_sha", "data_sha", "code_rev"} and m["seed"] == 7
assert verify(m, a, raw, "a1b2c3d") == []
assert verify(m, {**a, "lr": 0.1}, raw, "a1b2c3d") == ["config_sha"]
assert verify(m, a, raw + b"4\n", "a1b2c3d") == ["data_sha"]
assert verify(m, a, raw, "deadbee") == ["code_rev"]
assert verify(m, {**a, "lr": 0.1}, b"", "deadbee") == ["config_sha", "data_sha", "code_rev"]
print("all tests passed")
```

### Library track

Real experiments hash NumPy arrays and trained PyTorch weights, not text. Hash an array by its dtype, shape and bytes, and check that seeding makes two runs byte-identical. Install with `python3 -m pip install numpy torch` (CPU build is enough, in a virtual environment).

```python
import hashlib
import numpy as np
import torch


def array_sha(a):
    """Hash an array by its dtype, shape and C-ordered bytes (not by its printed text)."""
    a = np.ascontiguousarray(a)
    return hashlib.sha256(str((a.dtype, a.shape)).encode() + a.tobytes()).hexdigest()


# 1. NumPy: the same seed gives byte-identical output; another seed does not
run = lambda seed: np.random.default_rng(seed).normal(size=1000).cumsum()
assert array_sha(run(7)) == array_sha(run(7)) != array_sha(run(8))

# 2. dtype is part of the identity: the same numbers as float32 hash differently
x = run(7)
assert array_sha(x) != array_sha(x.astype(np.float32))


# 3. PyTorch: seed every generator, ask for deterministic kernels, run twice, compare hashes
def train(seed):
    torch.manual_seed(seed)
    torch.use_deterministic_algorithms(True)
    torch.set_num_threads(1)
    net = torch.nn.Linear(4, 1)
    opt = torch.optim.SGD(net.parameters(), lr=0.1)
    xs = torch.randn(64, 4)
    ys = xs.sum(dim=1, keepdim=True)
    for _ in range(50):
        opt.zero_grad()
        loss = ((net(xs) - ys) ** 2).mean()
        loss.backward()
        opt.step()
    return array_sha(net.weight.detach().numpy())


h1, h2, h3 = train(0), train(0), train(1)
print("same seed:", h1[:12], h2[:12], "| other seed:", h3[:12])
assert h1 == h2 and h1 != h3

# 4. Negative control: forgetting the seed breaks the manifest check
a, b = torch.randn(3).numpy(), torch.randn(3).numpy()
assert array_sha(a) != array_sha(b)
print("library track passed")
```

Expected: the script prints two equal short digests for seed 0 and a different one for seed 1. `torch.use_deterministic_algorithms(True)` makes PyTorch raise an error for operations that have no deterministic implementation instead of silently varying; GPU runs also need the settings described in the PyTorch reproducibility notes.

## Verification

- **Round trip.** Verify immediately after writing: it must return an empty list.
- **Tamper tests.** Change each ingredient alone; exactly one field should differ (test 5 above).
- **Reproduce from the manifest.** A fresh clone checked out at `code_rev`, with the same data hash and config, gives the same result.
- **Known vectors.** `sha256(b"abc")` begins `ba7816bf`; if not, you hashed text with a transformation.
- **Chunk invariance.** Hashing with chunk sizes 3 and 1 MiB gives the same digest.

## Failure modes

- **Hashing only the first chunk.** Two 5000-byte files differing in the last byte get the same digest (exercise 5), so corruption goes undetected.
- **Dirty working tree.** The logged revision describes code that did not run.
- **Order-dependent config hash.** Same settings, different hash; or worse, different settings, same hash if you hash only a subset of keys.
- **Unseeded randomness or hidden inputs.** Environment variables, current time, and library versions change results without changing any recorded hash.
- **Overwriting raw data.** Once raw data are edited in place, the data hash no longer identifies the original.
- **Manifest saved far from the result.** A manifest that is not stored with the result gets lost.

## Alternatives and trade-offs

| Need | Tool | Trade-off |
|---|---|---|
| Small scripts | Hand-rolled manifest (this lesson) | Transparent, no dependency; you maintain it |
| Large data files | Data version control tools such as DVC | Handles big files and pipelines; more setup |
| Many runs and metrics | Experiment trackers (MLflow, Weights & Biases) | Convenient dashboards; need the same provenance fields underneath |
| Whole environment | Containers or lock files | Fixes library versions; heavier to build |

Hashing everything is cheap for small files and expensive for terabytes; for large data, hash a manifest of file names, sizes and per-file hashes, or use content-addressed storage.

## Transfer and retention

Any pipeline benefits: a robot calibration produces a parameter file (record the calibration data hash and the code that fitted it), a trained model is an artifact (record its training manifest next to the weights), a paper figure is a result (store the manifest in the figure's folder).

To retain it, add the three-line manifest to the next script you write, before you need it.

## Exercise answers

1. Good answers: exact code revision (commit hash, clean tree), config values, data version or hash, random seed, environment (Python and library versions, hardware), command line, date and who ran it, and the metric definition.
2. Raw 2 GB dataset: not in git (too large, use external storage or data version control, keep a hash). `exp1.yaml`: yes (small, defines the experiment). Final `results.csv` of 200 rows: usually yes if small and final. Notebook with 40 MB embedded images: strip outputs or keep out of git. API key: never (use environment variables or a secrets store). Lock file: yes.
3. $7\times4=28$ bits, so $2^{28}=268{,}435{,}456$ abbreviations. $k\approx\sqrt{2\ln2\cdot2^{28}}\approx19{,}300$ commits for a 50% collision chance.
4. A, B, C, D, E: A equals B, C equals D (0.10 and 0.1 are the same float and serialise as `0.1`), E differs because it is a string. Without `sort_keys=True`, A and B serialise in insertion order and hash differently even though they mean the same.
5. It hashes only the first 1024 bytes, so both files get the same digest and corruption after byte 1024 goes unnoticed. Fix: loop over chunks, `for block in iter(lambda: f.read(1 << 20), b""): h.update(block)`.
6. The tree differed from `HEAD`, so checking out `HEAD` gives different code. Repairs: refuse to run on a dirty tree (`git status --porcelain` must be empty), or commit before running; alternatively store the hash or text of `git diff` in the manifest.
7. Examples: unseeded RNG in numpy/torch (record all seeds; run twice and compare), non-deterministic GPU kernels (record flags, compare results), multithreaded reductions (record thread count), library versions (record lock file hash), wall-clock dependent data (freeze the input), dataset shuffling order (record the order or seed). Detection: repeat the run and compare result hashes.
8. $k^2/(2\cdot2^{28})=25{,}000{,}000/536{,}870{,}912=0.04657$, so $P\approx1-e^{-0.04657}\approx 0.0455$ (about 4.5%). A collision of abbreviations only makes the short name ambiguous; git resolves by asking for more characters. With the full 160-bit (or 256-bit) hash the probability is negligible.
9. A good answer: `data/raw` read-only (`chmod a-w`), `configs/exp1.json`, `runs/<run_id>/result.json` and `manifest.json`; a command such as `python run.py configs/exp1.json` and `python verify.py runs/<run_id>`. For a missing file, `verify` must report it as MISSING (not crash, not pass) and exit non-zero.
10. A good answer shows a baseline run, three tamper runs, each with a single changed field in the verify output, a git tag for the code, and a reproduced result from a fresh clone.
