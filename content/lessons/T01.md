## Why this matters

Every robotics, ML and tooling workflow in this curriculum eventually runs on a Linux machine: training scripts on a workstation, ROS 2 nodes on a robot computer, containers in CI. The shell is how you start, inspect and stop all of it. Most "it works on my machine" failures are really failures of the basics: a script that only works from one directory, a file the wrong user cannot read, a command that silently fails inside a pipeline, a background job nobody can find. This lesson teaches the small set of ideas behind the shell (words, quoting, redirection, exit status), permissions, and processes, then turns them into a **repeatable project command** that does not depend on your shell history.

## Intuition

The shell is a program that reads a line, splits it into **words**, expands some of them (variables, globs), finds the program named by the first word, starts it as a **process** with the remaining words as arguments, and waits. Everything else is plumbing: file descriptors 0, 1 and 2 (standard input, output, error) can be redirected to files or connected by pipes; every process ends with an **exit status** (0 means success), which the shell exposes as `$?`.

Three questions explain most Linux surprises. *Where am I?* (current working directory, and the `PATH` that decides which executable a bare name finds.) *Who am I allowed to be?* (user, groups, and the nine permission bits on each file.) *What is running?* (a process tree with IDs, states and signals.)

![Left: the permission bit layout rwx r-x r-- for user, group and other with octal values 4, 2, 1. Right: a pipeline a | b | c with standard output flowing between stages and exit statuses shown, plus the process tree of a shell and its children.](/lesson-figures/T01.svg)

*Nine permission bits give the octal digits (left); a pipeline connects stdout to stdin and its status depends on `pipefail` (right).*

*A mental model: a kitchen with an order slip.* Imagine the shell as a kitchen clerk who receives a slip of paper (your line), cuts it into separate items at the spaces, replaces shorthand (a variable name, a star) with what it stands for, and hands each finished order to a cook (the program). The cook knows nothing about the slip; it only receives the list of items. This explains the most common disaster: if a shorthand expands to something containing a space, the clerk cuts it into two items and the cook receives two orders. A file called `my results` becomes `my` and `results`, and `rm $f` deletes two things you did not mean. Quotes are the instruction "do not cut here".

*Plumbing and permissions.* Each cook has three pipes attached when it starts: input, output, errors. Redirection is rearranging those pipes before the cook starts, in the order written on the slip. Permissions are a guest list on the door of each file: the doorman checks you against the owner line first, then the group line, then "everyone else", and stops at the first line that names you. That is why being in a more generous list lower down does not help an owner who has been given less.

*Predict before you compute.* (a) `f="x  y"; echo $f` and `echo "$f"` print different amounts of space: guess which and why. (b) A directory has mode `311`: can you `ls` it? Can you `cat` a file inside if you know its name? (c) `set -e` is on and a function ends with a failing command inside an `if f; then`: does the script stop? Write your guesses down; the Theory and the Exercises show how to test each in a few seconds.

*Wrong intuitions to drop.* "`set -e` makes every error fatal": it does not, in conditions, `&&`/`||` lists and non-final pipeline stages. "Permissions are additive across classes": they are not, the first match decides. "A long pipeline fails if any stage fails": by default only the last stage counts. "`kill` means destroy": it means *send a signal*, and the default signal can be caught.

## Theory and derivation

### Words, quoting and expansion

The shell splits on unquoted whitespace. `echo a   b` runs `echo` with two arguments; `echo "a   b"` with one. Double quotes allow `$variable` expansion; single quotes suppress everything. An unquoted `$f` containing spaces becomes several words, which is the single most common cause of scripts that delete the wrong thing. Quote every expansion: `"$f"`.

### Redirection and pipes

`cmd > out` sends stdout to a file (truncating), `>>` appends, `2> err` redirects stderr, `2>&1` makes fd 2 a copy of wherever fd 1 currently points. **Order matters**: `cmd > f 2>&1` sends both to `f`; `cmd 2>&1 > f` points stderr at the *old* stdout (the terminal) and then moves stdout to `f`. `a | b` connects `a`'s stdout to `b`'s stdin; the stages run concurrently.

### Exit status

`0` means success; anything else is a failure code chosen by the program. Conventions: `126` found but not executable, `127` command not found, `128+N` killed by signal $N$ (so `137` is SIGKILL and `143` is SIGTERM). A pipeline's status is, by default, that of the **last** stage, so `false | true` succeeds. `set -o pipefail` makes it the right-most failing stage's status. `set -e` (errexit) stops a script at the first failing command, `set -u` makes unset variables errors. The strict header `set -euo pipefail` turns many silent failures into loud ones (it has exceptions, for example commands in `if` conditions, so it is a safety net, not a proof).

### Permissions

Each file has an owner, a group and three permission triplets: **r**ead (4), **w**rite (2), e**x**ecute (1), for user, group and other. The mode `rwxr-x---` is octal $7\,5\,0$. Access is decided by the **first matching class**: owner, else group, else other. So a file with mode `070` owned by you is *not* readable by you even though your group has all rights. Directories use the same bits with different meaning: `x` is the right to enter/traverse, `r` the right to list names, `w` the right to create/delete entries. New files are created with the requested mode minus the **umask**: $\text{mode}\ \&\ \sim\text{umask}$. With umask `022`, regular files (requested `666`) become `644`, directories (`777`) become `755`. A file runs as a program only with an `x` bit; a first line `#!/usr/bin/env bash` (the shebang) chooses the interpreter.

### Processes and signals

Each process has a PID and a parent PID. The shell starts children; `cmd &` runs one in the background, `jobs` lists them, `ps`/`top` show all. Signals are asynchronous messages: `SIGINT` (Ctrl-C, 2), `SIGTERM` (15, polite "please exit", can be handled), `SIGKILL` (9, cannot be caught, no cleanup). Always try TERM first so a program can flush files. Resource state lives in `df -h` (disk), `du -sh` (directory size), `free -h` (memory) and `ulimit -a` (limits).

### A repeatable project command

A command is repeatable when it does not rely on your shell history, current directory, exported variables or manual edits. Properties: a shebang and the exec bit; strict mode; `cd` to the script's own directory; arguments with defaults and validation; deterministic outputs in a known folder; a log; meaningful exit codes (0 ok, 2 usage error); documentation in a comment header.

### The order of expansions in detail

Bash does not "just substitute variables". It processes each command line in a fixed order (GNU Bash Reference Manual, §3.5): brace expansion; then tilde, parameter and variable, arithmetic expansion and command substitution (left to right); then word splitting; then filename expansion (globbing); and finally quote removal. Only brace expansion, word splitting and filename expansion can increase the number of words; the exceptions are `"$@"` and `$*`. Two consequences follow. First, **word splitting and globbing apply to the *results* of expansions that were not in double quotes** (§3.5.7), but not to literal words. If `f="a b.txt"`, then `set -- $f` produces 2 words and `set -- "$f"` produces 1 (checked in Bash 5.1). If `v='*.txt'` and the directory holds `a b.txt` and `c.txt`, then the unquoted `$v` expands to 2 words (each match one word, because splitting happens before globbing and the glob result is not split again) while `"$v"` stays the literal 1 word `*.txt`. Second, `IFS` decides the split characters: with `IFS=:` the string `u:v w:z` becomes 3 fields `u`, `v w`, `z`; spaces no longer split. The difference between `$*` and `"$@"` is the same story: for the arguments `"p q"` and `r`, unquoted `$*` yields 3 words, `"$*"` yields 1 word `p q r`, and `"$@"` yields exactly the original 2 words. The rule to remember is not "always quote" but "quote every expansion unless you *want* splitting and globbing, and then say so in a comment".

### Redirection as file-descriptor plumbing

A redirection edits the table of open file descriptors of the child before the program starts, and **the redirections of one command are applied strictly left to right** (§3.6). `n>&m` makes descriptor $n$ a copy (a duplicate) of whatever $m$ points to *at that moment* (§3.6.8); it does not link them. Therefore `cmd >f 2>&1` first points fd 1 to `f` and then copies it onto fd 2 (both in `f`), whereas `cmd 2>&1 >f` first copies the terminal onto fd 2 and then moves fd 1 to `f`. In a pipeline `a | b`, the pipe is connected to fd 1 of `a` *before* the redirections of `a` are applied, which makes a classic idiom possible: `cmd 3>&1 1>&2 2>&3 | next` saves the pipe in fd 3, points stdout at the old stderr (the terminal), points stderr at the saved pipe, so `next` reads **only the former stderr** of `cmd` while stdout still goes to the terminal. The idiom `cmd 2>&1 >/dev/null | next` is the simpler version that discards stdout. Descriptors above 2 are free for scripts to use (`exec 3>log` keeps a log open for the whole script), and `exec` without a command applies the redirection to the current shell.

### When `set -e` does and does not stop the script

`set -e` (errexit) makes the shell exit when a pipeline, list or compound command returns non-zero, **except** when the failing command is part of the test of `if`/`elif`/`while`/`until`, part of an `&&` or `||` list other than the last command, a non-final stage of a pipeline (subject to `pipefail`), or negated with `!` (GNU Bash Reference Manual, §4.3.1, `set -e`). The subtle part is inheritance: if a function is *called* in such a context, `-e` is ignored for the whole function body, so in `f() { false; echo after; }; if f; then ...` the line `after` is printed (verified). Called plainly, the same function stops at `false` with status 1. Other traps: `local v=$(false)` returns the status of `local`, which is 0, so the failure is masked (declare, then assign); `x=$(false; echo hi)` gives `x=hi` because the command substitution's status is the last command; and `((n++))` with `n=0` evaluates to 0, which arithmetic reports as status 1, killing a strict script at an innocent line. The `ERR` trap obeys the same exceptions (§4.1, `trap`). The practical conclusion is that `set -e` is a safety net, not a control-flow tool: handle expected failures explicitly with `cmd || handle`, and use `set -u`, `pipefail` and `trap ... EXIT` beside it.

### Permissions as bit algebra

The permission check is described precisely in path_resolution(7): the first class that applies is used, namely the owner class if the effective UID equals the owner, else the group class if the file's group is the effective or a supplementary group of the process, else the other class; the superuser (or a capability) bypasses it. The three bits mean read, write and execute for files, but *list names*, *create/delete entries* and *search (traverse)* for directories. This gives non-obvious results (verified on Linux): in a directory of mode `311` you cannot list (`ls` is denied) but you can open a file whose name you know, because traversal needs only `x`; deleting a file depends on the **directory's** `w` and `x` bits, not on the file's own bits (a mode `000` file in a `755` directory can be removed, while a `444` file in a `555` directory cannot). The sticky bit on a directory restricts deletion or renaming to the owner of the file, the owner of the directory, or a privileged process (inode(7)), which is why `/tmp` is mode `1777`. The umask is a **mask, not a subtraction**: the kernel creates the file with `mode & ~umask` (umask(2)). The two agree only when the umask bits are a subset of the requested bits: with umask `033`, a requested `666` gives `644`, not the `633` that subtraction suggests.

### Signals, traps and exit status

A process ending because of signal $N$ is reported as status $128+N$ by the shell. `SIGKILL` (9) and `SIGSTOP` cannot be caught or ignored; `SIGTERM` (15) can. In a script, `trap 'commands' EXIT` runs the commands on every normal or error exit, which is the right place to delete temporary directories. A subtle rule from the Bash manual (§3.7.6): if Bash is waiting for a *foreground* command and receives a signal for which a trap is set, the trap is not executed until that command completes; if it is waiting with the `wait` builtin, `wait` returns immediately with status greater than 128 and the trap runs. In a script that does `sleep 4` in the foreground and receives `SIGTERM` after 1 s, the trap runs at 4 s; written as `sleep 4 & wait $!` it runs at 1 s (both measured). This is why long-running jobs in a script are often started in the background and waited on.

### How this connects to the rest of CoreLab

The same ideas reappear everywhere: a Python subprocess call is a fork and exec with the same descriptors and exit status; a Docker container is a process tree with a restricted view of users and files; CI runs your script with `set -e` off or on depending on the runner. Whenever a pipeline silently misbehaves, ask three questions in order: what words did the command receive, which descriptors did it have, and what status did each stage return?

## Worked example

### Basic cases

**Problem.** (a) Convert the symbolic mode `rwxr-x---` to octal and the octal mode `0640` to symbols. (b) A file is requested with mode $666$ and a directory with $777$ under umask $022$; repeat with umask $027$. (c) A file is owned by `alice:robots` with mode `0640`. What can Alice (owner), Bob (member of `robots`) and Carol (neither) do? (d) What are the exit status of `grep foo missing.txt | wc -l` by default and with `pipefail`, given that the file does not exist? (e) Where does the error message of `ls /nonexistent > o.txt 2>&1` go, and where does that of `ls /nonexistent 2>&1 > o2.txt` go? (f) After `sleep 30 &` and `kill -9 $!`, which status does `wait` report?

**Solution.**

1. (a) Each class is a sum of bits $r=4$, $w=2$, $x=1$: user `rwx` $=4+2+1=7$, group `r-x` $=4+0+1=5$, other `---` $=0$, so the mode is $750$.
2. The octal `0640` reads class by class: $6=4+2$ is `rw-`, $4$ is `r--`, $0$ is `---`, giving `rw-r-----`.
3. (b) The kernel clears the umask bits: $\text{mode}\ \&\ \sim\text{umask}$. For umask $022$: file $666\ \&\ \sim022=644$ (clear the write bit of group and other); directory $777\to755$.
4. For umask $027$: file $666\ \&\ \sim027=640$ (group loses write, other loses all); directory $777\ \&\ \sim027=750$.
5. (c) The kernel picks exactly one class: the owner class if the user is the owner, else the group class if in the group, else other. Alice is the owner, class `rw-`: read yes, write yes, execute no. Bob is in `robots`, class `r--`: read yes, write no. Carol is neither, class `---`: nothing.
6. (d) A pipeline's status is that of its last command by default. `grep` exits $2$ (file missing), `wc -l` reads empty input, prints `0` and exits $0$, so the status is $0$. With `set -o pipefail` the status is the last non-zero status in the pipeline: $2$.
7. (e) Redirections are processed left to right. In `> o.txt 2>&1`, stdout goes to `o.txt` first, then fd $2$ is made a copy of fd $1$, so the error message lands in `o.txt`. In `2>&1 > o2.txt`, fd $2$ is first copied from the terminal (the current stdout), then stdout is redirected: the message appears on the terminal and `o2.txt` stays empty.
8. (f) A process killed by signal $n$ reports status $128+n$. For `kill -9`, $128+9=137$.

**Check.** All of these were run in bash: `PIPESTATUS` was `2 0`, the default status $0$, `pipefail` status $2$; `o.txt` held the message and `o2.txt` had size $0$; `wait` returned $137$. Python gave the umask results $644,755,640,750$. For (a) the two conversions are inverse: $7,5,0$ back to bits is `rwx r-x ---`.

**Takeaway.** Modes are three octal digits of $r/w/x$ bits, the umask only removes bits, and the shell reads redirections left to right.

### A harder case: a defensive script that fails loudly and cleans up

**Problem.** Sum the byte counts of all `*.txt` files in a directory whose names may contain spaces, create temporary files safely, and remove them whatever happens. The script below is run in a directory with `a b.txt` containing `hello\n` ($6$ bytes) and `c.txt` containing `hi\n` ($3$ bytes):

```bash
#!/usr/bin/env bash
set -euo pipefail
tmp=$(mktemp -d)
trap 'rm -rf -- "$tmp"; echo "cleanup done" >&2' EXIT
dir=${1:?usage: hard.sh DIR}
cd -- "$dir"
for f in *.txt; do
  [ -e "$f" ] || { echo "no txt files" >&2; exit 3; }
  wc -c < "$f" > "$tmp/${f// /_}.size"
done
cat "$tmp"/*.size | paste -sd+ | bc
```

What does `./hard.sh .` print and return? What happens with `./hard.sh empty` (a directory with no `.txt` files) and with no argument? Explain the design choices.

**Solution.**

1. `set -euo pipefail` makes the script stop on an unhandled error (`-e`), on an unset variable (`-u`) and on a failure inside a pipeline (`pipefail`). `mktemp -d` creates a unique private directory, and `trap '...' EXIT` registers the cleanup, which runs on every exit path, normal or error.
2. `./hard.sh .`: the loop visits `a b.txt` and `c.txt`. `wc -c < "$f"` is run with input redirection so that it prints only the number ($6$ and $3$), without the file name. The name `a b.txt` is written as `a_b.txt.size` (`${f// /_}` replaces spaces), so the temporary file name has no space.
3. `cat "$tmp"/*.size | paste -sd+ | bc` joins the numbers with `+` giving `6+3`, and `bc` prints `9`. Then the trap prints `cleanup done` and the status is $0$.
4. `./hard.sh empty`: no file matches `*.txt`, so the glob stays the literal string `*.txt`. The guard `[ -e "$f" ]` is false, the script prints `no txt files`, exits with status $3$, and the trap still removes `$tmp`.
5. `./hard.sh` without an argument: `${1:?usage: hard.sh DIR}` aborts with the usage message and status $1$, and the EXIT trap deletes the temporary directory that was already created.
6. Design points: every expansion is quoted (`"$f"`, `"$tmp"`) so names with spaces stay one word; `--` ends option parsing in case a name starts with `-`; the redirect with `<` removes the file name from `wc` output; the no-match glob is a literal, hence the `-e` guard; and the trap covers all the error paths.

**Check.** Measured: `./hard.sh .` printed `9` then `cleanup done` with status $0$; `./hard.sh empty` printed `no txt files` then `cleanup done` with status $3$; `./hard.sh` printed the usage message then `cleanup done` with status $1$. The sum $6+3=9$ agrees with `wc -c` on the two files.

**Takeaway.** A defensive script quotes every expansion, guards the glob that matches nothing, fails loudly with distinct exit codes, and puts cleanup in an `EXIT` trap so it runs on every path.

## Reference implementation

A small Python model of the rules above: permission bit conversion, umask, the owner/group/other access decision, pipeline and `set -e` semantics, word splitting, `PATH` lookup and signal exit codes. (It models the concepts; the real shell and kernel are the authority.)

```python
import shlex

def sym_to_octal(s):
    """'rwxr-x---' -> 0o750 (nine permission characters, no file-type prefix)."""
    assert len(s) == 9
    return sum((1 << (8 - i)) for i, ch in enumerate(s) if ch != "-")

def octal_to_sym(m):
    return "".join(ch if m & (1 << (8 - i)) else "-" for i, ch in enumerate("rwxrwxrwx"))

def apply_umask(mode, umask):
    """Permissions of a newly created file/dir: the requested mode with the umask bits cleared."""
    return mode & ~umask & 0o777

def can_access(mode, owner, group, uid, gids, op):
    """Classic Unix check for op in 'r', 'w', 'x'. The FIRST matching class decides:
    owner if uid == owner, else group if group in gids, else other. uid 0 (root) may read/write
    anything and may execute only if some execute bit is set."""
    bit = {"r": 4, "w": 2, "x": 1}[op]
    if uid == 0:
        return True if op != "x" else bool(mode & 0o111)
    if uid == owner:
        cls = (mode >> 6) & 7
    elif group in gids:
        cls = (mode >> 3) & 7
    else:
        cls = mode & 7
    return bool(cls & bit)

def pipeline_status(statuses, pipefail):
    """Exit status of 'a | b | c' given each stage's status: the last stage's, or with pipefail
    the status of the right-most failing stage (0 if none failed)."""
    if not pipefail:
        return statuses[-1]
    for s in reversed(statuses):
        if s != 0:
            return s
    return 0

def errexit_run(statuses, errexit):
    """Run commands whose exit statuses are given. With errexit ('set -e') stop right after the first
    non-zero status. Return (number_executed, last_status)."""
    last = 0
    for i, s in enumerate(statuses):
        last = s
        if errexit and s != 0:
            return i + 1, last
    return len(statuses), last

def split_words(line):
    """How the shell splits a command line into words (quotes group, backslash escapes)."""
    return shlex.split(line)

def find_in_path(cmd, path, executables):
    """First directory in the colon-separated PATH where dir + '/' + cmd is in the set of executables."""
    for d in path.split(":"):
        if d and f"{d}/{cmd}" in executables:
            return f"{d}/{cmd}"
    return None

def exit_code_for_signal(sig):
    """Shell convention: a process killed by signal N reports 128 + N."""
    return 128 + sig

# tiny self-test
assert sym_to_octal("rwxr-xr--") == 0o754 and octal_to_sym(0o640) == "rw-r-----"
assert apply_umask(0o666, 0o022) == 0o644 and apply_umask(0o777, 0o027) == 0o750
assert pipeline_status([1, 0], False) == 0 and pipeline_status([1, 0], True) == 1
```

## Verification

- **Same result from anywhere:** run the command from `/`, from `/tmp` and from the project directory; outputs must be identical.
- **Hand computations:** modes $750$, $644$, $640$; `137`/`143`; pipeline status $0$ vs $1$.
- **Invariants:** octal/symbolic conversion round-trips for all $512$ modes; a umask never adds permissions.
- **Failure path:** invalid input must exit non-zero and write nothing to `out/result.txt`.
- **Falsifier:** if the script depends on something not in the repository (an alias, an exported variable, the current directory), a clean shell (`env -i bash --noprofile --norc ./run.sh`) will reveal it.

## Failure modes

- **Unquoted variables** splitting at spaces or expanding to nothing (`rm -rf $DIR/` with empty `DIR` removes `/`; always quote and validate).
- **`cd` that fails silently** and later commands run in the wrong directory (`set -e`, or `cd dir || exit 1`).
- **Relying on cwd:** works from the project folder, breaks from cron or CI.
- **Pipeline hides failure:** `producer | consumer` reports success when `producer` crashed.
- **Wrong redirection order**, losing stderr.
- **Permission surprises:** the owner class overrides the group class; `x` missing on a directory blocks `cd`; `umask 077` makes shared files unreadable.
- **`kill -9` first:** no cleanup, truncated output files.
- **Editing the installed copy of a script** instead of the repository version.
- **`#!/bin/bash` hard-coded** on systems where bash is elsewhere (prefer `#!/usr/bin/env bash`).

## Alternatives and trade-offs

| Need | Tool | Trade-off |
| --- | --- | --- |
| A few commands, one machine | shell script | quick; fragile quoting; hard to test |
| Named tasks with dependencies | Makefile / `just` | declarative; tab/syntax quirks |
| Logic, parsing, data | Python script with `argparse` | portable and testable; slower start |
| Many machines or environments | container or CI pipeline (T06) | reproducible; more setup |
| Long-lived services | systemd unit / supervisor | restarts, logging; needs privileges |

Use shell for glue (a dozen lines); switch to Python once you need data structures, error handling beyond exit codes, or tests.

For (iii): the pipe is already on fd 1; `3>&1` copies the pipe to fd 3; `1>&2` makes fd 1 a copy of fd 2 (the terminal); `2>&3` makes fd 2 a copy of fd 3 (the pipe); now `cmd`'s stderr feeds the pipe and its stdout goes to the terminal: a swap using a spare descriptor.
