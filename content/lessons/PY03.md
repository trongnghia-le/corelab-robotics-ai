## Why this matters

Many of the most expensive Python bugs in robotics code are not syntax errors or wrong formulas but wrong assumptions about *which object* a name refers to. A planner that "copies" a path and then mutates the copy also changes the original; an occupancy grid built with `[[0]*n]*n` lights up an entire column when one cell is set; a default argument accumulates measurements across calls; a lambda inside a loop captures the last loop value. These bugs produce plausible numbers, so they survive tests that only look at one call. The cure is a clear mental model of Python's data model: names, objects, identity, mutability and scope.

## Intuition

In Python a variable is not a box that holds a value; it is a **name tag attached to an object**. `b = a` attaches a second tag to the same object. Nothing is copied. If the object is **immutable** (an int, string or tuple) you cannot change it in place, so rebinding a tag is the only way to "change" it and aliasing is harmless. If the object is **mutable** (a list, dict, set or most user classes) every tag sees the same change.

![Two diagrams: a grid made by repeating a list holds three references to one row, so setting one cell changes every row; a list comprehension makes three distinct rows](/lesson-figures/PY03.svg)

*Figure: left, `[[0]*3]*3` repeats one reference, so the three tags `grid[0]`, `grid[1]`, `grid[2]` lead to one list; right, a comprehension builds three separate rows. Count the arrows that end at each list.*

Think of two engineers who each hold a link to the same shared spreadsheet. When one of them edits a cell through her link, the other sees the change at once, because there is only one spreadsheet. "Making a copy" is a separate, deliberate act that produces a second spreadsheet. A number or a tuple behaves like a printed page: you cannot edit it, so to "change" it you print a new page and move your own tag to it; nobody else's tag moves.

Now a robot. A planner returns `path`, a logger stores `history.append(path)`, and later the planner does `path.append(goal)` for the next goal. The log then shows the *same* list in every slot, all ending at the latest goal, and the plausible-looking numbers hide the bug. Nothing is wrong with `append`. The wrong assumption is that `history.append(path)` stored a snapshot; it stored a second tag on the live object. The fix is to decide, at the boundary, whether you want a snapshot (`path.copy()` or `tuple(path)`) or a shared object, and to write that decision into the function's contract.

**Predict before you compute.** Take `a = [[0]*2]*2; a[0][0] = 1`. What is `a`? Then take `x = 5; y = x; y += 1` and `l = [5]; m = l; m += [6]`: which of `x` and `l` changed? Write your answers down, draw the tags and the objects, and only then run the code. (Answers: `a` is `[[1, 0], [1, 0]]`; `x` stays 5 while `l` becomes `[5, 6]`.)

Three intuitions are tempting and wrong. First, "`b = a` copies `a`": it does not; it adds a tag. Second, "`[[0]*3]*3` is a 3 by 3 table of independent cells": it is one row seen three times. Third, "`x += y` is just shorthand for `x = x + y`": that is true for numbers and false for lists, where `+=` extends the existing object. The scope rules have their own wrong picture: that Python runs the lines in order and uses the global until it meets an assignment. In fact the compiler decides, before anything runs, which names are local to a function, and that decision is the same for every line of the body.

Scope answers a different question: *which name does this identifier mean here?* Python looks in the innermost function first, then enclosing functions, then the module, then built-ins (the LEGB rule). It is like looking up a phone number: your own contacts first, then your team's list, then the company directory, then the public phone book. Which lists you may search is fixed by where the name is *written* in the source (lexical scoping), not by who happens to call the function.

## Theory and derivation

### Names, identity, equality

Every object has an **identity** (`id(x)`, an integer unique among live objects, in CPython its address), a **type** and a **value**. `a is b` compares identities; `a == b` compares values via `__eq__`. Two equal objects can be distinct (`[1] == [1]` but `[1] is not [1]`), and identity of small immutable values is an implementation detail (interning), so never test numbers or strings with `is`; use `is` for `None` and sentinel objects only. A subtle effect of memory reuse: `id([]) == id([])` can be `True` because the first temporary list is freed before the second is created.

**Example.** A localiser keeps `pose_a = [0.5, 1.2]` (x and y in metres), another module builds `pose_b = [0.5, 1.2]`, and `pose_c = pose_a`. What do `pose_a == pose_b`, `pose_a is pose_b` and `pose_a is pose_c` give, and what happens to `pose_a` and `pose_b` after the robot moves with `pose_c[0] = 0.8`? (Python 3.11.9.)

**Solution.** `==` compares values and `is` compares identities. `pose_a` and `pose_b` hold the same values, so `pose_a == pose_b` is `True`, but they are two separate objects, so `pose_a is pose_b` is `False`. `pose_c = pose_a` binds a second name to the same object, so `pose_a is pose_c` is `True` (one object, two tags). The assignment `pose_c[0] = 0.8` mutates that one object, so `pose_a` becomes `[0.8, 1.2]` as well, while `pose_b` stays `[0.5, 1.2]`. Equal values do not imply one object, and aliases move together.

### Mutability and in-place operations

| Immutable | Mutable |
|---|---|
| `int`, `float`, `bool`, `str`, `bytes`, `tuple`, `frozenset`, `None` | `list`, `dict`, `set`, `bytearray`, user-defined objects |

`x += y` first tries `x.__iadd__(y)`. For a list this extends **in place** (all aliases see it); for an int, string or tuple there is no `__iadd__`, so Python computes `x = x + y`, a **new object** rebound to the name. Thus `l += [1]` inside a function changes the caller's list, while `l = l + [1]` does not. A tuple is immutable only in its slots: `([1], 2)[0].append(9)` is legal because the list inside is mutable.

**Example.** An encoder logger keeps `ticks = [10, 20]` and a helper does `alias = ticks; alias += [30]`. What are `ticks` and `alias is ticks` afterwards? For ints, what are `n` and `m` after `n = 10; m = n; m += 5`?

**Solution.** For a list, `alias += [30]` calls `list.__iadd__`, which extends the list in place and returns the same object, so the name `alias` is rebound to the object it already held: `ticks` is `[10, 20, 30]` and `alias is ticks` is `True`. An int has no `int.__iadd__`, so `m += 5` falls back to `m = m + 5`, which builds a new int `15` and rebinds `m`; `n` still names the old object, so `n == 10` and `m == 15`. In-place extension is visible through every alias; rebinding is not.

### Hashing and mutability: why a list cannot be a dictionary key

A `dict` or `set` finds an item by its hash, and the data model requires that "objects which compare equal have the same hash value" (Python language reference, Data model, §3.3.1 `object.__hash__`). If an object could change its value, and with it the result of `==`, while it sits inside a dict, its hash would change and the lookup would go to the wrong bucket. Python therefore makes the built-in mutable containers **unhashable**: `list.__hash__` is `None`, and `{[1, 2]: 'a'}` raises `TypeError: unhashable type: 'list'`. A tuple is hashable only if every item is: `hash((1, [2]))` raises the same error, which is the tuple-with-a-list trap of the previous subsection seen from another side. A user class that defines `__eq__` without `__hash__` also gets `__hash__ = None` (§3.3.1), because the author has redefined "equal" and Python will not guess a matching hash.

So "hashable" means "its value is fixed for its whole life". Use tuples or `frozenset` for keys and set members, for instance grid cells as `(row, col)`. If you define `__hash__` on a mutable class, never mutate the fields that `__eq__` and `__hash__` read while the object is stored in a hashed container: the entry is then lost, not removed.

**Example.** A path planner keeps `visited = set()` and adds cells as tuples: `visited.add((3, 4))`. What are `(3, 4) in visited` and the result of `visited.add([3, 4])`? For a class `P` whose `__eq__` and `__hash__` read the field `x`, a set `S` holds `p = P(1)` and then `p.x = 2` is executed: what are `P(2) in S`, `P(1) in S` and `len(S)`? (Python 3.11.9.)

**Solution.** A set finds items by hash, so items must be hashable. A tuple of ints is hashable, hence `(3, 4) in visited` is `True`. A list is unhashable (`list.__hash__` is `None`), so `visited.add([3, 4])` raises `TypeError: unhashable type: 'list'`. For `P`, the item was stored in the bucket of `hash(1)`. After `p.x = 2`, `P(2)` hashes to the bucket of `hash(2)`, which does not hold the entry, so `P(2) in S` is `False`; `P(1)` looks in the old bucket, finds the entry, but `__eq__` now compares `2 == 1`, so `P(1) in S` is `False`. The entry is still stored, so `len(S) == 1`: mutating the fields behind a hash loses the entry without removing it.

### Function calls

Arguments are passed by **assignment**: the parameter name is bound to the same object as the argument ("pass by object reference"). A function can mutate a mutable argument, visible to the caller, but rebinding the parameter name affects only the local name. Default values are evaluated **once**, at definition time, so a mutable default is shared by all calls: the idiom is `def f(x, acc=None): if acc is None: acc = []`.

**Example.** A filter clamps sensor readings in place: `def clamp_all(vals, lo, hi): for i, x in enumerate(vals): vals[i] = min(max(x, lo), hi)`. With `r = [-3.0, 0.5, 9.0]` and the call `clamp_all(r, 0.0, 5.0)`, what is `r` in the caller? A second helper `def reset(vals): vals = []` is then called as `reset(r)`: what is `r` afterwards?

**Solution.** The parameter `vals` is bound to the same list as `r`, so `vals[i] = ...` mutates the caller's list. Clamping each reading to $[0, 5]$ gives `min(max(-3.0, 0), 5) = 0.0`, `min(max(0.5, 0), 5) = 0.5` and `min(max(9.0, 0), 5) = 5.0`, so `r == [0.0, 0.5, 5.0]`. In `reset`, `vals = []` only rebinds the local name to a new empty list, and the caller's `r` is untouched: it is still `[0.0, 0.5, 5.0]`. Mutation crosses the call boundary; rebinding does not.

### Copying

- Assignment: no copy.
- `list(a)`, `a[:]`, `a.copy()`, `copy.copy(a)`: **shallow** copy, a new outer container whose elements are the same objects.
- `copy.deepcopy(a)`: recursively copies (and handles cycles and shared references).
- `[row] * n` and `[[0]*c]*r`: repetition repeats the same reference $n$ times.

For nested lists a shallow copy is not enough: `b = a.copy(); a[0][0] = 99` also changes `b[0][0]`.

**Example.** A controller configuration is `cfg = {"gains": [1.0, 0.1], "name": "pid"}`. After `sh = dict(cfg)` (shallow) and `dp = copy.deepcopy(cfg)`, the statements `cfg["gains"][0] = 2.0` and `cfg["name"] = "pd"` are executed. What are `sh` and `dp`?

**Solution.** The shallow copy `sh` is a new dict whose values are the same objects as in `cfg`, so `sh["gains"] is cfg["gains"]`. The statement `cfg["gains"][0] = 2.0` mutates that shared list, so `sh["gains"]` is now `[2.0, 0.1]`. The statement `cfg["name"] = "pd"` rebinds the key `"name"` in `cfg` only, so `sh["name"]` still refers to `"pid"`: `sh == {'gains': [2.0, 0.1], 'name': 'pid'}`. The deep copy `dp` has its own gains list and its own entries, so nothing reaches it: `dp == {'gains': [1.0, 0.1], 'name': 'pid'}`. A shallow copy shares nested mutable objects; a deep copy does not.

### Scope: LEGB, global, nonlocal

A name assigned anywhere in a function is **local** to that function for the whole function body. Reading it before assignment raises `UnboundLocalError`, even if a global of the same name exists. `global x` makes assignments refer to the module-level name; `nonlocal x` refers to a name in the nearest enclosing function. A **closure** captures *variables*, not values: `[lambda: i for i in range(3)]` creates three functions that all read the same `i`, which is 2 after the loop. Binding the value at definition time with a default argument (`lambda i=i: i`) fixes it. Comprehensions and generator expressions have their own scope, so their loop variable does not leak.

**Example.** A watchdog uses `limit = 10` at module level and defines `def check(v): if v > limit: limit = v`. What does the call `check(12)` do, and what changes if `global limit` is added as the first line of the function?

**Solution.** Scope is fixed at compile time: `limit = v` assigns to `limit` in the body, so `limit` is local to `check` for the whole body. The read in `v > limit` therefore looks in the local scope, finds no value, and the call raises `UnboundLocalError: cannot access local variable 'limit' where it is not associated with a value` (the module-level `limit = 10` is never consulted). With `global limit` as the first line, the name refers to the module-level variable, so `12 > 10` is true and the assignment sets the module's `limit` to 12. An assignment anywhere in a function makes the name local unless declared otherwise.

### Free variables, cells, and the class-body exception

Scope is decided **at compile time**, by looking at where a name is bound in the text of each block; the value is looked up **at run time**. A name that is used in a function but bound in an enclosing function is a *free variable*; the compiler stores it in a shared *cell*, and both functions refer to the same cell (Python language reference, Execution model, §4.2.1 "Binding of names" and §4.2.2 "Resolution of names"). Two consequences follow, neither of which needs a loop to appear:

1. **Late binding.** The cell holds a variable, not a value. In `def outer(): x = 1; def inner(): return x; x = 2; return inner`, calling `outer()()` returns `2`, and `outer()().__closure__[0].cell_contents` is the same cell. The famous `[lambda: i for i in range(3)]` is the same phenomenon: one cell for `i`, three functions reading it after the loop has left it at 2.
2. **Class bodies are skipped.** "The scope of names defined in a class block is limited to the class block; it does not extend to the code blocks of methods. This includes comprehensions and generator expressions" (§4.2.2). The one exception is mandated by the comprehension rules: "the iterable expression in the leftmost `for` clause is evaluated directly in the enclosing scope" (§6.2.6), so in a class body `ys = [x * 2 for x in xs]` works (the leftmost iterable `xs` is read in the class namespace), but `zs = [x * k for x in xs for k in xs]` raises `NameError` for the second `xs`, and so does `[k * x for x in range(2)]` when `k` is a class attribute. Methods that need a class constant must reach it as `self.k` or `ClassName.k`.

**Example.** `def make_scaler(k): def s(x): return x * k; k = k * 2; return s` and `f = make_scaler(3)`. What does `f(5)` return, and what is `f.__closure__[0].cell_contents`?

**Solution.** `k` is a free variable of `s`, stored in a cell shared by `s` and the `make_scaler` frame; the cell holds a variable, not the value at definition time. Inside `make_scaler(3)` the line `k = k * 2` rebinds `k` from 3 to $3 \cdot 2 = 6$ in that cell before `s` ever runs. The call `f(5)` then reads the cell and returns $5 \cdot 6 = 30$, not $5 \cdot 3 = 15$, and `f.__closure__[0].cell_contents` is `6`. A closure sees the latest value of the variable.

### Augmented assignment: what is evaluated, in what order, how many times

The reference states three precise rules for `target op= expr` (Python language reference, Simple statements, §7.2.1): the target "is only evaluated once"; the target's *current value* is read before the right-hand side is evaluated (`a[i] += f(x)` looks up `a[i]`, then evaluates `f(x)`, then stores); and the operation is done in place "when possible". The data-model reference (§3.3.8 "Emulating numeric types") spells out the protocol: Python calls `x.__iadd__(y)` if it exists and uses its **return value** as the new binding (it "could be, but does not have to be, self"); if `__iadd__` is missing or returns `NotImplemented`, it falls back to `x.__add__(y)` and `y.__radd__(x)`. The statement then performs a normal store. This is why `t[0] += [5]` on `t=([1],2)` both mutates the inner list *and* raises `TypeError`: the in-place step succeeds, the store back into the tuple slot fails. In bytecode, `L[i] += 1` loads `L` and `i` once, duplicates them, applies a single `BINARY_OP` marked `+=`, and ends in one `STORE_SUBSCR`; `L[i] = L[i] + 1` loads `L` and `i` twice and uses a plain `+` operation (`dis.dis` on CPython 3.11.9).

**Example.** With `calls = []`, `def i(): calls.append(1); return 0` and `L = [10]`, the statement `L[i()] += 5` is executed, and then `L[i()] = L[i()] + 5`. What are `len(calls)` and `L` after each statement?

**Solution.** In `target op= expr` the target is evaluated once, so `L[i()] += 5` calls `i()` once: `len(calls) == 1`, and the slot `L[0]` becomes $10 + 5 = 15$, so `L == [15]`. The spelled-out form `L[i()] = L[i()] + 5` evaluates the index expression twice (once on the right to read, once on the left to store), so `len(calls)` grows by two to $1 + 2 = 3$, and `L[0]` becomes $15 + 5 = 20$: `L == [20]`. The augmented form evaluates the index expression once, the spelled-out form twice.

### Deep copy: the memo dictionary

A shallow copy "inserts references" into a new container; a deep copy "recursively inserts copies" (Python docs, `copy`). Naively recursing has two problems the module names: recursive objects loop forever, and shared substructure is duplicated. `copy.deepcopy(x, memo)` avoids both with a dictionary mapping `id(original)` to its copy for the current pass: before copying an object it looks the object up, and if present returns the existing copy. Hence the *aliasing pattern* of the input is reproduced: if `s = [a, a]` then `d = copy.deepcopy(s)` has `d[0] is d[1]` (but both differ from `a`), and a self-referential list is copied to a self-referential list. The memo lives only for one call: two separate `deepcopy` calls on two containers that share `a` produce two unrelated copies of `a`, unless you pass the same `memo` dictionary to both. Immutable atomic values are returned as they are, and a tuple whose items are all unchanged by copying is returned unchanged (`copy.deepcopy(((1, 2), 'x'))` returns the very same tuple), so deep copying does not always allocate.

**Example.** A walking robot models two legs that share one joint-angle list: `leg = [0.0, 0.0]; robot = [leg, leg]`. After `d = copy.deepcopy(robot)`, what are `d[0] is d[1]` and `d[0] is leg`? What is `n[0] is n[1]` for the naive `n = [list(x) for x in robot]`, and what does that change in the model?

**Solution.** `deepcopy` keeps a memo mapping `id(original)` to its copy. The first element `leg` is copied and recorded; for the second element the memo already holds its copy, which is returned. So `d[0] is d[1]` is `True` (the sharing pattern is reproduced), and `d[0] is leg` is `False` (the copy is a new object). The naive `[list(x) for x in robot]` calls `list(leg)` twice with no memo and makes two unrelated lists, so `n[0] is n[1]` is `False`. That silently changes the model from "one shared joint list" to "two independent ones".

### Default values are objects created at `def` time

"Default parameter values are evaluated from left to right when the function definition is executed. This means that the expression is evaluated once, when the function is defined, and that the same pre-computed value is used for each call" (Python language reference, Compound statements, §8.7). The values are stored in the function object's `__defaults__` tuple (Data model, §3.2.8 "Callable types"), so a mutable default is state that lives in the function. That is a bug when unintended and a legitimate (if obscure) cache when intended; the intended use is only safe if the cached value depends on nothing but the key you cache by.

**Example.** `def tag(name, tags=[]): tags.append(name); return tags`. After `tag("a")` and `tag("b")`, what did the two calls return and what is `tag.__defaults__`?

**Solution.** The default `[]` is evaluated once, when `def` executes, and stored in `tag.__defaults__`; every call that omits `tags` uses that same list. `tag("a")` appends `"a"` to it and returns it, then `tag("b")` appends `"b"` to the same list. Both calls returned that one list, which now prints `['a', 'b']` for both results, and `tag.__defaults__` is `(['a', 'b'],)`. The state lives in the function object, created once at definition time.

## Worked example

### Case 1: the grid bug

**Problem.** A mapper stores occupancy in `grid = [[0]*3]*3` and then marks cell $(1,1)$ with `grid[1][1] = 7`. What does `grid` contain, how many distinct row objects are there, and what is the correct constructor?

**Solution.**

1. `[0]*3` creates one list $L$ = `[0, 0, 0]` (sequence repetition builds a new list from references to the element; ints are immutable, so this is safe).
2. `[L]*3` creates a new outer list with **three references to $L$**, by the same repetition rule, now applied to a mutable element: `grid[0] is grid[1] is grid[2]`.
3. `grid[1][1] = 7` evaluates `grid[1]` first (which is $L$), then stores 7 in slot 1 of $L$.
4. Because all three rows are $L$, printing gives `[[0, 7, 0], [0, 7, 0], [0, 7, 0]]` and `len({id(r) for r in grid}) == 1`.
5. Fix: `grid = [[0]*3 for _ in range(3)]`. The comprehension evaluates `[0]*3` once per iteration, so there are three distinct lists, and `grid[1][1] = 7` gives `[[0, 0, 0], [0, 7, 0], [0, 0, 0]]`.

**Check.** `len({id(r) for r in grid})` is `1` for the buggy grid and `3` for the fixed one (Python 3.11.9); the number of cells equal to 7 is 3 in the first and 1 in the second.

**Takeaway.** Repetition of a mutable element repeats the reference; build nested mutable data with a comprehension.

### Case 2: a default argument that remembers

**Problem.** `def add(x, acc=[]): acc.append(x); return acc`. What does `print(add(1), add(2))` print, what is `add.__defaults__` afterwards, and what does the idiom with `acc=None` print instead?

**Solution.**

1. At `def` time the expression `[]` is evaluated once and stored in `add.__defaults__` (Compound statements, §8.7). Call that list $A$.
2. `add(1)` binds `acc` to $A$ (no argument was given), appends 1 and returns $A$; $A$ is now `[1]`.
3. `add(2)` binds `acc` to the same $A$, appends 2 and returns $A$, now `[1, 2]`.
4. `print` receives the two return values, which are the same object $A$, and formats them after both calls have run: `[1, 2] [1, 2]`. `add.__defaults__` is `([1, 2],)`.
5. With `def add(x, acc=None): if acc is None: acc = []; ...` the list is created inside the call, so the two calls return two different lists: `[1] [2]`, and `add.__defaults__` is `(None,)`.

![Left: the default list of add(x, acc=[]) grows from [ ] to [1] to [1, 2] as one object; right: acc=None gives [1] then [2] as two lists.](/lesson-figures/PY03-4.svg)

*Figure: left, one default list $A$ grows in place from `[ ]` to `[1, 2]` and both calls return it; right, `acc=None` gives `[1]` and `[2]` as two lists.*

**Check.** `add(1) is add(2)` is `True` for the first definition and `False` for the second.

**Takeaway.** A default value is evaluated once; use `None` as a sentinel and create mutable defaults inside the function.

### Case 3: copy depth and a shared sub-object (harder)

**Problem.** `a = [[1, 2], [3, 4]]`, `b = a.copy()`, `c = copy.deepcopy(a)`, then `a[0][0] = 99`. Give `a`, `b`, `c` and say for each pair of rows whether it is the same object as in `a`.

**Solution.**

1. `a.copy()` is a shallow copy: a new outer list whose two slots hold references to the same inner lists $X$ = `[1, 2]` and $Y$ = `[3, 4]` (Copying, theory above).
2. `copy.deepcopy(a)` creates a new outer list and, through the memo dictionary, new inner lists $X'$ and $Y'$ with equal values.
3. `a[0][0] = 99` evaluates `a[0]` (which is $X$) and stores 99 in its slot 0; it does not touch any outer list.
4. So `a == [[99, 2], [3, 4]]`, `b == [[99, 2], [3, 4]]` (it sees $X$) and `c == [[1, 2], [3, 4]]` ($X'$ is separate).
5. Identity of rows: `[x is y for x, y in zip(a, b)]` is `[True, True]`; with `c` it is `[False, False]`.

**Check.** The same run in Python 3.11.9 prints exactly these lists, and `b is a` is `False` although every row is shared.

**Takeaway.** A shallow copy duplicates one level only; for nested mutable data decide the depth you need.

### Case 4: late binding and three fixes (harder)

**Problem.** `fs = [lambda: i for i in range(3)]`. What is `[f() for f in fs]`, why, and what do three fixes produce?

**Solution.**

1. The lambda body contains the free name `i`, which is bound in the enclosing scope, so the compiler stores `i` in a cell shared by all three functions (Execution model, §4.2.2).
2. The loop assigns `i` the values 0, 1, 2 and leaves it at 2; the cell holds 2 when the functions are finally called.
3. So `[f() for f in fs]` is `[2, 2, 2]`, and `fs[0].__closure__[0] is fs[1].__closure__[0]` is `True`.
4. Fix A, default argument: `lambda i=i: i` evaluates `i` at definition time into a parameter; there is no cell (`fs[0].__closure__` is `None`) and the result is `[0, 1, 2]`.
5. Fix B, `functools.partial(lambda i: i, i)`, binds the value inside the partial object: `[0, 1, 2]`. Fix C, a factory `def mk(i): return lambda: i`, makes one new cell per call: `[0, 1, 2]`, with three different cells whose `cell_contents` are 0, 1, 2.

**Check.** The cell contents printed for the buggy list are `[2, 2, 2]`; for fix C they are `[0, 1, 2]` (Python 3.11.9).

**Takeaway.** A closure captures the variable, not its value; bind the value explicitly when you need a snapshot.

## Reference implementation

```python
def make_grid(rows, cols, fill=0):
    return [[fill] * cols for _ in range(rows)]

def aliased_rows(grid):
    """Groups of row indices that are the same list object."""
    seen = {}
    for i, row in enumerate(grid):
        seen.setdefault(id(row), []).append(i)
    return [g for g in seen.values() if len(g) > 1]

def deep_copy_nested(x):
    if isinstance(x, list):
        return [deep_copy_nested(v) for v in x]
    if isinstance(x, tuple):
        return tuple(deep_copy_nested(v) for v in x)
    if isinstance(x, dict):
        return {k: deep_copy_nested(v) for k, v in x.items()}
    return x

def append_to(x, acc=None):
    if acc is None:
        acc = []
    acc.append(x)
    return acc

def make_counter(start=0):
    n = start
    def inc():
        nonlocal n
        n += 1
        return n
    return inc

def make_getters(n):
    return [lambda i=i: i for i in range(n)]

# self-test
bad = [[0] * 3] * 3
bad[1][1] = 7
assert bad == [[0, 7, 0]] * 3 and aliased_rows(bad) == [[0, 1, 2]]
good = make_grid(3, 3)
good[1][1] = 7
assert good == [[0, 0, 0], [0, 7, 0], [0, 0, 0]] and aliased_rows(good) == []
c = make_counter()
assert (c(), c(), c()) == (1, 2, 3)
assert [g() for g in make_getters(3)] == [0, 1, 2]
print("ok")
```

## Verification

Verify semantics experimentally. (1) Predict before running: write the object graph on paper (names, objects, arrows). (2) Check identity with `id()` or `is`, not by printing values. (3) Mutate through one name and read through another. (4) Run the function twice on the same input to expose state shared between calls (defaults, globals, closures). (5) For copies, mutate the *original deeply* and assert the copy is unchanged. A check that could reject you: after a supposed copy, `any(a_sub is b_sub ...)` for mutable sub-objects must be `False`.

## Failure modes

- `[[0]*n]*m`: one list repeated; setting one cell changes every row (the shown grid prints `[[0,7,0],[0,7,0],[0,7,0]]`).
- Shallow copy of nested data: `b = a.copy()` shares inner lists, so a later `a[0][0] = 99` appears in `b`.
- Mutable default arguments: `def f(x, acc=[])` returns `[1, 2] [1, 2]` for `f(1), f(2)`.
- `x += y` on a list inside a function silently mutates the caller's list, while `x = x + y` does not.
- Late-binding closures: `[lambda: i for i in range(3)]` returns `[2, 2, 2]`.
- `UnboundLocalError`: assigning to a name anywhere in a function makes it local everywhere in that function.
- Using `is` for numbers or strings: results depend on interning and can differ between runs or Python versions.
- `t[0] += [5]` on a tuple containing a list both succeeds in mutating the list and raises `TypeError` afterwards.

## Alternatives and trade-offs

Prefer **immutable** data (tuples, `frozenset`, `dataclass(frozen=True)`, `NamedTuple`) for values that should not change; aliasing then cannot hurt and objects are hashable. Mutate in place for large buffers where copying would cost too much (NumPy arrays, big grids), but document it in the function contract. `copy.deepcopy` is general but slow and surprising for objects holding resources (files, locks); a comprehension or a `.copy()` method is fine when you know the depth. For NumPy, slices are **views** that share memory while fancy indexing copies, so the same aliasing concerns appear (PY04). Prefer returning new values from functions unless in-place mutation is the point (`list.sort`, `dict.update`), and name in-place helpers with verbs that signal it.

## Transfer and retention

- A ROS node that stores the last message in an attribute and appends it to a history list may be storing the same mutable message object repeatedly; copy at the boundary if the middleware reuses buffers.
- A configuration dict copied with `dict(cfg)` shares nested sub-dicts across experiments; one run's modification changes another's baseline (PY08).
- From memory: draw the object graph for the worked example, then state the three copy depths. In a week, find a nested structure in your own code and write a test with `is` checks showing which parts are shared.

A class-level `k` used in the element expression, `[k * x for x in range(2)]`, raises `NameError: name 'k' is not defined` for the same reason. Fixes: compute outside the class (module-level helper or a function that builds the table), or pass the class value into the comprehension through its leftmost iterable, e.g. `zs = [x * k for x, k in itertools.product(xs, xs)]` (the single iterable `product(xs, xs)` is leftmost, so `xs` is read in the class scope). (c) `fs[0](5)` returns `5`: the default `i=i` is a parameter, so a caller can overwrite it; the closure is no longer a zero-argument function. `functools.partial(lambda i: i, i)` binds the value in the partial object (no free variable; the lambda has no cell); `def make(i): return lambda: i` called as `make(i)` creates one new cell per call, each holding that call's `i`. The `i=i` default creates no cell at all, only a parameter.
14. Computed on 3.11.9: `fib(20)` returns `6765` and makes `39` calls with the shared memo (the first call computes each `n` once, with `2*20-1 = 39` calls); calling `fib(20)` again makes `1` call, because the memo kept in `fib.__defaults__` persisted; the memo-free version makes `21891` calls. The memo is correct because `fib(n)` depends only on `n`, which is the cache key. For `scaled`: `scaled(2)` returns `2.0`; `scaled(2, factor=3)` also returns `2.0` instead of `6`, because the key `x` does not include `factor`: the cache invariant "the stored value is a function of the key" is violated. `scaled.__defaults__` is `(1.0, {2: 2.0})` afterwards (the dict is the object created at `def` time and mutated since). Fixes: key on `(x, factor)`, i.e. `key = (x, factor)`, or decorate a pure function with `functools.lru_cache`, which keys on all arguments, and pass `factor` explicitly.
