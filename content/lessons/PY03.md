## Why this matters

Many of the most expensive Python bugs in robotics code are not syntax errors or wrong formulas but wrong assumptions about *which object* a name refers to. A planner that "copies" a path and then mutates the copy also changes the original; an occupancy grid built with `[[0]*n]*n` lights up an entire column when one cell is set; a default argument accumulates measurements across calls; a lambda inside a loop captures the last loop value. These bugs produce plausible numbers, so they survive tests that only look at one call. The cure is a clear mental model of Python's data model: names, objects, identity, mutability and scope.

## Intuition

In Python a variable is not a box that holds a value; it is a **name tag attached to an object**. `b = a` attaches a second tag to the same object. Nothing is copied. If the object is **immutable** (an int, string or tuple) you cannot change it in place, so rebinding a tag is the only way to "change" it and aliasing is harmless. If the object is **mutable** (a list, dict, set or most user classes) every tag sees the same change.

![Two diagrams: a grid made by repeating a list holds three references to one row, so setting one cell changes every row; a list comprehension makes three distinct rows](/lesson-figures/PY03.svg)

*Left: `[[0]*3]*3` repeats one reference. Right: a comprehension builds three separate rows.*

Scope answers a different question: *which name does this identifier mean here?* Python looks in the innermost function first, then enclosing functions, then the module, then built-ins (the LEGB rule).

## Theory and derivation

### Names, identity, equality

Every object has an **identity** (`id(x)`, an integer unique among live objects, in CPython its address), a **type** and a **value**. `a is b` compares identities; `a == b` compares values via `__eq__`. Two equal objects can be distinct (`[1] == [1]` but `[1] is not [1]`), and identity of small immutable values is an implementation detail (interning), so never test numbers or strings with `is`; use `is` for `None` and sentinel objects only. A subtle effect of memory reuse: `id([]) == id([])` can be `True` because the first temporary list is freed before the second is created.

### Mutability and in-place operations

| Immutable | Mutable |
|---|---|
| `int`, `float`, `bool`, `str`, `bytes`, `tuple`, `frozenset`, `None` | `list`, `dict`, `set`, `bytearray`, user-defined objects |

`x += y` first tries `x.__iadd__(y)`. For a list this extends **in place** (all aliases see it); for an int, string or tuple there is no `__iadd__`, so Python computes `x = x + y`, a **new object** rebound to the name. Thus `l += [1]` inside a function changes the caller's list, while `l = l + [1]` does not. A tuple is immutable only in its slots: `([1], 2)[0].append(9)` is legal because the list inside is mutable.

### Function calls

Arguments are passed by **assignment**: the parameter name is bound to the same object as the argument ("pass by object reference"). A function can mutate a mutable argument, visible to the caller, but rebinding the parameter name affects only the local name. Default values are evaluated **once**, at definition time, so a mutable default is shared by all calls: the idiom is `def f(x, acc=None): if acc is None: acc = []`.

### Copying

- Assignment: no copy.
- `list(a)`, `a[:]`, `a.copy()`, `copy.copy(a)`: **shallow** copy, a new outer container whose elements are the same objects.
- `copy.deepcopy(a)`: recursively copies (and handles cycles and shared references).
- `[row] * n` and `[[0]*c]*r`: repetition repeats the same reference $n$ times.

For nested lists a shallow copy is not enough: `b = a.copy(); a[0][0] = 99` also changes `b[0][0]`.

### Scope: LEGB, global, nonlocal

A name assigned anywhere in a function is **local** to that function for the whole function body. Reading it before assignment raises `UnboundLocalError`, even if a global of the same name exists. `global x` makes assignments refer to the module-level name; `nonlocal x` refers to a name in the nearest enclosing function. A **closure** captures *variables*, not values: `[lambda: i for i in range(3)]` creates three functions that all read the same `i`, which is 2 after the loop. Binding the value at definition time with a default argument (`lambda i=i: i`) fixes it. Comprehensions and generator expressions have their own scope, so their loop variable does not leak.

## Worked example

**The grid bug.** A mapper stores occupancy in `grid = [[0]*3]*3` and then marks cell $(1,1)$ with `grid[1][1] = 7`.

1. `[0]*3` creates one list $L$ = `[0, 0, 0]`.
2. `[L]*3` creates a new outer list with **three references to $L$**: `grid[0] is grid[1] is grid[2]`.
3. `grid[1][1] = 7` evaluates `grid[1]` (which is $L$), then sets slot 1 of $L$.
4. Printing: `[[0, 7, 0], [0, 7, 0], [0, 7, 0]]`; `len({id(r) for r in grid}) == 1`.
5. Fix: `grid = [[0]*3 for _ in range(3)]`. The comprehension evaluates `[0]*3` three times, producing three distinct lists. Now `grid[1][1] = 7` gives `[[0,0,0],[0,7,0],[0,0,0]]`. (The inner `[0]*3` is safe because ints are immutable: the three zeros are shared but cannot change in place.)

**Default argument.** `def add(x, acc=[]): acc.append(x); return acc`; `print(add(1), add(2))` prints `[1, 2] [1, 2]`: both calls return the *same* list, and `print` shows it after the second call. With `acc=None` plus `acc = []` inside, the output is `[1] [2]`.

**Late binding.** `fs = [lambda: i for i in range(3)]; [f() for f in fs]` gives `[2, 2, 2]`; with `lambda i=i: i` it gives `[0, 1, 2]`.

**Copy depth.** `a = [[1,2],[3,4]]; b = a.copy(); c = copy.deepcopy(a); a[0][0] = 99` leaves `b == [[99,2],[3,4]]` and `c == [[1,2],[3,4]]`.

## Reference implementation

```python
def make_grid(rows, cols, fill=0):
    return [[fill] * cols for _ in range(rows)]

def aliased_rows(grid):
    """Groups of row indices that are the same list object."""
    seen = {}
    for i, row in enumerate(grid):
        seen.setdefault(id(row), []).append(i)
    return [g for g in seen.values() if len(g) > 1]

def deep_copy_nested(x):
    if isinstance(x, list):
        return [deep_copy_nested(v) for v in x]
    if isinstance(x, tuple):
        return tuple(deep_copy_nested(v) for v in x)
    if isinstance(x, dict):
        return {k: deep_copy_nested(v) for k, v in x.items()}
    return x

def append_to(x, acc=None):
    if acc is None:
        acc = []
    acc.append(x)
    return acc

def make_counter(start=0):
    n = start
    def inc():
        nonlocal n
        n += 1
        return n
    return inc

def make_getters(n):
    return [lambda i=i: i for i in range(n)]

# self-test
bad = [[0] * 3] * 3
bad[1][1] = 7
assert bad == [[0, 7, 0]] * 3 and aliased_rows(bad) == [[0, 1, 2]]
good = make_grid(3, 3)
good[1][1] = 7
assert good == [[0, 0, 0], [0, 7, 0], [0, 0, 0]] and aliased_rows(good) == []
c = make_counter()
assert (c(), c(), c()) == (1, 2, 3)
assert [g() for g in make_getters(3)] == [0, 1, 2]
print("ok")
```

### Library track

Python's own `copy` module is the reference tool, and NumPy shows how the same aliasing questions look in numeric code. Install `numpy` in a virtual environment, put the file next to your `sem_lab.py` (importing it also re-runs your tests, which is harmless) and run it.

```python
import copy
import numpy as np
from sem_lab import aliased_rows, deep_copy_nested

# 1. A NumPy 2-D array is one buffer, so the repeated-row bug cannot happen.
z = np.zeros((3, 3), dtype=int)
z[1, 1] = 7
assert z.sum() == 7                                   # exactly one cell changed

# 2. Converting the buggy list grid copies the numbers: the aliasing is gone from the array,
#    but the wrong data (three 7s) is already inside it.
bad = [[0] * 3] * 3
bad[1][1] = 7
assert np.array(bad).sum() == 21 and aliased_rows(bad) == [[0, 1, 2]]

# 3. Basic slices are views (shared memory); fancy indexing makes a copy.
a = np.arange(6)
view, fancy = a[1:4], a[[1, 2, 3]]
view[0] = 100
assert a[1] == 100 and fancy[0] == 1
assert np.shares_memory(a, view) and not np.shares_memory(a, fancy)
assert not np.shares_memory(a, a.copy())

# 4. Compare your deep copy with copy.deepcopy.
nested = [[1, 2], (3, [4]), {"k": [5]}]
mine, ref = deep_copy_nested(nested), copy.deepcopy(nested)
assert mine == ref == nested and mine[0] is not nested[0] and ref[0] is not nested[0]
# deepcopy remembers objects it has already copied (a memo), so sharing inside the copy is preserved;
# the naive recursive copy duplicates a shared row twice.
row = [0]
shared = [row, row]
d = copy.deepcopy(shared)
assert d[0] is d[1] and d[0] is not row
m = deep_copy_nested(shared)
assert m[0] is not m[1]
print("library track checks passed")
```

Extension: make `deep_copy_nested` preserve sharing by passing a `memo` dict keyed by `id(obj)`, then assert `m[0] is m[1]`.

## Verification

Verify semantics experimentally. (1) Predict before running: write the object graph on paper (names, objects, arrows). (2) Check identity with `id()` or `is`, not by printing values. (3) Mutate through one name and read through another. (4) Run the function twice on the same input to expose state shared between calls (defaults, globals, closures). (5) For copies, mutate the *original deeply* and assert the copy is unchanged. A check that could reject you: after a supposed copy, `any(a_sub is b_sub ...)` for mutable sub-objects must be `False`.

## Failure modes

- `[[0]*n]*m`: one list repeated; setting one cell changes every row (the shown grid prints `[[0,7,0],[0,7,0],[0,7,0]]`).
- Shallow copy of nested data: `b = a.copy()` shares inner lists, so a later `a[0][0] = 99` appears in `b`.
- Mutable default arguments: `def f(x, acc=[])` returns `[1, 2] [1, 2]` for `f(1), f(2)`.
- `x += y` on a list inside a function silently mutates the caller's list, while `x = x + y` does not.
- Late-binding closures: `[lambda: i for i in range(3)]` returns `[2, 2, 2]`.
- `UnboundLocalError`: assigning to a name anywhere in a function makes it local everywhere in that function.
- Using `is` for numbers or strings: results depend on interning and can differ between runs or Python versions.
- `t[0] += [5]` on a tuple containing a list both succeeds in mutating the list and raises `TypeError` afterwards.

## Alternatives and trade-offs

Prefer **immutable** data (tuples, `frozenset`, `dataclass(frozen=True)`, `NamedTuple`) for values that should not change; aliasing then cannot hurt and objects are hashable. Mutate in place for large buffers where copying would cost too much (NumPy arrays, big grids), but document it in the function contract. `copy.deepcopy` is general but slow and surprising for objects holding resources (files, locks); a comprehension or a `.copy()` method is fine when you know the depth. For NumPy, slices are **views** that share memory while fancy indexing copies, so the same aliasing concerns appear (PY04). Prefer returning new values from functions unless in-place mutation is the point (`list.sort`, `dict.update`), and name in-place helpers with verbs that signal it.

## Transfer and retention

- A ROS node that stores the last message in an attribute and appends it to a history list may be storing the same mutable message object repeatedly; copy at the boundary if the middleware reuses buffers.
- A configuration dict copied with `dict(cfg)` shares nested sub-dicts across experiments; one run's modification changes another's baseline (PY08).
- From memory: draw the object graph for the worked example, then state the three copy depths. In a week, find a nested structure in your own code and write a test with `is` checks showing which parts are shared.

## Exercise answers

1. `[1, 2, 3, 4] True`. `b = a` binds a second name to the same list; `append` mutates it.
2. First: `5 6`: ints are immutable, `y += 1` rebinds `y` to a new int. Second: `[5, 6] [5, 6]`: `list.__iadd__` extends in place, and `l` and `m` are the same object. Both use `+=`, but the result depends on whether `__iadd__` exists and mutates.
3. `[[0, 7, 0], [0, 7, 0], [0, 7, 0]]` and `1`. Constructors: `[[0]*3 for _ in range(3)]` and `[[0, 0, 0] for _ in range(3)]` (or `[list(row) for row in template]`). The inner `[0]*3` repeats a reference to the int 0, which is immutable, so no shared state can be modified; the outer repetition repeats a reference to a mutable list.
4. The default list is created once. `print(record(1), record(2), record(3, []))` prints `[1, 2] [1, 2] [3]` (the first two names show the same shared list after both calls). Fix: `log=None; if log is None: log = []`.
5. `UnboundLocalError` (message: cannot access local variable `n` where it is not associated with a value): `n += 1` assigns to `n`, making `n` local to `inc`, but it has no value yet. Fix 1: `nonlocal n` in `inc`. Fix 2: keep state in a mutable container such as `state = [0]` and use `state[0] += 1`, or use a class.
6. `[2, 2, 2]`: all three lambdas read the same variable `i` of the enclosing scope after the loop ends. Fix: `lambda i=i: i` (bind the value now) or `functools.partial`. A comprehension of values evaluates `i` immediately and stores the result, not a function that looks `i` up later.
7. `t[0].append(9)` works: the tuple's slot still refers to the same list, which is mutable; `t` becomes `([1, 9], 2)`. `t[0] += [5]` first calls `t[0].__iadd__([5])`, which extends the list in place (success), then tries to store the result back into `t[0]`, which raises `TypeError: 'tuple' object does not support item assignment`. Result: an error was raised, yet the list was mutated: after both statements `t == ([1, 9, 5], 2)` (running only the `+=` on a fresh `([1], 2)` also leaves `([1, 5], 2)`).
8. `wps.copy()` is shallow; `p[0] += 10` mutates the inner lists shared with `wps`, so the original waypoints become `[[10,0],[11,0],[11,1]]`. Alternatives: (a) `shifted = [[x + 10, y] for x, y in wps]`; (b) `shifted = copy.deepcopy(wps)` then mutate; (c) `shifted = [p.copy() for p in wps]` then mutate. Choose (a): no copy-then-mutate step, and it expresses the intent.
9. In-place style: `normalize_path(path)` mutates and returns `None` (the `list.sort` convention, so that callers cannot confuse the two). Functional style: returns a new list and leaves the input unchanged (the `sorted` convention). A unit test: `before = copy.deepcopy(path); out = normalize_path(path); assert path == before; assert out is not path`. Prefer the functional style unless performance requires in-place work; document the choice.
10. Minimal example: `m = [[0]*5]*5; a = m; a[0][0] = 1; print(m[4][0])` prints 1. `id(m[0]) == id(m[4])`; `plan` marks one "row" and all rows change, and two "copies" made with `list(m)` still share the inner lists. Fix: `make_grid`. Regression test: `assert aliased_rows(grid) == []` on every grid your code constructs, plus a test that `plan` on one grid does not change a second, independently built grid.
