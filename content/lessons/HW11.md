## Why this matters

Sooner or later the controller you wrote on the PC has to talk to a microcontroller (MCU) that reads encoders and drives motors. The cable between them is only a stream of bytes, and that stream loses bytes, adds garbage, and stops when someone unplugs a connector. A beginner link is a line of text such as `m 20 20\n`: it works on the bench and fails in the field, because one corrupted digit becomes a different speed and a silent cable leaves the motors running at the last command. This topic is the firmware half of the link: a small binary protocol with a checksum, a way to find the start of a frame again after any damage, sequence numbers to count what was lost, and a timeout that stops the robot. After that we look at **micro-ROS**, which moves this plumbing into a ready-made library, and at where each approach plugs into ROS 2 and `ros2_control`.

CoreLab's S06 (Hardware Integration) is the PC-side companion: it frames data in Python with a header byte, a length and a simple sum checksum, and adds a freshness reader. This topic is the MCU half and builds on that idea instead of repeating it: a stronger check (CRC8), a header byte that can never appear inside the data (byte stuffing or COBS), sequence numbers, and the receive state machine in C++ and MicroPython. Study it first or next to S06.

## Intuition

Think of the link as a postal service that sometimes drops, damages or mixes up letters. Four small habits make it dependable:

- **Envelope** (framing): every message starts with a marker and says how long it is, so the receiver knows where one message ends.
- **Seal** (CRC): a check number computed from the contents; if it does not match, throw the letter away, never "repair" it.
- **Numbered letters** (sequence): if letter 7 is followed by letter 10, exactly two were lost, and you know it.
- **Dead-man's switch** (timeout): if no valid letter has arrived for a while, the robot stops by itself.

The marker only works if it cannot appear inside the message. A payload is arbitrary binary, so a data byte may equal the marker. **Byte stuffing** (or **COBS**) rewrites the data so the marker byte appears only at real frame starts. Then resynchronisation is trivial: after any damage, wait for the next marker.

On the PC side there are two worlds. In the first, you write a small serial protocol and a `ros2_control` hardware interface that speaks it (this is what `diffdrive_arduino` does for an Arduino). In the second, the MCU runs a **micro-ROS client** that looks like a normal ROS 2 node, and a **micro-ROS agent** on the PC translates its messages into ordinary DDS traffic. The rest of the lesson helps you choose.

### Link budget: baud, bytes and load

A UART link in 8N1 format sends 10 bit times per byte (start bit, 8 data bits, stop bit). At baud rate $B$ the byte rate is $B/10$, so
$$\text{load}=\frac{L\cdot 10\cdot f}{B},\qquad L=\text{bytes on the wire per frame},\ f=\text{frames per second}.$$
At 115200 baud that is 11 520 bytes/s. Keep the load under about 50 % so that bursts, retries and the occasional stuffed byte fit. Raising the baud rate is cheap, but check it against the clock (next paragraph).

**Baud-rate error.** An AVR derives the baud rate from the CPU clock by an integer divider. For the ATmega328P (the Arduino Uno chip) the USART chapter gives
$$B_\text{normal}=\frac{f_\text{osc}}{16\,(\text{UBRR}+1)},\qquad B_\text{U2X}=\frac{f_\text{osc}}{8\,(\text{UBRR}+1)}.$$
At 16 MHz and a target of 115200: normal mode with UBRR $=8$ gives $111\,111$ baud ($-3.5\,\%$), double-speed mode with UBRR $=16$ gives $117\,647$ baud ($+2.1\,\%$). Receivers sample in the middle of each bit. The last bit of a frame (the stop bit) is sampled at 9.5 bit times, so the accumulated drift must stay below half a bit: $9.5\,\varepsilon<0.5$, i.e. the **combined** transmitter plus receiver error must stay under about $5\,\%$ by this simple estimate. The ATmega328P datasheet is stricter for 8 data bits: a total of about $\pm4.5\,\%$ in normal mode and $\pm3.9\,\%$ in double-speed mode, and it recommends at most $\pm2\,\%$ ($\pm1.5\,\%$ in double-speed mode) at the receiver to leave margin for noise. A $-3.5\,\%$ error on one side plus $+2\,\%$ on the other breaks that. At 16 MHz, 250 000 baud has UBRR $=3$ and an exact 0 % error, which is why robot firmware often uses 250 000 or 500 000 instead of 115200 (numbers from the ATmega328P datasheet USART chapter).

### Frame layout

The protocol used in this lesson (and in the lab) is:

| byte | name | meaning |
|---|---|---|
| 0 | SOF | start of frame, constant `0x7E` |
| 1 | LEN | payload length, 0 to 64 |
| 2 | ID | message type (1 = wheel command, 2 = telemetry, ...) |
| 3 | SEQ | sequence number, increments by 1 per frame, wraps at 256 |
| 4 ... | PAYLOAD | LEN bytes, for example two big-endian `int16` |
| last | CRC8 | CRC-8 (polynomial 0x07) over LEN, ID, SEQ and PAYLOAD |

Every byte after SOF is byte-stuffed. A frame carrying $n$ payload bytes is $n+5$ bytes before stuffing. S06 used a one-byte sum over length and payload; a sum cannot see two swapped bytes, and it has no sequence number. CRC8 plus SEQ closes both gaps.

### CRC8 in one paragraph

A CRC treats the message as a long binary polynomial and keeps the remainder after division by a fixed generator polynomial. In hardware terms it is a shift register with a few XORs. For CRC-8 with generator $x^8+x^2+x+1$ (written `0x07`), the code is: for each byte, XOR it into the register, then 8 times shift left, XORing `0x07` whenever a 1 falls out of the top. The catalogue entry "CRC-8/SMBUS" (init 0, no reflection, final XOR 0) lists the check value `0xF4` for the ASCII string `123456789`, a handy unit test. A CRC8 detects every single-bit error, every burst up to 8 bits long, and all but about 1 in 256 random corruptions. It is error **detection**, not security: a CRC is easy to forge and says nothing about who sent the frame. For long frames or noisy links use CRC16.

An important property: if you append the CRC to the data and run the CRC over everything again, the result is `0`. That lets a receiver check a frame with one pass.

### Byte stuffing and COBS

Choose `0x7E` as the frame marker. To keep it out of the body, replace each `0x7E` and each escape byte `0x7D` with the pair `0x7D, (byte XOR 0x20)`. So `0x7E` becomes `7D 5E` and `0x7D` becomes `7D 5D`. The receiver reverses it. The cost is up to 2x in the worst case (a payload of all `0x7E`) and about $2/256$ extra on random data.

**COBS** (Consistent Overhead Byte Stuffing) removes all `0x00` bytes from the data instead, so `0x00` can serve as the delimiter. It splits the data at each zero and replaces the zero by a length code: `11 22 00 33` becomes `03 11 22 02 33`. The overhead is at most one extra byte per 254 data bytes, so it is predictable, which is why it is popular for packet links. The price is that the encoder must look ahead to the next zero, so it needs the whole packet in a buffer. Byte stuffing is streaming (one byte in, one or two bytes out), which suits tiny MCUs.

### The receive state machine

A robust parser never waits inside a function for bytes. Each call gets one byte from the UART buffer and advances a small state machine. In the Arduino sketch of this lesson the states are: *idle* (ignore everything until `0x7E`), *collecting* (accumulate stuffed bytes, with an *escape* flag for the byte after `0x7D`) and *complete* (after LEN+4 un-stuffed bytes, check the CRC, then go idle). Four rules give resynchronisation for free:

1. A `0x7E` received at any time starts a new frame. If a frame was in progress it was truncated; count it and drop it.
2. A LEN above the maximum is rejected at once, otherwise a garbage byte could make the parser wait for 200 bytes that never come.
3. A bad CRC drops the frame; never "fix" bits.
4. Garbage between frames is ignored while idle.

### Sequence numbers, loss and timeout

If the last good frame had sequence $s_\text{prev}$ and this one has $s$, the number of frames lost between them is
$$\text{lost}=(s-s_\text{prev}-1)\bmod 256.$$
It is only unambiguous if fewer than 256 frames can disappear in a row, which is true for any sane link. The sequence number also tells the host whether it is hearing fresh telemetry or a repeat.

The watchdog is the second half of S06's "freshness" idea, now on the MCU: if no valid command frame arrives for $T$ ms, set the PWM outputs to zero, and re-enable only when a valid frame comes back. Pick $T$ as about three command periods. The distance a robot covers after the last command is $v\cdot T$ (plus up to one period), so $T=150$ ms at 0.5 m/s means up to 7.5 cm of unwanted motion. A heartbeat (a command or telemetry frame sent even when nothing changed) keeps an idle link distinguishable from a dead link.

### USB CDC versus UART

An Arduino Uno routes its UART through a second chip to appear as a USB serial port; an ESP32 DevKit uses a USB-to-UART bridge chip; boards with native USB (RP2040, ESP32-S2/S3 in USB mode, Teensy, STM32 with USB) show up as a CDC-ACM device (`/dev/ttyACM0`). To the software it is still a byte stream, so the same protocol works. USB adds buffering and latency timers on the PC side (see S06's failure modes), and the baud rate setting is ignored by native CDC devices because there is no physical baud clock.

### What micro-ROS is

micro-ROS is a ROS 2 client for microcontrollers. Its pieces, according to the micro-ROS documentation:

- A **client library** on the MCU: the C API of the ROS 2 client support library `rcl` plus the convenience layer `rclc`, with executors and timers, written so that after initialisation it needs no dynamic memory allocation.
- A middleware, **Micro XRCE-DDS** (by eProsima), implementing the DDS-XRCE protocol for extremely resource-constrained devices. A simple publisher/subscriber client needs only about 2 to 3 kB of RAM for the XRCE client itself (figures quoted by eProsima and the Vulcanexus documentation, which differ slightly between versions); a complete micro-ROS application needs tens of kilobytes (the supported-hardware page).
- A **micro-ROS agent** on the PC (or on a Raspberry Pi). The client talks the XRCE-DDS protocol to the agent over a transport (serial, UDP over Wi-Fi or Ethernet, USB CDC, depending on board); the agent creates the matching DDS publishers and subscribers on the client's behalf. To the rest of the ROS 2 graph, the MCU's node is a normal node: `ros2 topic list`, `ros2 topic echo`, `rqt` and your controllers see it as any other.

A publisher on the MCU is only a few lines of `rclc`; the agent is started on the PC with, for example, `ros2 run micro_ros_agent micro_ros_agent serial --dev /dev/ttyACM0 -b 115200`. micro-ROS officially supports mid-range 32-bit MCUs with tens of kilobytes of RAM and runs on an RTOS (FreeRTOS, Zephyr, NuttX) or, for supported boards, through the Arduino IDE (micro_ros_arduino). An ATmega328P Uno has 2 kB of SRAM, so it is not a micro-ROS target; an ESP32 (520 kB RAM) is.

### Connecting to ROS 2 and ros2_control

`ros2_control` separates **controllers** (for example `diff_drive_controller`) from the **hardware interface**, a plugin whose `read()` and `write()` are called by the controller manager every cycle and which exposes command and state interfaces (wheel velocity command, wheel position state). Three patterns reach an MCU:

| Pattern | MCU side | PC side | Good for |
|---|---|---|---|
| Custom serial protocol | firmware with the frame parser of this lesson (or a text protocol as in `ros_arduino_bridge`) | hardware interface plugin that opens the port and calls the protocol in `read()` and `write()` (as `diffdrive_arduino`) | 2-wheel robot, 1 MCU, simple, deterministic cycle |
| micro-ROS | `rclc` node publishing wheel ticks and subscribing to wheel commands | micro-ROS agent, plus a small bridge or hardware interface that subscribes and publishes those topics | many sensors as ROS topics, Wi-Fi or Ethernet MCUs, quick prototyping |
| CAN or Ethernet drivers | smart motor drivers speak CAN (for example CANopen-style) or EtherCAT | hardware interface using a vendor or open library | arms and legged robots with several joints at 500 Hz to 1 kHz |

The fast loop (encoder reading, PI, PWM) always runs on the MCU at a fixed rate (HW10). The link carries setpoints down at 20 to 100 Hz and measurements up at the same rate. Do not close a 1 kHz loop through DDS and a USB-serial adapter.

Rules of thumb for the choice (the numbers are typical, not limits): classic CAN is 1 Mbit/s with 8-byte payloads and hardware arbitration, good for several nodes; Ethernet is 10/100 Mbit/s but needs an MCU with a network stack; a UART at 115200 to 500000 baud is plenty for a 2-wheel robot (an exercise below budgets it).

## Worked example

### Serial protocol for a two-wheel robot: frames, link load, faults and timeout

**Problem.** A two-wheel robot has a Raspberry Pi 5 running ROS 2 (HW11's S03 background) and an ESP32 that reads two encoders and drives two motors. The Pi sends a wheel command at 50 Hz and the ESP32 returns encoder counts at 50 Hz over a 115200 baud UART, using the frame of this lesson (SOF `7E`, LEN, ID, SEQ, payload, CRC-8 with polynomial 0x07, byte stuffing). Find (a) the message design; (b) the frame for left = 100, right = $-100$, SEQ = 0; (c) the wire bytes for ID 1, SEQ 7, payload `7E 11`; (d) the link load; (e) what the parser does when a bit flips in the frame with SEQ 1 and the frame with SEQ 2 arrives next; (f) what it does when the cable is unplugged halfway through a frame; (g) a command watchdog timeout and the distance covered at 0.5 m/s; (h) the micro-ROS alternative.

**Solution.**

1. **Message design.** The command carries two target values in ticks per control period, each an `int16` (2 bytes), so the payload is $2\cdot2=4$ bytes, big-endian, ID 1. Telemetry carries two encoder counts, each an `int32` (4 bytes), so the payload is $2\cdot4=8$ bytes, ID 2. A frame with $n$ payload bytes is $n+5$ bytes before stuffing: 9 bytes for the command, 13 for telemetry.
2. **Encode the command.** Payload: $100=\texttt{0x0064}\to$ `00 64`; $-100=\texttt{0xFF9C}$ (two's complement, $65536-100$) $\to$ `FF 9C`. Body (LEN, ID, SEQ, payload) $=$ `04 01 00 00 64 FF 9C`. CRC-8 (register starts at 0; for each byte XOR it in, then 8 times shift left and XOR `0x07` when a 1 falls out): after the 7 body bytes the register is `1C`, `53`, `BE`, `33`, `A2`, `94`, `38`, so the CRC is `0x38`. Frame: `7E 04 01 00 00 64 FF 9C 38`, 9 bytes. No body byte equals `7E` or `7D`, so no stuffing is needed.
3. **A stuffed example.** ID 1, SEQ 7, payload `7E 11` (LEN 2): body `02 01 07 7E 11`; register after each byte `0E`, `2D`, `D6`, `51`, `C7`, so CRC `C7`. The data byte `7E` would look like a start marker, so it is replaced by `7D, 7E XOR 20 = 7D 5E`. Wire: `7E 02 01 07 7D 5E 11 C7`, 8 bytes (7 + 1 for the stuffed byte). The only bare `7E` is the start marker, so a receiver can always resynchronise on it.
4. **Link load.** In 8N1 each byte costs 10 bit times, so $\text{load}=L\cdot10\cdot f/B$. Command 9 bytes plus telemetry $1+3+8+1=13$ bytes make $L=22$ bytes per 20 ms cycle: $22\cdot10\cdot50/115200=11000/115200=9.5\,\%$ before stuffing. Doubling it gives 19 %, still below the 50 % guideline: 115200 baud is plenty.
5. **Damage.** A noise burst flips a payload bit in the frame with SEQ 1. The CRC computed by the receiver no longer matches the received one, so the parser drops the frame, counts one `crc_error` and goes idle (rule 3: bad CRC drops the frame, never repair). The next good frame has SEQ 2 and the previous good one was SEQ 0, so $\text{lost}=(s-s_\text{prev}-1)\bmod256=(2-0-1)\bmod256=1$.
6. **Truncation.** The cable is unplugged halfway through a frame and replugged. The parser is in the *collecting* state with a partial frame when the next `7E` arrives. By rule 1 a `7E` at any time starts a new frame: the parser counts a truncated frame, drops the partial bytes and starts collecting the new one. No explicit reset is needed.
7. **Timeout.** Commands arrive every $1/50=20$ ms. A watchdog of three periods is $3\cdot20=60$ ms; 150 ms is $150/20=7.5$, about seven periods. After the host goes silent the robot keeps moving for the timeout: $v\cdot T=0.5\cdot0.15=0.075$ m $=7.5$ cm with 150 ms, and $0.5\cdot0.06=3$ cm with 60 ms. If 7.5 cm is too far, choose 60 to 100 ms.
8. **The micro-ROS alternative.** The same ESP32 (520 kB RAM, enough for micro-ROS) could run a node `wheel_node` with a subscriber on `/wheel_cmd` and a publisher on `/wheel_ticks`. That removes the framing code, CRC and parser, but adds the micro-ROS agent on the Pi, a larger firmware with more RAM use, and the need to handle the agent disappearing.

**Check.** The CRC register values were recomputed with an independent CRC-8 routine (the same routine returns `0xF4` for the ASCII string `123456789`, the catalogue check value for CRC-8/SMBUS), and `struct.pack(">hh", 100, -100)` gives `00 64 FF 9C`. The load is also $(9+13)\cdot10$ bits $\cdot\,50=11000$ bit/s, 9.5 % of 115200 bit/s. The lost count follows from the sequence numbers alone: frames 0 and 2 arrive, so exactly frame 1 is missing.

**Takeaway.** Frame length, CRC and stuffing can be worked out by hand, and a handful of rules (a `7E` always restarts, a bad CRC drops, SEQ counts gaps) make the parser self-recovering; the watchdog timeout trades unwanted travel ($v\cdot T$) against false stops.

## Reference implementation

The PC-side encoder from the lesson, with the CRC-8/SMBUS check value and the worked-example frames. To follow along on a real board, first watch the raw bytes with `python3 -m serial.tools.miniterm /dev/ttyACM0 115200` (see S06).

```python
import struct

SOF, ESC, MAX_PAYLOAD = 0x7E, 0x7D, 64

def crc8(data, poly=0x07, init=0x00):
    crc = init
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = ((crc << 1) ^ poly) & 0xFF if crc & 0x80 else (crc << 1) & 0xFF
    return crc

def stuff(data):
    out = bytearray()
    for b in data:
        out += bytes([ESC, b ^ 0x20]) if b in (SOF, ESC) else bytes([b])
    return bytes(out)

def encode_frame(fid, seq, payload):
    body = bytes([len(payload), fid & 0xFF, seq & 0xFF]) + bytes(payload)
    return bytes([SOF]) + stuff(body + bytes([crc8(body)]))

def seq_gap(prev, cur):
    return (cur - prev - 1) % 256

assert crc8(b"123456789") == 0xF4                       # CRC-8/SMBUS check value from the CRC catalogue
frame = encode_frame(1, 0, struct.pack(">hh", 100, -100))
assert frame.hex(" ") == "7e 04 01 00 00 64 ff 9c 38"
assert encode_frame(1, 7, bytes([0x7E, 0x11])).hex(" ") == "7e 02 01 07 7d 5e 11 c7"
assert seq_gap(255, 0) == 0 and seq_gap(250, 2) == 7
print("reference ok")
```

## Independent practice

### Goal
Build the full byte-level protocol stack of the lesson in plain Python: CRC8, byte stuffing, a resynchronising frame parser with sequence-gap counting, a COBS encoder and decoder, a watchdog and the link-load formula. The same logic is then run as firmware in the Library track.

### Setup
Python 3 standard library only. Save starter and tests as `hw11_lab.py`. This is deliberately different from S06's sum-checksum frame: here the marker is `0x7E` and CRC-8 is used.

### Tasks
1. `crc8(data, poly=0x07, init=0x00)`.
2. `stuff(data)` and `encode_frame(fid, seq, payload)`; `ValueError` if the payload is longer than 64 bytes.
3. `seq_gap(prev, cur)`.
4. `cobs_encode(data)` and `cobs_decode(data)` (no `0x00` in the output; decoding must reject malformed input).
5. `FrameParser.feed(data)` with counters `crc_errors`, `truncated`, `bad_length` and `lost`; it must give the same result whether bytes arrive in one chunk or one by one.
6. `Watchdog(timeout_ms)` with `feed` and `expired`.
7. `link_load(frame_bytes, rate_hz, baud)`.
8. Write assumptions, baseline, boundary case and a rejecting observation as comments.

### Starter code
```python
import struct

SOF, ESC, MAX_PAYLOAD = 0x7E, 0x7D, 64

def crc8(data, poly=0x07, init=0x00):
    """CRC-8 over bytes, MSB first, no reflection, no final xor (CRC-8/SMBUS: crc8(b"123456789") == 0xF4)."""
    raise NotImplementedError

def stuff(data):
    """Replace every 0x7E and 0x7D by 0x7D followed by (byte ^ 0x20)."""
```

```cpp
// HW11 Wokwi sketch (Arduino Uno). Type a frame as hex in the Serial Monitor and press Enter,
// for example:  7E 04 01 00 00 64 FF 9C 38
// Frame: 7E LEN ID SEQ PAYLOAD... CRC8 ; byte stuffing 7E/7D -> 7D (b ^ 0x20) ; CRC-8 poly 0x07 over LEN..PAYLOAD
const uint8_t SOF = 0x7E, ESC = 0x7D, MAX_PAYLOAD = 16;
const unsigned long TIMEOUT_MS = 2000;
const uint8_t LED_PIN = 13;            // on = motors enabled, off = stopped by the watchdog

uint8_t buf[MAX_PAYLOAD + 4];
uint8_t n = 0;
bool active = false, escaped = false, haveSeq = false, stopped = true;
uint8_t lastSeq = 0, txSeq = 0;
uint16_t crcErrors = 0, lostFrames = 0;
unsigned long lastGood = 0;
int pendingNibble = -1;

uint8_t crc8(const uint8_t *d, uint8_t len) {
  uint8_t crc = 0x00;
  for (uint8_t i = 0; i < len; i++) {
    crc ^= d[i];
    for (uint8_t k = 0; k < 8; k++) crc = (crc & 0x80) ? (uint8_t)((crc << 1) ^ 0x07) : (uint8_t)(crc << 1);
  }
  return crc;
}

void printHexByte(uint8_t b) {                   // writes one (possibly stuffed) byte as text
  if (b < 16) Serial.print('0');
  Serial.print(b, HEX);
  Serial.print(' ');
}

void emit(uint8_t b) {                            // transmit-side byte stuffing
  if (b == SOF || b == ESC) { printHexByte(ESC); printHexByte(b ^ 0x20); }
  else printHexByte(b);
}

void sendFrame(uint8_t id, const uint8_t *p, uint8_t len) {
  uint8_t body[MAX_PAYLOAD + 3];
  body[0] = len; body[1] = id; body[2] = txSeq++;
  for (uint8_t i = 0; i < len; i++) body[3 + i] = p[i];
  printHexByte(SOF);
  for (uint8_t i = 0; i < len + 3; i++) emit(body[i]);
  emit(crc8(body, len + 3));
  Serial.println();
}

void onFrame(uint8_t id, uint8_t seq, const uint8_t *p, uint8_t len) {
  if (haveSeq) lostFrames += (uint8_t)(seq - lastSeq - 1);   // modulo-256 gap = frames lost in between
  lastSeq = seq; haveSeq = true;
  lastGood = millis(); stopped = false;
  Serial.print(F("OK id=")); Serial.print(id);
  Serial.print(F(" seq=")); Serial.print(seq);
  Serial.print(F(" len=")); Serial.print(len);
  if (id == 1 && len == 4) {                      // id 1 = wheel command: two big-endian int16
    int16_t left = (int16_t)(((uint16_t)p[0] << 8) | p[1]);
    int16_t right = (int16_t)(((uint16_t)p[2] << 8) | p[3]);
    Serial.print(F(" left=")); Serial.print(left);
    Serial.print(F(" right=")); Serial.print(right);
  }
  Serial.print(F(" lost=")); Serial.println(lostFrames);
  sendFrame(2, p, len);                           // echo as an id-2 "telemetry" frame
}

void feedByte(uint8_t b) {                        // non-blocking RX state machine, one byte per call
  if (b == SOF) { active = true; escaped = false; n = 0; return; }   // 7E always restarts: this is the resync
  if (!active) return;                            // garbage between frames is ignored
  if (escaped) { b ^= 0x20; escaped = false; }
  else if (b == ESC) { escaped = true; return; }
  buf[n++] = b;
  if (n == 1 && b > MAX_PAYLOAD) { active = false; Serial.println(F("BAD LEN")); return; }
  if (n == buf[0] + 4) {                          // LEN ID SEQ PAYLOAD CRC
    active = false;
    if (crc8(buf, n - 1) == buf[n - 1]) onFrame(buf[1], buf[2], buf + 3, buf[0]);
    else { crcErrors++; Serial.print(F("CRC FAIL count=")); Serial.println(crcErrors); }
  }
}

int hexValue(char c) {
  if (c >= '0' && c <= '9') return c - '0';
  if (c >= 'a' && c <= 'f') return c - 'a' + 10;
  if (c >= 'A' && c <= 'F') return c - 'A' + 10;
  return -1;
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  Serial.println(F("HW11 ready: type a frame as hex"));
}

void loop() {
  while (Serial.available()) {                    // never block: take whatever has arrived
    char c = Serial.read();
    if (c == '\n' || c == '\r') { pendingNibble = -1; continue; }
    int v = hexValue(c);
    if (v < 0) continue;
    if (pendingNibble < 0) pendingNibble = v;
    else { feedByte((uint8_t)(pendingNibble * 16 + v)); pendingNibble = -1; }
  }
  if (!stopped && millis() - lastGood > TIMEOUT_MS) {   // watchdog: no valid frame for 2 s
    stopped = true;
    Serial.println(F("TIMEOUT: motors stopped"));
  }
  digitalWrite(LED_PIN, stopped ? LOW : HIGH);
}
```

```python
SOF, ESC, MAX_PAYLOAD = 0x7E, 0x7D, 16

def crc8(data):
    crc = 0
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = ((crc << 1) ^ 0x07) & 0xFF if crc & 0x80 else (crc << 1) & 0xFF
    return crc


def encode(fid, seq, payload):
    body = bytes([len(payload), fid, seq]) + bytes(payload)
    out = bytearray([SOF])
    for b in body + bytes([crc8(body)]):
        if b in (SOF, ESC):
            out += bytes([ESC, b ^ 0x20])
        else:
            out.append(b)
    return bytes(out)


class Parser:
    def __init__(self):
        self.buf = bytearray()
        self.active = False
        self.esc = False
        self.crc_errors = 0
        self.last_seq = None
        self.lost = 0

    def feed_byte(self, b):
        """Return (id, seq, payload) when a frame completes, else None. Never blocks."""
        if b == SOF:                      # 7E can only mean "new frame": resync point
            self.active, self.esc = True, False
            self.buf = bytearray()
            return None
        if not self.active:
            return None
        if self.esc:
            b ^= 0x20
            self.esc = False
        elif b == ESC:
            self.esc = True
            return None
        self.buf.append(b)
        if len(self.buf) == 1 and b > MAX_PAYLOAD:
            self.active = False
            return None
        if len(self.buf) == self.buf[0] + 4:
            self.active = False
            if crc8(self.buf[:-1]) != self.buf[-1]:
                self.crc_errors += 1
                return None
            seq = self.buf[2]
            if self.last_seq is not None:
                self.lost += (seq - self.last_seq - 1) & 0xFF
            self.last_seq = seq
            return self.buf[1], seq, bytes(self.buf[3:-1])
        return None
```

## Verification

Check by hand before trusting code: the CRC of the check string (`0xF4`), the CRC of one byte (`0x07` for `0x01`), the frame of the worked example, and that appending the CRC to a body gives CRC `0`. Test damage on purpose: flip each bit of a known frame in turn and confirm every flip is rejected; delete one byte; insert a `7E` in the middle; send random bytes for a minute and confirm that no frame is accepted by accident (with CRC8 about 1 in 256 random frames of the right length would pass, so the length byte and SEQ checks matter too); send 300 frames and confirm the sequence wrap at 255 to 0 gives no loss. For the watchdog, measure with a scope, an LED or a timestamp log that the output goes to zero within the timeout, not just that a flag changes.

## Failure modes

- Stuffing applied to SOF itself or CRC computed over the stuffed bytes (instead of over LEN, ID, SEQ, PAYLOAD): the two ends disagree on every frame containing `7E` or `7D`, and the bug hides until a payload happens to contain one.
- Blocking read of "the next 9 bytes": a lost byte hangs the loop and the watchdog never runs. Use a state machine.
- LEN not validated: one garbage byte makes the parser wait for hundreds of bytes and swallow good frames.
- Sequence counter compared without modulo: a false "lost 250 frames" at every wrap.
- Baud mismatch: the MCU prints or parses garbage; check the baud error against the clock (115200 on a 16 MHz AVR in normal mode) and the receiver's tolerance.
- Mixed logic levels (a 5 V Uno TX into a 3.3 V ESP32 RX): garbage or damage; use a divider or level shifter (HW12).
- Watchdog fed by the wrong event: for example fed by any received byte, so a stream of garbage keeps the motors running. Feed it only on a valid frame.
- Timeout too long (a robot at speed travels $v\cdot T$) or too short (one late frame stops the robot).
- micro-ROS: running out of RAM when messages and entities are added; the agent not running (the client waits or loops); a slow executor blocking sensor reads.
- Putting the fast control loop on the PC side of a USB serial link: the latency and jitter make it unstable (HW10).

## Alternatives and trade-offs

**ASCII text protocols** (for example `m 20 20\n`, as in `ros_arduino_bridge`, which expects typing in the Serial Monitor at 57600 baud by default) are easy to debug by hand but long, slow to parse and without a CRC unless you add one. **Binary with CRC8** is compact and robust. **CRC16** is better for frames longer than about 20 bytes. **COBS** gives bounded overhead and a zero delimiter at the price of buffering. **rosserial** was an Arduino-to-ROS 1 bridge and has no ROS 2 port; **micro-ROS** is the ROS 2 route. **CAN** gives hardware arbitration and CRC per frame, with 8-byte payloads on classic CAN and a transceiver and termination to add (HW06). **Ethernet or Wi-Fi with UDP** needs a network stack and loses the determinism of a wire. Whatever you choose, keep one rule: the actuator side must stop on its own if the link goes quiet.

For a 2-wheel robot a custom serial protocol with a `ros2_control` hardware interface is the simplest route and teaches the most; micro-ROS pays off when the MCU has many sensors you want as ROS topics or when the MCU is on Wi-Fi. For an arm with smart servos (a bus the servos already speak), do not put your own protocol on top; use the servo bus through an existing driver or hardware interface. For a multi-joint legged robot with 500 Hz to 1 kHz loops, use CAN or EtherCAT drivers whose cycle times are bounded.

## Exercise answers

1. The frame has $1+1+1+1+4+1=9$ bytes. At 115200 baud 8N1, each byte takes $10/115200=86.8\ \mu\text{s}$, so the frame takes $9\cdot86.8\ \mu\text{s}=0.78$ ms. The link carries at most $115200/90=1280$ such frames per second (100 % load; the practical limit is half of that).
2. For the byte `0x01` the register becomes `0x01`; seven left shifts (top bit never set) give `0x80`; the eighth shift drops a 1 off the top and XORs `0x07`, so the CRC is `0x07`. For the two bytes `01 07`: after the first byte the register is `0x07`; XOR with the second byte `0x07` gives `0x00`, and shifting zeros leaves `0x00`. The CRC of data plus its own CRC is `0`, so a receiver can run the CRC over the whole received body including the CRC byte and accept the frame only if it is zero. (The lesson's parser compares the received CRC to the computed one, which is equivalent.)
3. `7E` becomes `7D 5E`, `01` stays, `7D` becomes `7D 5D`: `7D 5E 01 7D 5D`. The escaped values are $\text{0x7E}\oplus\text{0x20}=\text{0x5E}$ and $\text{0x7D}\oplus\text{0x20}=\text{0x5D}$, and neither equals `7E` or `7D`; so after stuffing the byte `7E` occurs only as a start marker and the escape byte `7D` is always followed by `5E` or `5D`.
4. Payload $4\cdot(4+2)=24$ bytes; frame $1+3+24+1=29$ bytes. Load $=29\cdot10\cdot100/115200=25.2\,\%$. Worst case: SOF plus $2\cdot28=56$ bytes $=57$ bytes, load $=57\cdot10\cdot100/115200=49.5\,\%$, which is right at the comfort limit. Random data averages only about 0.8 % stuffing, so the worst case is rare, but an all-`7E` pattern is possible from a stuck sensor. If the margin matters, raise the baud to 250000 (the load drops to 22.8 % worst case) or send fewer values.
5. The parser starts collecting after the first `7E`, receives `04 01 00 00 64` (five bytes, fewer than $4+4=8$ needed), then sees a bare `7E`, which can only be a new start: `truncated` becomes 1. The following frame is complete with a valid CRC, so it delivers `(id=1, seq=1, payload=00 64 FF 9C)`. `crc_errors` stays 0 and `lost` stays 0, because there was no previous valid sequence number to compare with.
6. The only gap is $251\to254$: $(254-251-1)=2$ frames lost (252 and 253); the other steps (including $255\to0$) lose none. Total 2. If exactly 256 consecutive frames vanish, the next sequence equals the previous plus one again and the gap is $0$ (ambiguous). At 100 Hz that is 2.56 s of total silence, which the watchdog (150 ms) already catches long before.
7. The timeout must be longer than a few command periods (20 Hz means 50 ms). With 60 ms the extra travel is $0.5\cdot0.06=3$ cm, but a single late command stops the robot (just over one period): too tight. With 150 ms (three periods): extra travel $0.5\cdot0.15=7.5$ cm. With 500 ms: $25$ cm. Pick 150 ms: it tolerates two lost commands and the stopping distance is small. Add the braking distance of the robot to the number.
8. Normal mode, UBRR = 8: $16\,000\,000/(16\cdot9)=111\,111$ baud, error $(111111/115200-1)=-3.5\,\%$. Double-speed, UBRR = 16: $16\,000\,000/(8\cdot17)=117\,647$ baud, $+2.1\,\%$. 250000, UBRR = 3: $16\,000\,000/(16\cdot4)=250\,000$, error $0\,\%$. Choose 250000 if the PC end supports it (most USB-serial chips do); if 115200 is required use double-speed mode (the Arduino core selects it when it gives a smaller error). The datasheet's combined limit is about 4.5 % (3.9 % in double-speed mode), so $-3.5\,\%$ against a PC with a small error leaves a thin margin, and both 115200 settings exceed the recommended receiver error of $\pm2\,\%$ ($\pm1.5\,\%$ in double-speed mode); that is another reason to prefer 250000.
9. A micro-ROS client needs a 32-bit MCU with tens of kilobytes of RAM (Vulcanexus supported-hardware page); the Micro XRCE-DDS client alone needs only about 2 to 3 kB for a simple publisher/subscriber (eProsima and Vulcanexus docs), but the full rcl/rclc stack and message buffers need far more. The Uno's ATmega328P has 2 kB SRAM, so no: use the custom serial protocol. The ESP32 has 520 kB of RAM and is an officially supported micro-ROS board (transports: UART, Wi-Fi UDP, Ethernet UDP); yes.
10. (a) Custom serial protocol (UART or USB CDC, 115200 to 250000 baud) with a `ros2_control` hardware interface such as `diffdrive_arduino`, or micro-ROS if you want sensors as topics; control loop (PI on wheel velocity) on the MCU at 100 Hz; risk: link loss, so a watchdog on the MCU. (b) The servos already have a bus (for example Dynamixel TTL/RS-485); use an existing driver or `ros2_control` hardware interface for that bus rather than your own protocol; control at 100 Hz on the PC is acceptable for position servos; risk: bus latency and the USB adapter's latency timer. (c) CAN (or EtherCAT) drivers with the loop inside the drivers or on a real-time computer; the 500 Hz loop must not cross a USB-serial adapter or DDS; risk: bus load and jitter, so budget the bits per cycle.
11. All `7E`: stuffing doubles it to 128 bytes; COBS has no zeros, so it adds one code byte: 65 bytes (plus the `00` delimiter). All `00`: stuffing leaves 64 bytes unchanged; COBS gives 65 bytes (each zero becomes a `01` code, plus one final code). Predictable overhead favours COBS; streaming simplicity favours stuffing. With a CRC and a small MCU, stuffing on the fly is fine for a command link whose payload rarely contains `7E`, while COBS is better when the payload is arbitrary data and the link is tight.
12. Expected: the clean stream gives all frames, `crc_errors = 0`, `lost = 0`; the boundary frame with `7E` and `7D` in the payload round-trips; the Python and firmware parsers print the same fields and the same CRC byte; after 2 s of silence the firmware stops. A rejecting observation: a corrupted frame accepted, a payload with `7E` mis-parsed, a loss count that wraps wrongly at 255 to 0, or a parser that stops accepting frames after a truncated one.
