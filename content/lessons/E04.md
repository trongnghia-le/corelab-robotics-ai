## Why this matters

A robot demo works once because the experimenter silently handled everything that could go wrong. A deployed robot needs skills that know their own limits: "pick up the cup" must say when it is not applicable (the cup is out of reach), must stop within a bounded time, and must tell its caller precisely what happened, so that a higher-level program can retry, replan or ask for help.

This builds on E01 (decisions in sequence) and on RL20, where an option was defined as an initiation set, an intra-option policy and a termination condition. A robot skill is an option with an engineering contract.

## Intuition

Think of a skill as a function with a signature that includes the physical world. The inputs are a target and parameters; the output is not only "done" but one of a small set of statuses with a reason. The controller inside may be learned, hand-written or a classical planner; the caller only relies on the contract.

## Theory and derivation

### The skill contract

A skill $\sigma$ has
- **Preconditions** $\mathrm{pre}(\sigma)$: conditions on the world and parameters under which the skill is allowed to start (target in reach, start and goal not in collision, gripper empty). If violated, the skill is **refused**: no motion happens.
- **A controller** that maps observations to commands while running.
- **Terminal conditions** with distinct statuses. *Success* is the postcondition $\mathrm{post}(\sigma)$ (target reached within tolerance $\varepsilon$ and held for $h$ steps). *Failure* modes are named: collision, loss of progress (stall), exceeded time (timeout), external abort.
- **Effects**: what the skill changes in the world on success. Planners (E05) use pre and effects, not the controller.

Exactly one status is reported, with a reason. This is the same set of ideas as the ROS 2 action interface (goal, feedback, result with a status, cancellation), which is why robot skills are usually implemented as action servers.

### Proportional reaching and a closed-form duration

Let the end effector be a point at $x_t$ moving toward the goal $g$ with error $e_t=\lVert g-x_t\rVert$. The controller commands the step $\min(ke_t,v_{\max})$ straight toward $g$. Away from the speed limit ($ke_t\le v_{\max}$) the error is multiplied by $(1-k)$ each step:
$$e_n=e_0(1-k)^n.$$
The first step with $e_n\le\varepsilon$ is the smallest integer
$$n=\left\lceil\frac{\ln(\varepsilon/e_0)}{\ln(1-k)}\right\rceil,$$
and requiring the error to stay inside the tolerance for $h$ consecutive steps reports success at step $n+h-1$. With a speed limit the first phase is linear: the error drops by $v_{\max}$ per step until $e\le v_{\max}/k$.

### Failure detectors

- **Collision**: new position within an obstacle radius. Check after each commanded step, and with a sampled path remember tunnelling: a step longer than the obstacle can jump over it.
- **Stall**: the error decreases by less than $\delta$ over a window of $w$ steps while the error is still above $\varepsilon$. The window and threshold must be consistent with normal behaviour: just outside the tolerance the unclamped controller still gains $\varepsilon\,(1-(1-k)^w)$ over a window, so $\delta$ must be smaller than that or a healthy run is reported as stalled.
- **Timeout**: a hard cap on steps (or seconds). Without it a skill blocks its caller forever.
- **Hold requirement**: requiring $h>1$ consecutive in-tolerance steps avoids declaring success on a single noisy sample that crosses the tolerance band.

### Composition

A sequence $\sigma_1;\sigma_2$ is valid if the effect and postcondition of $\sigma_1$ imply $\mathrm{pre}(\sigma_2)$. A mismatch of tolerances is a classic bug: a reach that stops within 1 cm of the pre-grasp pose followed by a grasp that requires 0.5 cm will be refused every time.

## Worked example

Planar point robot with base at the origin, maximum reach $1.0$, goal $(0.8,0)$, $k=0.25$, $v_{\max}=1$, $\varepsilon=0.01$, $h=3$.

**Step 1, preconditions.** Distance base to goal $=0.8\le1$: reachable. No obstacles. Start $(0,0)$ is not in collision. Skill may start.

**Step 2, closed-form duration.** $e_n=0.8(0.75)^n$. $n=15$: $0.8(0.01336)=0.0107>0.01$. $n=16$: $0.8(0.01002)=0.00802\le0.01$. So the error is inside the tolerance first at step 16. With $h=3$ the skill reports SUCCEEDED at step $16+3-1=18$. The final error is $0.8(0.75)^{18}=0.0045$.

**Step 3, obstacle on the line.** A circle at $(0.4,0)$, radius $0.1$. Positions: $x_1=0.2$ (distance $0.2>0.1$, safe), $x_2=0.35$ (distance $0.05\le0.1$): FAILED, reason collision, at step 2. The goal $(0.8,0)$ itself is fine, so the precondition passes but the straight-line controller cannot get there: obstacle avoidance would need a planner (E06) or a different skill.

**Step 4, out of reach.** Goal $(1.5,0)$: distance $1.5>1$, status REFUSED, steps 0, nothing executed.

**Step 5, timeout and stall.** With `max_steps = 5` the error is $0.8(0.75)^5=0.19$: TIMEOUT. With $k=0.0001$ the error falls by $8\times10^{-5}$ per step; over a 10-step window $<10^{-3}$, so STALLED at step 10.

**Step 6, speed limit.** $e_0=1$, $k=0.5$, $v_{\max}=0.1$, $\varepsilon=0.01$, $h=1$: eight linear steps bring the error to $0.2$ (where $ke=v_{\max}$), then it halves: $0.1,0.05,0.025,0.0125,0.00625$. Total 13 steps.

## Reference implementation

A simulated reaching skill: preconditions, controller, five terminal statuses and the closed-form duration.

```python
import math

def dist(a, b):
    return math.hypot(a[0] - b[0], a[1] - b[1])

def check_precondition(start, goal, base, max_reach, obstacles):
    """Contract part 1: may this skill start? Returns (ok, reason). obstacles = [(cx, cy, radius)]."""
    if dist(base, goal) > max_reach:
        return False, "goal_out_of_reach"
    for cx, cy, r in obstacles:
        if dist(start, (cx, cy)) <= r:
            return False, "start_in_collision"
        if dist(goal, (cx, cy)) <= r:
            return False, "goal_in_collision"
    return True, "ok"

def run_reach(start, goal, base, max_reach, obstacles=(), k=0.25, v_max=1.0, eps=0.01,
              hold=3, max_steps=200, stall_window=10, min_progress=1e-3):
    """Contract part 2: run a proportional reaching controller (step = min(k*error, v_max) toward the goal)
    and report exactly one terminal status:
      REFUSED   - precondition failed, nothing was executed
      SUCCEEDED - error <= eps for `hold` consecutive steps (the postcondition)
      FAILED    - 'collision' (entered an obstacle)
      STALLED   - error shrank by less than min_progress over stall_window steps while still > eps
      TIMEOUT   - max_steps exhausted
    """
    ok, reason = check_precondition(start, goal, base, max_reach, obstacles)
    if not ok:
        return {"status": "REFUSED", "reason": reason, "steps": 0, "error": dist(start, goal)}
    x = start; errs = [dist(x, goal)]; inside = 0
    for t in range(1, max_steps + 1):
        e = errs[-1]
        if e > 0:
            step = min(k * e, v_max)
            x = (x[0] + (goal[0] - x[0]) / e * step, x[1] + (goal[1] - x[1]) / e * step)
        if any(dist(x, (cx, cy)) <= r for cx, cy, r in obstacles):
            return {"status": "FAILED", "reason": "collision", "steps": t, "error": dist(x, goal)}
        errs.append(dist(x, goal))
        inside = inside + 1 if errs[-1] <= eps else 0
        if inside >= hold:
            return {"status": "SUCCEEDED", "reason": "within_eps", "steps": t, "error": errs[-1]}
        if errs[-1] > eps and t >= stall_window and errs[-1 - stall_window] - errs[-1] < min_progress:
            return {"status": "STALLED", "reason": "no_progress", "steps": t, "error": errs[-1]}
    return {"status": "TIMEOUT", "reason": "max_steps", "steps": max_steps, "error": errs[-1]}

def steps_to_succeed(e0, k, eps, hold):
    """Closed form for an unclamped proportional controller: error after n steps is e0*(1-k)**n.
    First n with error <= eps, plus hold-1 further steps inside the tolerance."""
    n = 0
    while e0 * (1 - k) ** n > eps:
        n += 1
    return n + hold - 1

if __name__ == "__main__":
    base, goal = (0.0, 0.0), (0.8, 0.0)
    r = run_reach((0.0, 0.0), goal, base, 1.0)
    print("nominal:", r, "closed form:", steps_to_succeed(0.8, 0.25, 0.01, 3))
    print("out of reach:", run_reach((0.0, 0.0), (1.5, 0.0), base, 1.0))
    print("obstacle on the line:", run_reach((0.0, 0.0), goal, base, 1.0, obstacles=[(0.4, 0.0, 0.1)]))
    print("goal inside obstacle:", run_reach((0.0, 0.0), goal, base, 1.0, obstacles=[(0.8, 0.0, 0.05)]))
    print("timeout:", run_reach((0.0, 0.0), goal, base, 1.0, max_steps=5))
    print("stall (tiny gain):", run_reach((0.0, 0.0), goal, base, 1.0, k=0.0001))
    assert r["status"] == "SUCCEEDED" and r["steps"] == steps_to_succeed(0.8, 0.25, 0.01, 3) == 18
    print("self-test passed")
```

Expected: SUCCEEDED in 18 steps (closed form 18); REFUSED for the out-of-reach goal; FAILED collision at step 2; TIMEOUT with five steps; STALLED at step 10.

### Goal

Implement the skill contract and show with tests that each status is reported only in its own situation, with a reason.

### Setup

Python 3 standard library only. Paste the starter into `lab_e04.py`, implement the three stubs and append the tests.

### Tasks

2. Implement `steps_to_succeed` and check 18 for the worked example.
3. Implement `run_reach` for the controller, collision and success logic.
4. Add the stall and timeout statuses; verify 10 steps for the stall case.

6. Run the already-at-goal edge case and explain the step count.

### Starter code

```python
import math

def dist(a, b):
    return math.hypot(a[0] - b[0], a[1] - b[1])

def check_precondition(start, goal, base, max_reach, obstacles):
    """May the skill start? Return (ok, reason). obstacles = [(cx, cy, radius)].
    Reasons, checked in this order: 'goal_out_of_reach' (distance from base to goal > max_reach),
    'start_in_collision', 'goal_in_collision' (inside or on a circle), else 'ok'."""
    raise NotImplementedError

def run_reach(start, goal, base, max_reach, obstacles=(), k=0.25, v_max=1.0, eps=0.01,
              hold=3, max_steps=200, stall_window=10, min_progress=1e-3):
    """Run a proportional reaching controller: each step moves min(k*error, v_max) straight toward
    the goal. Return a dict {status, reason, steps, error} with exactly one terminal status:
      REFUSED   precondition failed (steps = 0, nothing executed)
      FAILED    reason 'collision': the new position is inside or on an obstacle circle
      SUCCEEDED reason 'within_eps': error <= eps for `hold` consecutive steps (steps = this step)
      STALLED   reason 'no_progress': error > eps, t >= stall_window and the error decreased by
                less than min_progress over the last stall_window steps
      TIMEOUT   reason 'max_steps': max_steps executed without any of the above
    Check order inside a step: collision, then success, then stall."""
    raise NotImplementedError

def steps_to_succeed(e0, k, eps, hold):
    """Closed form for the unclamped controller: error after n steps is e0*(1-k)**n. Return the
    step at which SUCCEEDED is reported: first n with error <= eps, plus hold-1 more steps."""
    raise NotImplementedError
```

### Tests

```python
base, goal = (0.0, 0.0), (0.8, 0.0)
# 1. nominal run agrees with the closed form: 0.8*0.75**16 = 0.0079 <= 0.01 (n = 16), plus hold-1 = 2 -> 18
assert steps_to_succeed(0.8, 0.25, 0.01, 3) == 18
r = run_reach((0.0, 0.0), goal, base, 1.0)
assert r["status"] == "SUCCEEDED" and r["steps"] == 18 and r["error"] <= 0.01
# 2. preconditions refuse without executing
assert check_precondition((0, 0), (1.5, 0), base, 1.0, []) == (False, "goal_out_of_reach")
assert check_precondition((0.4, 0), goal, base, 1.0, [(0.4, 0.0, 0.1)]) == (False, "start_in_collision")
r = run_reach((0.0, 0.0), goal, base, 1.0, obstacles=[(0.8, 0.0, 0.05)])
assert r["status"] == "REFUSED" and r["reason"] == "goal_in_collision" and r["steps"] == 0
# 3. each failure condition is reported with its own status
r = run_reach((0.0, 0.0), goal, base, 1.0, obstacles=[(0.4, 0.0, 0.1)])
assert (r["status"], r["reason"], r["steps"]) == ("FAILED", "collision", 2)        # x_2 = 0.35 is inside
assert run_reach((0.0, 0.0), goal, base, 1.0, max_steps=5)["status"] == "TIMEOUT"
assert run_reach((0.0, 0.0), goal, base, 1.0, k=0.0001)["status"] == "STALLED"
# 4. edge: already at the goal succeeds after exactly `hold` steps
assert run_reach(goal, goal, base, 1.0)["steps"] == 3
# 5. properties: closed form equals simulation; SUCCEEDED <=> error <= eps; REFUSED => steps == 0
for k in (0.1, 0.25, 0.5, 0.9):
    for e0 in (0.2, 0.5, 0.9):
        out = run_reach((0.0, 0.0), (e0, 0.0), base, 1.0, k=k, v_max=10.0, max_steps=500)
        assert out["status"] == "SUCCEEDED" and out["steps"] == steps_to_succeed(e0, k, 0.01, 3)
for g in [(0.3, 0.2), (1.2, 0.0), (0.0, -0.9)]:
    out = run_reach((0.0, 0.0), g, base, 1.0)
    assert out["status"] in {"REFUSED", "FAILED", "SUCCEEDED", "STALLED", "TIMEOUT"}
    assert (out["status"] == "SUCCEEDED") == (out["error"] <= 0.01 and out["status"] != "REFUSED")
    assert out["status"] != "REFUSED" or out["steps"] == 0
print("all tests passed")
```

## Verification

- Compare the simulated duration with the closed form for several $(e_0,k)$ pairs.
- For each status, write one test that triggers it and one that must not.
- Check the invariants: exactly one terminal status; REFUSED means no motion; SUCCEEDED means the postcondition holds at the end.
- Run randomised goals and look for runs that end in TIMEOUT: they reveal gaps in the failure detectors.

## Failure modes

- **Falling through to success** (exercise 5): returning SUCCEEDED after the loop ends hides timeouts.
- **Single-sample success**: with sensor noise, one in-tolerance sample is not success; use a hold window.
- **False stall**: a threshold $\delta=0.01$ with window 10 flags the healthy run because the gain inside the tolerance band is $0.0094<0.01$.
- **Tunnelling**: a step of 0.3 m jumps over a 0.1 m obstacle; check along the segment, not only at the end.
- **Mismatched tolerances in a sequence** (exercise 9).
- **No timeout**: the caller is blocked for ever when the skill never reaches the goal.
- **Refusing silently**: report the reason; "failed" without a cause cannot be recovered from.

## Alternatives and trade-offs

| Approach | Strength | Weakness |
| --- | --- | --- |
| Monolithic learned policy | No hand-written contract | No guarantees; hard to debug |
| Skills with contracts (this lesson) | Composable, testable, recoverable | Contract engineering; tolerances to maintain |
| Finite state machine | Simple, explicit | Grows quickly with branches |

Prefer skills with contracts wherever a failure must be detected and handled by a caller.

## Transfer and retention

The skill contract appears in ROS 2 action servers, in behavior trees (SUCCESS, FAILURE, RUNNING) and in task planners (operators with preconditions and effects). In E05 the preconditions and effects become the symbolic operators; in E06 their geometric feasibility is checked. ## Exercise answers

1. A controller maps state to command (closes a loop); a policy maps observation to action, possibly learned, with no stated start or end; a skill wraps a controller or policy with preconditions, termination and failure statuses, and effects, so it can be called, monitored and composed.
2. Goal: target position and tolerance; feedback: current error (and step count); result: the status (SUCCEEDED, ABORTED/FAILED and reason) and the final error; cancel: a request to stop, giving CANCELED. A good answer also notes that REFUSED corresponds to rejecting the goal.
3. $e_n=0.5(0.5)^n$: $e_4=0.03125>0.02$ and $e_5=0.0156\le0.02$, so the error is first inside at $n=5$. Success at step $5+3-1=7$.
4. Linear phase: the error falls by 0.1 per step from 2 to 0.2: 18 steps. Then $0.1,0.05,0.025,0.0125,0.00625$: 5 more steps. Total 23.
5. If the loop ends because `max_steps` is reached, the code still returns SUCCEEDED. Fix: use `for ... else`, or return SUCCEEDED inside the `if`, and return TIMEOUT after the loop; also require a hold window.
6. $k=1$: the first step moves the full distance (0.8 $\le v_{\max}$) so the error is 0; success needs $h=3$ steps inside the tolerance: SUCCEEDED, 3 steps, error 0.
7. A good contract: preconditions — object grasped, arm can reach the shelf pose, shelf slot free (no collision); postcondition — object within tolerance of the slot pose and gripper open, object released; effects — object on shelf, gripper empty; failures — slot occupied (refused), collision, force limit, slip/drop, timeout; each with a reason.
8. A healthy run just outside the tolerance has error $e>\varepsilon$ and gains $e\,(1-(1-k)^w)>\varepsilon\,(1-(1-k)^w)$ over the window. So $\delta<\varepsilon\,(1-(1-k)^w)$. For $\varepsilon=0.01,k=0.25,w=10$: $0.01(1-0.0563)=0.00944$. Use $\delta=10^{-3}$.
9. The reach ends with error up to 1 cm, but the grasp precondition requires 0.5 cm, so the precondition fails whenever the reach stops in (0.5, 1] cm. Fixes: tighten the reach tolerance to $\le0.5$ cm (or make the pre-grasp a hover pose with a looser grasp precondition and a visual-servo step), or let the grasp skill start with its own alignment move. BT fallback: a Fallback node tries grasp, and on REFUSED runs a fine-align skill and retries once, then reports FAILURE with the reason.
10. A good project reports the success rate with 95 percent confidence intervals for both conditions, the distribution of failure reasons, the boundary case (the goal on the obstacle edge is refused or fails, retries do not help) and rejects "retries improve the success rate" if the intervals overlap or retries only help against transient failures.
