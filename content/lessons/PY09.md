## Why this matters

A perception pipeline that handles 10 scans per second on a laptop must handle 30 per second on the robot's small computer. A planner that takes 80 ms is too slow for a 10 Hz control loop. Making code faster is cheap compared with buying hardware, but only if you optimize the right thing: programmers are notoriously poor at guessing where the time goes. The discipline is simple and strict: **measure, find the bottleneck, change one thing, measure again, and prove the answer is unchanged**. This lesson gives the measurement tools (`cProfile`, `timeit`, `tracemalloc`), the arithmetic for predicting gains (Amdahl's law, complexity), and the main fixes (vectorization, better algorithms, less memory traffic) together with the checks that keep optimization honest.

## Intuition

Total time is a sum over parts. If one part takes 78% of the time, making it twice as fast saves 39%; making a 12% part a hundred times faster saves 12% at most. So you profile to learn the shares, and you fix the biggest share first. Python loops are slow because every iteration executes interpreter bytecode with boxed objects (each float is a 24-byte object plus an 8-byte pointer); NumPy moves the loop into compiled code operating on a packed array of raw 8-byte doubles. A **better algorithm** beats any constant-factor speedup: recomputing a window sum from scratch costs $O(nk)$, keeping a running sum costs $O(n)$.

## Theory and derivation

### Measure before changing

`python -m cProfile -s cumulative script.py` (or `cProfile.Profile()` around a function) reports per function: `ncalls`, `tottime` (time in the function itself, excluding callees), `cumtime` (including callees). Optimize by `tottime` first. The profiler adds overhead (a slowdown of two to four times for call-heavy code), so use it for *shares*, not absolute times. For small snippets use `timeit`: it runs the code many times and the **minimum** over repeats is the best estimate of intrinsic speed, since noise (other processes, frequency scaling) only adds time. Benchmarks must exclude setup (data creation), warm up caches, use realistic sizes and inputs, and compare equal work.

### Amdahl's law

If a fraction $p$ of the runtime is sped up by a factor $s$, the overall speedup is

$$S=\frac{1}{(1-p)+p/s},\qquad S_{\max}=\frac{1}{1-p}\ \text{as } s\to\infty.$$

For $p=0.9$, $s=10$: $S=1/(0.1+0.09)=5.26$; the limit is 10. For $p=0.115$ even $s=100$ gives only $1.13$. Use it *before* the work to decide whether an optimization is worth doing.

### Complexity and vectorization

Count operations: the naive moving average of $n$ points with window $k$ does $(n-k+1)k$ additions; the running-sum version does about $2n$. For $n=20{,}000$ and $k=500$ that is $9.75\times10^6$ versus about $4\times10^4$ (measured speedup 36). Vectorization replaces a Python-level loop by array operations (`np.cos(a)`, boolean masks, `np.sum`): the same arithmetic, executed in C with no per-element interpreter overhead, typically 10 to 100 times faster for arithmetic-bound loops, less when the loop body is already dominated by a library call. Vectorization is not free: it creates **temporary arrays** (memory traffic, peak memory) and often computes things you then discard (compute-then-mask).

### Memory

A Python `float` object takes 24 bytes and a list slot adds 8 bytes, so a list of floats uses about 32 bytes per element (measured: 32.1); a `float64` array uses 8 bytes per element (8.0). A broadcast of two length-$N$ vectors into an $N\times N$ matrix needs $8N^2$ bytes: for $N=20{,}000$ that is $3.2$ GB, which ends the program with `MemoryError` or the OS killing it. Use `tracemalloc` (Python allocations, including NumPy buffers) or `memory_profiler`/`resource` for peak usage; `array.nbytes` for an array's size. Reduce memory with chunking, in-place operations (`np.multiply(a, b, out=a)`), views instead of copies, smaller dtypes (float32: half the bytes, but only about 7 digits).

### Numerical equivalence

Reordering floating-point additions changes the last bits (M11): `sum(list)` and `np.sum` (pairwise) can differ by a few ulps (here $4\times10^{-9}$ absolute on a sum of size $10^5$, i.e. relative $4\times10^{-15}$). Compare with tolerances (`math.isclose`, `np.allclose`) sized to the expected rounding, and keep the slow implementation as a **test oracle**. Faster algorithms can also be less stable: a running sum accumulates rounding errors and can lose small values after a huge value leaves the window.

## Worked example

A lidar scan has $N=200{,}000$ points `(range r, angle a)`. We want the number of valid points (those with $0<r\le r_{\max}=8$) and their centroid $(\bar x,\bar y)$, $x=r\cos a$, $y=r\sin a$.

1. **Reference loop** (`scan_stats_loop`): 159,869 valid points, centroid $(0.0012674089113911,\ 0.0054182118308)$. Time 44 ms (best of 3).
2. **Profile** of the loop (160k valid points, with profiler overhead 0.165 s total): own time in the function 0.128 s (78%), `math.cos` 0.019 s (12%), `math.sin` 0.019 s (12%). The loop body dominates; the trigonometry is a small share. Amdahl: even an infinitely fast `sin` and `cos` would give $1/(1-0.23)=1.30$.
3. **Vectorized version** (`scan_stats_vec`): mask `(r > 0) & (r <= r_max)`, then `np.sum(rk*np.cos(ak))`. Result: the same count; centroid agrees to $1\times10^{-17}$ and $1.3\times10^{-16}$ (floating-point order). Time 11.4 ms: 3.9 times faster. The loop was removed but `cos`/`sin` on 160k elements remains, so the gain is moderate; that is the truth the profile predicted.
4. **Memory.** Building a list of the $x$ values uses 32.1 bytes per point (6.4 MB for 200k); `ra*np.cos(aa)` uses 8.0 bytes per point (1.6 MB), a ratio of 4.
5. **Algorithm.** For a moving average with $k=500$ on 20,000 floats, the naive version takes 97 ms and the running-sum version 2.7 ms (36 times faster); the maximum difference between them is $3.2\times10^{-15}$.
6. **A trap.** For data `[1e16, 1, 1, ...]` with $k=2$ the running sum returns `[5e15, 0, 0, ...]` while the naive version returns `[5e15, 1, 1, ...]`: after the huge value leaves the window the running sum has lost the 1s (absorption). The faster algorithm is wrong on this input.

## Reference implementation

```python
import math, time, tracemalloc
import numpy as np

def scan_stats_loop(ranges, angles, r_max):
    n = 0
    sx = sy = 0.0
    for r, a in zip(ranges, angles):
        if 0 < r <= r_max:
            sx += r * math.cos(a)
            sy += r * math.sin(a)
            n += 1
    if n == 0:
        raise ValueError("no valid points")
    return n, sx / n, sy / n

def scan_stats_vec(ranges, angles, r_max):
    r = np.asarray(ranges, dtype=float)
    a = np.asarray(angles, dtype=float)
    keep = (r > 0) & (r <= r_max)
    n = int(keep.sum())
    if n == 0:
        raise ValueError("no valid points")
    rk, ak = r[keep], a[keep]
    return n, float(np.sum(rk * np.cos(ak)) / n), float(np.sum(rk * np.sin(ak)) / n)

def moving_average_naive(xs, k):
    if not 1 <= k <= len(xs):
        raise ValueError("bad window")
    return [sum(xs[i:i + k]) / k for i in range(len(xs) - k + 1)]

def moving_average_fast(xs, k):
    if not 1 <= k <= len(xs):
        raise ValueError("bad window")
    s = sum(xs[:k])
    out = [s / k]
    for i in range(k, len(xs)):
        s += xs[i] - xs[i - k]
        out.append(s / k)
    return out

def best_time(f, repeat=5, number=1):
    best = float("inf")
    for _ in range(repeat):
        t0 = time.perf_counter()
        for _ in range(number):
            f()
        best = min(best, (time.perf_counter() - t0) / number)
    return best

def peak_memory(f):
    tracemalloc.start()
    try:
        f()
        return tracemalloc.get_traced_memory()[1]
    finally:
        tracemalloc.stop()

def amdahl(p, s):
    return 1.0 / ((1 - p) + p / s)

# self-test
rs, an = [1, 2, 0, 20], [0, math.pi / 2, 0, 0]
a = scan_stats_loop(rs, an, 10); b = scan_stats_vec(rs, an, 10)
assert a[0] == b[0] == 2 and all(abs(u - v) < 1e-12 for u, v in zip(a, b))
assert moving_average_naive([1, 2, 3, 4, 5], 2) == [1.5, 2.5, 3.5, 4.5]
assert abs(amdahl(0.9, 10) - 5.263157) < 1e-5
print(a)
```

### Extension challenge

Fix `moving_average_fast` so that it passes the absorption case without becoming $O(nk)$ (for example by recomputing the window sum exactly every $m$ steps, or by using `math.fsum` for the first window and Kahan compensation for updates), and measure its speed and its worst-case error on adversarial data.

## Verification

Verify an optimization with four checks. (1) **Equivalence**: the new code agrees with the old one on hand-computed cases, edge cases (empty selection, boundary values), random data (tolerance $10^{-9}$ for float64 sums), and adversarial data (large dynamic range). (2) **Speed**: use the minimum of several repeats on realistic sizes; report the speedup with the machine and library versions; check that the speedup grows or stays as $n$ increases (the complexity claim). (3) **Memory**: peak bytes, including temporaries, at the largest size you intend to use. (4) **Prediction**: compare the measured speedup with Amdahl's prediction; a large gap means the profile was misread. A check that could reject an optimization: equivalence failing on the absorption case, or the measured total speedup being below what the profile allowed.

## Failure modes

- Optimizing without profiling: tuning `sin` (12% share) gives at most 1.13 times.
- Timing the wrong thing: including data generation, a single cold run, or comparing different work.
- Using the mean of noisy timings instead of the minimum.
- Vectorized pairwise distances without thinking about size: $20{,}000^2\times8$ bytes $=3.2$ GB.
- Hidden copies: fancy indexing and `astype` copy; chained expressions create temporaries.
- Replacing a stable computation by a faster unstable one: the running sum returns `0.0` where the truth is `1.0`.
- float32 for accumulations: the sum of $10^6$ copies of 0.1 in float32 is `100000.0078` (relative error $8\times10^{-8}$), acceptable for display, not for a long-running integral.
- Comparing results with `==`: even correct optimizations reorder floating-point sums.
- Micro-optimizing the Python loop while the real cost is I/O or a library call.

## Alternatives and trade-offs

Vectorization with NumPy is the first tool, and it is limited by temporaries and by loops with dependencies between iterations (a recurrence such as a filter cannot be vectorized naively). `numba` compiles Python loops to machine code and keeps readable loop code at the price of an extra dependency and compile time; Cython and C++ extensions (CPP topics) give full control and more maintenance work. Better algorithms or data structures (running sums, KD-trees for nearest neighbours, sorting once) often give 100 to 1000 times, more than any constant factor. Multiprocessing helps for independent chunks but adds pickling overhead and breaks determinism of floating-point order (PY08); GPUs help for large regular arithmetic and not for small or branchy work. Caching (`functools.lru_cache`) trades memory for time. Do the cheapest change that meets the requirement and stop.

## Transfer and retention

- A control loop has a deadline: profile the worst-case iteration, not the average, and keep the allocation pattern constant (no growing lists inside the loop).
- Point-cloud processing and image pipelines are dominated by memory traffic; every temporary array you avoid is a speedup.
- In training, data loading often dominates GPU compute; profile the pipeline before buying hardware.
- From memory: write Amdahl's law, the five measurement rules and the equivalence checklist. In a week, profile one of your own scripts and predict the speedup of the top function before changing it.
