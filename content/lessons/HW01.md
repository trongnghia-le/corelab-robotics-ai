## Why this matters

Every robot you will ever build or buy is made of the same few kinds of parts. If you can name the blocks, you can read any robot's spec sheet, any wiring diagram and any forum post about "my robot resets when the motors start". If you cannot, every new part feels like a new mystery.

This lesson is the map for the whole Hardware & Embedded track. It does not go deep into any single part. It teaches you to ask four questions about any hardware: *what block is it, what does it connect to, how fast must it be, and what happens when it fails?* The later topics (electricity, power, sensors, motors, buses, firmware) each zoom into one box of the map.

## Intuition

A robot is a loop of *sense, think, act*, but made of physical things. A sensor turns something physical (a wheel turning, a wall nearby, a tilt) into an electrical signal. A computer turns signals into decisions. A driver turns a weak decision signal into real power. An actuator (usually a motor) turns that power into motion. A battery feeds everything, and wires or radio links connect it all.

So there are six blocks:

1. **Compute**: a microcontroller (MCU) such as an Arduino or ESP32, a single-board computer (SBC) such as a Raspberry Pi, or a GPU module such as a Jetson Orin Nano.
2. **Sensors**: encoders, IMUs, distance sensors, cameras, LiDAR, current sensors.
3. **Drivers**: motor drivers, servo controllers, anything that handles more current than a microcontroller pin can.
4. **Actuators**: DC gearmotors, servos, steppers, brushless motors, LEDs, speakers.
5. **Power**: battery, fuse, switch, regulators (voltage converters), wiring.
6. **Communications**: the wires and protocols between blocks (UART, I2C, SPI, CAN, USB, Ethernet, Wi-Fi).

A useful habit: the *electrical* picture is separate from the *information* picture. Power flows from the battery out to everything. Information flows around the sense, think, act loop. A good diagram draws both, and a common beginner bug is that the two disagree (for example a signal wire with no shared ground).

## Theory and derivation

### The two-tier architecture

Almost every hobby and research mobile robot splits compute in two tiers:

| Tier | Typical part | What it is good at | What it is bad at |
| --- | --- | --- | --- |
| Microcontroller (MCU) | ATmega328P (Arduino Uno), ESP32 | Hard timing: reading encoders, generating PWM, running a 100 to 1000 Hz control loop with predictable delay; very low power; boots instantly | Little memory (Uno: 2 KB RAM, 32 KB flash), no operating system, hard to run big software |
| Single-board computer (SBC) | Raspberry Pi 4 | Linux, ROS 2, networking, cameras, planning, logging, a normal programming environment | Not hard real-time: the operating system can pause your code for milliseconds; many GPIO tasks are awkward |
| GPU module | Jetson Orin Nano | Neural networks, depth processing, heavy vision | Power hungry, expensive, same Linux timing caveats as an SBC |

The rule of thumb used by many robot builders (for example in the Articulated Robotics tutorials) is: *put anything that needs exact timing on a microcontroller, and anything that needs a lot of memory or a full software stack on the SBC.* The two talk over a serial link (USB or UART). ROS 2 usually lives on the SBC; the MCU either speaks a simple custom protocol to a ROS node (you will build this in HW11 and S06) or runs micro-ROS.

Real numbers help you feel the gap. The ATmega328P datasheet gives about 9.2 mA typical supply current at 16 MHz and 5 V (Table 28.3, "Active 16 MHz, VCC = 5V"), so an Uno-class chip runs for days on a small battery. An ESP32 has two cores up to 240 MHz and hundreds of KB of RAM (Espressif datasheet), but still no Linux. A Raspberry Pi 4 or Jetson module draws watts rather than milliwatts. Treat vendor "typical" numbers as a guide and read the datasheet for your exact part.

### Typical robot architectures

Three layouts cover most of what you will meet:

- **Differential-drive base** (two driven wheels and a caster): a Raspberry Pi runs ROS 2 and the LiDAR; an Arduino or ESP32 reads two wheel encoders and an IMU and drives two motor drivers. Link: USB serial between Pi and MCU.
- **Robot arm with smart servos on a bus**: the servos (for example Dynamixel-style or serial bus servos) contain their own driver, sensor and tiny controller. The computer talks to all of them over one half-duplex serial bus using an addressed protocol. Fewer wires, but one shared bus has a limited message budget.
- **Quadruped or other many-joint robot with CAN motor drivers**: each joint has a brushless motor with an integrated driver on a CAN bus (differential, multi-drop, robust against noise). A central computer sends torque or position commands at a few hundred hertz.

All three are the same six blocks. What changes is how much is bundled into one part: a smart servo is sensor, driver, actuator and a bus interface in one box.

### Following a signal: sensing path and command path

Pick a concrete chain for the differential-drive robot. Sensing: wheel turns, a magnetic encoder produces A/B pulses (digital edges), the MCU counts them in an interrupt routine (HW08), the main loop converts counts to speed, the MCU packs a message and sends it on the serial link, a ROS 2 node on the Pi receives it and publishes odometry. Command: a navigation node publishes a velocity command, the Pi sends it over the serial link, the MCU runs a speed loop, it writes a PWM duty (HW05), the motor driver switches battery current into the motor, the wheel turns.

Write each link as `producer --(interface)--> consumer`:

$$\text{encoder}\xrightarrow{\text{A/B pulses}}\text{MCU}\xrightarrow{\text{UART/USB}}\text{Pi}\xrightarrow{\text{UART/USB}}\text{MCU}\xrightarrow{\text{PWM + DIR}}\text{driver}\xrightarrow{\text{motor power}}\text{motor}.$$

If you can write this chain for any robot, you can debug it by bisection: probe the middle, see which half is wrong, repeat.

### Bus time: the formulas you will reuse

Two formulas let you check whether a link can carry what you want. For a UART frame in the common 8N1 format (1 start bit, 8 data bits, 1 stop bit) every byte costs 10 bit times:

$$t_{\text{UART}}=\frac{10\,n}{\text{baud}}.$$

For I2C, every byte on the wire takes 9 clock periods (8 data bits plus an acknowledge bit). A register burst read sends the device address with the write bit, the register address, then the address again with the read bit, and then receives $n$ data bytes. Ignoring START, STOP and clock stretching:

$$t_{\text{I2C}}\approx\frac{9\,(3+n)}{f_{\text{SCL}}}.$$

For $n=14$ bytes (the accelerometer, temperature and gyroscope registers of an MPU-6050 are contiguous, so one burst reads them all) at $f_{\text{SCL}}=400$ kHz: $9\cdot17/400\,000=382.5\ \mu$s. At the standard-mode rate of 100 kHz it is 1.53 ms. So a 1 kHz sampling loop (1 ms period) fits at 400 kHz, using about 38 % of the period, but cannot work at 100 kHz. (The I2C basics are in the SparkFun I2C tutorial; HW06 and HW09 go deeper.)

The same arithmetic for a bus shared by $m$ messages per cycle: utilization is

$$U=\sum_i \frac{t_i}{T}=\frac{\text{time per cycle spent on the wire}}{\text{cycle time}}.$$

Above about 50 to 70 % there is no room for retries, jitter or a forgotten debug print.

### Latency chains

Latency is the time from something happening in the world to the motor responding to it. Add the stages:

$$L=\sum_k l_k .$$

Typical stages: waiting for the next sample (on average half a sample period), the bus transfer, the code that processes it, the transfer to the next processor, the controller's own loop period, the driver, and the motor's own mechanical and electrical response. Latency matters because the robot keeps moving while the system reacts: distance travelled is $d=v\,L$. A robot at 1 m/s with 50 ms total latency has moved 5 cm before the first correction reaches the wheels.

A practical rule: the *fast, safety-relevant* loops (motor speed control, current limit, emergency stop) should not depend on a long chain through a non-real-time computer. That is exactly why the MCU tier exists.

### Typical latency numbers to remember

| Link or stage | Typical order of magnitude | Why |
| --- | --- | --- |
| MCU interrupt response | microseconds | Hardware jumps straight to your handler |
| I2C 14-byte burst at 400 kHz | about 0.4 ms | Computed above |
| UART 20-byte message at 115200 baud | about 1.7 ms | Computed above |
| USB-serial adapter | 1 to 16 ms | Adapters buffer bytes; Linux USB serial drivers use a latency timer (commonly 16 ms by default on FTDI chips) |
| Linux (non-real-time) scheduling jitter | milliseconds, occasionally tens | Other processes can run first |
| Wi-Fi hop | 2 to 100+ ms with large variation | Shared radio medium |
| Camera frame at 30 fps | 33 ms between frames, plus processing | One frame period before you even see the image |

These are rules of thumb collected from common practice, not specifications. Measure your own system. The USB latency-timer figure is a documented FTDI default and is the classic cause of "jittery" serial robots.

### Where ROS 2 sits

ROS 2 is software middleware. It runs on the SBC (or a PC), not inside a basic MCU. It connects nodes with topics. Your hardware appears to ROS as a *hardware interface*: a node (or ros2_control plugin) that reads sensor values from the MCU and writes commands to it. The MCU firmware is a separate program whose job is to be the reliable, real-time translator between electrons and messages. Later topics (HW11, S06, S07) cover this boundary.

### The usual failure points

Experienced builders learn to look in this order before they suspect software:

1. **Power**: voltage sag when motors start, a regulator too small, a battery near empty, a loose power connector.
2. **Connectors and wires**: a breadboard contact, a Dupont wire that does not grip, a cable that fails only when the robot moves.
3. **Ground**: two parts that talk by a signal wire must also share a ground reference.
4. **Logic levels**: a 3.3 V part driven from a 5 V pin (HW02).
5. **Timing**: a loop that takes longer than its period, a bus that is too full, a stale value used as if it were fresh (S06).

### Tracing latency and bus load with three numbers

For a first estimate you need only: the rate each producer must run at, the bytes it sends, and the link speed. Multiply and compare. If the answer is near or above 1, the design is wrong on paper, which is far cheaper than finding out on the bench.

## Worked example

A small differential-drive robot has: two 12 V gearmotors with magnetic encoders, two TB6612FNG-class motor drivers (one dual driver chip), an MPU-6050 IMU, an Arduino Uno-class MCU, a Raspberry Pi 4, an RPLIDAR A1-class LiDAR, and a 3S LiPo battery with a switch, fuse and two voltage regulators.

### Step 1: classify

**Problem.** Assign every part of the robot to one of the six blocks: compute, sensors, drivers, actuators, power, communications.

**Solution.**

1. Compute: parts that run code, the Arduino and the Raspberry Pi.
2. Sensors: parts that turn a physical quantity into a signal, the encoders (wheel rotation), the MPU-6050 (acceleration and rotation rate) and the LiDAR (range).
3. Drivers: the TB6612FNG, which switches battery current for a logic-level command.
4. Actuators: the two gearmotors.
5. Power: the LiPo, fuse, switch and the two regulators.
6. Communications: USB serial between Pi and Arduino, USB to the LiDAR, I2C to the IMU.

**Check.** Every listed part appears exactly once: 2 compute + 3 sensor kinds + 1 driver type + 1 actuator type + 4 power parts, and the three links are the communications block.

**Takeaway.** Any robot decomposes into the same six blocks; naming the block of each part is the first step of every design and every debug.

### Step 2: interfaces

**Problem.** For each connection between blocks, state the interface that carries it.

**Solution.**

1. Encoders to MCU: A/B pulses are digital edges, so they go to interrupt-capable pins to be counted.
2. IMU to MCU: the MPU-6050 is a register-based chip, so I2C.
3. MCU to driver: one PWM (speed) plus two direction pins per motor.
4. Driver to motor: not a signal but battery power, switched by the driver.
5. LiDAR to Pi: USB (a serial link inside).
6. Pi to MCU: USB serial.

**Check.** Follow the chain $\text{encoder}\to\text{MCU}\to\text{Pi}\to\text{MCU}\to\text{driver}\to\text{motor}$: every arrow has exactly one interface, and the driver-to-motor arrow is the only one that carries power instead of information.

**Takeaway.** Writing each link as producer, interface, consumer makes a robot debuggable by bisection.

### Step 3: an I2C budget

**Problem.** The MPU-6050 burst is 14 bytes at $f_{\text{SCL}}=400$ kHz. Find the transfer time and the bus load if the MCU reads it at 200 Hz.

**Solution.**

1. A burst read sends the device address with write bit, the register address, the device address with read bit, then $n=14$ data bytes: $3+14=17$ bytes. Each byte costs 9 clock periods (8 data bits and an acknowledge bit).
2. $t=\dfrac{9\,(3+n)}{f_{\text{SCL}}}=\dfrac{9\cdot17}{400\,000}=\dfrac{153}{400\,000}=382.5\ \mu$s.
3. Bus busy fraction: $t\,f_{\text{read}}=382.5\ \mu\text{s}\times200=76.5$ ms per second $=7.65\,\%\approx7.7\,\%$.
4. $7.7\,\%$ is far below the 50 to 70 % comfort limit, so this is fine.

**Check.** Units: $\mu$s times Hz is dimensionless. At 100 kHz the same burst takes $153/100\,000=1.53$ ms, longer than a 1 ms loop, so the 400 kHz mode is what makes a 1 kHz read possible (38 % of the period).

**Takeaway.** Bus load is bytes on the wire times bit time times rate; compute it before building.

### Step 4: a serial budget

**Problem.** The MCU sends a 20-byte status message (two wheel speeds, IMU values, battery voltage) to the Pi at 50 Hz over a 115200 baud UART (8N1). Find the message time and the link utilization.

**Solution.**

1. In 8N1 each byte takes 10 bit times (start, 8 data, stop): $t_{\text{UART}}=10n/\text{baud}$.
2. One message: $t=\dfrac{10\cdot20}{115200}=1.736\ \text{ms}\approx1.74$ ms.
3. At 50 messages per second: $U=50\cdot1.736\ \text{ms}=86.8$ ms per second $=8.7\,\%$.
4. Leaves about $91\,\%$ of the link free, enough for a command message in the other direction.

**Check.** Equivalent check by bytes: $50\cdot20=1000$ bytes/s $=10\,000$ bit/s versus $115\,200$ bit/s gives $10\,000/115\,200=8.68\,\%$.

**Takeaway.** Multiply rate, bytes and bit time and compare with 1; far below it means the design has room for retries and jitter.

### Step 5: a latency chain

**Problem.** An IMU measures a tilt; find the time until the motors react when the reaction is handled in the MCU's own loop (1 kHz IMU, I2C 0.38 ms, 1 kHz MCU loop, driver and motor electrical response about 0.1 ms), and compare with sending it through the Pi (serial 1.7 ms, USB latency up to 16 ms, Linux scheduling, ROS 2).

**Solution.**

1. Latency is the sum of stages, $L=\sum_kl_k$. Waiting for the next sample is on average half a sample period: $0.5\cdot1\ \text{ms}=0.5$ ms.
2. I2C transfer: $0.38$ ms (from the I2C budget above). The control loop can add up to its full period: $1$ ms (1 kHz). Driver and motor electrical response: about $0.1$ ms.
3. MCU path: $0.5+0.38+1+0.1=1.98\approx2$ ms.
4. Pi path: the data must cross the serial link to the Pi and the command must cross back. One crossing costs $1.74$ ms plus up to $16$ ms of USB latency timer, so two crossings cost up to $2\,(1.74+16)\approx35$ ms, before Linux scheduling and ROS 2 add more and add jitter.
5. The MCU path is roughly $2$ ms against tens of milliseconds, a factor of ten or more.

**Check.** Distance moved during the delay, $d=vL$: at 1 m/s, 2 ms is 2 mm while 35 ms is 3.5 cm. The Pi-path figure is an upper-end estimate from rules of thumb, not a specification: the argument holds even if the USB timer is much smaller.

**Takeaway.** Fast, safety-relevant loops belong on the MCU; this is the argument for the two-tier split.

### Step 6: the fault finder

**Problem.** The Pi is powered from a power bank, the Arduino from the Pi's USB, and the motor driver from the LiPo. All three grounds meet only through the USB cable and the driver; the driver's logic ground is wired to the LiPo negative but the Arduino's ground is not connected to it directly. The motors twitch randomly. Find the cause and the fix.

**Solution.**

1. A signal (PWM, direction) is a voltage measured against a reference. The driver measures it against its own logic ground, the Arduino generates it against its own ground.
2. The two grounds are joined only by a long indirect path (USB cable shield and the driver), so their potentials can differ and move when the motors draw current. The driver then sees a PWM level that wanders relative to its reference, and the motors twitch.
3. Cause: no deliberate common ground between the signal source and the driver.
4. Fix: connect the Arduino ground to the driver logic ground and to the battery negative at one point.

**Check.** The symptom matches ground failure (power and ground come first in the usual failure order: power, connectors, ground, logic levels, timing). After the fix every part that exchanges a signal wire shares one ground reference, which can be confirmed with a multimeter in continuity mode between the Arduino GND and the battery negative.

**Takeaway.** Two parts that talk by a signal wire must share a ground; do it deliberately, at one point.

## Reference implementation

You do not need hardware for this lesson's lab. The reference below is the minimal calculator the exercises use: a part classifier, bus-time formulas, a latency sum and a design-fault finder.

```python
BLOCKS = {
    "esp32-wroom": "compute",
    "arduino uno": "compute",
    "raspberry pi 4": "compute",
    "jetson orin nano": "compute",
    "mpu-6050": "sensor",
    "vl53l0x": "sensor",
    "hc-sr04": "sensor",
    "rplidar a1": "sensor",
    "tb6612fng": "driver",
    "max14870": "driver",
    "pololu 37d gearmotor": "actuator",
    "sg90 servo": "actuator",
    "18650 cell": "power",
    "lm2596 buck module": "power",
    "mcp2515": "comms",
    "usb-uart bridge": "comms",
}

def classify(part):
    key = part.strip().lower()
    if key not in BLOCKS:
        raise ValueError("unknown part: " + part)
    return BLOCKS[key]

def i2c_read_us(n_bytes, clock_hz):
    clocks = 9 * (3 + n_bytes)
    return clocks / clock_hz * 1e6

def uart_us(n_bytes, baud):
    return n_bytes * 10 / baud * 1e6

def chain_latency_ms(stages):
    return sum(ms for _, ms in stages)

def distance_cm(speed_m_s, latency_ms):
    return speed_m_s * latency_ms / 1000 * 100

def find_faults(design):
    faults = []
    if not design.get("common_ground", False):
        faults.append("no common ground")
    if not design.get("fuse", False):
        faults.append("no fuse")
    if not design.get("estop", False):
        faults.append("no emergency stop")
    if not design.get("driver_between_mcu_and_motor", False):
        faults.append("motor wired to MCU pin")
    if not design.get("logic_levels_match", False):
        faults.append("logic level mismatch")
    return sorted(faults)

assert classify("TB6612FNG") == "driver"
assert abs(i2c_read_us(14, 400_000) - 382.5) < 1e-9
assert abs(uart_us(20, 115200) - 1736.111) < 1e-3
assert find_faults({"fuse": True}) == [
    "logic level mismatch", "motor wired to MCU pin", "no common ground", "no emergency stop"]
print("reference ok")
```

## Independent practice

### Goal
Write a small hardware-planning calculator: classify parts into blocks, compute bus times, add up a latency chain, and flag missing essentials in a design, all checked against hand calculations before you spend money on parts.

### Setup
Python 3 standard library. Save the starter and tests together as `hw01_lab.py` and run `python3 hw01_lab.py`.

### Tasks
1. `classify(part)`: look up the part in `BLOCKS` ignoring case and surrounding spaces; raise `ValueError` for an unknown part.
2. `i2c_read_us(n_bytes, clock_hz)`: microseconds for a register burst read, $9(3+n)/f$.
3. `uart_us(n_bytes, baud)`: microseconds for 8N1 bytes.
4. `chain_latency_ms(stages)`: sum the millisecond values of `(name, ms)` pairs.
5. `distance_cm(speed_m_s, latency_ms)`: distance moved during the latency.
6. `find_faults(design)`: a sorted list of fault names; a missing key counts as not satisfied.
7. As comments, write the assumptions of your model, a baseline case, a boundary case (for example a 14-byte read at exactly the speed where it just fits) and one measurement that would show the model wrong.

    "mpu-6050": "sensor",
    "vl53l0x": "sensor",
    "hc-sr04": "sensor",

### Library track

Optional, free, no hardware: open [wokwi.com](https://wokwi.com), create an **Arduino Uno** project and add an **HC-SR04** ultrasonic sensor. Wire VCC to 5V, GND to GND, TRIG to pin 9 and ECHO to pin 10. Paste the sketch below, start the simulation, open the serial monitor, and drag the distance slider on the sensor.

```cpp
const int TRIG = 9;
const int ECHO = 10;

void setup() {
  Serial.begin(115200);
  pinMode(TRIG, OUTPUT);
  pinMode(ECHO, INPUT);
}

void loop() {
  unsigned long t0 = micros();
  digitalWrite(TRIG, LOW);
  delayMicroseconds(2);
  digitalWrite(TRIG, HIGH);
  delayMicroseconds(10);
  digitalWrite(TRIG, LOW);
  unsigned long echo_us = pulseIn(ECHO, HIGH, 30000);
  float cm = echo_us * 0.0343 / 2.0;
  unsigned long dt_us = micros() - t0;
  Serial.print("echo_us=");
  Serial.print(echo_us);
  Serial.print(" cm=");
  Serial.print(cm);
  Serial.print(" measure_ms=");
  Serial.println(dt_us / 1000.0);
  delay(100);
}
```

What to observe: this is the whole sensing path in miniature. A physical quantity (distance) becomes a pulse width (the echo), the MCU converts it to a number, and the number leaves on the serial link. Set the slider to 100 cm. **Pass criterion:** `echo_us` is about 5830 (round trip $2\cdot1\,\text{m}/343\ \text{m/s}=5.83$ ms), `cm` is about 100, and `measure_ms` is close to the echo time, because the MCU is *blocked* inside `pulseIn` waiting. Note that the loop also sleeps 100 ms, so the sensor is read about 9 times per second. Think about what this means for latency: the reading can be up to one full loop old when you use it.

**Real hardware (optional).** An Arduino Uno-class board, an HC-SR04 and four jumper wires reproduce this exactly. Power from USB only. Keep any real motors and batteries out of this exercise; power rules are HW03.

## Verification

Check by hand before you trust any tool: the I2C time of one burst, the UART time of one message, the sum of a latency chain. Check classifications by asking, for each part, "what does it do to energy or information?" (sensors convert physical quantities to signals; drivers amplify power; actuators convert power to motion). When you draw a diagram, verify that every box has a power connection *and* a signal connection with a named interface, and that every pair of parts that share a signal share a ground. With real hardware, verify by bisection: measure the middle of the chain first.

## Failure modes

- Treating the diagram as only signals and forgetting the power paths: motors on the same regulator as the MCU, and the MCU resets when the motors start.
- No common ground between parts that exchange signals: erratic behaviour, sometimes only when something else is touched.
- A motor wired directly to an MCU pin: the pin cannot supply the current and can be damaged (the ATmega328P absolute maximum is 40 mA per pin and its test conditions are 20 mA).
- Putting a time-critical loop on a non-real-time computer and discovering jitter later.
- A bus that is already 80 % full on paper: any extra message breaks timing.
- Counting only the bus transfer in the latency and forgetting waiting for the next sample, the loop period and the USB adapter's buffering.
- Mixing 3.3 V and 5 V logic without checking levels.
- A connector or breadboard contact that only fails when the robot moves: intermittent faults are usually mechanical.

## Alternatives and trade-offs

You can run everything on one SBC if timing is relaxed (a slow line follower) and use hats or a PWM driver chip for motors; this is simpler but you lose hard real-time and robust shutdown. You can run everything on one MCU if the task is small (a balancing toy). You can use a Raspberry Pi Pico or an ESP32 instead of an Arduino Uno: more speed and memory for little money. Smart servos and integrated motor drivers reduce wiring and sizing work at the cost of one shared bus and vendor protocols. Wireless links add flexibility but add latency jitter, so keep safety-critical loops on the robot. A rule that holds across all of these: decide the *timing and safety* requirements first, then pick the hardware.
