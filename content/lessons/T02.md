## Why this matters

A numerical result is only as trustworthy as your ability to say exactly what produced it: which code, which configuration, which random seed, which data. Git is the tool that records this. It stores every version of your files as an immutable snapshot, lets you branch to try ideas safely, and shows you precisely what changed between two states with a **diff**. For a self-taught learner, Git is also the habit that makes everything else recoverable: a failed refactor, an overwritten notebook, a "which learning rate did I use for the good run?" question. This lesson explains the three objects behind Git (commits, branches, diffs), checks the model against real Git hashes, and ends with the workflow that commits **one numerical experiment with its exact configuration**.

## Intuition

Think of Git as a content-addressed database of snapshots plus a set of movable labels.

- A **commit** is a snapshot of the whole project plus a message, an author, a time and a pointer to its parent commit(s). Its name is a hash of that content, so identical content has the same name and any change gives a new name.
- A **branch** is nothing more than a movable label that points to a commit. Creating a branch costs a few bytes; committing on it moves the label forward.
- A **diff** is computed on demand by comparing two snapshots; Git stores snapshots, not patches.

Your files live in three places: the **working tree** (what you edit), the **index** or staging area (what the next commit will contain) and the **repository** (committed history). `git add` copies working-tree changes into the index; `git commit` turns the index into a new commit.

## Theory and derivation

### Objects and hashes

Git stores four kinds of objects, each named by the SHA-1 of a header plus its content:

$$\text{id}=\mathrm{SHA1}\big(\text{"<kind> <length>"}\ \Vert\ \mathtt{0x00}\ \Vert\ \text{content}\big).$$

- **blob**: the bytes of one file (no file name).
- **tree**: a directory listing of `(mode, name, id)` entries pointing to blobs and subtrees.
- **commit**: `tree <id>`, zero or more `parent <id>` lines, `author`, `committer`, a blank line and the message.
- **tag**: a named, optionally annotated pointer to another object.

Because a commit contains its parents' ids, changing anything (a file, the message, a parent) changes the commit id and, transitively, the id of every descendant. History is therefore **tamper-evident**, and "rewriting history" (rebase, amend) creates new commits rather than editing old ones.

### The commit graph

Commits form a directed acyclic graph (DAG): each commit points to its parents. A branch label names a tip; the branch's history is every commit reachable from the tip. Useful graph facts:

- $a$ is an **ancestor** of $b$ if $a$ is reachable from $b$.
- The **merge base** of two tips is their best common ancestor (the one with the largest generation number).
- `git rev-list --left-right --count A...B` gives how many commits each side has that the other lacks (**ahead/behind**).
- A merge of branch $B$ into $A$ is a **fast-forward** exactly when $A$'s tip is an ancestor of $B$'s tip; then Git just moves the label. Otherwise Git creates a merge commit with two parents (or you rebase).

### Diffs

A diff lists the lines added and removed between two snapshots, usually in the unified format:

```text
--- a/config.json
+++ b/config.json
@@ -1 +1 @@
-{"lam": 4, "lr": 0.1, "steps": 3, "theta0": 1.0}
+{"lam": 4, "lr": 0.6, "steps": 3, "theta0": 1.0}
```

`@@ -1 +1 @@` means: starting at line 1 of the old file (one line) and line 1 of the new file (one line). A replaced line counts as one removal plus one addition. Line endings and whitespace count as changes, which is why a stray `\r\n` shows up as a diff of every line.

### What belongs in a commit

Commit **code, configuration, small inputs, environment declarations (T05) and small result summaries**; do not commit secrets, large data, caches or build products (use `.gitignore`, a data store or Git LFS). A good commit does one logical thing and has a message that says *why*. To make an experiment reproducible, the result file must record the **commit id** and whether the working tree was **dirty** when it ran; refuse to record a result from uncommitted changes.

### Recovery and safety

Committed work is very hard to lose (`git reflog` lists where HEAD has been). Uncommitted edits are not: `git restore <file>`, `git checkout -- <file>` and `git reset --hard` discard them without a trace. Rule of thumb: commit (or `git stash`) before any command you do not fully understand.

## Worked example

**Hashing by hand.** The file `hello\n` has 6 bytes, so its blob id is $\mathrm{SHA1}(\text{"blob 6"}\Vert0\Vert\text{"hello\n"})=$ `ce013625030ba8dba906f756967f9e9ca394464a` (identical to `echo hello | git hash-object --stdin`). A tree containing only that file as `a.txt` (mode 100644) is `2e811714...`, and a commit of that tree with no parent, author `A U <a@x> 1700000000 +0000` and message `first` is `5bb3fa44...`. Changing the message to `first!` changes the commit id entirely; a child commit includes the parent id, so its id changes too.

**Graph.** Commits: `C0 ← C1 ← C2` on `main`, and `C1 ← C3 ← C4` on `feature`.

- Ancestors of `C4`: $\{C4,C3,C1,C0\}$. The merge base of `C2` and `C4` is `C1`.
- Ahead/behind of `main` relative to `feature`: `main` has $\{C2\}$ not in `feature` (1), `feature` has $\{C3,C4\}$ not in `main` (2): $(1,2)$.
- Fast-forward? `C2` is not an ancestor of `C4`, so no: a merge commit `M` with parents `C2` and `C4` is needed. After merging, `C2`, `C4` and everything below are ancestors of `M`.

**Experiment workflow (numbers).** Commit `config.json` with `lam=4, lr=0.1, steps=3, theta0=1`; the script returns $\theta_3=(1-0.1\cdot4)^3=0.6^3=0.216$ and loss $\tfrac12\cdot4\cdot0.216^2=0.093312$, recorded with the commit id and `dirty: false`. Changing `lr` to $0.6$ gives $\theta_3=(1-2.4)^3=-2.744$, loss $15.059072$, and the diff shows exactly one changed line.

## Reference implementation

A Python model of Git's object database and graph operations, checked against real Git ids: blob/tree/commit hashing, ancestry, merge base, ahead/behind, fast-forward test and a line-diff counter.

```python
import hashlib, difflib

def object_hash(kind, body):
    """Git object id: sha1 of b'<kind> <len>\\0' + body."""
    return hashlib.sha1(f"{kind} {len(body)}".encode() + b"\0" + body).hexdigest()

def blob_hash(data):
    return object_hash("blob", data)

def tree_hash(entries):
    """entries: list of (mode, name, hex_sha) for plain files; git sorts by name."""
    body = b"".join(m.encode() + b" " + n.encode() + b"\0" + bytes.fromhex(h) for m, n, h in sorted(entries, key=lambda e: e[1]))
    return object_hash("tree", body)

def commit_hash(tree, parents, author, committer, message):
    """author/committer are full lines like 'A U <a@x> 1700000000 +0000'."""
    lines = [f"tree {tree}"] + [f"parent {p}" for p in parents] + [f"author {author}", f"committer {committer}", "", message]
    return object_hash("commit", ("\n".join(lines) + "\n").encode())

def ancestors(parents, c):
    """Set of c and all its ancestors. parents: dict commit -> list of parent commits."""
    seen, stack = set(), [c]
    while stack:
        x = stack.pop()
        if x not in seen:
            seen.add(x); stack.extend(parents[x])
    return seen

def is_ancestor(parents, a, b):
    """True if a is reachable from b (a == b counts)."""
    return a in ancestors(parents, b)

def generation(parents, c):
    return 1 + max((generation(parents, p) for p in parents[c]), default=0)

def merge_base(parents, a, b):
    """Common ancestor of a and b with the largest generation number (ties: smallest name)."""
    common = ancestors(parents, a) & ancestors(parents, b)
    return min(common, key=lambda c: (-generation(parents, c), c)) if common else None

def ahead_behind(parents, a, b):
    """(commits reachable from a but not b, commits reachable from b but not a)."""
    A, Bs = ancestors(parents, a), ancestors(parents, b)
    return len(A - Bs), len(Bs - A)

def can_fast_forward(parents, branch_tip, target):
    """Branch can be fast-forwarded to target iff its tip is an ancestor of target."""
    return is_ancestor(parents, branch_tip, target)

def diff_stat(old, new):
    """(lines added, lines removed) between two lists of lines."""
    added = removed = 0
    for tag, i1, i2, j1, j2 in difflib.SequenceMatcher(a=old, b=new, autojunk=False).get_opcodes():
        if tag in ("replace", "delete"): removed += i2 - i1
        if tag in ("replace", "insert"): added += j2 - j1
    return added, removed

# tiny self-test
assert blob_hash(b"hello\n") == "ce013625030ba8dba906f756967f9e9ca394464a"
assert blob_hash(b"") == "e69de29bb2d1d6434b8b29ae775ad8c2e48c5391"
```

### Tasks

3. Change `lr` to `0.6` *without* committing and run the script: it must refuse (exit status 1). Show the change with `git diff`, then commit and re-run to get `run2.json` (`theta` $-2.744$, `loss` $15.059072$).

5. Verify the object model: compare `git hash-object config.json` with `blob_hash` of the same bytes from Python, and `git rev-parse HEAD^{tree}` with a `tree_hash` of the files you track (use `git ls-tree HEAD` for modes and names; subdirectories complicate this, so keep the project flat).
6. Save the Python starter as `t02_model.py`, append the tests and make them pass.

```python
"""experiment.py - run one tiny numerical experiment and record exactly what produced it."""
import json, subprocess, sys

def git(*args):
    return subprocess.check_output(["git", *args], text=True).strip()

cfg = json.load(open("config.json"))
theta = cfg["theta0"]
for _ in range(cfg["steps"]):
    theta -= cfg["lr"] * cfg["lam"] * theta          # gradient descent on 0.5*lam*theta^2
result = {
    "config": cfg,
    "theta": round(theta, 6),
    "loss": round(0.5 * cfg["lam"] * theta ** 2, 6),
    "commit": git("rev-parse", "HEAD"),
    "dirty": bool(git("status", "--porcelain", "--untracked-files=no")),
}
if result["dirty"]:
    sys.exit("refusing to record a result from uncommitted changes")
print(json.dumps(result, sort_keys=True))
```

## Verification

- **Hash agreement:** `blob_hash` equals `git hash-object` for the same bytes; `tree_hash` and `commit_hash` match `git write-tree` / `git hash-object -t commit`.
- **Reproducibility:** checkout the recorded commit in a fresh clone (`git switch --detach <id>`), rerun, and compare the numbers.
- **Invariants:** `git status --porcelain` is empty at the time results are recorded; every result file names the commit that produced it; the ahead/behind counts equal `git rev-list --left-right --count`.
- **Falsifier:** if re-running the recorded commit gives a different number (unseeded randomness, a changed dependency, a data file outside Git), your commit does not capture the experiment.

## Failure modes

- **Committing secrets or data** (`git add .`): the key is in history forever; rotate it, then remove the file from history with a dedicated tool; `.gitignore` only affects untracked files.
- **Results without provenance:** a CSV in the repo with no commit id or config recorded.
- **Dirty-tree runs:** the numbers came from code that exists nowhere in history.
- **Giant commits** ("many changes") that cannot be reviewed or bisected.
- **Force-pushing or rebasing shared history**, creating duplicate commits with different ids for collaborators.
- **Detached HEAD work** that is lost when you switch branches (create a branch before committing).
- **Line-ending noise** (`\r\n` versus `\n`) making diffs show every line as changed.
- **Misreading `git diff`**: without arguments it compares working tree to index; `git diff --staged` compares index to HEAD.

## Alternatives and trade-offs

| Need | Tool | Trade-off |
| --- | --- | --- |
| Code, configs, small files | Git | the standard; poor with big binaries |
| Large datasets/models | Git LFS, DVC, object storage with a hash recorded in Git | extra service/setup, but keeps the repo small |
| Experiment tracking dashboards | MLflow, Weights and Biases | convenient comparison; still record commit and config |
| Notebook versions | Git + `nbstripoutput` or jupytext | diffs readable; extra tooling |
| Sharing | hosted remote (GitHub, GitLab) | backup and review; policies and secrets care |

Use plain Git for the smallest reproducible record, and add tools only when the volume of experiments or data demands it.

## Exercise answers

1. Git stores a full snapshot (tree of blobs) per commit and computes differences when asked, rather than storing a chain of patches. Files are *modified* (changed in the working tree), *staged* (marked in the index for the next commit) or *committed* (stored in the repository). `git add` copies the current content into the index.
2. `AM a.txt`: staged as new (A) and modified in the working tree after staging (M). `git commit -m x` records the content staged at `git add` time (a file containing `1`), not the later `2`.
3. Merge base `C1`. Main is 1 ahead, feature is 2 ahead: `(1,2)`. Not a fast-forward (`C2` is not an ancestor of `C4`). The merge commit has two parents: `C2` and `C4`.
4. Same tree, parent, author line, committer line and message give the same commit id (it is a pure function of the content). One second of difference in the committer timestamp gives a different id. Amend/rebase create new commits with new ids; anyone who already has the old ones now has a divergent history, which is why shared commits should not be rewritten.
5. 2 lines added, 1 removed. `@@ -3,3 +3,4 @@` says the hunk starts at line 3 and covers 3 lines in the old file and 4 lines in the new file (net +1 line). The replaced `seed` line counts as one removal and one addition; `data=v2` is a pure addition.
6. Problems: the secret `.env` is committed (and will be pushed), 4 GB of data bloats the repository forever, and `__pycache__` is noise; the commit message is meaningless. Fix: add the entries to `.gitignore`, `git rm --cached -r .env data __pycache__`, commit selectively with `git add -p`. The key must be treated as leaked: revoke and replace it, then purge it from history with a history-rewriting tool if the repository was ever shared.
7. `git restore train.py`, `git checkout -- train.py` and `git reset --hard` discard the edits with no recovery. `git stash` and `git commit -a` save them. `git switch` refuses to switch (or carries compatible edits) rather than discarding them.
8. A good answer: commit code, config, a README/protocol, environment lockfile and small summary tables; ignore raw/derived large data (store with a manifest and hash), caches and secrets; a `results/` file per run containing the commit id, config and data version; a script `make figures` or `python make_fig2.py` that regenerates figure 2 from tagged inputs; tags for paper versions; collaborators clone, check out the tag, create the environment and run one command.
9. Packfiles store similar objects as deltas against each other, so two versions of a big file take about the size of one plus a small delta, even though logically each commit has a full snapshot. Identical content hashes to the same blob id, so two identical files share one object. The blob id does not contain the file name, mode or location: those live in the tree.
