## Why this matters

A numerical result is only as trustworthy as your ability to say exactly what produced it: which code, which configuration, which random seed, which data. Git is the tool that records this. It stores every version of your files as an immutable snapshot, lets you branch to try ideas safely, and shows you precisely what changed between two states with a **diff**. For a self-taught learner, Git is also the habit that makes everything else recoverable: a failed refactor, an overwritten notebook, a "which learning rate did I use for the good run?" question. This lesson explains the three objects behind Git (commits, branches, diffs), checks the model against real Git hashes, and ends with the workflow that commits **one numerical experiment with its exact configuration**.

## Intuition

Think of Git as a content-addressed database of snapshots plus a set of movable labels.

- A **commit** is a snapshot of the whole project plus a message, an author, a time and a pointer to its parent commit(s). Its name is a hash of that content, so identical content has the same name and any change gives a new name.
- A **branch** is nothing more than a movable label that points to a commit. Creating a branch costs a few bytes; committing on it moves the label forward.
- A **diff** is computed on demand by comparing two snapshots; Git stores snapshots, not patches.

Your files live in three places: the **working tree** (what you edit), the **index** or staging area (what the next commit will contain) and the **repository** (committed history). `git add` copies working-tree changes into the index; `git commit` turns the index into a new commit.

![Left: a commit graph with commits C0 to C4 and a merge commit M, with branch labels main and feature pointing at tips. Right: three areas working tree, index, repository with the commands add, commit, restore moving content between them.](/lesson-figures/T02.svg)

*Left: commits form a graph; branches are labels. Right: files move between working tree, index and repository.*

*A mental model: a library of sealed boxes.* Picture every version of every file sealed in a transparent box, labelled with a fingerprint of its contents. Two boxes with the same contents have the same label, so Git never stores the same content twice. A folder is a box whose contents are a list of labels; a commit is a box holding the label of the top folder, the label of the previous commit, and a note. Because each label is derived from what is inside, you cannot open a box and change it without changing its label, and then every box that mentions that label needs a new label too. This is the whole reason history is tamper-evident, and the whole reason "rewriting history" means building a new chain of boxes next to the old one.

*Branches are sticky notes.* A branch is a sticky note stuck on one commit's box. When you commit, you place a new box that points back to the old one and move the sticky note. Nothing else changes. Two sticky notes on the same box are not "two copies"; they are two names for one thing. Merging asks "is the other note's box already behind mine?" (then just move my note: a fast-forward) or "do our chains split somewhere?" (then build a new box pointing at both).

*The three places, again.* The working tree is the desk where you edit; the index is the tray where you stack what you intend to photograph; the repository is the photo album. `git add` puts a copy of a file on the tray, `git commit` photographs the tray, and `git reset` can move the album pointer, refill the tray from the album, or rewrite the desk from the album, depending on a single flag.

*Predict before you compute.* (a) A directory holds a subdirectory `a` and a file `a.txt`. Which comes first inside the tree object? (b) You run `git reset --soft HEAD~1`, then `--mixed HEAD~1`, then `--hard HEAD~1` in three separate copies of one state. In which copies do your staged and unstaged edits survive? (c) A regression is somewhere in 1,000 commits and each test takes a minute. How many minutes at most, using binary search? Write down guesses first; the Theory and Exercises let you check each.

*Wrong intuitions to drop.* "A branch is a copy of the code": it is a pointer. "Git stores diffs": it stores snapshots and compresses them later. "Reset is dangerous": only `--hard` can destroy uncommitted work (Pro Git §7.7). "Deleting a branch deletes commits": the commits stay until nothing refers to them and they are garbage-collected.

## Theory and derivation

### Objects and hashes

Git stores four kinds of objects, each named by the SHA-1 of a header plus its content:

$$\text{id}=\mathrm{SHA1}\big(\text{"<kind> <length>"}\ \Vert\ \mathtt{0x00}\ \Vert\ \text{content}\big).$$

- **blob**: the bytes of one file (no file name).
- **tree**: a directory listing of `(mode, name, id)` entries pointing to blobs and subtrees.
- **commit**: `tree <id>`, zero or more `parent <id>` lines, `author`, `committer`, a blank line and the message.
- **tag**: a named, optionally annotated pointer to another object.

Because a commit contains its parents' ids, changing anything (a file, the message, a parent) changes the commit id and, transitively, the id of every descendant. History is therefore **tamper-evident**, and "rewriting history" (rebase, amend) creates new commits rather than editing old ones.

### The commit graph

Commits form a directed acyclic graph (DAG): each commit points to its parents. A branch label names a tip; the branch's history is every commit reachable from the tip. Useful graph facts:

- $a$ is an **ancestor** of $b$ if $a$ is reachable from $b$.
- The **merge base** of two tips is their best common ancestor (the one with the largest generation number).
- `git rev-list --left-right --count A...B` gives how many commits each side has that the other lacks (**ahead/behind**).
- A merge of branch $B$ into $A$ is a **fast-forward** exactly when $A$'s tip is an ancestor of $B$'s tip; then Git just moves the label. Otherwise Git creates a merge commit with two parents (or you rebase).

### Diffs

A diff lists the lines added and removed between two snapshots, usually in the unified format:

```text
--- a/config.json
+++ b/config.json
@@ -1 +1 @@
-{"lam": 4, "lr": 0.1, "steps": 3, "theta0": 1.0}
+{"lam": 4, "lr": 0.6, "steps": 3, "theta0": 1.0}
```

`@@ -1 +1 @@` means: starting at line 1 of the old file (one line) and line 1 of the new file (one line). A replaced line counts as one removal plus one addition. Line endings and whitespace count as changes, which is why a stray `\r\n` shows up as a diff of every line.

### What belongs in a commit

Commit **code, configuration, small inputs, environment declarations (T05) and small result summaries**; do not commit secrets, large data, caches or build products (use `.gitignore`, a data store or Git LFS). A good commit does one logical thing and has a message that says *why*. To make an experiment reproducible, the result file must record the **commit id** and whether the working tree was **dirty** when it ran; refuse to record a result from uncommitted changes.

### Recovery and safety

Committed work is very hard to lose (`git reflog` lists where HEAD has been). Uncommitted edits are not: `git restore <file>`, `git checkout -- <file>` and `git reset --hard` discard them without a trace. Rule of thumb: commit (or `git stash`) before any command you do not fully understand.

### Tree objects in detail, and why identical content is stored once

A tree object is a sequence of entries, each written as the ASCII mode, a space, the file name, a zero byte and the **raw 20-byte** id of the object it points to (not the 40-character hex string). The mode is `100644` for a regular file, `100755` for an executable, `120000` for a symbolic link, and `40000` for a subtree (`git ls-tree` prints it padded as `040000`). The id of the tree is the SHA-1 of the header `tree <length>` and a zero byte followed by these bytes (Pro Git, §10.2). Entries are sorted by name **as if directory names ended with `/`**. A directory `a` and a file `a.txt` therefore appear as `a.txt` first and `a` second, because the character `.` (0x2e) sorts before `/` (0x2f). I checked this by computing the ids in Python and comparing them with `git rev-parse` in a scratch repository (Exercise 13): the two agree exactly.

Two consequences follow from the construction, which is a **Merkle tree**: the id of a node depends only on the ids of its children. (1) Two directories with identical contents have the same id, so they are stored once; copying a directory costs nothing. (2) Changing one byte in one file changes that blob's id, hence the id of every tree on the path to the root, hence the commit id. The number of new objects for a one-file change in a project of depth $k$ is therefore $1+k+1$: one blob, $k$ trees including the root, one commit. All other subtrees are reused unchanged.

### Reachability, ranges and the merge base

Let $P(c)$ be the set of commits reachable from $c$ by following parent links, including $c$. The statement "$a$ is an ancestor of $b$" is $a\in P(b)$. The two range notations of Pro Git (§7.1) are set operations on these sets:

$$A..B = P(B)\setminus P(A),\qquad A...B = P(A)\,\triangle\,P(B).$$

The first lists commits on $B$ not on $A$; the second is the symmetric difference, the commits reachable from either side but not both, and `--left-right` marks which side each came from. The counts of `git rev-list --left-right --count A...B` are $|P(A)\setminus P(B)|$ and $|P(B)\setminus P(A)|$, the ahead/behind pair. A **merge base** of $A$ and $B$ is a common ancestor with no descendant that is also a common ancestor, that is, a maximal element of $P(A)\cap P(B)$. In a history with only simple branches there is exactly one; with *criss-cross merges* (each branch has merged the other's earlier part) there can be several, and `git merge-base --all` prints all of them (Exercise 11). Merging $B$ into $A$ is a fast-forward exactly when $P(A)\subseteq P(B)$, that is, when $A$ itself is the merge base.

### The three trees and reset

Pro Git (§7.7) describes Git as managing three "trees": **HEAD** (the last commit), the **index** (the proposed next commit) and the **working directory**. `git reset` has three steps: move the branch that HEAD points to (`--soft` stops here); make the index look like the new HEAD (`--mixed`, the default, stops here); make the working directory look like the index (`--hard`). Verified on a scratch repository with commits c1, c2, c3, a staged change `v4` and an unstaged edit `v5`: after `reset --soft HEAD~1`, HEAD is c2, the index is still `v4`, the working file `v5`; after `--mixed` the index is `v2` (the content of c2), the file still `v5`; after `--hard` both are `v2`. The staged `v4` and the edit `v5` are gone for good. `git reflog` brings back the committed c3 but never the uncommitted states, because they were never objects in a commit. The practical rule: before `--hard`, make sure everything you care about is committed or stashed.

### Why snapshots stay small: packfiles and deltas

Every commit logically holds a full snapshot, yet repositories stay small. Loose objects are zlib-compressed individually; when Git packs them (`git gc` or on push), it looks for objects with similar names and sizes and stores one in full and the others as deltas against it (Pro Git, §10.4). Pro Git's example shows a 400-line file with one added line stored as a completely new loose object, which becomes a small delta after packing. Interestingly, Git stores the *newest* version intact and older versions as deltas, since recent versions are the ones most often needed. Delta storage is purely a storage-level optimisation: it never changes object ids or the logical model, so the reasoning above (ids, Merkle structure) is unaffected.

### Finding the commit that broke something: binary search

If a property is true on commit $g$ ("good") and false on a later commit $b$ ("bad"), and the history between them is linear and the property flips only once, then the first bad commit is among the $n-1$ commits after $g$ up to and including $b$ (given $n$ commits from $g$ to $b$ inclusive, $b$ is known bad, so $n-1$ candidates). Testing the middle candidate halves the candidate set, so the number of tests needed in the worst case is $\lceil\log_2(n-1)\rceil$. `git bisect` automates this (Pro Git, §7.10), and `git bisect run script` uses the script's exit code: 0 means good, 1 to 127 except 125 means bad, and 125 means "cannot test this commit, skip it" (git-bisect documentation). The conditions that make the argument valid are the ones that fail in practice: the predicate must be deterministic (a flaky test breaks the search silently), it must flip once (if a bug appears, vanishes and reappears, bisect finds *a* boundary, not the only one), and each tested commit must be buildable (use exit code 125 for those that are not). On a history with merges the "middle" is chosen by the commit graph rather than by time, but the halving argument is unchanged.

### What a commit id does and does not certify

The commit body holds the tree id, the parent ids, an author line, a committer line (each with name, e-mail, Unix time and time zone) and the message. The id certifies that *this exact* content, including the parents, is what was committed; it says nothing about who typed it, because author lines are free text unless the commit is signed (Pro Git, §7.4). Two practical consequences: rebasing or amending keeps the author line but creates a new committer time, hence a new id; and two people who commit identical files with identical metadata onto the same parent really do obtain the same id, which is a useful property for reproducibility checks but never a proof of authorship.

### How this connects to the rest of CoreLab

Experiment tracking in later modules relies on exactly these facts: a result file that records the commit id points to an immutable snapshot, and the "dirty" flag says whether the working tree differed from it. Environment files (T05) are committed so the snapshot includes the software versions, and a CI run (see the project topics) is a fresh checkout of a commit, which is why it exposes files you forgot to add.

## Worked example

### Basic cases

**Hashing by hand.** The file `hello\n` has 6 bytes, so its blob id is $\mathrm{SHA1}(\text{"blob 6"}\Vert0\Vert\text{"hello\n"})=$ `ce013625030ba8dba906f756967f9e9ca394464a` (identical to `echo hello | git hash-object --stdin`). A tree containing only that file as `a.txt` (mode 100644) is `2e811714...`, and a commit of that tree with no parent, author `A U <a@x> 1700000000 +0000` and message `first` is `5bb3fa44...`. Changing the message to `first!` changes the commit id entirely; a child commit includes the parent id, so its id changes too.

**Graph.** Commits: `C0 ← C1 ← C2` on `main`, and `C1 ← C3 ← C4` on `feature`.

- Ancestors of `C4`: $\{C4,C3,C1,C0\}$. The merge base of `C2` and `C4` is `C1`.
- Ahead/behind of `main` relative to `feature`: `main` has $\{C2\}$ not in `feature` (1), `feature` has $\{C3,C4\}$ not in `main` (2): $(1,2)$.
- Fast-forward? `C2` is not an ancestor of `C4`, so no: a merge commit `M` with parents `C2` and `C4` is needed. After merging, `C2`, `C4` and everything below are ancestors of `M`.

**Experiment workflow (numbers).** Commit `config.json` with `lam=4, lr=0.1, steps=3, theta0=1`; the script returns $\theta_3=(1-0.1\cdot4)^3=0.6^3=0.216$ and loss $\tfrac12\cdot4\cdot0.216^2=0.093312$, recorded with the commit id and `dirty: false`. Changing `lr` to $0.6$ gives $\theta_3=(1-2.4)^3=-2.744$, loss $15.059072$, and the diff shows exactly one changed line.

### A harder case: a criss-cross merge and its two merge bases

Build (verified in a scratch repository): `A` on `main`; branch `x` from `A` with commit `B`; back on `main` commit `C`; branch `y` from `C` with commit `D`. On `x` merge `y` (commit `M1`, parents `B` and `D`). Then on `y` merge `x~1`, that is `B` (commit `M2`, parents `D` and `B`). The two tips `M1` and `M2` have each merged the other's earlier tip, so $P(M1)=\{M1,B,D,C,A\}$ and $P(M2)=\{M2,D,B,C,A\}$. The common ancestors are $\{B,D,C,A\}$. Maximal elements: `C` is an ancestor of `D`, `A` of everything, so the maximal ones are `B` and `D`, which are *not* ancestors of each other. `git merge-base --all x y` printed exactly `B` and `D`. The ahead/behind count `git rev-list --left-right --count x...y` is $(1,1)$ (only `M1` on the left, only `M2` on the right), and `x..y` is `M2` while `y..x` is `M1`. Lesson: "the" merge base is not always unique; Git's default merge strategy copes by first merging the bases into a virtual one, but you should not assume a single base when reasoning about history.

## Reference implementation

A Python model of Git's object database and graph operations, checked against real Git ids: blob/tree/commit hashing, ancestry, merge base, ahead/behind, fast-forward test and a line-diff counter.

```python
import hashlib, difflib

def object_hash(kind, body):
    """Git object id: sha1 of b'<kind> <len>\\0' + body."""
    return hashlib.sha1(f"{kind} {len(body)}".encode() + b"\0" + body).hexdigest()

def blob_hash(data):
    return object_hash("blob", data)

def tree_hash(entries):
    """entries: list of (mode, name, hex_sha) for plain files; git sorts by name."""
    body = b"".join(m.encode() + b" " + n.encode() + b"\0" + bytes.fromhex(h) for m, n, h in sorted(entries, key=lambda e: e[1]))
    return object_hash("tree", body)

def commit_hash(tree, parents, author, committer, message):
    """author/committer are full lines like 'A U <a@x> 1700000000 +0000'."""
    lines = [f"tree {tree}"] + [f"parent {p}" for p in parents] + [f"author {author}", f"committer {committer}", "", message]
    return object_hash("commit", ("\n".join(lines) + "\n").encode())

def ancestors(parents, c):
    """Set of c and all its ancestors. parents: dict commit -> list of parent commits."""
    seen, stack = set(), [c]
    while stack:
        x = stack.pop()
        if x not in seen:
            seen.add(x); stack.extend(parents[x])
    return seen

def is_ancestor(parents, a, b):
    """True if a is reachable from b (a == b counts)."""
    return a in ancestors(parents, b)

def generation(parents, c):
    return 1 + max((generation(parents, p) for p in parents[c]), default=0)

def merge_base(parents, a, b):
    """Common ancestor of a and b with the largest generation number (ties: smallest name)."""
    common = ancestors(parents, a) & ancestors(parents, b)
    return min(common, key=lambda c: (-generation(parents, c), c)) if common else None

def ahead_behind(parents, a, b):
    """(commits reachable from a but not b, commits reachable from b but not a)."""
    A, Bs = ancestors(parents, a), ancestors(parents, b)
    return len(A - Bs), len(Bs - A)

def can_fast_forward(parents, branch_tip, target):
    """Branch can be fast-forwarded to target iff its tip is an ancestor of target."""
    return is_ancestor(parents, branch_tip, target)

def diff_stat(old, new):
    """(lines added, lines removed) between two lists of lines."""
    added = removed = 0
    for tag, i1, i2, j1, j2 in difflib.SequenceMatcher(a=old, b=new, autojunk=False).get_opcodes():
        if tag in ("replace", "delete"): removed += i2 - i1
        if tag in ("replace", "insert"): added += j2 - j1
    return added, removed

# tiny self-test
assert blob_hash(b"hello\n") == "ce013625030ba8dba906f756967f9e9ca394464a"
assert blob_hash(b"") == "e69de29bb2d1d6434b8b29ae775ad8c2e48c5391"
```

## Independent practice

### Goal

Commit one numerical experiment together with its exact configuration, tie the result to the commit id, and use Git to inspect and compare runs; verify your mental model with the Python object model.

### Setup

```python
"""experiment.py - run one tiny numerical experiment and record exactly what produced it."""
import json, subprocess, sys

def git(*args):
    return subprocess.check_output(["git", *args], text=True).strip()

cfg = json.load(open("config.json"))
theta = cfg["theta0"]
for _ in range(cfg["steps"]):
    theta -= cfg["lr"] * cfg["lam"] * theta          # gradient descent on 0.5*lam*theta^2
result = {
    "config": cfg,
    "theta": round(theta, 6),
    "loss": round(0.5 * cfg["lam"] * theta ** 2, 6),
    "commit": git("rev-parse", "HEAD"),
    "dirty": bool(git("status", "--porcelain", "--untracked-files=no")),
}
if result["dirty"]:
    sys.exit("refusing to record a result from uncommitted changes")
print(json.dumps(result, sort_keys=True))
```

```python
import hashlib, difflib

def object_hash(kind, body):
    """Git object id: sha1 hex of  f"{kind} {len(body)}".encode() + b"\\0" + body."""
    raise NotImplementedError

def blob_hash(data):
    """Id of a file's content (bytes)."""
    raise NotImplementedError

def tree_hash(entries):
    """entries: list of (mode, name, hex_sha) for plain files, e.g. ("100644", "a.txt", sha).
    Body = for each entry sorted by name: mode + b" " + name + b"\\0" + the 20 raw bytes of sha."""
    raise NotImplementedError

def commit_hash(tree, parents, author, committer, message):
    """Lines: tree T, one 'parent P' per parent, author, committer, a blank line, message; joined with
    newlines plus a trailing newline. author/committer are full lines like 'A U <a@x> 1700000000 +0000'."""
    raise NotImplementedError

def ancestors(parents, c):
    """Set of c and all its ancestors. parents: dict commit -> list of parent commits."""
    raise NotImplementedError

def is_ancestor(parents, a, b):
    """True if a is reachable from b (a == b counts)."""
    raise NotImplementedError

def generation(parents, c):
    """1 for a root commit, else 1 + max generation of the parents."""
    raise NotImplementedError

def merge_base(parents, a, b):
    """Common ancestor with the largest generation number (ties: smallest name); None if none."""
    raise NotImplementedError

def ahead_behind(parents, a, b):
    """(number of commits reachable from a but not b, number reachable from b but not a)."""
    raise NotImplementedError

def can_fast_forward(parents, branch_tip, target):
    """True iff the branch tip is an ancestor of target."""
    raise NotImplementedError

def diff_stat(old, new):
    """(lines added, lines removed) between two lists of lines (difflib.SequenceMatcher opcodes)."""
    raise NotImplementedError
```

## Verification

- **Hash agreement:** `blob_hash` equals `git hash-object` for the same bytes; `tree_hash` and `commit_hash` match `git write-tree` / `git hash-object -t commit`.
- **Reproducibility:** checkout the recorded commit in a fresh clone (`git switch --detach <id>`), rerun, and compare the numbers.
- **Invariants:** `git status --porcelain` is empty at the time results are recorded; every result file names the commit that produced it; the ahead/behind counts equal `git rev-list --left-right --count`.
- **Falsifier:** if re-running the recorded commit gives a different number (unseeded randomness, a changed dependency, a data file outside Git), your commit does not capture the experiment.

## Failure modes

- **Committing secrets or data** (`git add .`): the key is in history forever; rotate it, then remove the file from history with a dedicated tool; `.gitignore` only affects untracked files.
- **Results without provenance:** a CSV in the repo with no commit id or config recorded.
- **Dirty-tree runs:** the numbers came from code that exists nowhere in history.
- **Giant commits** ("many changes") that cannot be reviewed or bisected.
- **Force-pushing or rebasing shared history**, creating duplicate commits with different ids for collaborators.
- **Detached HEAD work** that is lost when you switch branches (create a branch before committing).
- **Line-ending noise** (`\r\n` versus `\n`) making diffs show every line as changed.
- **Misreading `git diff`**: without arguments it compares working tree to index; `git diff --staged` compares index to HEAD.

## Alternatives and trade-offs

| Need | Tool | Trade-off |
| --- | --- | --- |
| Code, configs, small files | Git | the standard; poor with big binaries |
| Large datasets/models | Git LFS, DVC, object storage with a hash recorded in Git | extra service/setup, but keeps the repo small |
| Experiment tracking dashboards | MLflow, Weights and Biases | convenient comparison; still record commit and config |
| Notebook versions | Git + `nbstripoutput` or jupytext | diffs readable; extra tooling |
| Sharing | hosted remote (GitHub, GitLab) | backup and review; policies and secrets care |

Use plain Git for the smallest reproducible record, and add tools only when the volume of experiments or data demands it.

## Exercise answers

1. Git stores a full snapshot (tree of blobs) per commit and computes differences when asked, rather than storing a chain of patches. Files are *modified* (changed in the working tree), *staged* (marked in the index for the next commit) or *committed* (stored in the repository). `git add` copies the current content into the index.
2. `AM a.txt`: staged as new (A) and modified in the working tree after staging (M). `git commit -m x` records the content staged at `git add` time (a file containing `1`), not the later `2`.
3. Merge base `C1`. Main is 1 ahead, feature is 2 ahead: `(1,2)`. Not a fast-forward (`C2` is not an ancestor of `C4`). The merge commit has two parents: `C2` and `C4`.
4. Same tree, parent, author line, committer line and message give the same commit id (it is a pure function of the content). One second of difference in the committer timestamp gives a different id. Amend/rebase create new commits with new ids; anyone who already has the old ones now has a divergent history, which is why shared commits should not be rewritten.
5. 2 lines added, 1 removed. `@@ -3,3 +3,4 @@` says the hunk starts at line 3 and covers 3 lines in the old file and 4 lines in the new file (net +1 line). The replaced `seed` line counts as one removal and one addition; `data=v2` is a pure addition.
6. Problems: the secret `.env` is committed (and will be pushed), 4 GB of data bloats the repository forever, and `__pycache__` is noise; the commit message is meaningless. Fix: add the entries to `.gitignore`, `git rm --cached -r .env data __pycache__`, commit selectively with `git add -p`. The key must be treated as leaked: revoke and replace it, then purge it from history with a history-rewriting tool if the repository was ever shared.
7. `git restore train.py`, `git checkout -- train.py` and `git reset --hard` discard the edits with no recovery. `git stash` and `git commit -a` save them. `git switch` refuses to switch (or carries compatible edits) rather than discarding them.
8. A good answer: commit code, config, a README/protocol, environment lockfile and small summary tables; ignore raw/derived large data (store with a manifest and hash), caches and secrets; a `results/` file per run containing the commit id, config and data version; a script `make figures` or `python make_fig2.py` that regenerates figure 2 from tagged inputs; tags for paper versions; collaborators clone, check out the tag, create the environment and run one command.
9. Packfiles store similar objects as deltas against each other, so two versions of a big file take about the size of one plus a small delta, even though logically each commit has a full snapshot. Identical content hashes to the same blob id, so two identical files share one object. The blob id does not contain the file name, mode or location: those live in the tree.
10. A good answer shows three commits with different `lr`, result files naming commits, `git diff HEAD~2 HEAD -- config.json`, a small test script (`python3 experiment.py | python3 -c "..."` returning non-zero when loss $>1$) used with `git bisect start`, `git bisect bad`, `git bisect good <id>`, `git bisect run ./check.sh` and the identified first bad commit.

11. (a) $P(M1)=\{M1,B,D,C,A\}$, $P(M2)=\{M2,D,B,C,A\}$. (b) The common ancestors are $\{B,D,C,A\}$. `C` is an ancestor of `D` and `A` is an ancestor of everything else, so both are dominated; `B` and `D` are not ancestors of each other (neither is in the other's history), so each is maximal and neither can be dropped: the merge bases are `B` and `D`, which `git merge-base --all M1 M2` confirmed. (c) `M1..M2` $=P(M2)\setminus P(M1)=\{M2\}$; `M2..M1` $=\{M1\}$; `M1...M2` $=\{M1,M2\}$; the count is `1	1`. (d) Merging $B'$ into $A'$ is a fast-forward iff $P(A')\subseteq P(B')$ (equivalently $A'\in P(B')$). Here $M1\notin P(M2)$ (and $M2\notin P(M1)$), so it is not a fast-forward: Git creates a real merge commit, using a virtual merge base built from `B` and `D`.
12. Start: HEAD file `v3`, index `v4`, working `v5`. After `--soft HEAD~1`: HEAD `v2`, index `v4`, working `v5` (nothing lost). After `--mixed HEAD~1`: HEAD `v2`, index `v2`, working `v5` (the staged `v4` is lost, the working edit survives). After `--hard HEAD~1`: HEAD `v2`, index `v2`, working `v2` (staged `v4` and the unstaged `v5` are both unrecoverable). The reflog records where HEAD was (commit c3), so `git reset --hard HEAD@{1}` moves HEAD to c3 and then makes the index and working directory equal to it: both `v3` (checked). The three steps explain this: `--hard` runs all three, so it sets the index and working file from the commit it resets to, which can only be a committed state; `v4` and `v5` were never part of any commit, so no object contains them. (An index entry does write a blob object when you `git add`, so `v4` could in principle be dug out with `git fsck --lost-found` until garbage collection, but `v5` never became an object.)
13. Header-and-body rule: the id is the SHA-1 of the ASCII `<kind> <body length>`, a zero byte, and the body. Results (Python and `git rev-parse` agree): blob `hello\n` `ce013625030ba8dba906f756967f9e9ca394464a`; subtree (only `b.txt`) `add4794d9c94872b96c1697c056fb82ae0d72880`; root tree `da42db87a7f4327a309dd083601a7d212580f273`; commit `6c15756bb7a1d78fd638ddd1b3e01bafa0a21cdc`. The root tree lists `a.txt` before `a`: entries are sorted as if directory names had a trailing `/`, and `.` (0x2e) < `/` (0x2f). Tree entries use the raw 20 bytes of the id, and the subtree mode is written `40000`. Changing the message to `first!` changes the commit body, so its id becomes `0b426f1a5805cc672a01a2d0a66ed2d386a1575c`; the tree id is unchanged. A child commit contains `parent <commit id>` in its body, so it is a different object whose id is computed from the parent's: for the example child with message `child` the id is `5e70ea3c8aff207bd52eb414173f7d90077b940a`, and replacing the parent by the `first!` commit would change it again.
14. (a) The first bad commit is one of commits 2 to 1000, so $999$ candidates. Each test answers yes/no, so $t$ tests distinguish at most $2^t$ outcomes; we need $2^t\ge999$, hence $t\ge\lceil\log_2 999\rceil=10$ (since $2^9=512<999\le1024$). Testing the middle candidate leaves at most $\lceil m/2\rceil$ candidates out of $m$, so after 10 tests at most 1 remains: 10 suffice, and 10 are necessary. (b) A scratch run with `git bisect run` and a script testing the file content stopped at `c613` after exactly 10 executions. (c) A non-deterministic test can return the wrong answer once and send the search to the wrong half with no warning: make the test deterministic or repeat it, and if a commit cannot be judged use exit code 125 (skip). A bug that appears, disappears and reappears has several boundaries; bisect returns one of them, so confirm by testing neighbours. Broken intermediate commits (will not build) must not be classified bad: return 125 so bisect skips them. Exit codes above 127 abort the run.
