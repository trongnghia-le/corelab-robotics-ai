## Why this matters

Every robot has a small computer that must read switches and sensors, drive motors and LEDs, and never stop paying attention to any of them. A microcontroller (the chip on an Arduino or ESP32 board, see HW06) has no operating system to share its time between jobs. If your code sits in `delay(500)`, the emergency-stop button, the encoder and the serial link all wait. The habits in this lesson are the ones that separate a blinking demo from firmware you can put on a robot: never wait, always check the clock, keep each job a tiny state machine, and know the numbers (volts per ADC step, PWM duty, register sizes) so you can predict what the board will do before you flash it. You will write the real Arduino C++ and MicroPython, and test the logic on your computer with plain Python.

## Intuition

Think of `loop()` as a cook watching three pots. The `delay()` style is staring at one pot for 500 ms with eyes shut: the other pots may boil over. The `millis()` style is a cook who walks past every pot many times per millisecond, glances at the kitchen clock and acts only if a pot is due. The clock never stops, and nobody waits for it.

![Left top: delay(500) keeps loop() asleep so a 300 ms button press is missed. Left bottom: a millis() loop passes many times per millisecond, toggles the LED on schedule and sees the press at once. Right: a three-state machine IDLE, PRESSED, HELD with its transitions](/lesson-figures/HW07.svg)

*A loop that never waits can serve many jobs; each job remembers where it is in a tiny state machine.*

Two more ideas make this work. First, every pin value is just a number written to or read from a register, so the arithmetic of duty cycles and ADC codes is simple integer maths you can do by hand. Second, a variable that must remember something between passes of `loop()` (the last time, the current state) has to live outside the function (a global or a `static` local).

## Theory and derivation

### Two boards, one mental model

| | Arduino Uno R3 (ATmega328P) | ESP32 DevKit (ESP32) |
|---|---|---|
| CPU | 8-bit AVR, 16 MHz | dual-core 32-bit Xtensa, up to 240 MHz |
| Memory | 32 KB flash, 2 KB SRAM, 1 KB EEPROM | 520 KB SRAM, flash external (often 4 MB) |
| Logic level | 5 V | 3.3 V (pins are not 5 V tolerant) |
| ADC | 10 bit (0 to 1023) | 12 bit (0 to 4095), non-linear, see below |
| `int` size | 16 bit (max 32767) | 32 bit |
| PWM | `analogWrite`, 8 bit, about 490 Hz (pins 3, 9, 10, 11) or 980 Hz (5, 6) | LEDC, 1 to 20 bit, any frequency in range |

*(Sources: ATmega328P datasheet, ESP32 datasheet, Arduino analogWrite reference; links in Further reading.)* A sketch is C++ with two required functions: `setup()` runs once, `loop()` runs forever. On a bare microcontroller there is no `malloc` habit to lean on: with 2 KB of SRAM you declare what you need up front, avoid `String` objects that grow, and mark variables shared with interrupts `volatile` (HW08).

### GPIO: pins in and out

`pinMode(pin, OUTPUT)` makes a pin drive HIGH (logic supply) or LOW (ground). `INPUT_PULLUP` turns on an internal resistor to the supply, so an unconnected pin reads HIGH and a button wired between the pin and ground reads LOW when pressed (**active low**). That needs no external resistor. Never power a load from a pin: the ATmega328P datasheet gives 40 mA as the absolute maximum per I/O pin, with about 20 mA the sensible continuous limit. An LED needs a series resistor $R=(V_{cc}-V_f)/I$, and motors need a driver (HW05).

### ADC: code to volts

An $N$-bit ADC with reference $V_{ref}$ turns an input voltage into a code. The ATmega328P datasheet gives $\text{ADC}=V_{in}\cdot1024/V_{ref}$, so
$$V_{in}\approx\text{raw}\cdot\frac{V_{ref}}{2^N},\qquad \text{LSB}=\frac{V_{ref}}{2^N}.$$
Uno: $5/1024=4.88$ mV per step. ESP32 (nominal, 3.3 V): $3.3/4096=0.806$ mV. The ESP32 ADC is not a precision part: the response bends near both ends, depends on the attenuation setting (0, 2.5, 6 or 11 dB), and **ADC2 channels cannot be used while Wi-Fi is on**; use ADC1 pins (GPIO32 to 39). Pins 34 to 39 are input only and have no internal pull-up. Averaging several samples cuts noise; a calibration table fixes the bend (see the Espressif ADC page).

### PWM: duty to average voltage

A pin switched fast between 0 and $V_{cc}$ with duty $D$ delivers an average $\bar V=D\,V_{cc}$ to a slow load (LED, motor inertia). On the Uno, `analogWrite(pin, v)` with $v\in[0,255]$ gives $D=v/255$. To convert the 10-bit reading to that range use `map(raw, 0, 1023, 0, 255)`, which uses **integer** arithmetic and truncates toward zero.

On the ESP32 the LEDC peripheral counts a timer from 0 to $2^{b}-1$ using an 80 MHz clock. One PWM period needs $2^b$ counts, so
$$2^{b}\cdot f_{pwm}\le f_{clk}\quad\Longrightarrow\quad b_{max}=\lfloor\log_2(f_{clk}/f_{pwm})\rfloor .$$

| PWM frequency | Max resolution (80 MHz) | Duty step |
|---|---|---|
| 1 kHz | 16 bit | 0.0015 % |
| 5 kHz | 13 bit | 0.012 % |
| 20 kHz | 11 bit | 0.049 % |
| 40 kHz | 10 bit | 0.098 % |

Faster PWM (above hearing, about 20 kHz, for quiet motors) costs resolution. This is the frequency-versus-resolution trade-off of every PWM peripheral.

### Blocking versus non-blocking

`delay(ms)` stops the program for `ms`. With one `delay()` of $T$ ms per loop pass the button is read once every $T$ ms, so the worst-case reaction time is $T$, and a press shorter than $T$ is often missed entirely. The fix is to ask the clock instead. `millis()` returns the milliseconds since power-up as a 32-bit unsigned number, wrapping to 0 after $2^{32}$ ms $=49.7$ days. The scheduling rule is
```
if ((unsigned long)(now - last) >= period) { last += period; do_work(); }
```
Subtraction of unsigned numbers is done modulo $2^{32}$, so `now - last` is correct even when `now` has wrapped past zero and `last` has not. Do **not** write `now >= last + period`: near the rollover `last + period` wraps to a small number and the test fires on every pass. Advancing `last += period` (not `last = now`) keeps the long-run period exact even if one pass was late.

### State machines

When a job has memory ("the button went down at time t and I am waiting to see if it stays down"), name its situations as **states** and write down the **transitions**. In code: an `enum` plus a `switch`, evaluated once per pass, never waiting inside a state. A button-hold job needs three states (IDLE, PRESSED, HELD, as in the figure). The same pattern describes a gripper (OPEN, CLOSING, CLOSED), a start-up sequence or a debouncer.

### Serial debugging and its cost

`Serial.print` is the oscilloscope of the beginner. Its cost: a byte takes 10 bit times (8N1, as in S06), so a 30-byte line costs $30\cdot10/9600=31$ ms at 9600 baud but only 2.6 ms at 115200. The Uno's transmit buffer holds 64 bytes; when it is full `print` waits, which silently turns a fast loop into a slow one. Print on a schedule (every 100 to 200 ms) and use 115200 baud.

### MicroPython and the trade-offs

MicroPython runs a Python interpreter on the chip (ESP32, RP2040, others); you type in a REPL or copy `main.py` with `mpremote`. The mapping is direct:

| Arduino C++ | MicroPython |
|---|---|
| `digitalWrite(p, HIGH)` | `Pin(p, Pin.OUT).value(1)` |
| `pinMode(p, INPUT_PULLUP)` | `Pin(p, Pin.IN, Pin.PULL_UP)` |
| `analogRead(p)` | `ADC(Pin(p)).read_u16()` (0 to 65535) |
| `analogWrite` / LEDC | `PWM(Pin(p), freq=5000).duty_u16(x)` |
| `millis()` | `time.ticks_ms()`, compare with `ticks_diff` / `ticks_add` |

Trade-offs: C++ is far faster (tight loops are one to two orders of magnitude quicker; measure on your board), has deterministic timing and a small memory footprint. MicroPython is quicker to write and change over the REPL, but it allocates objects, so a **garbage collector** (GC) occasionally pauses the program for milliseconds; it needs more RAM, and interrupt handlers must avoid allocating memory (HW08). Use it for prototypes, logging and glue; use C++ for tight timing (motor loops, high-rate interrupts) and large projects.

## Worked example

Goal: LED A blinks every 500 ms; LED B lights after the button has been held for 1 s; neither job may block the other. Uno wiring: LED A on D13, LED B on D12 (each with 220 ohm to ground), button between D2 and GND.

```cpp
const uint8_t LED_BLINK = 13, LED_HOLD = 12, BUTTON = 2;
const unsigned long BLINK_MS = 500, HOLD_MS = 1000;

unsigned long lastBlink = 0;
bool blinkState = false;

enum State { IDLE, PRESSED, HELD };
State state = IDLE;
unsigned long pressedAt = 0;

void setup() {
  pinMode(LED_BLINK, OUTPUT);
  pinMode(LED_HOLD, OUTPUT);
  pinMode(BUTTON, INPUT_PULLUP);          // pressed = LOW
  Serial.begin(115200);
}

void taskBlink(unsigned long now) {
  if (now - lastBlink >= BLINK_MS) {      // unsigned subtraction survives the millis() rollover
    lastBlink += BLINK_MS;                // advance by one period, not to "now": no drift
    blinkState = !blinkState;
    digitalWrite(LED_BLINK, blinkState);
  }
}

void taskHold(unsigned long now) {
  bool pressed = (digitalRead(BUTTON) == LOW);
  switch (state) {
    case IDLE:
      if (pressed) { pressedAt = now; state = PRESSED; }
      break;
    case PRESSED:
      if (!pressed) {
        state = IDLE;                     // released too early
      } else if (now - pressedAt >= HOLD_MS) {
        digitalWrite(LED_HOLD, HIGH);
        Serial.print("HELD at ");
        Serial.println(now);
        state = HELD;
      }
      break;
    case HELD:
      if (!pressed) { digitalWrite(LED_HOLD, LOW); state = IDLE; }
      break;
  }
}

void loop() {
  unsigned long now = millis();           // read the clock once per pass
  taskBlink(now);
  taskHold(now);
}
```

The same program in MicroPython on an ESP32 (LEDs on GPIO18 and GPIO19, button on GPIO4 to ground):

```python
from machine import Pin
from time import ticks_ms, ticks_diff, ticks_add

led_blink = Pin(18, Pin.OUT)
led_hold = Pin(19, Pin.OUT)
button = Pin(4, Pin.IN, Pin.PULL_UP)        # pressed = 0

BLINK_MS, HOLD_MS = 500, 1000
IDLE, PRESSED, HELD = 0, 1, 2
state, pressed_at = IDLE, 0
last_blink = ticks_ms()

while True:
    now = ticks_ms()
    if ticks_diff(now, last_blink) >= BLINK_MS:
        last_blink = ticks_add(last_blink, BLINK_MS)     # ticks_* handle the wrap-around
        led_blink.value(not led_blink.value())
    pressed = button.value() == 0
    if state == IDLE:
        if pressed:
            pressed_at, state = now, PRESSED
    elif state == PRESSED:
        if not pressed:
            state = IDLE
        elif ticks_diff(now, pressed_at) >= HOLD_MS:
            led_hold.value(1)
            print("HELD at", now)
            state = HELD
    else:
        if not pressed:
            led_hold.value(0)
            state = IDLE
```

Check it by hand with the clock. Press the button at $t=1000$ ms and keep it down: pass at 1000 sees LOW, state PRESSED, `pressedAt=1000`. At $t=2000$: `now - pressedAt = 1000 >= 1000`, so LED B on, print `HELD at 2000` (a real board may print 2000 or 2001, depending on the pass). Release at 2300: LED B off. Meanwhile the blink task toggled at 500, 1000, 1500, 2000 and 2500 with no interruption. Compare with the blocking version:

```cpp
void setup() {
  pinMode(13, OUTPUT);
  pinMode(12, OUTPUT);
  pinMode(2, INPUT_PULLUP);
}

void loop() {
  digitalWrite(13, HIGH);
  delay(500);                        // nothing else can run for 500 ms
  digitalWrite(13, LOW);
  delay(500);
  digitalWrite(12, digitalRead(2) == LOW);   // the button is looked at once per second
}
```

It reads the button once per 1000 ms, so the reaction time is up to 1 s and a 300 ms tap is seen only with probability 300/1000.

Numbers for the ADC and PWM half. A potentiometer at the Uno's A0 reads 614. $V=614\cdot5/1024=2.998$ V. `map(614,0,1023,0,255)` $=614\cdot255/1023=153.05\to153$, a duty of $153/255=60\%$ and an average output near 3.0 V (the LED looks about 60 % bright, a little more because eyes are non-linear). On an ESP32 the same pot gives about 2048 (12 bit, 1.65 V nominal), and an 8-bit LEDC duty would be `map(2048, 0, 4095, 0, 255)` $=127$.

## Reference implementation

Real commands for a first upload (Linux): `arduino-cli core install arduino:avr`, then `arduino-cli compile --fqbn arduino:avr:uno MySketch` and `arduino-cli upload -p /dev/ttyACM0 --fqbn arduino:avr:uno MySketch`, and `arduino-cli monitor -p /dev/ttyACM0 -c baudrate=115200`. For MicroPython, once the firmware is flashed: `mpremote connect /dev/ttyUSB0 run main.py` runs a file, and `mpremote connect /dev/ttyUSB0 cp main.py :main.py` stores it. The arithmetic of this lesson in Python:

```python
MASK32 = 0xFFFFFFFF

def elapsed(now, last):
    return (now - last) & MASK32            # unsigned 32-bit subtraction, like unsigned long in C

def pwm_counts(duty, bits):
    return round(duty * ((1 << bits) - 1))

def adc_to_volts(raw, bits, vref):
    return raw * vref / (1 << bits)

def ledc_max_bits(freq_hz, clk_hz=80_000_000):
    bits = 0
    while (1 << (bits + 1)) * freq_hz <= clk_hz:
        bits += 1
    return bits

assert elapsed(200, 4294967000) == 496 and elapsed(1000, 400) == 600
assert pwm_counts(0.5, 8) == 128 and pwm_counts(1.0, 10) == 1023
assert abs(adc_to_volts(614, 10, 5.0) - 2.998) < 1e-3 and abs(adc_to_volts(2048, 12, 3.3) - 1.65) < 1e-9
assert ledc_max_bits(5000) == 13 and ledc_max_bits(20000) == 11
print("reference ok")
```

### Starter code
```python
MASK32 = 0xFFFFFFFF


def elapsed(now, last):
    """Milliseconds from `last` to `now` on a 32-bit millis() counter (unsigned wrap-around)."""
    raise NotImplementedError


def map_range(x, in_min, in_max, out_min, out_max):
    """Arduino map(): integer arithmetic, the division truncates toward zero (as in C, not like Python //).
    ValueError if in_min == in_max."""
    raise NotImplementedError


def pwm_counts(duty, bits):
    """Integer compare value for a duty fraction 0..1 with `bits` of resolution: round(duty * (2**bits - 1)).
    ValueError if duty is outside [0, 1]."""
    raise NotImplementedError


def adc_to_volts(raw, bits, vref):
    """Voltage represented by an ADC code: raw * vref / 2**bits. ValueError if raw is outside 0 .. 2**bits - 1."""
    raise NotImplementedError


def ledc_freq_ok(freq_hz, bits, clk_hz=80_000_000):
    """ESP32 LEDC rule: the counter must fit in one PWM period, 2**bits * freq <= clk."""
    raise NotImplementedError


class Board:
    """A tiny virtual Arduino: a clock, output pins with a write log, and scripted input pins."""

    def __init__(self):
        self.now = 0
        self.inputs = {}
        self.log = []          # (time_ms, pin, value) for every digital_write

    def millis(self):
        return self.now & MASK32

    def digital_read(self, pin):
        return self.inputs.get(pin, 1)     # idle high: INPUT_PULLUP

    def digital_write(self, pin, value):
        self.log.append((self.millis(), pin, value))


class Blinker:
    """Non-blocking blink: toggle `pin` every `period_ms` without ever waiting."""

    def __init__(self, board, pin, period_ms):
        self.board, self.pin, self.period = board, pin, period_ms
        self.last = board.millis()
        self.level = 0

    def tick(self):
        """If a full period has elapsed (use elapsed()), advance self.last by exactly one period
        (not to 'now', so the long-run period stays exact), flip self.level and write it."""
        raise NotImplementedError


IDLE, PRESSED, HELD = "IDLE", "PRESSED", "HELD"


class HoldDetector:
    """Button on an INPUT_PULLUP pin (pressed = 0). LED goes on after `hold_ms` of continuous press."""

    def __init__(self, board, button_pin, led_pin, hold_ms):
        self.board, self.button, self.led, self.hold_ms = board, button_pin, led_pin, hold_ms
        self.state = IDLE
        self.pressed_at = 0

    def tick(self):
        """IDLE -> PRESSED when the button goes down (remember the time);
        PRESSED -> IDLE if released early, PRESSED -> HELD (write led 1) once held for hold_ms;
        HELD -> IDLE on release (write led 0)."""
        raise NotImplementedError


def run(board, tasks, end_ms, events=None):
    """Advance the clock 1 ms at a time; apply scripted input events {time_ms: (pin, value)}, then tick every task."""
    events = events or {}
    while board.now < end_ms:
        board.now += 1
        if board.now in events:
            pin, value = events[board.now]
            board.inputs[pin] = value
        for task in tasks:
            task.tick()
```

**B. ADC to PWM fader on an Uno.** Add a potentiometer (SIG to A0, VCC to 5V, GND to GND) and one LED on D9 via 220 ohm. Sketch:

```cpp
const uint8_t POT = A0, LED = 9;      // pin 9 is PWM-capable on the Uno (about 490 Hz)

void setup() {
  Serial.begin(115200);
  pinMode(LED, OUTPUT);
}

void loop() {
  static unsigned long lastPrint = 0;
  int raw = analogRead(POT);                    // 0..1023, about 100 us per conversion
  int duty = map(raw, 0, 1023, 0, 255);         // analogWrite takes 0..255
  analogWrite(LED, duty);
  if (millis() - lastPrint >= 200) {            // print 5 times a second without blocking
    lastPrint += 200;
    Serial.print("raw=");      Serial.print(raw);
    Serial.print(" duty=");    Serial.print(duty);
    Serial.print(" volts=");   Serial.println(raw * 5.0 / 1024.0, 3);
  }
}
```
Observe: the printed `duty` follows `raw` divided by about 4 and the LED brightness follows the knob. **Pass:** on every printed line `duty` equals `raw * 255 / 1023` rounded toward zero (for example `raw=614` gives `duty=153` and `volts=2.998`), and `duty` rises from 0 to 255 as you turn the knob from one end to the other. On an ESP32 the raw range is 0 to 4095: change `A0` to a GPIO34 pin, scale with `map(raw, 0, 4095, 0, 255)`, and compare the step size.

**C. MicroPython twin on an ESP32** ([new MicroPython ESP32 project](https://wokwi.com/projects/new/micropython-esp32)). Parts: ESP32, potentiometer (SIG to GPIO34), LED on GPIO18 via 220 ohm to GND. Paste into `main.py`:

```python
from machine import Pin, ADC, PWM
from time import ticks_ms, ticks_diff, ticks_add

adc = ADC(Pin(34))                  # GPIO34: ADC1, input only
adc.atten(ADC.ATTN_11DB)            # widest input range (about 0 to 3.3 V)
led = PWM(Pin(18), freq=5000)       # 5 kHz PWM on GPIO18

last = ticks_ms()
while True:
    raw16 = adc.read_u16()          # 0..65535 (the 12-bit reading scaled up)
    led.duty_u16(raw16)             # 0..65535 -> 0..100 % duty
    if ticks_diff(ticks_ms(), last) >= 200:
        last = ticks_add(last, 200)
        print("raw16 =", raw16, " duty = %.1f %%" % (raw16 / 65535 * 100))
```
**Pass:** `raw16` ranges from about 0 to about 65535 as you turn the knob, `duty` follows it, and the LED brightness follows. Note how the Arduino and MicroPython versions differ in scale (10-bit versus 16-bit) but not in meaning.

## Verification

Predict before you run: write the expected log of LED changes with timestamps, then compare with the board or simulator. Test the clock logic at the boundaries: a rollover (`elapsed(5, 4294967290)` is 11), exactly one period (`>=` fires), one tick less (does not fire). Check ADC and PWM numbers by measuring or by Serial: `raw`, `duty` and `volts` printed together should satisfy `volts` $\approx$ `raw` $\cdot\,5/1024$ and `duty` $\approx$ `raw`/4. Measure your own loop time with `micros()` around one pass; a pass that takes longer than your shortest period means a task will be late.

## Failure modes

- A `delay()` hidden in a helper function (or a long `Serial.print` on a slow baud rate) blocks every task.
- `int` overflow on a 16-bit board: `60 * 1000` becomes $-5536$; use `unsigned long` and `UL` suffixes.
- `now >= last + period` instead of `now - last >= period`: a burst of toggles once every 49.7 days.
- `last = now` instead of `last += period`: the period drifts by the lateness of every pass.
- Forgetting `INPUT_PULLUP`: a floating input toggles randomly and a button seems to press itself.
- Reading `HIGH` for "pressed" with an active-low button: the logic is inverted.
- ESP32: a 5 V signal on a 3.3 V pin (damage), a button on a strapping pin such as GPIO12 (no boot), `analogRead` on ADC2 with Wi-Fi on (garbage), a Wi-Fi call in a tight loop (watchdog resets).
- MicroPython: allocating inside an interrupt handler, or a loop that creates many objects, causing GC pauses at the worst moment.

## Alternatives and trade-offs

`delay()` is fine for a one-job demo and for setup code. A tiny cooperative scheduler (the `millis()` pattern) is the right tool for a handful of jobs and a few kHz of timing. When jobs have different priorities or must wait on slow I/O, a real-time operating system (FreeRTOS, already running under the Arduino-ESP32 core) gives each job its own task, at the cost of memory and the need to protect shared data (HW08 introduces this). Libraries such as `Bounce2` or `TaskScheduler` package the pattern, but you should write it once by hand. PlatformIO is an alternative to the Arduino IDE with better dependency handling; CircuitPython (Adafruit) is a close cousin of MicroPython with a different library set.
