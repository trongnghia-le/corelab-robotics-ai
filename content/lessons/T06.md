## Why this matters

T05 made the Python packages reproducible. Containers go one step further: they package the user-space of a machine - the operating system libraries, the interpreter, your dependencies and your code - into an **image** that runs the same way on a laptop, a lab server or a robot computer. But containers also introduce a new kind of mistake: treating a container as a small virtual machine whose files persist. They do not. A container is disposable by design; whatever you write inside it vanishes when you replace it unless you stored it somewhere explicit. This lesson explains containers, images and layers, and volumes, and gives you the discipline to answer the practical question every experiment raises: *when I replace this container, which files survive?*

## Intuition

Four nouns, one picture.

- An **image** is an immutable, layered template: a stack of read-only filesystem layers plus metadata (default command, environment variables). Think of it as a class or a frozen recipe.
- A **container** is a running (or stopped) instance of an image: a normal Linux process (T01) started with an isolated view of the filesystem, network and process table, plus one thin **writable layer** on top. Think of it as an instance.
- A **volume** or **bind mount** attaches storage that lives *outside* the container's writable layer: a Docker-managed volume (named, persistent) or a directory of the host. Writes there outlive the container.
- A **registry** stores and distributes images (Docker Hub, GitHub Container Registry).

Because many containers can share the same read-only layers, starting one is fast and cheap, and replacing one is a normal operation. A container is **not** a virtual machine: it shares the host's kernel, so kernel version, drivers (for GPUs) and CPU architecture are *not* packaged.

![Left: a container as a stack of read-only image layers (base OS, dependencies, code) with a writable layer on top that is discarded on docker rm. Right: a named volume mounted at /results and a read-only bind mount at /app, both living outside the container and surviving its removal.](/lesson-figures/T06.svg)

*Anything written to the top writable layer is lost when the container is removed; data in mounted volumes persists.*
**A picture from everyday life.** Think of a printed form kept in a binder. The binder holds a stack of transparent sheets: the bottom sheet carries the printed form (the operating system), the next sheets add stamps (libraries, your dependencies), and each new sheet can only *add* ink or *cover* something with white-out tape. You never erase a lower sheet. A container is a person who puts one more blank sheet on top and writes on it with a pencil. When you throw that top sheet away (`docker rm`), the stack underneath is untouched, and so is anything the person wrote on a *separate* notebook that was clipped to the binder (a volume). On a robot the same picture applies: the ROS 2 workspace and its libraries are the frozen sheets; the bag files and logs must go into the notebook, or they are thrown away with the pencil sheet when you redeploy.

**Predict before you compute.** Before reading on, answer without any arithmetic: a 2 GB dataset is added in one layer, and the next instruction runs `rm` on it. Is the final image 2 GB smaller than without the `rm`? Next: your Dockerfile has ten instructions and you edit the file that the fourth one copies. How many instructions run again, and does the answer change if the edited file is only needed by instruction nine? Finally, you write a log line to a file that exists in the image: how many bytes does Docker have to copy before your write can happen?

**The common wrong intuition.** Most newcomers treat a container as a small virtual machine: "I installed something and saved a file, so it is there". Three consequences surprise them. Deleting a file in a later layer does not make the image smaller, because layers only add. The build cache is not a cache of *results* that Docker re-checks against the world; it is a cache keyed by the text of the instruction and the files copied, so `RUN apt-get update` stays stale for months. And "reproducible" does not mean "bit-identical on every machine": the kernel, the GPU driver and the CPU come from the host. The answers to the three prompts are: no, the image is not smaller; seven instructions rerun (positions four to ten), but only two (nine and ten) if the edited file is first copied at instruction nine; and the entire file, however large. The derivations are in the theory section and the second worked case.

## Theory and derivation

### Images and layers

Each instruction in a **Dockerfile** that changes the filesystem (`RUN`, `COPY`, `ADD`) creates a layer; layers are content-addressed and shared between images. A minimal experiment image:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.lock .
RUN pip install --no-cache-dir -r requirements.lock
COPY . .
CMD ["python", "experiment.py"]
```

Key instructions: `FROM` (base image; **pin** it, ideally by digest), `WORKDIR` (working directory, also a creator of the directory), `COPY` (files from the build context into the image), `RUN` (execute at build time), `ENV` (environment variables; **never** secrets: they are visible in the image), `CMD`/`ENTRYPOINT` (what runs when the container starts). A `.dockerignore` keeps `.git`, `.venv`, `.env` and data out of the build context.

### The build cache

Docker reuses a layer from the cache when its instruction and everything *before* it are unchanged. For `COPY`, the content of the copied files is part of the key. So the **first changed instruction invalidates all following layers**. If you `COPY . .` before `RUN pip install`, every code edit reinstalls all dependencies; copy the lock first, install, then copy the code. With $L$ instructions and the first changed one at position $k$ (1-based), $k-1$ layers are reused and $L-k+1$ are rebuilt.

### What happens to files

A container sees a **union filesystem**: lower read-only image layers plus the container's writable layer; a write to a file from a lower layer copies it up first (copy-on-write); a deletion hides the file with a whiteout in the upper layer. When the container is removed (`docker rm`), the writable layer is discarded. Stopping a container does *not* remove it: `docker start` brings it back with its writable layer, which is why leftover containers can mask a missing volume.

For a path $p$ written inside the container, the destination is decided by the **longest mount target that is a prefix of $p$** (by path component):

$$\text{dest}(p)=\begin{cases}\text{mount kind}&\text{if some mount target } t\text{ covers }p\ (\text{longest wins}),\\ \text{writable layer}&\text{otherwise.}\end{cases}$$

A read-only mount (`:ro`) makes the write fail. Only files whose destination is a volume or bind mount survive replacing the container.

### Volumes, bind mounts and tmpfs

| Kind | Syntax | Lives | Typical use |
| --- | --- | --- | --- |
| Named volume | `-v results:/results` | Docker-managed area | results, databases; portable and persistent |
| Bind mount | `-v "$PWD/out:/results"` | a host directory you choose | code under development, inspecting outputs |
| tmpfs | `--tmpfs /scratch` | memory | secrets or scratch not to touch disk |
| Writable layer | (default) | with the container | temporary files only |

Bind mounts expose host file ownership: a process running as root in the container writes root-owned files into your host directory; run with `--user "$(id -u):$(id -g)"` to avoid it.

### Configuration and reproducibility

Pass configuration at run time, not build time: `docker run -e EXP_SEED=1 ...` (as in T05). Record the **image digest** (`docker inspect --format '{{.Id}}' image`) with each result; a tag like `latest` can move. A container fixes the user-space, not the hardware: GPU drivers, kernel, CPU instruction sets and non-deterministic kernels still matter.
### Layers as filesystem changesets, and why deleting does not shrink an image

An image layer is not a snapshot of a whole disk. In the OCI image format a layer is a **changeset**: an archive that lists only the paths added, modified or deleted relative to the layers below it, and the filesystem a container sees is obtained by applying the changesets in order (OCI Image Format Specification, `layer.md`, "Layer Changesets"). Three rules follow directly from that definition.

1. *Additions and modifications are stored in full.* If a layer changes one byte of a 500 MB file, the changeset contains the whole new 500 MB file, because the format works at the file level, not the block level.
2. *Deletions are stored as markers.* A deleted path is represented by an empty **whiteout** file named `.wh.<basename>` placed in the same directory; a whiteout may only hide resources in lower layers, and once applied it hides itself too (`layer.md`, "Whiteouts"). Deleting a whole directory needs one whiteout for the directory, not one per descendant. Removing *all children* of a directory while keeping the directory can use an **opaque whiteout**, the file `.wh..wh..opq`, which hides every sibling present in lower layers; implementations should emit explicit whiteouts but must accept both forms.
3. *Lower layers are never edited.* Layers are immutable and shared, so a later layer can only add information.

Let $s_i$ be the size of the changeset of layer $i$. The size of an image is the sum of its layers,
$$\text{size}=\sum_{i=1}^{L} s_i ,$$
and a whiteout has $s\approx 0$. Hence `RUN rm big.tar` in a *later* instruction removes $big.tar$ from the visible filesystem but does **not** reduce $\text{size}$: the bytes still sit in the earlier layer and are pushed, pulled and stored. Anyone who can pull the image can read them, which is why a secret copied into one layer and deleted in the next is still leaked. The remedy is to create and remove the file inside the *same* `RUN` instruction (the temporary file then never appears in any changeset).

### Layer identity: DiffID, ChainID and why the build cache is prefix-only

The OCI image configuration gives each layer a **DiffID**, the digest of its uncompressed changeset. A DiffID identifies a changeset but not the *filesystem* it produces, because the same changeset applied on different lower layers yields different results. The specification therefore defines the **ChainID** of a stack by recursion (`config.md`, "Layer ChainID"):
$$\text{ChainID}(L_0)=\text{DiffID}(L_0),\qquad \text{ChainID}(L_0|\dots|L_n)=\text{Digest}\big(\text{ChainID}(L_0|\dots|L_{n-1})\;\text{“ ”}\;\text{DiffID}(L_n)\big).$$
Unrolled, $\text{ChainID}(A|B|C)=\text{Digest}(\text{Digest}(\text{DiffID}(A)\,\text{“ ”}\,\text{DiffID}(B))\,\text{“ ”}\,\text{DiffID}(C))$, a hash chain. Two consequences matter for experiments. First, $\text{ChainID}(C)\neq\text{ChainID}(A|B|C)$: the identity of a layer *in context* depends on every layer below and on their order, so two images share storage for a layer only if they share the whole prefix beneath it. Second, the same prefix-dependence explains the **build cache**: a cached result is valid only for the same sequence of preceding instructions, which is why a changed instruction invalidates everything after it. Reordering two independent instructions changes every ChainID from the first swapped position on.

### What goes into a cache key, and how a cache goes stale

The builder's rule differs by instruction (Docker Docs, "Build cache invalidation"). For `ADD` and `COPY` it computes a checksum from the **metadata of the files involved** and invalidates when that changes; the modification time is not included, so touching a file without changing it does not bust the cache. For every other instruction, notably `RUN`, the files inside the container are *not* examined: only the **command string** is compared. So `RUN pip install -r requirements.lock` is re-executed when the lock file changes only because the preceding `COPY requirements.lock .` was invalidated, and `RUN apt-get update` or `RUN git clone ...` is silently reused for months even though the outside world changed. This is the central trap of the cache: it is a function of the *text* of your Dockerfile and the *copied files*, not of the state of the network. Three defences are standard: pin versions and digests so that the text itself changes when the dependency changes; combine `apt-get update && apt-get install pkg=version` in one `RUN`; and pass a build argument (for example a date or commit) that you deliberately change when you want a refresh, since changing an `ARG` used by an instruction invalidates it and its successors. Note also that a cache hit is a statement about build *inputs*; two builds with the same cache keys can still produce different bytes if a step is non-deterministic, which is why you record the image digest (above) and not just the Dockerfile.

### Copy-up: what a write to an image file really costs

With the `overlay2` storage driver the container filesystem is an overlay of the read-only image layers (`lowerdir`) and the writable layer (`upperdir`). The first time a container writes to a file that exists only in an image layer, the driver performs a **copy-up**: it copies the *whole file* to the upper layer and then applies the write; later writes to that file hit the copy already in the upper layer. OverlayFS works at the file level, so changing one byte of a 3 GB checkpoint file copies 3 GB (Docker Docs, "OverlayFS storage driver", "Modifying files or directories"). Deleting a file in a container creates a whiteout in the upper layer, exactly as in an image layer. The docs therefore recommend **volumes for write-heavy workloads**: a volume bypasses the storage driver and avoids both the copy-up latency and the overlay overhead.

A simple cost model captures the trade-off. Let a container modify $m$ distinct image files of sizes $F_1,\dots,F_m$ and write $w$ further bytes of new data. The writable layer grows to $\sum_j F_j + w$ and the one-time latency is $\sum_j F_j / B$ for disk bandwidth $B$. With $n$ concurrent containers from one image the layers are *not* shared, so the extra disk is $n\big(\sum_j F_j+w\big)$, whereas mounting the files read-only and sending $w$ to a volume costs only $nw$. Whenever your program edits a large file that was baked into the image, or writes heavily, the right design is to move that path onto a mount.

### Expected rebuild time of a Dockerfile (an exchange argument)

The "slow-changing first" advice can be derived. Suppose instruction $i$ costs $c_i$ seconds to rebuild, and between two consecutive builds its own input changes independently with probability $q_i$ (a new line of code, a new dependency). Instruction $i$ is rebuilt if it or any earlier instruction changed, which has probability $1-\prod_{j\le i}(1-q_j)$, so the expected build time is
$$E=\sum_{i=1}^{L} c_i\Big(1-\prod_{j\le i}(1-q_j)\Big).$$
Swap two adjacent independent instructions $u,v$ that follow a prefix with survival probability $S=\prod_{j<u}(1-q_j)$. Writing the contribution of the pair in each order and subtracting gives
$$E_{uv}-E_{vu}=S\big[(1-q_v)c_v q_u-(1-q_u)c_u q_v\big],$$
which is negative, so $u$ should come first, exactly when $c_u(1-q_u)/q_u>c_v(1-q_v)/q_v$. The index $c(1-q)/q$ is large for *expensive and rarely changing* steps, so the optimal order puts them first; with $q\ll1$ it reduces to $c/q$, the cost divided by the change rate. This is the quantitative content of "order from less frequently changed to more frequently changed". The assumption that instructions are independent fails when one instruction needs files from another (for example `RUN pip install` needs the copied lock file), which is exactly why the lock file is copied separately: splitting `COPY` into a rarely changing part and a frequently changing part creates two instructions with different $q$ and gives the exchange argument something to optimise. Connection to T05: the lock file is the artefact whose change rate $q$ you control; to T07 and T08: the same expected-cost reasoning prices retries and checkpoints.

## Worked example

### Basic cases

**Where do the writes go?** Mounts: `/results` (named volume, read-write), `/app` (bind mount, read-only). The program writes `/results/run.json`, `/tmp/scratch.txt`, `/root/.cache/x`:

- `/results/run.json` $\to$ volume; survives `docker rm`.
- `/tmp/scratch.txt`, `/root/.cache/x` $\to$ writable layer; lost.
- A write to `/app/x` fails with *Read-only file system*.

**Cache arithmetic.** The naive Dockerfile has five instructions (`FROM`, `WORKDIR`, `COPY . .`, `RUN pip install`, `CMD`). Editing `train.py` changes the third instruction's key, so only $2$ layers are reused and the dependency install is repeated. In the dependency-first Dockerfile (six instructions: `FROM`, `WORKDIR`, `COPY requirements.lock`, `RUN pip install`, `COPY . .`, `CMD`) the same edit changes the fifth, so $4$ layers are reused (the install is cached) and only `COPY . .` and `CMD` are rebuilt.

**Shared storage.** Three images: $120+300+5$ MB, $120+300+5$ MB (a different 5 MB code layer) and $120+40$ MB, sharing the 120 MB base and the 300 MB dependency layer. Stored once: $120+300+5+5+40=470$ MB instead of $425+425+160=1010$ MB unshared.

**Real run (lab).** A first container writes `/results/run.json` (volume) and `/tmp/scratch.txt` (layer). `docker rm` it; a second container mounting the same volume lists `run.json` but `ls /tmp/scratch.txt` reports *No such file or directory*; `docker diff` on the first container showed `A /results`, `C /tmp`, `A /tmp/scratch.txt`, `A /app` (the mount points themselves and the one scratch file; the order may vary).
### A harder case: image size, expected build time and a copy-up bill

**Setting.** An experiment image is built from these instructions, in this order: `FROM python:3.12-slim` (120 MB, never rebuilt), `RUN apt-get ...` (90 s, 200 MB, changes with probability $q=0.01$ per commit), `RUN pip install` of the locked dependencies (240 s, 300 MB, $q=0.05$), `COPY weights/` (60 s, 3 GB, $q=0.02$), `COPY src/` (5 s, 5 MB, $q=0.9$) and `COPY configs/` (2 s, 1 MB, $q=0.3$). Treat the changes as independent.

**Step 1: size and a whiteout trap.** The five layers after `FROM` sum to $200+300+3000+5+1=3506$ MB, plus 120 MB, so $3626$ MB. If a later `RUN rm -r /app/weights` is added, the visible filesystem loses 3 GB, but the layer with the weights remains and the whiteout layer adds roughly 0, so the size stays $3626$ MB (OCI `layer.md`, "Whiteouts"). Only moving the weights to a mount or deleting them inside the same `RUN` that created them lowers it.

**Step 2: expected build time of the given order.** Let $S_i=\prod_{j\le i}(1-q_j)$ be the probability that nothing up to instruction $i$ changed. With $q=(0.01,0.05,0.02,0.9,0.3)$ the survival probabilities are $S=(0.99,\;0.9405,\;0.92169,\;0.092169,\;0.0645183)$ and the rebuild probabilities $1-S=(0.01,0.0595,0.07831,0.907831,0.9354817)$. So
$$E=90(0.01)+240(0.0595)+60(0.07831)+5(0.907831)+2(0.9354817)=26.289\ \text{s}.$$
Notice that almost all of this comes from the dependency layer: $240\times0.0595=14.28$ s. Moving `COPY src/` and `COPY configs/` *before* an expensive step would be a disaster: the worst of the $5!=120$ orders costs $370.8$ s.

**Step 3: improve it with the exchange rule.** The index $c(1-q)/q$ is $8910$ (apt), $4560$ (pip), $2940$ (weights), $4.67$ (configs) and $0.56$ (src). Sorting in decreasing order gives apt, pip, weights, configs, src, which swaps the last two instructions of the original order, and $E$ drops to $25.266$ s. The gain is small here (about $1$ s) because the cheap tail instructions cost little, which shows that the order of the *expensive* steps matters, not the cheap ones. The exchange rule also tells you what to do when the expensive step is the one that changes often: split it. Splitting the pip step into "copy only the lock file" ($q=0.05$) and "copy source" ($q=0.9$) is what makes the cache useful at all.

**Step 4: the copy-up bill at run time.** A job opens `weights/model.bin` (3 GB) in read-write mode and rewrites 1 KB of header. The first write copies the full file: at $B=1.5$ GB/s that costs $3/1.5=2$ s once, and the container's writable layer grows by 3 GB. Twenty such containers on one host need $20\times3=60$ GB of writable layers, while the 3 GB in the image is shared once. Mounting `weights/` read-only and writing the header to a volume costs only the 1 KB per container. This is the same decision rule as in the theory section: large baked-in files that your program modifies belong on a mount.

## Reference implementation

A Python model of the rules above: which mount covers a path (longest-prefix wins), where a write lands, which files survive container removal, layer flattening with deletions, Dockerfile parsing, build-cache reuse and shared-layer storage. (The real behavior is Docker's; this model lets you predict it.)

```python
def find_mount(path, mounts):
    """mounts: list of (target, kind, read_only) with kind 'volume' or 'bind'. Return the mount with the
    longest target that contains path (path == target or path starts with target + '/'), else None."""
    best = None
    for m in mounts:
        t = m[0].rstrip("/")
        if path == t or path.startswith(t + "/"):
            if best is None or len(t) > len(best[0].rstrip("/")):
                best = m
    return best

def write_destination(path, mounts):
    """Where a write to path inside a container lands: 'volume', 'bind', 'container' (the throw-away
    writable layer) or 'error-readonly' when the covering mount is read-only."""
    m = find_mount(path, mounts)
    if m is None:
        return "container"
    return "error-readonly" if m[2] else m[1]

def surviving_files(writes, mounts):
    """Sorted list of the written paths that still exist after the container is removed
    (those that landed in a volume or bind mount)."""
    return sorted(p for p in writes if write_destination(p, mounts) in ("volume", "bind"))

def flatten(layers):
    """Merge image layers bottom to top. A layer is a dict path -> content; content None deletes the path
    (like a whiteout). Return the final {path: content}."""
    fs = {}
    for layer in layers:
        for p, c in layer.items():
            if c is None:
                fs.pop(p, None)
            else:
                fs[p] = c
    return fs

def parse_dockerfile(text):
    """List of (INSTRUCTION, arguments) from Dockerfile text: skip blank lines and '#' comments,
    join lines ending in a backslash, upper-case the instruction."""
    out, buf = [], ""
    for raw in text.splitlines():
        line = raw.strip()
        if not buf and (not line or line.startswith("#")):
            continue
        if line.endswith("\\"):
            buf += line[:-1].strip() + " "
            continue
        full = (buf + line).strip(); buf = ""
        inst, _, args = full.partition(" ")
        out.append((inst.upper(), args.strip()))
    return out

def cache_reuse(old, new):
    """Number of leading instructions of `new` that can come from the build cache, i.e. the length of the
    common prefix of two parsed Dockerfiles (everything after the first difference is rebuilt).
    (A real COPY also compares file contents; here they are included in the argument text.)"""
    n = 0
    for a, b in zip(old, new):
        if a != b:
            break
        n += 1
    return n

def unique_bytes(images):
    """Total storage when images share layers. images: list of lists of (layer_id, size_in_mb);
    a layer id that appears in several images is stored once."""
    seen = {}
    for img in images:
        for lid, size in img:
            seen[lid] = size
    return sum(seen.values())

# tiny self-test

assert write_destination("/results/run.json", m) == "volume" and write_destination("/tmp/x", m) == "container"
assert write_destination("/app/x", m) == "error-readonly"
```

## Verification

- **Predict, then observe:** write down which files you expect to survive before running Task 3; compare with `ls` output. The Python model must give the same list.
- **Invariants:** a path is in exactly one place (a covering mount or the writable layer); a read-only mount never yields a surviving write; layer reuse equals the length of the common instruction prefix.
- **Digest equality:** host, venv (T05) and container all print `7d5f7244248d` for seed 0, 1000 steps, because the program is deterministic and only needs the standard library.
- **Falsifier:** if a file you expected to persist is missing after replacing the container, check mount targets (typos make a path fall into the writable layer), whether you mounted an anonymous volume, and whether a different volume name was used.

## Failure modes

- **Writing results to the container filesystem** (for example `/app/results`) and then `docker rm`: results lost.
- **Mount target typo** (`/result` vs `/results`): the program writes into the writable layer and nothing fails until the container is removed.
- **Anonymous volumes** (`VOLUME` in a Dockerfile or `-v /path`) that accumulate under random names.
- **`COPY . .` before dependency install:** every code change reinstalls everything.
- **Secrets in the image** (`ENV API_KEY=...`, copied `.env`): anyone with the image can read them from the layers.
- **Unpinned base (`latest`)** or unpinned packages: the image rebuilt next month differs.
- **Running as root** and creating root-owned files on bind mounts.
- **Treating the container as a VM:** SSH into it, edit files by hand, rely on its state.
- **Assuming the kernel is packaged:** GPU driver and kernel features come from the host.
- **Large build contexts** (data, `.git`) slowing every build; use `.dockerignore`.

## Alternatives and trade-offs

| Approach | Reproduces | Cost |
| --- | --- | --- |
| venv + lock (T05) | Python packages | no OS libraries, no system tools |
| Container image | OS libraries, interpreter, packages, your code | image build and size; kernel/driver shared |
| Virtual machine | the whole OS including kernel | heavy, slow to start |
| Nix / Guix | bit-for-bit build of the full dependency graph | steep learning curve |
| Docker Compose | several containers with volumes and networks | extra file; still one host |
| Dev containers | the editor attached to a container (T03) | setup; Docker required |

Use a venv for quick local work, a container when system libraries or other people's machines matter, and always keep results in a volume or a bind mount with a recorded image digest and commit id.
