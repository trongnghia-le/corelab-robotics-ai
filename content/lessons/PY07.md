## Why this matters

Build tests that can detect a plausible wrong implementation. This lesson develops the core calculation before asking you to apply it in a new setting. Start with the diagnostic if you think you already know it; prior tool use is not evidence of understanding.

## Intuition

A test is an experiment that tries to falsify a claim about code. Passing tests gives evidence only for what the tests constrain. A good test suite catches a realistic bug, not merely the exact values already shown in the lesson.

![Mutation testing: an original function and three mutants are run through a test suite and each is killed or survives](/lesson-figures/PY07.svg)

*Figure: a good suite passes the original and kills every non-equivalent mutant.*

## Theory and derivation

Define a contract as inputs, outputs, exceptions, and allowed side effects. Partition the input space into meaningful cases: ordinary inputs, boundaries, empty data, invalid dimensions, and extreme scales. A unit test isolates a calculation; an integration test checks that components agree at their boundary.

For floating-point outputs use $|a-b|\le\mathrm{atol}+\mathrm{rtol}|b|$, choosing tolerances from the problem scale. Exact equality is appropriate for integer counts, identifiers, and exact protocol fields, but often brittle for numerical algorithms. An overly broad tolerance can hide a real error.

An oracle is an independent source of expected behavior. A hand-worked example, a slow reference loop, or a physical invariant can serve as an oracle. Test vector addition commutativity, rotation length preservation, or a solver residual. Deliberately mutate the implementation—remove a term, swap an axis, change a sign—and ensure at least one test fails. This is a practical check on test quality.

## Worked example

A mean implementation accidentally returns the sum. Testing [0,0] passes, while [2,4] should return 3 and catches the bug. A function that returns the first element passes constant lists but fails [1,3,8]. An empty-list test must assert the declared exception rather than accept any crash.

## Exercises

3. **(Easy, predict)** *(Adapted from: Python docs, unittest, `assertEqual` and `assertAlmostEqual`)* Which of `assertEqual(0.1 + 0.2, 0.3)` and `assertAlmostEqual(0.1 + 0.2, 0.3)` passes, and why? What is the actual difference?
4. **(Medium)** Three buggy versions of `mean(values)` return (A) the sum, (B) the first element, (C) the median. For each of the test inputs `[0, 0]`, `[2, 4]`, `[1, 3, 8]` (correct answers 0, 3, 4) state which bugs it catches. Which minimal test set kills all three?
5. **(Medium, find the bug)** Two bugs hide in this *test*. Find them and rewrite it.
   ```python
   def test_mean():
       for values, expected in [([1, 2, 3], 2), ([2, 4], 3)]:
           assert mean(values) == expected
           return
       try:
           mean([])
       except Exception:
           pass
   ```
6. **(Medium, applied)** You test a planar two-link arm `fk(q1, q2)` with $l_1=l_2=1$ (see the forward-kinematics lesson). A buggy version uses $\cos q_2,\sin q_2$ instead of $\cos(q_1+q_2),\sin(q_1+q_2)$. Which of these checks catch it: (a) `fk(0, pi/2) == (1, 1)`; (b) `fk(pi/2, 0) == (0, 2)`; (c) the reach bound $0\le r\le2$; (d) the exact identity $r^2=l_1^2+l_2^2+2l_1l_2\cos q_2$?
7. **(Medium, debugging)** *(Adapted from: Pro Git, Debugging with Git, git bisect)* A regression appeared somewhere among 1000 commits; commit 1 is known good and commit 1000 is bad. How many test runs does `git bisect` need at most? What property must the test have for bisection to be valid?
8. **(Medium-hard, applied)** A CI test asserts that the mean of 25 noisy range readings (noise $\sigma$ known) lies within $3\sigma_m$ of the truth, with no fixed seed. Per run it fails about $0.27\%$ of the time. What is the chance of at least one failure in 100 CI runs? Give two ways to make the test deterministic and meaningful.
9. **(Hard, property test)** Write a property-style test for a function `rotate2d(p, theta)` using three invariants (length, composition, inverse), say why a handful of seeded random angles is better than one hand-picked angle, and describe one bug each invariant can miss.
10. **(Hard, integration)** A perception pipeline reads images with OpenCV (BGR order) and passes them to a model trained on RGB. Every unit test passes. Design a tiny integration test that fails when the channels are swapped, using a synthetic 2x2 image, and say what it checks.
11. **(Hard, reasoning)** A suite generates 20 mutants of your code and kills 17. What is the mutation score? Two survivors are real gaps and one is an equivalent mutant (changes no behaviour). Explain why 100% line coverage with zero assertions is still a score of 0 on any behavioural mutant.
12. **(Mini-project)** Pick `moving_average(values, k)`. Write a test suite, then hand-write five mutants (off-by-one window, wrong divisor, mutates input, wrong exception for `k=0`, returns a list one element too long). Report your suite's mutation score and add tests until it is 100%.

## Independent practice

### Goal

Practise testing as falsification. You will write a test suite for a `median` function, prove that it is good by showing it kills six deliberately broken versions (mutants) of `median`, and then write a delta-debugging helper that shrinks a failing input to a minimal one.

### Setup

Python 3 standard library only. Save the starter code and the tests below in one file, `test_lab.py`, and run `python3 test_lab.py`.

### Tasks

1. Implement `is_close(a, b, rtol, atol)` with the rule $|a-b|\le \mathrm{atol}+\mathrm{rtol}\,|b|$.
2. Implement `suite_passes(f)`: run your own test cases against a candidate `median` function `f` and return `True` only if all pass. Include ordinary odd and even inputs, a single element, a case with an outlier, a two-element case, negative numbers, a check that the input list is not modified, and a check that `f([])` raises `ValueError` (and not another exception, or nothing).
3. Implement `kill_count(suite, mutants)` returning how many mutants the suite rejects.
4. Run the tests: the correct implementation must pass your suite and all six mutants must be rejected. If a mutant survives, add a test that kills it.
5. Implement `shrink(values, fails)`: repeatedly remove one element while `fails(values)` stays true and return the smallest list you reach.
6. Explain in a comment, for each mutant, which of your cases kills it.

### Tests

```python
def median_ok(values):
    if not values:
        raise ValueError("empty")
    s = sorted(values)
    n = len(s)
    return float(s[n // 2]) if n % 2 else (s[n // 2 - 1] + s[n // 2]) / 2

def m_unsorted(values):          # forgets to sort
    n = len(values)
    return float(values[n // 2]) if n % 2 else (values[n // 2 - 1] + values[n // 2]) / 2
def m_upper(values):             # even length: upper middle
    if not values: raise ValueError
    return float(sorted(values)[len(values) // 2])
def m_mean(values):              # mean instead of median
    if not values: raise ValueError
    return sum(values) / len(values)
def m_inplace(values):           # sorts the caller's list
    if not values: raise ValueError
    values.sort()
    return median_ok(values)
def m_intdiv(values):            # integer division for the even case
    if not values: raise ValueError
    s = sorted(values); n = len(s)
    return float(s[n // 2]) if n % 2 else (s[n // 2 - 1] + s[n // 2]) // 2
def m_noerror(values):           # returns 0 on empty input
    return 0.0 if not values else median_ok(values)
MUTANTS = [m_unsorted, m_upper, m_mean, m_inplace, m_intdiv, m_noerror]

assert is_close(1000.0005, 1000.0, rtol=1e-6, atol=1e-9)
assert not is_close(1e-7, 0.0, rtol=1e-6, atol=1e-9)       # edge: near zero
assert suite_passes(median_ok)
assert kill_count(suite_passes, MUTANTS) == len(MUTANTS), "a mutant survived"

# shrink: failure needs both 3 and 7 present
fails = lambda v: 3 in v and 7 in v
small = shrink([1, 3, 5, 7, 9, 2], fails)
assert small == [3, 7]
assert fails(small) and not any(fails(small[:i] + small[i + 1:]) for i in range(len(small)))
assert shrink([4, 4], lambda v: len(v) >= 1) == [4]
print("mutants killed:", kill_count(suite_passes, MUTANTS), "of", len(MUTANTS))
print("minimal failing input:", small)
print("all tests passed")
```

## Failure modes

Coverage says which lines ran, not whether their meaning was checked. A deterministic random seed improves repeatability but does not establish robustness across seeds or input distributions.

## Alternatives and trade-offs

Example tests communicate intended behavior; property tests cover families of inputs; integration tests catch boundary mismatches. End-to-end tests are valuable but slower and less diagnostic, so keep a small set for essential flows.

## Exercise answers

1. A good partition: below range (`clamp(-5, 0, 90) = 0`), inside (`45`), above (`120 -> 90`), exactly on `lo` and on `hi` (unchanged), degenerate `lo == hi`, invalid `lo > hi` (expects `ValueError`), huge value (`1e308`), `float('nan')` (decide: raise or propagate), negative zero. The point is to cover each behaviour region and each boundary once.
2. (a) Tolerance is $10^{-9}+10^{-6}\cdot1000=1.000001\times10^{-3}$; the difference is $5\times10^{-4}$, so equal. (b) With $b=0$ the relative term vanishes; the tolerance is $10^{-9}$ and the difference is $10^{-7}$, so not equal. Lesson: `rtol` alone fails near zero, so `atol` must be set from the physical scale of the quantity.
3. `assertEqual(0.1 + 0.2, 0.3)` fails because `0.1 + 0.2 = 0.30000000000000004` (difference about $5.6\times10^{-17}$). `assertAlmostEqual` rounds the difference to 7 places and passes. Use an explicit tolerance that you can defend.
4. A (sum) is caught by `[2, 4]` and `[1, 3, 8]`, not by `[0, 0]`. B (first element) is caught by `[2, 4]` (returns 2) and `[1, 3, 8]` (returns 1). C (median) is caught only by `[1, 3, 8]` (median 3 vs mean 4); it passes `[0, 0]` and `[2, 4]` (median 3). `[1, 3, 8]` alone kills all three; you still want `[0, 0]` and an empty-list test for other bugs.
5. Bug 1: `return` inside the loop ends the test after the first case, so `[2, 4]` is never checked. Bug 2: the empty-list check passes whether or not an exception is raised, and accepts any exception type. Rewrite: loop over cases without `return` (or use `subTest`), and use `with self.assertRaises(ValueError): mean([])` so that no exception is a failure.
6. (a) does not catch it: with $q_1=0$, $\cos q_2=\cos(q_1+q_2)$, both give $(1,1)$. (b) catches it: correct is $(0,2)$ but the bug gives $(\cos\frac\pi2+\cos0,\ \sin\frac\pi2+\sin0)=(1,1)$. (c) does not: $\sqrt2\in[0,2]$. (d) catches it: the correct $r^2=4$ but the bug gives $2$. Moral: a bound is a weak oracle; an exact identity or an asymmetric known pose is strong.
7. At most $\lceil\log_2 1000\rceil=10$ test runs. The test must be deterministic and monotone: every commit after the first bad one must also fail (no flaky or intermittently fixed behaviour), and commits must be buildable.
8. $1-(1-0.0027)^{100}=0.237$, so roughly a 24% chance per 100 runs that the build goes red for no reason. Fixes: fix the random seed and assert on a value computed once by hand/oracle; or test the statistic with a much looser, justified bound (e.g. $6\sigma_m$, failure $\approx2\times10^{-9}$) combined with a separate deterministic test of the estimator on fixed data.
9. Invariants: $\|R(\theta)p\|=\|p\|$; $R(a)R(b)p=R(a+b)p$; $R(-\theta)R(\theta)p=p$. Use many seeded random $(p,\theta)$ pairs plus the boundary angles $0,\pm\pi/2,\pi$, because one angle can pass by accident (at $\theta=0$ every rotation bug vanishes). Misses: length is preserved by a pure reflection or by the wrong direction of rotation; composition is satisfied by a consistently wrong sign convention; the inverse property holds for any family of the form $R(s\theta)$, so it cannot reveal a wrong scale $s$ (for example degrees treated as radians). Add one hand-computed case: $R(\pi/2)(1,0)=(0,1)$.
10. Build a 2x2 image whose top-left pixel is pure red in the order the decoder returns (`[0, 0, 255]` in BGR). Run the real preprocessing path and assert that the model input's channel 0 (R) at that pixel is 255 and channels 1 and 2 are 0. This crosses the boundary between two components, so it catches the swap that each unit test cannot see.
11. Score $=17/20=85\%$. Equivalent mutants cannot be killed and should be excluded or documented, so the real gap is 2 mutants. A suite with no assertions executes every line (100% coverage) yet no mutant changes whether a test fails, so it kills 0 of N: coverage measures execution, not checking.
12. A good answer lists the suite (hand-computed `[1,2,3,4,5], k=3 -> [2,3,4]`, `k=1` identity, `k=n` single value, length `n-k+1`, input unchanged, `ValueError` for `k=0` and `k>n`) and shows each mutant being killed by a named test. Untouched mutants (e.g. the wrong divisor only matters when values are not all equal) show why non-constant inputs are needed.
