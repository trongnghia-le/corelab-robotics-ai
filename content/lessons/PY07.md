## Why this matters

Build tests that can detect a plausible wrong implementation. This lesson develops the core calculation before asking you to apply it in a new setting. Start with the diagnostic if you think you already know it; prior tool use is not evidence of understanding.

## Intuition

A test is an experiment that tries to falsify a claim about code. Passing tests give evidence only for what the tests constrain, so a good test suite catches a realistic bug, not merely the exact values already shown in the lesson. A smoke detector shows the idea: pressing its test button checks the battery and the horn, but not whether smoke would set it off, and a green light after the press says nothing about that second question. A passing unit test is evidence of the same kind: it covers the part of the behaviour that its assertion actually looks at, and nothing more.

Take a function from a robot's odometry, `speed(distance_m, dt_s)`, specified to return `distance_m / dt_s` in metres per second. A first test is quick to write: `speed(7.0, 1.0) == 7.0`. **Predict before you compute.** Which of the three wrong bodies `distance_m * dt_s`, `distance_m ** dt_s` and `distance_m / dt_s ** 2` pass that test, and what single change to the test would expose all of them? Write the answer down before reading on.

Mutation testing turns the question around. Instead of asking "does the code pass?", it asks "would the suite notice if the code were wrong in a plausible way?". A tool, or a person, makes small edits to the code (a flipped comparison, a dropped term, a swapped argument); each edited copy is a **mutant**. If some test fails on a mutant, the mutant is *killed*; if every test still passes, it *survives*, and the suite has a blind spot that a real bug could hide in.

![Mutation testing: an original function and three mutants are run through a test suite and each is killed or survives](/lesson-figures/PY07.svg)

*Figure: a good suite passes the original and kills every non-equivalent mutant; a survivor marks a case the suite cannot tell apart from correct code.*

The answer to the prediction: all three wrong bodies pass, because with `dt_s = 1.0` multiplication, a power and a division by a square all leave 7.0 unchanged. The value 1 is a neutral input that hides every dependence on `dt_s`. The test `speed(6.0, 2.0) == 3.0` exposes all three at once: they return 12.0, 36.0 and 1.5.

Four intuitions are tempting and wrong. First, "all tests are green, so the code is right": green means only that the checks made so far could not tell this code from a correct one. Second, "high coverage means well tested": coverage says which lines ran, not whether anything was asserted about their results. Third, "random inputs will find any bug": a bug that lives at one exact value of a continuous input, such as a threshold at 11.1 V, is drawn with probability zero, so boundary values must be chosen by hand. Fourth, "debugging means reading the code until the bug appears": a reliable process makes the failure repeatable, shrinks the failing input, and then narrows the cause by halving, over the input, over the commit history, or over the program state.

A robot makes the last point concrete. A nightly test of a state estimator started failing some time in the last 90 commits and nobody remembers touching it. Reading 90 diffs is slow and error-prone; bisecting the history finds the first bad commit in at most seven test runs without reading a single diff first, and the regression test written afterwards keeps the bug from returning. The sections below make each of these ideas precise: how to pick inputs, where expected values come from, how large a numerical tolerance may be, where unit tests stop being enough, and how to search for a fault.

## Theory and derivation

Define a contract as inputs, outputs, exceptions, and allowed side effects. Partition the input space into meaningful cases: ordinary inputs, boundaries, empty data, invalid dimensions, and extreme scales. A unit test isolates a calculation; an integration test checks that components agree at their boundary.

For floating-point outputs use $|a-b|\le\mathrm{atol}+\mathrm{rtol}|b|$, choosing tolerances from the problem scale. Exact equality is appropriate for integer counts, identifiers, and exact protocol fields, but often brittle for numerical algorithms. An overly broad tolerance can hide a real error.

An oracle is an independent source of expected behavior. A hand-worked example, a slow reference loop, or a physical invariant can serve as an oracle. Test vector addition commutativity, rotation length preservation, or a solver residual. Deliberately mutate the implementation—remove a term, swap an axis, change a sign—and ensure at least one test fails. This is a practical check on test quality.

### Partitions, boundaries and the cost of combining parameters

A test suite is a finite sample of an input space that is usually infinite, so the real design question is *which* sample. The standard answer (MIT 6.031, Reading 3, "Choosing test cases by partitioning") divides the input space into **subdomains**: sets of inputs on which the specification asks for the same kind of behaviour. The subdomains must be disjoint and together cover every input, i.e. form a **partition**, and one test case is drawn from each. The argument behind this is an assumption, not a theorem: if the program is right on one member of a subdomain, it is right on all of them. The assumption fails exactly where behaviour changes abruptly, which is why bugs concentrate at **boundaries** such as $0$, $\pm1$, the empty list, or $x=\mathrm{lo}$. The reading's remedy (§"Include boundaries in the partition") is to give each boundary a one-element subdomain of its own and shrink the neighbouring subdomains to exclude it, so that a boundary test is forced into the suite.

**Example.** A battery gauge `battery_state(v)` maps a pack voltage in volts to a state: below 10.5 V `critical`, from 10.5 V up to (excluding) 11.1 V `low`, from 11.1 V to 12.6 V inclusive `ok`, above 12.6 V `invalid`. The partition has four subdomains and three boundaries (10.5, 11.1, 12.6). One test inside each region (9.0, 10.8, 12.0, 13.0) passes the original and also passes all three mutants that turn a `<` into `<=` or a `<=` into `<`, because those edits change the result only exactly at a boundary. The three boundary tests 10.5, 11.1 and 12.6 each kill exactly one of them. Python 3.11.9:

```python
def battery_state(v):
    if v < 10.5:
        return "critical"
    if v < 11.1:
        return "low"
    if v <= 12.6:
        return "ok"
    return "invalid"

for v in (9.0, 10.5, 10.8, 11.1, 12.0, 12.6, 13.0):
    print(v, battery_state(v))
```

Output:

```text
9.0 critical
10.5 low
10.8 low
11.1 ok
12.0 ok
12.6 ok
13.0 invalid
```

The mutant with `if v <= 11.1` returns `low` for 11.1 and `ok`, `critical`, `invalid` unchanged for 9.0, 12.0, 13.0, so only the 11.1 test fails.

![Number line of battery_state in volts with four regions, test dots inside each region and on the three boundaries, and a table of three mutants each killed by one boundary test only](/lesson-figures/PY07-2.svg)

*Figure: hollow dots are one test per region, filled dots are boundary tests. Each comparison mutant changes the result at exactly one filled dot, so the hollow dots alone kill none of them.*

Several parameters multiply. If parameter $i$ has $k_i$ subdomains, the Cartesian product has $\prod_i k_i$ cells; for $n$ parameters with $k$ subdomains each that is $k^n$, while "cover each subdomain at least once" needs only $\max_i k_i$ calls because one call exercises one subdomain of every parameter. The cheap option is blind to interactions between parameters; the full product is thorough but infeasible beyond a few parameters. Two honest reductions exist: cells that cannot occur (mutually exclusive subdomains) disappear from the product, and cells that the specification treats identically can be merged. Use the full product only for parameters the specification couples.

**Example.** A drive command `set_drive(speed, mode)` has speed in {zero, slow, fast} (3 subdomains) and mode in {manual, auto} (2). The full product has $3\times2=6$ cells; covering every subdomain once needs only $\max(3,2)=3$ calls, for instance (zero, manual), (slow, auto), (fast, manual). If the specification says that auto mode limits only fast speed, the coupled cell (fast, auto) is added as a fourth call and the remaining cells stay merged: 4 tests instead of 6.

Coverage measures the other direction: which code your suite exercised. Statement coverage asks that every statement run, branch coverage that every `if`/`while` take both outcomes, path coverage that every combination of outcomes occur (§"Coverage" of the same reading); each is strictly stronger than the previous. For a function with $k$ sequential, independent `if` statements, one test can reach full statement coverage, two tests reach full branch coverage, and $2^k$ are needed for path coverage. None of them says that the executed code was *checked*; coverage is a way to find what you have not tried, not a measure of correctness.

### Oracles and properties

An example-based test fixes one input and its expected output. A **property-based test** states a predicate that must hold for every input of a described kind and lets a generator draw the inputs. The idea comes from QuickCheck (Claessen & Hughes, ICFP 2000, §2.1), which checks each property on 100 random cases by default; Hypothesis keeps the same default of 100 examples (Hypothesis docs, "Introduction"). A property is only as strong as the **oracle** behind it, the independent source of the expected behaviour. Four kinds, from strongest to weakest:

1. a *reference computation* that is slow but obviously right (a direct $O(n^2)$ sum for a fast transform);
2. a *round trip*: `decode(encode(x)) == x` (the Hypothesis introduction lists round-trip properties as both powerful and easy to write);
3. a *metamorphic relation*: the output must change in a known way when the input is transformed (shuffling a list leaves its median unchanged);
4. an *invariant or bound*: the output lies between the smallest and the largest input.

Bounds are cheap and weak: worked case 2 shows a bug that satisfies the bound and is caught only by a property about the sign.

How many random inputs does a property need? Suppose the bug fires on a fraction $p$ of the inputs the generator draws, and the $n$ draws are independent. One draw misses the bug with probability $1-p$, all $n$ draws miss with $(1-p)^n$, so
$$P(\text{detect})=1-(1-p)^n,\qquad n\ \ge\ \frac{\ln(1-c)}{\ln(1-p)}\ \approx\ \frac{\ln\frac{1}{1-c}}{p}\quad(p\ \text{small}),$$
where $c$ is the confidence wanted; the approximation uses $\ln(1-p)\approx-p$. Both assumptions matter. If the generator draws from a distribution in which the bug has $p=0$, for instance an exact boundary value such as 11.1 drawn from a continuous range, no number of draws helps; boundaries are therefore written by hand or added as explicit examples. If the draws are not independent (the same seed or the same data in every test), the formula overstates the confidence. When a property fails, the generator tries to **shrink** the counterexample: QuickCheck reports a smaller failing case (§5.4), and Hypothesis does the same, so the report is a small input rather than the large random one that first failed.

**Example.** A range-sensor driver returns a stale reading on 2 % of the inputs, $p=0.02$. With the default 100 random examples the detection probability is only $1-0.98^{100}=0.8674$, and $\lceil\ln 0.05/\ln 0.98\rceil=149$ examples are needed for 95 %. A simulation of 20 000 independent 100-example runs agrees (0.8663 observed). Python 3.11.9:

```python
import math, random

p, n = 0.02, 100                  # bug fires on 2 % of the inputs; 100 random tests
print(round(1 - (1 - p) ** n, 4))                                   # miss probability is (1-p)^n
print(math.ceil(math.log(0.05) / math.log(1 - p)))                  # n for 95 % confidence

random.seed(3)
runs = 20000
hits = sum(any(random.random() < p for _ in range(n)) for _ in range(runs))
print(hits / runs)
```

Output:

```text
0.8674
149
0.8663
```

### Tolerances from rounding-error analysis

Choosing `rtol` and `atol` by feel is a guess; for sums it can be derived. Let $u=2^{-53}$ be the relative rounding error bound of IEEE double precision, and let the left-to-right sum be $s_1=x_1$, $s_i=(s_{i-1}+x_i)(1+\delta_i)$ with $|\delta_i|\le u$. Unrolling the recursion gives
$$\hat s_n=\sum_{j=1}^{n}x_j\prod_{i=\max(j,2)}^{n}(1+\delta_i),$$
so the computed sum is the *exact* sum of slightly perturbed inputs $x_j(1+\theta_j)$ with $|\theta_j|\le(n-j+1)u$ (and $|\theta_1|\le(n-1)u$) to first order (Goldberg, "What Every Computer Scientist Should Know About Floating-Point Arithmetic", §"Errors in Summation", eq. 31: the first term is perturbed by about $n\epsilon$, the last by only $\epsilon$). Therefore
$$|\hat s_n-s_n|\le (n-1)\,u\sum_{j=1}^{n}|x_j|\;+\;O(n^2u^2)\sum_j|x_j|.$$
Three consequences for tests:

1. The error scales with $\sum|x_j|$, **not** with $|s_n|$. When terms of both signs cancel, $|s_n|$ can be tiny or exactly $0$, and a purely relative tolerance $\mathrm{rtol}\,|s_n|$ rejects correct code. The right `atol` is proportional to $n\,u\sum|x_j|$.
2. The bound is attainable, so it is not just pessimism. Take $x=[1,u,u,\dots,u]$: each $1+u$ lies exactly halfway between $1$ and $1+2u$ and rounds to even, back to $1$, so every small term is lost and the error is $(n-1)u\approx(n-1)u\sum|x_j|$.
3. Compensated summation breaks the dependence on $n$. In Kahan's algorithm (`y = x - c; t = s + y; c = (t - s) - y; s = t`) Goldberg's Theorem 8 shows the computed sum equals $\sum x_j(1+\delta_j)$ with $|\delta_j|\le2\epsilon$ plus an $O(n\epsilon^2)$ term, so for the same data the tolerance becomes about $2u\sum|x_j|$. `math.fsum` goes further and returns the correctly rounded sum, which makes it a good oracle.

Typical (random) errors are far below the worst case, because rounding errors partly cancel, which is why tolerances taken from the *bound* are safe and tolerances taken from one observed run are fragile.

**Example.** A drift check sums the readings $[10^{8},\,0.1,\,-10^{8}]$: a large offset, a small signal, the offset removed again. The true sum is 0.1. Python 3.11.9:

```python
import math

s = 0.0
for x in [1e8, 0.1, -1e8]:
    s += x
print(s, math.fsum([1e8, 0.1, -1e8]))
print(math.isclose(s, 0.1, rel_tol=1e-9))
u = 2.0 ** -53
bound = (3 - 1) * u * (1e8 + 0.1 + 1e8)
print(bound, abs(s - 0.1) <= bound)
```

Output:

```text
0.09999999403953552 0.1
False
4.440892100721072e-08 True
```

The loop adds 0.1 to $10^8$, where neighbouring doubles are $2^{-26}\approx1.5\times10^{-8}$ apart, so the 0.1 is rounded to a multiple of that spacing; the observed error is $6\times10^{-9}$, a relative error of $6\times10^{-8}$. A relative tolerance of $10^{-9}$ rejects this correct code. The bound with $n=3$ and $\sum|x_j|=2\times10^{8}+0.1$ is $2u\sum|x_j|=4.4\times10^{-8}$, and the observed error is inside it. `math.fsum` returns the correctly rounded 0.1.

### Unit tests, integration tests and where interface bugs hide

A **unit test** checks one component in isolation, with its collaborators replaced by fixed values or simple stand-ins; an **integration test** runs two or more real components together and checks what crosses the boundary (MIT 6.031, Reading 3, "Unit and integration testing"). Interface bugs live in what each side silently assumes about the other: units (mm against m), frames, channel or axis order, row-major against column-major, zero-based against one-based indices, clocks, sign conventions. Every unit test can be correct with respect to its own assumption while the pair is wrong, so the unit suite stays green. A sound allocation for a small robotics code base is many unit tests on pure calculations, one integration test at each boundary where two authors' assumptions meet, and only a few end-to-end runs, which are slow and say little about where a fault is (the "test pyramid": cost rises and diagnostic power falls going up). A failure found in the field is added as a permanent **regression test** so that it cannot return unnoticed (MIT 6.031, "Automated regression testing"). A good integration test is a *known-answer* test: its expected value is computed by hand from the specification, not by the code under test.

**Example.** Wheel odometry: `ticks_to_mm` converts encoder ticks to millimetres (1440 ticks per revolution, wheel radius 0.05 m) and `advance_x` adds a distance in metres to a position. Each has a passing unit test. Python 3.11.9:

```python
import math

TICKS_PER_REV, WHEEL_R_M = 1440, 0.05

def ticks_to_mm(ticks):                    # unit test: 2000 ticks -> 436.33 mm
    return ticks / TICKS_PER_REV * 2 * math.pi * WHEEL_R_M * 1000

def advance_x(x_m, distance_m):            # unit test: 0.10 m + 0.25 m -> 0.35 m
    return x_m + distance_m

assert math.isclose(ticks_to_mm(2000), 436.33, abs_tol=0.01)
assert math.isclose(advance_x(0.10, 0.25), 0.35)

x_m = advance_x(0.0, ticks_to_mm(2000))   # integration: the pieces disagree on the unit
print(x_m)
print(math.isclose(x_m, 0.4363, abs_tol=1e-4))
```

Output:

```text
436.3323129985823
False
```

Both unit tests pass, yet driving 2000 ticks moves the pose by 436 m instead of 0.4363 m (the circumference $2\pi\cdot0.05=0.3142$ m times $2000/1440$ revolutions). Only the known-answer integration test, 2000 ticks $\to0.4363$ m, fails.

### Debugging as search: reproduce, shrink, bisect

Debugging is a search for the smallest difference between a run that works and a run that fails, and the three searches that follow all use the same halving idea.

*Over the input.* First make the failure repeatable (fix seeds, record the input, freeze the clock), then shrink the input. Delta debugging (Zeller & Hildebrandt 2002, as presented in The Debugging Book, "Reducing Failure-Inducing Inputs") removes chunks of size $1/2$, $1/4$, ... of the input while the failure persists, and ends with a **1-minimal** input: removing any single element makes the failure disappear. It needs a number of tests proportional to $\log_2 n$ when failures survive halving and up to $O(n^2)$ in the worst case (same source). The `shrink` function of the independent practice is the last stage of this algorithm.

*Over history.* `git bisect` keeps an interval of commits $(lo,hi]$ where commit $lo$ is good and commit $hi$ is bad, so the first bad commit lies inside. Testing the middle commit halves the number $N=hi-lo$ of candidates. Since $k$ runs distinguish at most $2^k$ outcomes, at most $\lceil\log_2 N\rceil$ runs are needed, where $\lceil x\rceil$ is the smallest integer not below $x$ (git-bisect(1)). Three conditions make this valid: the test is deterministic; the status is *monotone* (every commit after the first bad one is bad); every probed commit can be built and run, otherwise it is skipped (exit code 125 in `git bisect run`). If a bug was introduced and later fixed inside the range, monotonicity fails and bisection returns some commit where the status changes, not necessarily the wanted one.

*Over program state.* With a short failing run in hand, stop it where the fault is suspected: `breakpoint()` opens the Python debugger `pdb` at that line, and `pdb.post_mortem()` or `python -m pdb script.py` opens it at an uncaught exception (Python docs, `pdb`). Bisecting state means checking an intermediate value half-way through the computation: if it is already wrong, the fault is in the first half. The end product is a minimal reproducible example, which becomes a regression test.

**Example.** A nightly estimator test passes at commit 1 and fails at commit 90, and the first bad commit is 58. There are $N=89$ candidates, so at most $\lceil\log_2 89\rceil=7$ runs ($2^6=64<89\le128=2^7$). The model probe $m=\lfloor(lo+hi)/2\rfloor$ needs 6. Python 3.11.9:

```python
def first_bad(n, is_bad):
    lo, hi, runs = 1, n, []
    while hi - lo > 1:
        m = (lo + hi) // 2
        runs.append(m)
        if is_bad(m):
            hi = m
        else:
            lo = m
    return hi, runs

print(first_bad(90, lambda c: c >= 58))
```

Output:

```text
(58, [45, 67, 56, 61, 58, 57])
```

### How the pieces connect

Partitions and boundaries choose the inputs; oracles and properties say what the outputs must be; tolerances turn a real-number expectation into a pass-or-fail decision with a justified margin; the mutation score checks that the suite can tell wrong code from right code; integration tests cover what unit tests cannot see; and debugging turns each field failure into a smaller input and a permanent test. The invariants used as properties come from the neighbouring topics: rotations preserve length and compose by adding angles, and forward kinematics obeys the law of cosines.

## Worked example

### Case 1: which test kills which defect

**Problem.** `mean(values)` must return the arithmetic mean of a list of numbers and raise `ValueError` for an empty list. Four defective versions exist: A returns `sum(values)`, B returns `values[0]`, C returns `(values[0] + values[-1]) / 2`, and D returns `0.0` for an empty list instead of raising. Which of the tests `[0, 0] -> 0`, `[2, 4] -> 3`, `[1, 3, 8] -> 4` and `mean([])` raising `ValueError` kills which defect, and what is the smallest suite that kills all four?

**Solution.**

1. Compute the expected values by hand from the definition $\bar x=\sum x_i/n$ (an oracle independent of the code): $[0,0]$ gives $0/2=0$; $[2,4]$ gives $6/2=3$; $[1,3,8]$ gives $12/3=4$.
2. Defect A returns the sum: on $[0,0]$ it returns 0, which equals the expected 0, so the test passes; on $[2,4]$ it returns 6, not 3; on $[1,3,8]$ it returns 12, not 4. The second and third tests kill A.
3. Defect B returns the first element: 0 on $[0,0]$ (passes), 2 on $[2,4]$ (expected 3), 1 on $[1,3,8]$ (expected 4). The second and third tests kill B.
4. Defect C averages the two ends: $(0+0)/2=0$ (passes), $(2+4)/2=3$ (passes, because for two elements the mean of the ends is the mean), $(1+8)/2=4.5$ (expected 4). Only the third test kills C.
5. Defect D is correct on every non-empty list, so only the test that calls `mean([])` and requires `ValueError` fails (D returns 0.0). A test that writes `except Exception: pass` would accept D, and so would any crash.
6. The kill counts are 0, 2, 3, 1 for the four tests. No single test kills all four defects: D needs the empty-list test and A, B and C need a non-empty test. `[1, 3, 8]` together with `mean([])` kills all four.

### Case 2: a bound is not enough (harder)

**Problem.** A velocity limiter must keep a command inside $[-v_{\max},v_{\max}]$. The code below has a defect. Two properties are tested with Hypothesis for speeds in $[-100,100]$ and limits in $[0,10]$: P1, $|{\rm out}|\le v_{\max}$; P2, the output is 0 or has the same sign as the input. Which property fails, what counterexample is reported after shrinking, and what is the fix?

```python
import math
from hypothesis import given, strategies as st

def saturate(v, vmax):
    """Limit v to the interval [-vmax, vmax]."""
    if abs(v) > vmax:
        return vmax          # bug: loses the sign of v
    return v

speeds = st.floats(-100.0, 100.0, allow_nan=False)
limits = st.floats(0.0, 10.0)

@given(speeds, limits)
def test_bounded(v, vmax):
    assert abs(saturate(v, vmax)) <= vmax

@given(speeds, limits)
def test_sign_kept(v, vmax):
    out = saturate(v, vmax)
    assert out == 0 or (out > 0) == (v > 0)
```

**Solution.**

1. For P1: if $|v|\le v_{\max}$ the function returns $v$, so $|{\rm out}|=|v|\le v_{\max}$; otherwise it returns $v_{\max}$, so $|{\rm out}|=v_{\max}\le v_{\max}$. P1 holds for every input, including the defective ones: it is a necessary condition that the defect satisfies.
2. For P2: for $v=-2.0$ and $v_{\max}=1.0$ the condition $|v|>v_{\max}$ is true, the function returns $+1.0$, whose sign differs from the sign of $v$, and `out == 0` is false. P2 is violated.
3. How likely is a random test to hit this? The defect fires when $v<-v_{\max}$. If $v$ were uniform on $[-100,100]$ and $v_{\max}$ uniform on $[0,10]$, then $p\approx0.5-E[v_{\max}]/200=0.475$, so by the detection formula of the theory 100 draws miss with probability $(1-0.475)^{100}\approx10^{-28}$. The failure appears at once.
4. Hypothesis shrinks the failing case. In three runs with a fresh example database (Hypothesis 6.170.15, pytest 9.2.0) the reported counterexample was `v = -2.0, vmax = 1.0`. Smaller-looking cases do not fail: with $v_{\max}=0$ the output is 0 and `out == 0` makes P2 true.
5. Fix: `return math.copysign(vmax, v)` keeps the sign of $v$. Both properties then pass (`2 passed`).

**Check.** With the defect, pytest prints `1 failed, 1 passed`: the failing test is `test_sign_kept` and `test_bounded` passes. After the fix it prints `2 passed`. As a mutation view, P1 alone kills 0 of 1 defects, P2 kills 1 of 1.

**Takeaway.** A bound is a necessary property; add one that fixes the direction or an exact known value, otherwise the suite passes wrong code.

### Case 3: bisecting 200 commits (harder)

**Problem.** A state-estimator test passes at commit 1 and fails at commit 200. Find the first bad commit (it is commit 137, unknown to the person searching) with the probe $m=\lfloor(lo+hi)/2\rfloor$, and give the number of test runs and its upper bound.

**Solution.**

1. Start with $lo=1$ (good) and $hi=200$ (bad). The first bad commit is one of $2,\dots,200$, so $N=199$ candidates. The bound is $\lceil\log_2199\rceil=8$ because $2^7=128<199\le256=2^8$.
2. Probe $m=\lfloor(1+200)/2\rfloor=100$: good, so $lo=100$.
3. Probe $m=\lfloor(100+200)/2\rfloor=150$: bad, so $hi=150$.
4. Probe $m=\lfloor(100+150)/2\rfloor=125$: good, $lo=125$.
5. Probe $m=\lfloor(125+150)/2\rfloor=137$: bad, $hi=137$.
6. Probe $m=\lfloor(125+137)/2\rfloor=131$: good, $lo=131$.
7. Probe $m=\lfloor(131+137)/2\rfloor=134$: good, $lo=134$.
8. Probe $m=\lfloor(134+137)/2\rfloor=135$: good, $lo=135$.
9. Probe $m=\lfloor(135+137)/2\rfloor=136$: good, $lo=136$. Now $hi-lo=1$, so the first bad commit is $hi=137$ after 8 runs, equal to the bound.

```python
def first_bad(n, is_bad):
    lo, hi, runs = 1, n, []
    while hi - lo > 1:
        m = (lo + hi) // 2
        runs.append(m)
        if is_bad(m):
            hi = m
        else:
            lo = m
    return hi, runs

print(first_bad(200, lambda c: c >= 137))
```

Output:

```text
(137, [100, 150, 125, 137, 131, 134, 135, 136])
```

```text

```

def median_ok(values):
    if not values:
        raise ValueError("empty")
    s = sorted(values)
    n = len(s)
    return float(s[n // 2]) if n % 2 else (s[n // 2 - 1] + s[n // 2]) / 2

def m_unsorted(values):          # forgets to sort
    n = len(values)
    return float(values[n // 2]) if n % 2 else (values[n // 2 - 1] + values[n // 2]) / 2
def m_upper(values):             # even length: upper middle
    if not values: raise ValueError
    return float(sorted(values)[len(values) // 2])
def m_mean(values):              # mean instead of median
    if not values: raise ValueError
    return sum(values) / len(values)

14. (a) Unrolling gives $\hat s_n=\sum_j x_j\prod_{i\ge\max(j,2)}(1+\delta_i)$. Each product satisfies $\prod_{i}(1+\delta_i)=1+\theta_j$ with $|\theta_j|\le(1+u)^{n-j+1}-1\le(n-j+1)u+O(n^2u^2)$, and for $j=1$ there are $n-1$ factors. So $|\hat s_n-s_n|\le\sum_j|x_j||\theta_j|\le(n-1)u\sum_j|x_j|$ to first order. The observed error equals the bound to about ten digits, so the bound is attained: each $1+u$ is a tie and rounds to even, back to 1. Hence the correct answer requires all 6 bad probes on the true path to fail, each independently with probability $0.7$: $0.7^6=0.117649$. (c) A probe now detects with probability $1-0.3^r$, so success is $(1-0.3^r)^6$: $r=1$: $0.1176$; $r=2$: $0.5679$; $r=3$: $0.8485$; $r=4$: $0.9524$; $r=5$: $0.9855$; $r=6$: $0.9956$. 16. (a) Results: `score(1,-1)`: first `if` sets `s=1`, second skipped, returns 1. `score(-1,1)`: first skipped, `s=0`, second gives $2+0=2$. Both match the specification.
