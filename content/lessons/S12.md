## Why this matters

A robot that is correct on paper can still fail because an answer arrives too late. A controller designed for a 20 ms loop that actually runs every 20 to 54 ms is a different controller. A grasp planned from a camera frame that is 300 ms old targets where the object *was*. Advanced robotics software is the discipline of writing down, for every piece of the system, **when it runs, how long it may take, who owns its data, and what happens when it is late**. With S10 you know how ROS 2 control is wired and with CPP10 you know how threads and locks behave; this lesson combines them into timing arguments you can compute and test.

## Intuition

Think of the robot as an assembly line. Each station (sensor driver, detector, estimator, controller, motor driver) takes some time and only picks up work at certain moments. Two things add delay: *work time* (the station is busy) and *waiting time* (the item sits until the station looks at it). Waiting is easy to forget. A 100 Hz timer that reads the latest value adds up to 10 ms of waiting even if its computation is instant.

![Sensor-to-command chain: camera, detector, controller and driver stages with the period wait and response time of each stage, and a stale-data gate before the actuator](/lesson-figures/S12.svg)

*Each stage contributes a wait for its next period (periodic stages only) plus its response time; the gate before the actuator rejects data older than the budget.*

Two further ideas shape everything below. **Callbacks are not preempted by each other** inside one ROS 2 executor thread, so a long callback delays every short one queued behind it. And **queues hide lateness**: a deep queue never drops data, so a slow consumer reads data that grows older and older while no error is ever raised.

## Theory and derivation

### Timing contract of a periodic task

A task $i$ has period $T_i$, worst-case execution time $C_i$ (WCET: the longest it runs when it has the CPU), and deadline $D_i$ (here $D_i=T_i$). Its **response time** $R_i$ is release-to-completion, including time spent waiting for others. The task is fine when $R_i\le D_i$. **Jitter** is the variation of the actual start or period around the nominal one. Utilization is
$$U=\sum_i \frac{C_i}{T_i}.$$
$U>1$ cannot work on one core. For rate-monotonic (RM) priorities (shorter period, higher priority) and preemption, Liu and Layland showed that $U\le n(2^{1/n}-1)$ is *sufficient* (for $n=3$ it is $0.7798$; it tends to $\ln 2\approx0.693$). It is not necessary, so a set above the bound may still be schedulable and needs the exact test.

### Exact response time (preemptive fixed priority)

Higher-priority tasks interrupt task $i$. In a window of length $r$ task $j$ can release $\lceil r/T_j\rceil$ jobs, so the response time is the smallest fixed point of
$$R_i = C_i+\sum_{j\in hp(i)}\left\lceil \frac{R_i}{T_j}\right\rceil C_j .$$
Start with $r=C_i$ and iterate $r\leftarrow C_i+\sum\lceil r/T_j\rceil C_j$. The sequence is non-decreasing, so it either converges or passes $D_i$ (deadline miss).

### Non-preemptive callbacks: blocking

An executor runs a callback to completion. Then a high-priority callback can be **blocked** by one lower-priority callback that started just before it was released. Let $B_i=\max_{k\in lp(i)} C_k$. A standard conservative bound for integer time is
$$w_i=B_i+\sum_{j\in hp(i)}\left(\left\lfloor \frac{w_i}{T_j}\right\rfloor+1\right)C_j,\qquad R_i=w_i+C_i,$$
where $w_i$ is the longest time a job can wait before it *starts*. Only one blocking term appears: once the blocker finishes, every later start decision picks by priority, and any lower-priority job that starts must have been running when $i$ arrived, or else $i$ (higher priority) would have been chosen.

### Chain latency and data age

Let a measurement be stamped at capture time. A **polled** stage (timer) reads the latest value at its tick and may have to wait up to one period $T_i$; an **event-driven** stage (subscription callback) starts when data arrives, so its waiting is inside its response time (queueing and blocking). With latest-value-wins communication, a conservative bound on the age of the data when the last stage finishes is
$$L_{\max}\le\sum_{\text{stages}}\bigl(\,[\text{periodic}]\;T_i+R_i\bigr),$$
where the sensor counts as a stage with period $T_s$ and $R_s$ = exposure-and-transfer delay. It is a bound, not an average: the typical age is smaller, and a stale-data gate must be set from the bound.

### Queues, Little's law and QoS

If a consumer needs $s$ seconds per message and messages arrive faster than $1/s$, a queue of depth $d$ fills and each message waits about $d\cdot s$ before service. With `KEEP_LAST` depth 1 the consumer always sees the newest message and the age stays bounded; with depth 100 it sees data $100s$ old. Little's law, $N=\lambda W$ (items in system = arrival rate × time in system), gives the same estimate from the queue length. Control and perception inputs that represent *state* want small depth and latest-wins; logs and commands that must not be lost want deep, reliable queues.

### Composition and ownership

Nodes in separate processes exchange serialized copies through the middleware; nodes composed into one process container can pass a `unique_ptr` without copying (intra-process communication), at the price of sharing a process and, by default, an executor. Place stages in *callback groups* or executors by timing class: a mutually-exclusive group serializes its callbacks (safe, but they block each other); separate groups on a multithreaded executor run in parallel (needs locks for shared state). Keep **one owner per command**: exactly one node publishes to the actuator interface; others send requests to it. Two writers make "last one wins" an accident.

### Layers and failure handling

Put the hard-timing loop (driver, low-level control) in a small layer that never waits on best-effort components (perception, planning). Best-effort output enters through a bounded buffer with an **age check**. When the check fails the real-time layer applies a declared fallback: hold, decay to zero velocity, or stop. The gate threshold satisfies
$$L_{\max}+\text{margin}\le \text{max\_age}\le \text{age at which the action becomes unsafe}.$$
Too low and healthy operation trips it; too high and it protects nothing.

## Worked example

### Are three tasks schedulable?

**Problem.** Three periodic tasks $(C,T)$ in ms: $\tau_1=(1,4)$, $\tau_2=(2,6)$, $\tau_3=(3,12)$, with rate-monotonic priorities $\tau_1>\tau_2>\tau_3$, preemptive, deadline $D=T$. Decide whether all deadlines hold.

**Solution.**

1. Utilization: $U=\frac14+\frac26+\frac3{12}=0.25+0.3333+0.25=0.8333$. The Liu and Layland bound for $n=3$ is $3(2^{1/3}-1)=0.7798$. Since $0.8333>0.7798$, the sufficient test is inconclusive (and $U<1$, so the set is not ruled out): the exact test is needed.
2. Use $R_i=C_i+\sum_{j\in hp(i)}\lceil R_i/T_j\rceil C_j$, iterating from $r=C_i$. For $\tau_1$ (no higher priority): $R_1=1\le4$.
3. $\tau_2$ (higher: $\tau_1$): $r=2$; $2+\lceil2/4\rceil\cdot1=3$; $2+\lceil3/4\rceil\cdot1=3$. Fixed point $R_2=3\le6$.
4. $\tau_3$ (higher: $\tau_1,\tau_2$): $r=3$; $3+\lceil3/4\rceil\cdot1+\lceil3/6\rceil\cdot2=3+1+2=6$. $r=6$: $3+\lceil6/4\rceil+\lceil6/6\rceil\cdot2=3+2+2=7$. $r=7$: $3+\lceil7/4\rceil+\lceil7/6\rceil\cdot2=3+2+4=9$. $r=9$: $3+\lceil9/4\rceil+\lceil9/6\rceil\cdot2=3+3+4=10$. $r=10$: $3+\lceil10/4\rceil+\lceil10/6\rceil\cdot2=3+3+4=10$. Fixed point $R_3=10\le12$.
5. Every $R_i\le T_i$, so all deadlines hold even though $U$ exceeds the bound.

**Check.** A timeline at the critical instant (all released at $t=0$): $\tau_1$ runs $0$ to $1$, $\tau_2$ $1$ to $3$, $\tau_3$ $3$ to $4$, then $\tau_1$ again $4$ to $5$, $\tau_3$ $5$ to $6$, $\tau_2$ (released at 6) $6$ to $8$, $\tau_1$ $8$ to $9$, $\tau_3$ $9$ to $10$ and finishes at $10$, matching $R_3=10$. A Python fixed-point iteration gives the same sequences.

**Takeaway.** The utilization bound is only sufficient; a set above it can still be schedulable, and the exact response-time test decides.

### Latency of a vision chain

**Problem.** A chain has a camera ($T=40$ ms, capture-to-delivery delay 15 ms), a detector (event-driven, worst response 30 ms), a controller (timer, $T=20$, $R=4$) and a motor driver (timer, $T=5$, $R=1$), all in ms. Find the worst-case data age $L_{\max}$ at the end of the chain and choose a stale-data gate `max_age`.

**Solution.**

1. Use $L_{\max}\le\sum_{\text{stages}}([\text{periodic}]\,T_i+R_i)$: a polled (timer) stage adds up to one period of waiting plus its response time; an event-driven stage adds only its response time; the sensor counts as a periodic stage with $R_s$ = capture-to-delivery delay.
2. Camera: $40+15=55$ ms. Detector (event-driven, no period term): $30$ ms. Controller: $20+4=24$ ms. Motor driver: $5+1=6$ ms.
3. Sum: $L_{\max}=55+30+24+6=115$ ms.
4. Gate: $L_{\max}+\text{margin}\le\text{max\_age}$. A `max_age` of 100 ms is below 115 and would trip during healthy operation. Choose 115 plus a margin, for example 140 ms, if a 140 ms-old measurement is still safe for the task; otherwise fix the pipeline instead of the number.

**Check.** The sum $55+30+24+6=115$ was verified in Python. Limiting case: removing all queueing and waiting terms leaves only $15+30+4+1=50$ ms of pure processing, so $115$ ms is the processing plus the worst sampling waits $40+20+5=65$ ms.

**Takeaway.** The stale-data gate is set from the worst-case bound, not from the average; sampling waits of polled stages often dominate.

### Executor blocking

**Problem.** A 30 ms detector (period 40 ms) and a 4 ms controller (period 20 ms) share one single-threaded executor whose callbacks run to completion; the controller has higher priority. Find the response time of each and decide whether the deadlines (the periods) hold.

**Solution.**

1. Utilization: $U=\frac4{20}+\frac{30}{40}=0.2+0.75=0.95$, which looks only "busy".
2. Controller. It has no higher-priority task, but it can be blocked by the detector if that has just started: $B=\max_{k\in lp}C_k=30$ ms. Then $w=B=30$ (no higher-priority term) and $R_{ctrl}=w+C=30+4=34$ ms $>20$ ms: the controller misses its period.
3. Detector. Nothing has lower priority, so $B=0$. $w=B+(\lfloor w/20\rfloor+1)\cdot4$ starts at $w=0$: $(0+1)\cdot4=4$; then $(\lfloor4/20\rfloor+1)\cdot4=4$: stays. $R_{det}=w+C=4+30=34\le40$: the detector meets its deadline.

**Check.** At the worst case the controller is released one instant after the detector starts, so it waits the full 30 ms and then runs 4 ms: $34$ ms, which matches. The fixed-point iteration was repeated in Python and stays at $w=4$.

**Takeaway.** Low utilization or even $0.95$ does not tell whether a high-priority callback is safe: one long non-preemptive callback blocks it, so long work belongs in another executor or thread.

## Reference implementation

The functions below are the analysis tools of this lesson in plain Python. Run them; the asserts reproduce the worked example.

```python
from math import ceil

def utilization(tasks):               # tasks: list of (C, T)
    return sum(c / t for c, t in tasks)

def rm_bound(n):
    return n * (2 ** (1 / n) - 1)

def response_time(tasks, i):
    """Preemptive fixed priority, index 0 = highest. Deadline = period.
    Returns R_i, or None if it exceeds T_i."""
    c, t = tasks[i]
    r = c
    while True:
        nxt = c + sum(ceil(r / tj) * cj for cj, tj in tasks[:i])
        if nxt > t:
            return None
        if nxt == r:
            return r
        r = nxt

def chain_latency(stages):
    """stages: list of (kind, T, R); kind is 'periodic' or 'event'."""
    return sum(r + (t if kind == "periodic" else 0) for kind, t, r in stages)

def fresh(now, stamp, max_age):
    age = now - stamp
    return 0 <= age <= max_age        # reject future stamps too

tasks = [(1, 4), (2, 6), (3, 12)]
assert [response_time(tasks, i) for i in range(3)] == [1, 3, 10]
assert abs(utilization(tasks) - 5 / 6) < 1e-12 and utilization(tasks) > rm_bound(3)
chain = [("periodic", 40, 15), ("event", 0, 30), ("periodic", 20, 4), ("periodic", 5, 1)]
assert chain_latency(chain) == 115
assert fresh(10, 0, 10) and not fresh(11, 0, 10) and not fresh(0, 5, 10)
print("reference checks passed")
```

### Setup

1. Implement `hyperperiod(tasks)`, the least common multiple of the periods.
2. Implement `np_response_times(tasks)` with the non-preemptive formula of the Theory section.
3. Implement `simulate(tasks, offsets, horizon)`: a non-preemptive executor. At each decision time it picks, among released jobs, the lowest priority index (ties: earliest release) and runs it to completion; if none is ready it jumps to the next release. import rclpy
```python
from rclpy.node import Node
from rclpy.callback_groups import MutuallyExclusiveCallbackGroup
from rclpy.executors import SingleThreadedExecutor, MultiThreadedExecutor
from std_msgs.msg import Empty

class Demo(Node):
    def __init__(self, multi):
        super().__init__("s12_demo")
        g_ctrl = MutuallyExclusiveCallbackGroup() if multi else None   # None = node default group
        g_det = MutuallyExclusiveCallbackGroup() if multi else None
        self.starts = []
        self.create_timer(0.020, self.control, callback_group=g_ctrl)
        self.create_subscription(Empty, "frame", self.detect, 1, callback_group=g_det)
        self.pub = self.create_publisher(Empty, "frame", 1)
        self.create_timer(0.040, lambda: self.pub.publish(Empty()), callback_group=g_det)

    def control(self):
        self.starts.append(time.perf_counter())

    def detect(self, _msg):
        time.sleep(0.030)            # stand-in for a 30 ms detector

def main():
    multi = sys.argv[1] == "multi"
    rclpy.init()
    node = Demo(multi)
    ex = MultiThreadedExecutor(num_threads=2) if multi else SingleThreadedExecutor()
    ex.add_node(node)
    t_end = time.perf_counter() + 5.0
    while time.perf_counter() < t_end:
        ex.spin_once(timeout_sec=0.01)
    gaps = [1e3 * (b - a) for a, b in zip(node.starts, node.starts[1:])]
    print(f"control period: max {max(gaps):.1f} ms, mean {sum(gaps)/len(gaps):.1f} ms")
    rclpy.shutdown()

main()
```

Compare the `single` maximum with the analytic $R_{ctrl}=34$ ms bound. If the numbers disagree, look for hidden queueing (the subscription uses depth 1 so it does not hide any) and for the timer sharing a group with the detector.

## Verification

Check a result three ways. First, hand-compute a tiny case (the worked example) and compare. Second, check invariants: the simulated maximum never exceeds the analytic bound; $R_i\ge C_i$; adding a higher-priority task never lowers any $R_i$. Third, measure: in ROS 2 record message header stamps and subtract them from the clock at the consumer (`now - header.stamp`), plot the maximum, and compare with $L_{\max}$. If the measured maximum exceeds the bound, an assumption is wrong (hidden queue, blocked callback, clock offset between machines), and that is the finding. Test the gate at the exact boundary (age equals `max_age`), one tick past it, and with a stamp in the future.

## Failure modes

- **Averaging instead of bounding.** Quoting a 5 ms mean while the 99.9th percentile is 40 ms. The deadline is violated by the tail, not the mean.
- **Forgetting the wait.** Summing only processing times for the example chain gives $15+30+4+1=50$ ms instead of $115$ ms.
- **Long callback in a shared executor.** Controller period becomes about $4+30=34$ ms, not 20.
- **Deep queues.** Depth 100 at 50 ms per message yields about 5 s of age with no error.
- **`now - stamp <= max_age` with no lower bound.** A clock jump or a different machine's clock makes the age negative and the data "fresh" forever.
- **Mixed clocks.** Stamps from the sensor clock compared with the system clock; use one clock domain or an explicit offset estimate.
- **Two command publishers.** The actuator follows whichever wrote last; the symptom is jerky motion that depends on message timing.
- **Priority inversion.** A low-priority task holds a mutex that the high-priority task needs while a medium one preempts the holder; use priority inheritance or avoid sharing locks across priorities.

## Alternatives and trade-offs

| Choice | Gain | Cost |
|---|---|---|
| One process, intra-process comms | No serialization, low latency | One crash takes everything down; shared executor blocking |
| Separate processes | Fault isolation, per-process priorities | Serialization and copies, extra latency |
| Single-threaded executor | Simple, no data races | Callbacks block each other |
| Multithreaded executor + groups | Parallelism | Locks, ordering questions |
| Latest-wins queue (depth 1) | Bounded age | May drop data |
| Deep reliable queue | No loss | Unbounded age under overload |
| Timer-polled stage | Predictable rate | Up to one period of wait |
| Event-driven stage | No polling wait | Rate follows input, bursts |

Exact response-time analysis is more work than the utilization bound but gives a yes/no answer on sets the bound cannot decide. For hard guarantees on a general-purpose OS, none of this replaces a real-time kernel and measurement.
