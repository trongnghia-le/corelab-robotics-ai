## Why this matters

A figure in a paper or report is the end of a long chain: sensors or simulators produced raw numbers; scripts cleaned and aggregated them; a plotting command drew the picture. If any link is undocumented, the figure cannot be checked, extended, or trusted, including by you six months later. Robotics adds extra hazards: hardware that drifts, calibration that changes, simulators with hidden randomness, and results that depend on library versions.

Reproducibility is not a virtue added after the research; it is a set of cheap habits that make the research itself faster, because you can re-run, debug and extend it with confidence.

## Intuition

Three words are often confused (the ACM terminology used by many venues):

- **Repeatability**: the same team, same setup, gets the same result again.
- **Reproducibility**: a different team, using the *original* artifacts (data, code, environment), gets the same result.
- **Replicability**: a different team, with a *new* setup and independently collected data, supports the same conclusion.

The first two are about engineering discipline (you can control them); the third is about scientific validity (you can only increase the odds). A good project aims for the first two on day one so the third becomes possible.

## Theory and derivation

### Sources of non-determinism

| Source | Example | Control |
|---|---|---|
| Random seeds | weight initialisation, data shuffling, noise | set and record seeds for every library (Python, NumPy, framework, simulator) |
| Floating-point order | parallel reductions, GPU kernels | use deterministic kernels or accept a tolerance |
| Software versions | a library changes a default | lock exact versions |
| Hardware/OS | CPU vs GPU, driver | record hardware; test on a second machine |
| Data order and splits | train/test split by time | save split indices |
| External state | network downloads, wall-clock time | cache inputs; avoid time-dependent code |
| Human steps | manual cleaning, hand-edited figure | script every step |

Floating-point addition is not associative. For example in IEEE double precision `(1e16 + 1.0) - 1e16` is `0.0` while `(1e16 - 1e16) + 1.0` is `1.0`, because $10^{16}+1$ rounds back to $10^{16}$. (Python 3.12 and later make the built-in `sum()` of floats compensated, so `sum([1e16, 1.0, -1e16])` there returns `1.0`; write the additions explicitly, or use a plain loop, to see the effect.) Changing the order of a parallel sum can change the last digits (and, in chaotic training dynamics, the result).

### Artifacts and the manifest

An experiment's **artifacts** are: raw data (never edited), the code at an exact version, the environment (language and library versions, hardware notes), configuration (all hyperparameters and seeds), intermediate results, and final outputs (tables, figures). A **manifest** lists each artifact with a cryptographic hash such as SHA-256. Two byte-identical files have the same hash; any change, even one bit, changes it with overwhelming probability. A hash of the canonical form of the configuration (sorted keys, fixed separators) identifies a run regardless of key order.

### Environment locking

A lock file fixes exact versions and, optionally, hashes of the distribution files (`pip install --require-hashes -r requirements.lock`), or a container image is pinned by digest rather than by a floating tag. Git records code versions: store the commit hash with every result and refuse to run on a dirty working tree (`git describe --always --dirty` shows `-dirty`).

### Tolerances and seed variance

Even a perfect pipeline will not give identical numbers across different hardware, so decide the tolerance beforehand from the seed-to-seed variability. If one run has SD $\sigma$ and you report the mean of $n$ seeds, the mean has $\mathrm{SE}=\sigma/\sqrt n$, and the difference between two independent re-runs has SD $\sqrt2\,\sigma/\sqrt n$. A re-run is consistent with the original if the difference lies within about $1.96\sqrt2\,\sigma/\sqrt n$. With $\sigma=2$ and $n=5$ this is $2.48$ points: a replication that lands 1.5 points away is consistent; 4 points away is not. For exact re-runs on the same machine with fixed seeds, the tolerance is zero (bit-for-bit) or close to machine precision.

### Protocol

A protocol is the written, ordered, runnable description of the experiment: question, hypotheses, factors (RS02), measurement definitions, number of seeds and trials, stopping rule, analysis plan (RS03), and what will be reported. Writing the analysis plan before running prevents unconscious tuning of the analysis to the result.

## Worked example

**Task.** Reproduce "Figure 1: mean accuracy by condition" from a CSV of raw measurements.

Raw file `measurements.csv`:
```
condition,value
A,70
A,72
B,68
B,70
B,69
```
**Summary step.** Condition A: mean $(70+72)/2=71.0$, $n=2$. Condition B: $(68+70+69)/3=69.0$, $n=3$. This table is the data behind the figure; the plotting script only draws it.

**Hashing.** The hash of the empty byte string is `e3b0c442...b855` and of `abc` is `ba7816bf...15ad`; these two well-known test vectors let you check your SHA-256 function. For the manifest, you hash `measurements.csv`, `analyze.py`, `config.json` and `requirements.lock`. If someone later edits one value in the CSV (72 to 73), the CSV's hash changes and `verify_manifest` reports `measurements.csv`, before any figure is trusted.

**Config hash.** `config_hash({"a":1,"b":2})` hashes the canonical text `{"a":1,"b":2}`; the same dictionary with keys in the other order gives the identical digest.

**Seeds.** `run_experiment(seed, n)` is the mean of $n$ draws from $N(10,2^2)$. For a fixed seed it returns the same value on every call (`run_experiment(0,5)` gives `9.2878...`); for seed 1 it gives `10.3789...`. Across 1000 seeds with $n=100$ the means have SD about $0.20$, which matches $2/\sqrt{100}=0.2$. So two re-runs with different seeds should differ by up to about $1.96\sqrt2(0.2)=0.55$ without anything being wrong, whereas two re-runs with the same seed must match exactly.

**Decision.** A replication reports 71.4 for a quantity you reported as 72.5 using the mean of five seeds with $\sigma=2$: difference 1.1 points $<2.48$. Consistent; do not treat as a failure. If the same seeds and code gave 71.4 on your own machine, that would be a failure (the pipeline is not deterministic).

## Reference implementation

Commands you would run (Linux/macOS shell), followed by a Python model of the checks:

```bash
git rev-parse HEAD                      # exact code version
git status --porcelain                  # empty output means a clean tree
python -m venv .venv && . .venv/bin/activate
pip freeze --all > env/requirements.lock
sha256sum data/measurements.csv code/analyze.py config.json env/requirements.lock > MANIFEST.sha256
sha256sum -c MANIFEST.sha256            # prints "OK" per file, non-zero exit on mismatch
python code/analyze.py --config config.json --out fig1.csv
```

```python
import hashlib, json, os, random

def sha256_bytes(data): return hashlib.sha256(data).hexdigest()

def sha256_file(path):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(65536), b""):
            h.update(chunk)
    return h.hexdigest()

def config_hash(cfg):
    return sha256_bytes(json.dumps(cfg, sort_keys=True, separators=(",", ":")).encode("utf-8"))

def run_experiment(seed, n):
    rng = random.Random(seed)
    return sum(rng.gauss(10.0, 2.0) for _ in range(n)) / n

if __name__ == "__main__":
    print(sha256_bytes(b"abc"))
    print(config_hash({"a": 1, "b": 2}) == config_hash({"b": 2, "a": 1}))
    print(round(run_experiment(0, 5), 4), run_experiment(0, 5) == run_experiment(0, 5))
    # --- self-test ---
    assert sha256_bytes(b"") == "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
    assert sha256_bytes(b"abc") == "ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad"
    assert config_hash({"a": 1, "b": 2}) == sha256_bytes(b'{"a":1,"b":2}')
    assert run_experiment(3, 1) == random.Random(3).gauss(10.0, 2.0)
    assert run_experiment(0, 5) != run_experiment(1, 5)
    print("self-test passed")
```

### Library track

Check the habits with NumPy and PyTorch (CPU). The script shows that the same seed gives the same NumPy stream, that `SeedSequence.spawn` gives independent per-run streams from one recorded seed, that seeding `random` alone does not seed NumPy or PyTorch, that a tiny PyTorch training run is bit-for-bit repeatable on one machine (compare SHA-256 of the weights; the printed hash can differ between machines or versions, which is why the tolerance matters), and that float32 sums depend on the order.

```python
import hashlib, random
import numpy as np, torch

def sha(b): return hashlib.sha256(b).hexdigest()

# 1) NumPy generators: same seed, same stream; independent child streams from one SeedSequence.
a, b = np.random.default_rng(7), np.random.default_rng(7)
assert (a.random(3) == b.random(3)).all()
children = np.random.SeedSequence(2024).spawn(3)                  # one stream per seed/run, no overlap
runs = [np.random.default_rng(c).normal(10, 2, 100).mean() for c in children]
assert runs == [np.random.default_rng(c).normal(10, 2, 100).mean() for c in np.random.SeedSequence(2024).spawn(3)]
print("three child-stream means", np.round(runs, 4))

# 2) Seeding only `random` does not seed NumPy or PyTorch.
random.seed(0)
n1, n2 = np.random.default_rng().random(), np.random.default_rng().random()
assert n1 != n2                                                    # unseeded generators differ
torch.manual_seed(0); t1 = torch.randn(3)
torch.manual_seed(0); t2 = torch.randn(3)
assert torch.equal(t1, t2)                                         # the framework seed controls torch.randn

# 3) A tiny deterministic training run: identical weights bit for bit on the same machine.
def train(seed):
    torch.manual_seed(seed)
    net = torch.nn.Linear(4, 1); opt = torch.optim.SGD(net.parameters(), lr=0.1)
    x = torch.randn(64, 4); y = x.sum(1, keepdim=True)
    for _ in range(50):
        opt.zero_grad(); ((net(x) - y) ** 2).mean().backward(); opt.step()
    return net.weight.detach().numpy().tobytes()
assert sha(train(0)) == sha(train(0)) and sha(train(0)) != sha(train(1))
torch.use_deterministic_algorithms(True)                           # raises if an op has no deterministic kernel
print("weights hash", sha(train(0))[:16])

# 4) Floating-point order: the sum depends on the order; tolerances must be justified, not zero.
x = np.array([1e16, 1.0, -1e16])
assert (x[0] + x[1]) + x[2] == 0.0 and (x[0] + x[2]) + x[1] == 1.0
v = np.random.default_rng(0).normal(size=100_000).astype(np.float32)
s_fwd, s_rev = np.sum(v), np.sum(v[::-1])
print("float32 sum forward vs reversed", s_fwd, s_rev, "difference", abs(float(s_fwd) - float(s_rev)))
assert abs(float(s_fwd) - float(s_rev)) < 1e-2
print("library track passed")
```

Expected: three child-stream means (identical on every run), a weights hash prefix, a tiny forward-versus-reversed float32 difference, then `library track passed`. For GPU training also set `torch.backends.cudnn.benchmark = False` and the `CUBLAS_WORKSPACE_CONFIG` environment variable; not run here (no GPU).

## Verification

- **Test vectors:** check your SHA-256 against the standard vectors before trusting a manifest.
- **Clean-room run:** run the pipeline from a fresh clone in a new virtual environment or container; this is the only way to find undeclared dependencies.
- **Double run:** run twice on the same machine with the same seeds and compare outputs byte for byte.
- **Tamper test:** change one value in the raw data; the manifest check must fail before any figure is produced.
- **Tolerance justification:** write the tolerance and the $\sigma$, $n$ it came from next to the number.

## Failure modes

| Mistake | Consequence |
|---|---|
| Editing raw data by hand | irreproducible; hash mismatch cannot be explained |
| Seeding only `random` | other generators still vary between runs |
| Floating tags (`latest`, `>=1.0`) | the environment changes under you |
| Comparing floats for equality across machines | spurious failures; use a justified tolerance |
| Reporting best-of-N without recording N | irreproducible selection and optimistic numbers |
| Figures made in a GUI | no record of the steps; the plot cannot be regenerated |
| Output hash recorded but input hash not | cannot tell whether data or code changed |

## Alternatives and trade-offs

- **Virtual environment plus lock file**: light and quick; does not fix the OS or drivers.
- **Container image pinned by digest**: freezes the user space and tools; heavier, and still depends on the host kernel and GPU driver.
- **Nix/Guix-style functional builds**: strongest guarantees, steeper learning curve.
- **Notebook-only workflows**: convenient, but hidden state and execution order hurt reproducibility; export to a script or run with a clean kernel.
- **Data versioning (DVC, git-annex) versus plain hashes**: tools help with large files; a manifest of hashes is the minimum.
- **Bitwise reproducibility versus statistical reproducibility**: GPU training often supports only the latter; document which one you claim.

## Exercise answers

2. Dictionaries with the same content but different insertion order serialise to different strings with naive dumps, so (a) the digests of `{"a":1,"b":2}` and `{"b":2,"a":1}` differ (the first is `{"a": 1, "b": 2}` and the second `{"b": 2, "a": 1}`). With (b) sorted keys the text is identical, so the digests are equal. Canonical form makes the hash depend on content only.
3. A manual edit has no record: nobody can say which rows were removed or why, and the raw data no longer matches the paper. Instead keep the raw file untouched and write a cleaning script with the rule (for example "drop rows where value is more than 4 MAD from the median"), log the dropped row ids, and report the number removed; run it as part of the pipeline.
4. $\mathrm{SE}=3/\sqrt9=1.0$. Difference between two re-runs: SD $=\sqrt2\times1.0=1.414$. 95% tolerance $=1.96\times1.414=2.77$ points. A 2.5-point difference is within it: consistent (but near the edge; consider more seeds).
5. A good answer names a concrete file for each: `data/README` (data), `git rev-parse HEAD` in `RESULTS.md` (code), `env/requirements.lock` (environment), `config.json` (hyperparameters and seeds), `HARDWARE.md` (hardware), `protocol.md` (evaluation), `analysis.py` (statistics), `compute.md` (budget) and `failures.md` (failure cases).
6. Output: `True 0.0 1.0`. Two generators with the same seed produce identical sequences, and floating-point addition order changes the result because $10^{16}+1$ rounds to $10^{16}$ (the first expression loses the 1.0, the second keeps it).
7. Other sources: NumPy's global generator (`numpy.random.seed`), the framework's generator and GPU kernels (`torch.manual_seed`, deterministic algorithms flag), data-loader worker seeds and shuffling, hash randomisation of Python strings (`PYTHONHASHSEED`), and non-deterministic multithreaded reductions. Control each by setting and recording seeds and enabling deterministic modes where available, and by accepting a tolerance for the remainder.
8. Verify at the start of every run and in continuous integration, so a changed file is caught immediately; on mismatch stop, report which artifact changed, and either restore it or create a new versioned run. Hashes of data and code do not fix the environment, hardware or seeds, and parallel floating-point reductions can differ between machines, so the output can still differ within tolerance.
9. $\mathrm{Var}(\bar X_1-\bar X_2)=\mathrm{Var}(\bar X_1)+\mathrm{Var}(\bar X_2)=2\sigma^2/n$ for independent re-runs, so SD $=\sqrt2\sigma/\sqrt n$. Require $1.96\sqrt2\sigma/\sqrt n\le1$: $n\ge(1.96\sqrt2\cdot3)^2=2\cdot3.8416\cdot9=69.2\to70$ seeds. Agreement within 1 point therefore needs far more seeds than are usually run; report a tolerance instead of promising closer agreement.
10. A good answer lists the files, the one command (for example `make figure`), the clean-room result (what differed and why), the tolerance used, and the rejecting outcome (a hash mismatch of an input, or an output outside the tolerance with fixed seeds).
