## Why this matters

One experiment on one laptop is easy. A sweep of 144 training runs, spread over a few machines that can be preempted, rebooted or run out of disk, is an infrastructure problem. The typical failures are not exotic: a run dies at 90% and restarts from zero; two runs write the same file; a result file is half written when the node dies; six months later nobody knows which code and settings produced the number in the paper.

This lesson turns those failures into design rules. You will build a job that is **idempotent** (running it twice gives the same state as running it once), **resumable** (a crash costs minutes, not hours) and **auditable** (outputs carry a checksum manifest and the identity of the code and configuration). You use containers from T06 and the measurement habits from T07 to reason about cost.

## Intuition

Treat a job like a function with a contract. Inputs: a configuration and an immutable code+environment image. Outputs: files in a known place, plus a marker that says "these outputs are complete". Anything in between (the process, the node, the network) is allowed to disappear at any time. If the contract is written so that a second attempt can either skip finished work or continue it, failures become routine.

## Theory and derivation

### The job contract

A well-formed batch job has four parts.

1. **Input contract.** Configuration (hyper-parameters, seeds, dataset version) is passed explicitly, for example as a JSON file or environment variables, and never edited inside the image. The Twelve-Factor App states the rule: strict separation of config from code.
2. **Output contract.** A directory whose name is derived from the inputs, for example `runs/<name>/<config-hash>/`, containing the result files, a `manifest.json` of `{file: sha256}` and a `DONE` marker.
3. **Restart behaviour.** What happens if the process is killed at any instruction. Resolve it with checkpoints and an idempotent entry point.
4. **Identity.** The image digest and code commit, written into the manifest.

### Idempotence and atomicity

Retries are only safe if repeating the job is harmless. Two tools give this:

- **Content-derived names.** $h=\text{sha256}(\text{canonical JSON of config})$ truncated to 12 hex characters gives the same directory for the same settings and a different one for any change. Canonical means sorted keys and fixed separators; note that `1` and `1.0` serialize differently.
- **Atomic publish.** Write to a temporary file in the *same directory*, flush and `fsync`, then `os.replace` it onto the final name. On POSIX the rename is atomic, so a reader sees the old file or the whole new file, never half of one. Write the `DONE` marker last: its existence must imply that every output is complete.

Distributed schedulers give *at-least-once* execution: if the scheduler never hears back it starts the job again, even when the first attempt had already finished its work. *Exactly-once* is achieved by making the at-least-once job idempotent.

### Retries and backoff

After failure number $i=0,1,2,\ldots$ wait $d_i=\min(d_{\max},\,d_0\,2^i)$ seconds before the next attempt, and give up after a limit (Kubernetes calls it `backoffLimit`). Exponential delay avoids hammering a broken dependency; the cap bounds the wait; the limit turns a permanent bug into a visible failure instead of an endless loop. Retry only failures that can be transient; a `ValueError` from a bad config will fail identically forever.

### Checkpoint interval

Let a checkpoint cost $C$ seconds and let failures occur on average every $M$ seconds. With interval $T$, the overhead fraction is about $C/T$ for writing and, since a failure loses on average half an interval, $T/(2M)$ for lost work. Minimise
$$f(T)=\frac CT+\frac{T}{2M}\quad\Rightarrow\quad f'(T)=-\frac C{T^2}+\frac1{2M}=0\quad\Rightarrow\quad T^*=\sqrt{2CM}.$$
This first-order approximation (Young) assumes $T\ll M$. The minimum is broad: being a factor of two off costs little.

### Artifacts and deployment

An **artifact** is any output you may need again: a model file, a metrics table, a container image. Store each with (a) the config hash, (b) the code commit, (c) the image digest, (d) its own sha256. Tags such as `latest` are movable pointers; a digest (`sha256:...`) names exact bytes. Deploy by **immutable image**: build once (`docker build -t exp:3f9c2ab .`), push, and run the same tag everywhere. A rollout replaces old instances gradually while a health check decides whether to continue; a rollback is redeploying the previous tag, which only works if old tags were never overwritten. Mount outputs from a volume (`docker run -v $PWD/runs:/runs ...`) so they outlive the container.

## Worked example

A job has 200 steps of 3 s. It checkpoints every 25 steps at 2 s per checkpoint. The node is preempted right after step 130 completes. The first retry waits $d_0=5$ s.

1. **Failure-free time.** Compute $200\times3=600$ s. There are $200/25=8$ checkpoints costing $8\times2=16$ s, so the run takes 616 s.
2. **Where it resumes.** Checkpoints exist after steps 25, 50, ..., 125. The last one before step 130 is 125, so 5 steps are redone: $5\times3=15$ s.
3. **Total with the crash.** $616+15+5\,(\text{backoff})=636$ s.
4. **Without checkpoints.** All 130 finished steps are lost: $130\times3=390$ s. Total $600+390+5=995$ s, 56% longer.
5. **Is 25 steps a good interval?** With $C=2$ s and $M=3600$ s, $T^*=\sqrt{2\cdot2\cdot3600}=120$ s, that is 40 steps. Overhead at $T=75$ s (25 steps): $2/75+75/7200=0.0267+0.0104=3.7\%$. At $T=120$ s: $2/120+120/7200=0.0167+0.0167=3.3\%$. The difference is small, confirming the broad minimum.
6. **Backoff schedule.** With $d_0=5$, cap 60 and six retries: 5, 10, 20, 40, 60, 60 s, a total of 195 s before giving up.

## Reference implementation

The reference shows the minimal idempotent job: a config-hash directory, atomic writes, and `DONE` written last. The self-test runs the job twice and shows the second run does no work.

```python
import hashlib, json, os, tempfile

def config_hash(cfg):
    """Stable 12-hex id of a config: same settings -> same id, regardless of key order."""
    blob = json.dumps(cfg, sort_keys=True, separators=(",", ":")).encode()
    return hashlib.sha256(blob).hexdigest()[:12]

def write_atomic(path, data: bytes):
    """Write to a temp file in the same directory, then rename: readers never see half a file."""
    d = os.path.dirname(path)
    fd, tmp = tempfile.mkstemp(dir=d)
    with os.fdopen(fd, "wb") as f:
        f.write(data)
        f.flush(); os.fsync(f.fileno())
    os.replace(tmp, path)

def run_once(root, cfg, work):
    """Idempotent job: the output directory is named by the config hash; DONE marks success."""
    out = os.path.join(root, config_hash(cfg))
    os.makedirs(out, exist_ok=True)
    done = os.path.join(out, "DONE")
    if os.path.exists(done):
        return out, False                       # already finished: skip (idempotent)
    write_atomic(os.path.join(out, "result.json"), json.dumps(work(cfg)).encode())
    write_atomic(done, b"ok")                   # written LAST
    return out, True

# --- self-test ---
assert config_hash({"lr": 0.1, "seed": 1}) == config_hash({"seed": 1, "lr": 0.1})
assert config_hash({"lr": 0.1, "seed": 1}) != config_hash({"lr": 0.1, "seed": 2})
calls = []
with tempfile.TemporaryDirectory() as root:
    cfg = {"lr": 0.1, "seed": 1}
    out, ran = run_once(root, cfg, lambda c: calls.append(1) or {"loss": 0.5})
    out2, ran2 = run_once(root, cfg, lambda c: calls.append(1) or {"loss": 0.5})
    assert ran and not ran2 and out == out2 and len(calls) == 1
    assert json.load(open(os.path.join(out, "result.json"))) == {"loss": 0.5}
print("T08 reference OK")
```

## Independent practice

### Goal

### Library track

Redo the fault-injection test with real PyTorch training state (`pip install torch` in a virtual environment). A resumable training job must save the optimizer state as well as the weights: SGD with momentum keeps a velocity buffer, and without it the resumed run diverges from the uninterrupted one. The data of step `i` depends only on `i`, so a resumed run sees the same batches. This reuses your `write_atomic`.

```python
import io, os, tempfile, torch
# from job_lab import write_atomic   (your solution)

def train(ckpt, steps, crash_at=None):
    torch.manual_seed(0)
    model = torch.nn.Linear(3, 1)
    opt = torch.optim.SGD(model.parameters(), lr=0.1, momentum=0.9)
    start = 0
    if os.path.exists(ckpt):
        st = torch.load(ckpt)
        model.load_state_dict(st["model"]); opt.load_state_dict(st["opt"]); start = st["next"]
    for i in range(start, steps):
        g = torch.Generator().manual_seed(1000 + i)      # batch depends only on the step index
        x = torch.randn(8, 3, generator=g); y = x.sum(1, keepdim=True)
        loss = ((model(x) - y) ** 2).mean()
        opt.zero_grad(); loss.backward(); opt.step()
        buf = io.BytesIO()
        torch.save({"model": model.state_dict(), "opt": opt.state_dict(), "next": i + 1}, buf)
        write_atomic(ckpt, buf.getvalue())
        if crash_at == i + 1:
            raise RuntimeError("preempted")
    return model.weight.detach().clone()

with tempfile.TemporaryDirectory() as d:
    clean = train(os.path.join(d, "clean.pt"), 10)
    p = os.path.join(d, "run.pt")
    try:
        train(p, 10, crash_at=6)
    except RuntimeError:
        pass
    assert torch.equal(clean, resumed := train(p, 10))
print("resumed == uninterrupted: OK")
```

## Verification

Verify an infrastructure design by breaking it. Kill the job at random points (`kill -9`, or raise in the middle of a step) and check three invariants: the final result equals the crash-free result, no step before the last checkpoint is recomputed, and a finished job restarts as a no-op. Recompute checksums from the files and compare them with the manifest. Compare the observed overhead with $C/T+T/(2M)$. State a check that could reject the design: for example "if killing during the final write ever leaves `DONE` without a valid `result.json`, the contract is wrong".

## Failure modes

- **`DONE` before data.** A crash between the two writes makes every later attempt skip a job whose result does not exist.
- **Non-atomic overwrite.** Opening the real file with mode `"w"` truncates it first; a crash leaves an empty file that looks present.
- **Temp file on another filesystem.** `os.replace` across mounts cannot be an atomic rename (it fails with `OSError`, and a copy-then-delete fallback would not be atomic); create the temp file in the destination directory.
- **Unstable hash input.** Using `str(dict)`, floats printed with different precision, or unsorted keys makes the same experiment land in different directories (duplicate work) or two experiments collide.
- **Retry of a permanent error.** A typo in a path retried six times with backoff wastes minutes and hides the real error.
- **Mutable tags.** `latest` changes silently; the run is not reproducible.
- **State inside the container.** Writes to the container filesystem vanish with the container; use a volume or object storage.

## Alternatives and trade-offs

| Need | Simple choice | Heavier choice | Trade-off |
|---|---|---|---|
| Run many jobs | shell loop plus `xargs -P` | Kubernetes Job, Slurm array | Orchestrator adds retries and scheduling, plus operating cost |
| Resume | application checkpoints | none (rerun) | Checkpoints cost time and code; rerun is fine for jobs shorter than a few minutes |
| Artifact store | directories plus manifest | MLflow, DVC, object store | Tools add search and lineage; plain files are transparent |
| Deploy | `docker run` of a pinned tag | rolling update with health checks | Rollouts avoid downtime but need a health check you trust |

Prefer the simplest mechanism whose failure you can explain. For a 3-minute job, "delete the directory and rerun" is a legitimate recovery plan.

## Exercise answers

1. The first and second are equal (`0.10` parses to the same float, and keys are sorted). The third differs: `json.dumps` writes `1.0` instead of `1`, so the hash changes. A launcher that reads seeds as floats would silently create a new directory and rerun finished experiments; normalise types (cast seeds to `int`) before hashing.
2. Three waves of two pods: $3\times10=30$ minutes. Parallelism limits it; cluster capacity or failures can only make it longer.
3. Delays $2,4,8,16,30,30$ (since $32>30$), sum 90 s. The cap matters from the 5th retry.
4. Baking config into the image forces a rebuild for each sweep point, makes images differ by one number, and hides the setting from the output record. The image holds code and dependencies; config is passed at run time and recorded in the output; artifacts hold results, the config, the commit and the image digest.
5. A crash after the empty `DONE` is created but before or during the JSON write leaves `DONE` with a missing or truncated `result.json`; the restart sees `DONE` and skips. Fix: write `result.json` atomically first, then `DONE` last (and ideally have `DONE` hold the result's checksum).
6. `latest` is a movable tag: a new build or a base-image update replaced it. Tag with the commit (`exp:3f9c2ab`), push, and record the image digest in the manifest; pull by digest to reproduce.
7. $T^*=\sqrt{2\cdot5\cdot7200}=\sqrt{72000}\approx268.3$ s. Overhead $5/268.3+268.3/14400=0.01863+0.01863\approx0.0373$, about 3.7%.
8. The scheduler guarantees at-least-once execution; correctness must come from idempotence. The new pod first looks for `DONE` in the config-hash directory (and optionally verifies the manifest); if present it exits successfully without recomputing. This works because outputs were published atomically and `DONE` was written last.
9. $f'=-C/T^2+1/(2M)=0\Rightarrow T^2=2CM$. $f''=2C/T^3>0$ so it is a minimum. $f(T^*)=C/\sqrt{2CM}+\sqrt{2CM}/(2M)=2\sqrt{C/(2M)}=\sqrt{2C/M}$. If $C\ll M$ (for example $C=2$, $M=3600$ gives 3.3%) the overhead is small; it grows only like $\sqrt{C}$.
10. $48\times3=144$ runs $\times20$ min $=2880$ min of work, over 4 machines $=720$ min $=12$ h if perfectly balanced (more with failures). A good answer includes `runs/<sweep>/<hash>/` with `config.json`, `manifest.json`, `DONE`; logs with commit, image digest, host and timings; skipping by `DONE`; verifying checksums against the manifest; and the commit recorded in the manifest.
11. A good project injects crashes with a fixed random seed, asserts equality with the clean results, counts step executions (clean steps plus redone steps since the last checkpoint) and reports total overhead against the formula.
